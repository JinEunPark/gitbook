### 1. 첫 매물 6개를 DB 에 직접 넣다 (대화 16:22\~16:34)

#### 운영 서버 기록 보기 (16:22)

👤 "운영기 로그를 보고 싶은데 어떻게 해야해"에, 서버에 들어가 앱 컨테이너의 기록을 실시간으로 보는 명령과 컨테이너 목록(앱, nginx, 화면, DB, Redis)을 정리해 줬다. 주의할 점도 세 가지 들었다. 기록의 시각이 한국 시간이 아니라 UTC 라는 것, 컨테이너를 새로 만들면 이전 기록이 사라진다는 것, 그리고 운영 설정에 기록 크기 제한이 없어서 끝없이 쌓인다는 것이다. 파일당 10MB, 5개까지로 제한하자는 권장은 11/5 에 반영됐다.

#### 넣었는데 하나도 안 보인다 (16:25\~16:34)

9/13 대화에서 정리한 6개를 웹에서 사양을 더 찾아 보강한 다음 DB 에 직접 넣는 SQL 을 만들었다(라셀르 4도어 45박스 냉장고, 매직쎸븐 식기세척기, 다이나믹 제빙기, 린나이 22L 튀김기, 그랜드우성 테이블냉장고 900, 엔터팩 실링기). 추정한 값엔 "\[추정]" 표시를 달았다. 가격은 9/13 에 정한 "절반 넘게 할인"(18만\~45만 원)이 아니라 35만\~120만 원, 정가 70만\~350만 원으로 넣었다. 그러고 나서 👤 "이걸로 데이터를 삽입했는데 왜 현재 페이지에서 상품이 하나도 안 뜨지 빠진 칼럼이 있어서 그런가"라고 물었다.

원인은 빠진 칸이 아니라 값의 형식이었다.

| 넣은 값                       | 무엇이 문제였나                                      | 결과                                             |
| -------------------------- | --------------------------------------------- | ---------------------------------------------- |
| 판매 상태를 "판매중"(한글)으로         | 목록은 영문 `ACTIVE` 인 상품만 보여 준다                   | 목록에서 빠짐                                        |
| 카테고리를 "냉장고", "식기세척기"처럼 한글로 | 카테고리는 영문 코드(`REFRIGERATOR`, `KITCHEN` 등)로 맞춘다 | 어느 탭에도 안 나옴. 둘이 연결돼 있지 않아서 넣는 것 자체는 성공         |
| 미사용 제빙기 등급을 "S" 로          | 등급은 A·B·C 만 있다                                | 서버가 그 상품을 읽다가 모르는 값이라 오류를 내서 관리자 상품 목록 전체가 500 |

👤 "DB 락킹이 걸려있나"라고도 물었는데, PostgreSQL 은 쓰기 잠금이 읽기를 막지 않고, 잠금 때문이라면 응답이 늦다가 시간 초과가 났을 거라는 답이었다. 대신 DB 도구가 수동 저장 모드라 넣은 게 아직 확정되지 않았을 가능성을 의심하고 확인 방법을 알려 줬다. 직접 상품 목록 API 를 불러 보니 빈 목록에 총 0건이 나와서, 판매중 상품이 0개인 게 확인됐다. 이어서 운영 서버 기록을 붙여 넣었더니 관리자 상품 목록(50개씩) 요청이 500 이었고 "등급 값 'S' 가 정의돼 있지 않다"는 오류가 찍혀 있었다. 같은 화면에서 비활성 상품 1개만 불러오는 요청은 200 이었다. 그 상품이 안 걸리면 정상이라는 뜻이다.

16:33 에 👤 "데이터가 하나 안 맞다고 전체 반환 값이 깨지지 않았으면 좋겠는데 제일 좋은 처리 방법이 뭘까"라고 물었다. 답은 잘못된 값이 DB 에 아예 못 들어가게 막는 게 가장 좋다는 것이었다. 5/1 설계 때 상태·등급 같은 칸을 일반 글자 칸으로 만들고 DB 에 허용 값 검사(CHECK 제약)를 걸지 않았으니, 그 검사를 켜고 DB 변경 스크립트를 만들면 된다(JPA 로 치면 `@Enumerated(STRING)` 칸에 CHECK 를 붙이는 것). 읽을 때 이상한 행을 건너뛰는 방법은 문제를 숨기는 것이고, 총 개수와 실제 목록 개수가 어긋나 페이지 나누기가 틀어진다고 했다. 대화는 "바로 진행할까요?"로 끝났고 이후 저장한 코드는 없다.

{% hint style="info" %}
**배운 점 — 허용 값 검사를 DB 에 안 건 대가**

5/1 부터 상태·등급 칸은 DB 입장에선 평범한 글자 칸이라 아무 글자나 들어간다. 서버 코드를 거쳐 넣으면 검사가 되지만 SQL 로 직접 넣으면 그대로 저장되고, 읽는 순간 그 한 줄 때문에 목록 전체가 500 이 된다. 관리자 화면으로 등록했다면 막혔을 값들이다.
{% endhint %}

{% hint style="info" %}
**추정 — 왜 SQL 로 직접 넣었나**

9/13 에는 관리자 등록 화면 항목에 맞춰 정리했는데 실제로는 SQL 로 넣었다. 6개를 한 번에 넣으려고 화면 대신 DB 도구를 쓴 것 같다(대화 16:26 "앞으로는 검증해 주는 관리자 API 로 등록하면 같은 실수를 막을 수 있다"). SQL 에 사진은 없으니 사진은 나중에 관리자 화면으로 붙였을 것이다. 9/13 노트에 남긴 "실제로 등록했나"라는 물음의 답은, 10/16 에 SQL 로 넣었다는 것이다.
{% endhint %}

### 2. 장바구니에 상품 사진이 안 보이던 것 (0.3.1)

16:46 👤 "장바구니 화면에서 상품의 이미지가 안 보이는데". 상품 정보 API 는 사진 주소를 제대로 주고 있었고 받아 오는 쪽 코드도 이미 그 값을 담아 두고 있었는데, 화면에서 사진 칸에 그 값을 넘기지 않아서 가전 아이콘만 그려지고 있었다. 장바구니, 주문서의 주문 상품 목록, PC 검색 미리보기 세 곳이 같은 상태여서 각각 한 줄씩 사진 주소를 넘기게 고쳤다.

장바구니의 이 부분은 5/2 가짜 데이터 화면에서 바뀐 적이 없었고, 사진 주소는 6/23 상품을 서버와 연결할 때부터 있었다([06.23 일지](../2026-06/2026-06-23.md)). 넉 달 가까이 아이콘만 보였을 테데, 운영에 실제 사진이 있는 상품이 이날 처음 생겨서 드러났다.

👤 "배포 규칙 잘 지키고 버전 정보 잘 달아서 git tag 달아줘"라고 해서 0.3.0 다음인 0.3.1 을 붙여 올렸고, Jenkins 배포는 내가 직접 했다. 빌드할 때 다시 만들어지는 사이트맵 파일은 저장에서 뺐다.

### 3. 퀵계좌이체 (대화 17:12\~17:25)

👤 "결제창에서 퀵 계좌이체 라디오 버튼 제거할 수 있어 ? 다른 비지니스 로직에는 지장이 없어야해"에는 코드로는 못 지운다는 답이 나왔다. 결제수단 목록은 토스 결제창 부품 안쪽(토스 페이지를 끼워 넣은 틀)에 있고, 결제수단을 그리는 기능은 붙일 위치와 화면 설정 이름만 받는다. 토스 상점 관리 화면의 결제 화면 설정에서 끄면 되고, 테스트용과 실제용 설정을 따로 꺼야 한다.

👤 "퀵 계좌 이체는 결제창이 안 열리는데 ??"에는 그 결제수단 계약이나 활성화가 안 됐거나, 로그인하지 않은 익명 고객 구분값 때문일 거라는 추정이 나왔다. 그리고 "같이 알아 둘 부작용"으로, 결제하기를 누르면 결제창을 열기 전에 주문부터 만들기 때문에 퀵계좌이체를 누를 때마다 결제 안 된 결제대기 주문이 하나씩 쌓이고 있을 거라고 했다. 퀵계좌이체가 넘기는 결제수단 이름이 서버 쪽 이름표에 없으면 카드로 기록될 수도 있는데, 확인하지는 못했다.

### 4. "결제창을 닫으면 다시 결제할 수 없다" — 원인 찾기 (대화 17:30\~17:55)

17:30 👤 "왜 결제중에 현재 주문할 수 없는 상품이라고 나오지 ?", 17:40 👤 "카드 결제창을 열었다가 다시 닫으면, 왜 다른 결제 수단으로 결제할 수가 없고 해당 오더를 삭제하는 과정을 거쳐야 되지 ??"

원인은 9/3 노트의 버그 그대로였고([09.03 일지](../2026-09/2026-09-03.md)), 10/2 에 문서로만 정리해 둔 것이다([10.02 일지](2026-10-02.md)). 주문을 만들 때 재고를 줄이니, 결제창을 닫으면 첫 주문이 결제대기로 남아 재고를 잡고 있다. 다시 결제하면 새 주문을 만들려 하는데 재고가 1에서 0이 돼 상품이 품절 상태라서 "현재 주문할 수 없는 상품" 오류가 난다. 30분 만료 처리는 주문 상세를 볼 때만 돈다.

#### 처음 내놓은 비교 (17:52)

프론트 대화창의 분석을 백엔드 대화창에 붙여 넣고 "제일 쉽고 가장 간단하게 해결할 방법"을 물었더니 네 가지를 비교해 줬다. 서버가 새 주문을 만들기 전에 그 사람의 결제대기 주문을 자동으로 취소하는 방법은 결제창을 닫은 경우와, 탭을 닫았어도 본인이 다시 시도하는 경우는 해결하지만 다른 사람이 기다리는 문제는 못 푼다. 화면이 오류나 실패 화면에서 취소하는 방법은 탭을 닫으면 못 쓴다. 기존 주문을 다시 쓰는 방법은 가장 복잡했다. 주기적으로 정리하는 작업은 30분 뒤에야 풀리지만 모든 경우를 덮는다. 남는 위험도 하나 짚었다. 토스 승인은 성공했는데 응답이 중간에 사라진 상태에서 다시 주문하면, 첫 주문은 취소되고 뒤늦은 웹훅이 결제만 완료로 만들어서 돈만 빠질 수 있다.

#### 모든 경우를 따져 보기 (17:54\~17:55)

👤 "최대한 모든 경우에 수에 대응할 수 있게 로직을 개선 가능한가 ?"라고 하자, 취소를 더 잘하는 것만으로는 부족하고 원칙이 하나 더 필요하다는 답이 왔다. "결제가 됐는지 확실히 모르면 취소하지 않는다. 토스에 실제 결제 상태를 물어보고 나서 정리한다. 이 원칙만 지키면 최악이어도 재고가 잠깐 묶이는 정도로 끝난다."

### 5. 서버에서 방치 주문 근본 수정 (0.0.4)

사용자가 결제창을 닫거나 탭을 닫아도 재고가 오래 묶이지 않도록, 그리고 승인 결과를 모를 때 함부로 취소해 돈만 빠지는 일이 없도록 서버를 고쳤다. 이제 한 사람당 결제대기 주문은 하나만 남는다. 새 주문을 만들면 이전 결제대기 주문을 토스에 상태를 확인한 뒤 정리하고, 아무도 다시 오지 않는 주문은 2분마다 도는 정리 작업이 30분이 지나면 풀어 준다. 대화 18:08 의 설명으로는 "다른 탭에서 결제를 진행하던 중에 새 주문을 만들면 이전 탭의 결제는 승인 단계에서 거절된다. 거절이라 돈은 빠지지 않는다."

#### 진행 순서 (테스트를 먼저 쓰고 맞추는 방식)

17:58 에 첫 단계 테스트로 버그가 재현됐다("결제는 결제완료로 확정됐는데 재고는 이미 복구된 상태, 즉 이중 판매가 가능한 상태"). 17:59 에 승인할 때 주문을 잠그고, 웹훅도 주문 다음 결제 순서로 잠그게 고쳐 통과시켰다(교착이 안 생기는지 확인하는 테스트 포함). 17:59\~18:01 에는 토스에 주문번호로 결제를 조회하는 기능과 결제대기 주문 정리 기능을 만들었다. 18:02 에는 통합 테스트로 "사용자가 겪은 '현재 주문할 수 없는 상품' 오류가 그대로 재현"됐다. 원래 테스트는 주문 생성과 결제 준비를 한 DB 세션에 몰아넣어서 이 문제가 안 보였는데, 실제처럼 두 요청을 따로 나눠더니 드러났다. 18:03\~18:04 에 취소된 주문의 결제 완료 웹훅을 자동 환불하게 했고, 18:05 에 주기적 정리 작업을 만들었다("정리 작업 3개가 동시에 돌아도 재고는 정확히 5만 복구"). 18:06 에 580개 테스트가 통과했고 앱이 문제없이 뜨는 것도 확인했다.

#### 바뀐 내용

승인 처리는 이제 주문을 잠그고 읽는다. 주석에 "결제대행사 승인을 기다리는 사이 취소나 만료가 끼어들어 재고를 돌려놓은 뒤 이 처리가 결제완료로 덮어쓰는 이중 판매를 막는다. 잠그는 순서는 항상 주문, 그다음 결제"라고 적었다. 웹훅 처리도 결제 번호로 주문을 먼저 찾아 주문을 잠그고 결제를 잠근다. 결제 완료 웹훅인데 주문이 이미 취소돼 있으면 "취소된 주문의 결제 승인 감지 — 자동 환불"을 오류로 기록하고 전액 취소한다. 환불 결과를 알 수 없으면 오류로 답해서 토스가 웹훅을 다시 보내게 한다.

결제대기 주문 정리는 이렇게 돈다. 주문을 다시 잠그고, 결제대기가 아니면 그냥 둔다. 결제창을 연 적이 없어서 결제 기록이 없으면 바로 취소한다. 결제 기록이 있으면 토스에 주문번호로 조회해서, 토스에 없거나 아직 승인 전·중단·만료·취소 상태면 취소하고 재고를 돌려놓는다. 토스에서 완료로 나오면 취소하지 않고 결제를 확정한다(웹훅 완료 처리를 그대로 쓴다). 조회가 실패하면 손대지 않고 미룬다. 승인 전 상태를 안심하고 지워도 되는 이유도 주석에 적었다. 승인은 rekit 서버가 승인을 요청해야만 일어나는데, 승인 처리는 결제대기가 아닌 주문을 거절하기 때문이다.

주문 만들기는 시작할 때 그 사람의 결제대기 주문을 찾아 위 방식으로 정리한다. "장바구니 단위로 결제하니 결제대기 주문은 한 사람당 하나면 충분하다." 기존 30분 만료 처리도 같은 정리 기능을 쓰게 바꿨다. 주기적 정리 작업은 새 파일로 만들었다. 30분 넘은 결제대기 주문을 오래된 순으로 하나씩 잠가 가져오되 다른 작업이 잠근 건 건너뛰고, 주문 하나를 DB 작업 하나로 처리하며, 한 번에 최대 50건, 이번 차례에 미룬 건은 다시 집지 않는다. 오류가 나도 멈추지 않고 계속 돈다. 서버가 뜸 때 함께 시작하고 꺼질 때 멈추며, 간격은 설정으로 바꿀 수 있다(기본 120초, 0 이면 끔).

잠그고 다시 읽는 조회 세 곳에는 "이미 읽어 둔 객체도 DB 의 최신 값으로 덮어쓰라"는 옵션을 달았다. 이게 없으면 같은 세션에서 먼저 읽은 주문의 낡은 상태로 다시 확인하게 된다. 테스트는 정리 작업 통합 테스트(158줄, 작업 3개 동시 실행), 다시 주문하기 재현 테스트(106줄), 결제 처리 테스트 129줄, 단위 테스트 300줄 정도가 늘었다.

{% hint style="success" %}
**불확실하면 취소하지 않는다**

방치된 주문을 지우는 코드는 돈이 빠졌는지 모르는 상태(승인은 성공했는데 응답이 사라진 경우)에서 돌 수 있다. 그래서 지우기 전에 결제대행사에 진짜 상태를 묻고, 물을 수 없으면 미룬다. 잘못 미루면 재고가 잠깐 묶이는 걸로 끝나지만, 잘못 지우면 돈만 빠진다. 손해의 크기가 다르니 조심하는 쪽을 골랐다.
{% endhint %}

{% hint style="info" %}
**Spring 으로 치면**

잠그고 다시 읽을 때 최신 값으로 덮어쓰는 옵션은 `EntityManager.refresh()`, 또는 `@Lock(PESSIMISTIC_WRITE)` 조회가 1차 캐시를 무시하고 다시 읽게 하는 것과 같다. 주기적 정리 작업은 `@Scheduled(fixedDelay=120000)` 에 `SELECT … FOR UPDATE SKIP LOCKED` 를 붙여서 서버가 여러 대여도 ShedLock 없이 겹치지 않게 하는 패턴이다. 잠그는 순서를 맞춘 건, 두 작업이 A 다음 B, B 다음 A 로 잠그면 서로 기다리다 멈추기 때문에 모든 코드에서 주문 다음 결제로 고정한 것이다.
{% endhint %}

{% hint style="warning" %}
**여전히 남은 것 (원본 확인)**

### 6. 화면 쪽 보조 (0.3.2)

근본적인 해결은 서버 0.0.4 가 하고, 화면은 재고를 조금이라도 더 빨리 돌려놓는 역할을 맡았다. 주문서는 만든 주문번호를 기억해 두었다가 결제창을 띄우기 전에 실패하면 그 주문을 취소한다. 취소가 실패해도 화면엔 아무 영향이 없게 했다. 남은 주문은 다시 주문할 때나 정리 작업이 서버에서 처리하니까.

결제 실패 화면은 열릴 때 그 주문을 조회해서 결제대기일 때만 취소한다. 결제가 끝난 주문인데 뒤로 가기 같은 걸로 이 화면이 다시 열리면, 취소가 곧 환불이 되기 때문이다.

결제 후 돌아오는 화면은 승인 결과가 불확실한 응답(연결 끊김, 502·503·504)을 받으면 1.5초, 3초, 5초 간격으로 최대 세 번 다시 요청한다. 10/2 에 승인 요청에 중복 방지 표시가 붙어서 다시 보내도 안전하다. 그래도 안 되면 주문 상태를 조회해서 최종 판단한다. 결제대기나 취소가 아니면 완료 화면으로 보낸다. 웹훅이 먼저 결제를 확정했을 수도 있기 때문이다. 화면 할 일 문서의 방치 주문 항목은 완료로 바꿨다.
