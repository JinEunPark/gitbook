### 1. 결제 남은 일 점검과 승인 실패 처리 보강

20:54 에 👤 "지금 현재 프로젝트 분석해서, 결제 관련해서 추가로 수행해야하는 것들 알려줘"라고 물었더니 다섯 가지가 나왔다. 가장 급한 건 승인 처리 보강이었다. 토스가 승인을 거절하면 서버가 "Toss confirm 실패: 상태코드"만 남기고 토스가 준 오류 코드와 메시지는 버렸고, 같은 승인 요청이 두 번 가는 걸 막는 표시도 없었다. 그리고 "더 중요한 문제"로, 승인 실패를 잡아 처리하는 부분이 없어서 실패한 결제가 결제 준비 상태로 영영 남고 왜 실패했는지도 DB 에 남지 않는다는 지적이 있었다. 나머지 네 가지는 안 쓰는 파일과 API 문서 정리, 운영 점검(승인 유실 시나리오를 아직 안 해 봄), 부분취소 정책, 마무리 점검과 운영 대응 문서가 없다는 것이었다. 21:05 👤 "이거 우선적으로 변경하고 커밋 푸시해줘".

승인 요청이 거절되면 9/4 취소 작업 때 만들어 둔 오류 변환 함수를 그대로 써서 토스의 오류 코드와 메시지를 담아 올리게 했다. 승인 요청에도 "confirm-결제번호" 형태의 중복 방지 표시를 붙였다. 서버 쪽 승인 처리는 토스가 분명히 거절한 경우에만 그 결제를 실패 상태로 바꾸고 실패 사유를 적은 뒤 오류를 다시 올린다. 네트워크가 끊겨서 성공했는지 모르는 경우는 상태를 건드리지 않고 그대로 올려서 다시 시도하게 했다. 테스트를 먼저 써서 실패를 보고(21:06) 코드를 맞췄다(21:07). 토스 오류 코드가 담기는지, 중복 방지 표시가 붙는지, 실패 사유와 상태가 기록되는지 세 가지를 추가했다.

저장할 때 Claude 가 "작업 폴더에 이번 대화와 상관없는 변경(카테고리, 저장소, 업로드 등)이 섞여 있어서 제가 고친 결제 파일만 골라서 저장했다"고 했다. 옆 대화창에서 같은 저장소로 카테고리 작업을 하고 있었기 때문이다. 9/4 에 바뀐 파일을 통째로 저장했던 것과는 달랐다.

{% hint style="danger" %}
**실패 상태와 실패 사유가 실제로는 저장되지 않는다 (지금도)**

서버는 요청 하나를 DB 작업 하나로 묶어서, 정상으로 끝나면 저장하고 오류가 나면 전부 되돌린다. 그런데 승인 처리는 결제를 실패 상태로 바꾼 다음 오류를 다시 올린다. 그러니 방금 바꾼 실패 상태와 사유도 같이 되돌려진다. 결과적으로 승인이 거절된 결제는 여전히 결제 준비 상태로 남고 사유도 안 남는다. 대화에서 지적한 "영영 준비 상태로 남는 문제"는 풀리지 않은 셈이다. 단위 테스트는 메모리 안의 가짜 저장소를 써서 되돌리기가 없으니 통과한다. 11/16 현재 코드도 구조가 같다(수치를 세는 기능만 추가됐다). 고치려면 실패 기록을 따로 저장하거나, 오류를 올리는 대신 실패 응답을 돌려줘야 한다. Spring 으로 치면 `@Transactional` 메서드 안에서 엔티티를 FAILED 로 바꾸고 `RuntimeException` 을 던지면 같이 롤백되는 상황이라, `REQUIRES_NEW` 로 실패 이력을 따로 남기는 패턴이 필요한 자리다.
{% endhint %}

### 2. 카테고리 대표 이미지와 업로드 보안

#### 왜 시작했나

홈 화면 카테고리 칸에는 코드에 직접 그려 둔 가전 아이콘(냉장고·세탁기·TV·에어컨·전자레인지·메뉴 여섯 가지)만 쓸 수 있었고, 관리자 화면의 아이콘 칸은 이모지나 아이콘 이름을 글자로 적는 입력란뿐이었다. 새 카테고리가 생겨도 맞는 그림을 붙일 방법이 없었다. 그래서 관리자가 카테고리마다 대표 이미지를 올리면 홈에 그 이미지가 나오게 만들었다.

대화는 👤 "현재 카테고리 관련해서 로직 알려줘"로 시작했다. 카테고리 표와 상품의 카테고리 칸은 서로 연결(외래키)되지 않은 채 글자로만 맞춰져 있었다. Claude 는 "JPA 감각으로 보면 `@ManyToOne` 없이 그냥 String 칸으로 느슨하게 이어 놓은 것"이라고 설명했고, 그래서 카테고리를 지워도 그걸 쓰는 상품이 있는지 막지 않는다. 👤 "카테고리 사진이나 아이콘을 변경하거나 설정할 수 있는 로직이 있나 ?"에는 글자 입력란뿐이고 이미지 업로드는 없다는 답이 나왔다. 그래서 21:00 에 👤 "이미지랑 아이콘을 설정하는 로직을 만들어줄 수 있나 ? 그리고 클라이언트 에이전트에게 해당 개발된 api 를 연동할 수 있게 알려줘"라고 요청했다.

{% hint style="info" %}
**추정 — 왜 이때 카테고리 이미지였나**

9/13 첫 매물 6개가 전부 튀김기·식기세척기·제빙기 같은 주방 설비였고, 대화 21:35 에 "튀김기, 식기세척기 아이콘 생성해줘"가 이어진다. 기존 여섯 가지 아이콘으로는 새 카테고리를 나타낼 수 없어서 시작한 것으로 보인다. 내 PC 의 DB 에는 이미 튀김기 카테고리가 있었다(대화 21:54).
{% endhint %}

### 4. 운영 배포 (대화 22:31\~22:52)

#### Jenkins 가 https 로 튕긴다 (22:31)

👤 "젠킨스가 http 인데 https 로 자꾸 리다이렉팅되는데 이거 어케하냐". 서버에 들어가 보니 맨 앞 nginx 가 `rekit.co.kr` https 응답에 "앞으로 이 사이트와 하위 도메인은 https 로만 오라"는 HSTS 설정(1년)을 붙이고 있었다. Jenkins 는 nginx 와 상관없이 다른 포트로 바깥에 직접 열려 있었고, 서버 안에서 불러 보면 https 로 바뀌지 않았다. 원인은 HSTS 가 도메인 이름을 기준으로 걸리고 포트는 가리지 않는다는 데 있었다. 브라우저가 `http://rekit.co.kr:포트` 도 요청을 보내기 전에 https 로 바꿔 버린다.

당장은 IP 로 접속하거나, 브라우저의 HSTS 기억을 지우거나, 시크릿 창을 쓰면 된다. 제대로 하려면 Jenkins 용 하위 도메인을 따로 두고 nginx 와 인증서 뒤에 숨기는 게 맞고, "CI 도구를 암호화 없는 포트로 바깥에 그대로 열어 두는 것도 피할 수 있다"는 이점도 있다.

{% hint style="info" %}
**배운 점 — HSTS 는 포트를 가리지 않는다**

하위 도메인까지 포함한 HSTS 는 같은 도메인의 모든 포트에 https 를 강제한다. 같은 도메인에 암호화 없는 관리 도구를 다른 포트로 띄우면 브라우저로는 못 들어간다.
{% endhint %}

다시 안 생기게 하는 방법으로는 빌드를 하나 끝나고 다음 것을 돌리기, 동시 빌드를 막는 Jenkins 플러그인, 하나의 작업으로 묶어 순서대로 돌리기, 도커 저장 방식을 예전 것으로 되돌리기(도커 재시작 필요)가 나왔다. 20번 빌드는 혼자 돌고 있었다.
