# 05.06 · 회원가입·로그인 서버 첫 구현

### 이날을 한 문단으로

전날 세운 서버 개발 계획의 1주차(회원가입·로그인)를 처음으로 실제 코드로 옮겼다. 서버에 회원가입, 로그인, 로그인 연장, 로그아웃, 아이디 중복 확인 다섯 기능이 생겼고, 이 기능을 이후 다른 기능들이 따라 할 견본으로 만들었다. 만드는 도중에 "로그인 아이디"와 "화면에 보일 이름"을 부르는 이름이 서로 엉켜 있다는 걸 정리했고, 회원가입 때 이름을 받지 않기로 했다가 30분도 안 돼 직접 받는 쪽으로 바꿨다. 화면 쪽은 서버와 이름을 맞추고 회원가입에 이름 입력란을 넣었지만, 아직 서버를 실제로 부르지는 않고 가짜 로그인으로 움직였다.

### 1\~2. 로그인 관련 서버 기능 5개

5/1 에는 로그인 기능을 일부러 빼 둔 상태였는데, 전날 다시 나눈 기능별 폴더 구조 위에 이날 처음으로 회원가입과 로그인을 세웠다. 코드 곳곳에 "다른 기능도 이 파일 모양을 따라 만든다"고 적어 놓은 걸 보면, 첫 기능을 이후 모든 기능의 견본으로 삼으려 했다.

| 기능        | 보내는 것                            | 돌려받는 것                       | 실패할 때                             |
| --------- | -------------------------------- | ---------------------------- | --------------------------------- |
| 회원가입      | 로그인 아이디, 이름, 비밀번호, 이메일, 약관 동의 3개 | 회원 정보 + 짧은 출입증, 갱신용 출입증은 쿠키로 | 아이디 중복·이메일 중복(409), 입력 형식 틀림(422) |
| 아이디 중복 확인 | 로그인 아이디                          | 쓸 수 있는지 여부                   | 형식 틀림(422)                        |
| 로그인       | 아이디, 비밀번호, 로그인 유지 여부             | 짧은 출입증, 갱신용은 쿠키로             | 아이디·비밀번호 틀림(401)                  |
| 로그인 연장    | (갱신용 쿠키)                         | 새 짧은 출입증과 새 갱신용 쿠키           | 쿠키가 없거나 만료(401)                   |
| 로그아웃      | 없음                               | 갱신용 쿠키 지우기                   | 없음. 여러 번 눌러도 결과가 같다               |

주소는 모두 `/api/v1/auth/` 아래에 있다. 회원가입 응답에 회원 정보와 출입증을 같이 돌려줘서, 가입하면 바로 로그인된 상태가 되고 화면이 "내 정보"를 한 번 더 물어볼 필요가 없게 했다.

#### 이렇게 정한 이유들 (코드 주석에서)

* 아이디가 없을 때, 비밀번호가 틀렸을 때, 정지된 계정일 때 모두 같은 "아이디·비밀번호 틀림"을 돌려준다. 그래야 남이 아무 아이디나 넣어 보면서 어떤 아이디가 실제로 있는지 알아낼 수 없다.
* 갱신용 출입증은 자바스크립트가 못 읽는 쿠키(HttpOnly)에 넣고, 짧은 출입증만 응답 본문으로 준다. 화면에 악성 코드가 끼어들어도 오래 가는 출입증은 훔쳐 갈 수 없게 하려는 것이다.
* 이 쿠키는 로그인 관련 주소(`/api/v1/auth`)로 갈 때만 붙게 했다. 쿠키 정책(samesite)은 가장 엄격한 Strict 대신 Lax 로 했는데, Strict 로 하면 다른 사이트의 링크를 타고 들어올 때 로그인이 끊기기 때문이다. 보안 연결 전용 표시(secure)는 운영 서버에서만 켠다.
* 쿠키를 굽는 옵션과 지우는 옵션을 한곳에서 관리한다. 쿠키는 이름·경로·도메인이 모두 같아야 같은 쿠키로 보는데, 로그아웃할 때 경로가 하나라도 어긋나면 쿠키가 안 지워지는 흔한 버그가 생긴다.
* 회원의 역할(일반/관리자)은 짧은 출입증에만 넣고 갱신용에는 넣지 않았다. 역할이 바뀌면 30분 안에 짧은 출입증이 새로 나오면서 바로 반영된다.
* 로그인을 연장할 때마다 갱신용 출입증도 새로 준다. 도둑맞은 출입증이 오래 살아남지 못하게 하려는 것인데, 이때는 옛 갱신용 출입증을 폐기해 둘 저장소가 없어서 옛 것도 기한까지는 그대로 쓸 수 있었다.
* "로그인 유지"를 고르면 갱신용 출입증이 30일, 아니면 14일이다.
* 가입할 때 아이디 중복, 이메일 중복 순으로 먼저 확인하고 저장한다. 이 확인은 사용자에게 친절한 안내를 하려는 것이고, 두 사람이 동시에 같은 아이디로 가입하는 경우는 DB 의 중복 금지 조건이 최종적으로 막는다.
* 이메일은 소문자로 바꾸는 일을 입력 검사와 업무 규칙에서 두 번 한다. 업무 규칙이 관리자 도구나 스크립트에서 곧바로 불릴 때도 같은 결과가 나오게 하려고.

{% hint style="warning" %}
**로그아웃해도 30분은 남는다 (주석에 적어 둠)**

서버가 출입증을 따로 기억하지 않는 방식이라, 로그아웃해도 이미 나간 짧은 출입증은 기한(30분)까지 유효하다. 주석에 "Redis 세션을 도입하면 출입증 폐기 기능을 추가한다"고 적어 두었다.
{% endhint %}

#### 입력 검사는 화면과 똑같이

아이디 규칙(영문·숫자·밑줄 4\~20자)은 화면의 회원가입 검사와 똑같이 맞췄다. 서버가 화면보다 느슨하거나 엄격하면 "화면에서는 통과했는데 서버가 거절"하는 어색한 상황이 생기기 때문이다. 비밀번호는 8자 이상에 영문과 숫자가 다 들어가야 한다. 필수 약관(이용약관, 개인정보) 중 하나라도 동의하지 않으면 거절한다. 서버는 칸 이름을 `loginId` 와 `login_id` 둘 다 받아 주고, 돌려줄 때는 화면 쪽 관례대로 `loginId` 식으로 보낸다. 돌려주는 회원 정보에는 번호, 로그인 아이디, 이름, 이메일, 전화번호, 본인 확인 여부, 절약한 탄소량(아직 0)이 들어 있다.

{% hint style="info" %}
**덜 정리된 이름**

로그인 아이디가 중복될 때 내는 에러 이름이 여전히 "사용자 이름 중복(`USERNAME_TAKEN`)"이다. 5/5 에 서버 명세서의 에러 목록을 그대로 옮기면서 생긴 이름이다. 중복 확인 응답 설명에도 옛 주소(`/auth/check-username`)가 남아 있다. 기능에는 영향이 없다.
{% endhint %}

### 3. 회원 표 변경 (DB 변경 스크립트 2개)

같은 날 방향이 한 번 바뀐 흔적이 스크립트 두 개에 그대로 남아 있다. 22:04 에 만든 첫 번째 스크립트는 로그인 아이디 칸(20자, 중복 금지)과 약관 동의 시각 세 칸을 추가하고, 이름 칸을 비워 둘 수 있게 바꿨다. 이때 생각은 "가입 화면에서는 이름을 받지 않고, 나중에 본인인증을 하면 인증 결과의 실명으로 채운다"였다. 두 번째 스크립트(22:30 표기)는 이걸 뒤집어서 가입 화면에서 이름을 직접 받기로 하고 이름 칸을 다시 필수로 만들었다. 동시에 칸 이름도 정리해서, 첫 번째 스크립트에서 `username` 이라고 불렀던 로그인 아이디 칸은 `login_id` 로, 예전 `name` 칸은 `username`(화면에 보일 이름)으로 바꿨다.

약관 동의는 예/아니오가 아니라 "동의한 시각"으로 저장한다. 모델 주석에 따르면 전자상거래법상 동의 시각을 남겨야 하고, 나중에 약관이 바뀌면 "동의 시각이 새 약관 게시일보다 이른 회원"에게 다시 동의를 받으면 되기 때문이다. 필수 약관 두 개는 비워 둘 수 없고, 마케팅은 동의하지 않으면 비어 있다.

이메일 칸 설명도 "로그인 아이디 겸 알림 수단"에서 "비밀번호 찾기 같은 본인 확인용"으로 바뀌었다. 이메일 로그인이 아니라 아이디 로그인으로 확정했다는 뜻이다. 문자 인증 쪽 주석도 "회원가입 때 필수"에서 "회원가입과 따로 가는 흐름"으로 바뀌었다.

{% hint style="warning" %}
**데이터가 있으면 실패하는 스크립트 (주석에 적어 둠)**

필수 칸을 새로 만들거나 필수로 바꾸는 작업은 이미 회원이 있으면 실패한다. 주석에 "운영 환경에서는 기본값을 넣고, 기존 행을 채우고, 기본값을 지우는 단계로 나눠야 한다. 이 스크립트는 개발용(데이터 없음)을 가정한다"고 적었다.
{% endhint %}

### 4. 서버 주소 묶음을 한 파일로

그전에는 서버 시작 파일이 기능마다 "`/api/v1` 아래에 이 주소들을 붙여라"를 따로 적었다. 이날 `/api/v1` 묶음을 한 파일에 만들고 그 안에 사진 업로드와 로그인 주소를 모은 뒤, 시작 파일에서는 그 묶음 하나만 붙이게 했다. 같은 말을 반복하지 않고, 나중에 v2 가 생기면 이 파일만 나누면 되고, 서버 주소 전체를 한곳에서 볼 수 있다는 이유였다. 새 기능을 추가하면 이 파일에 한 줄 넣는다.

### 5. 테스트 33개 추가

입력 검사 테스트 17개는 빈 아이디·비밀번호 거절, `loginId` 이름으로 보내도 받는지, 로그인 유지 기본값이 꺼져 있는지, 이메일이 소문자로 바뀌는지, 아이디 형식 위반, 너무 짧거나 숫자 또는 영문이 빠진 비밀번호, 필수 약관 미동의 두 경우, 빈 이름, 응답 칸 이름(`accessToken`, `loginId`, `ecoKg`)이 맞게 나가는지를 본다.

업무 규칙 테스트 16개는 로그인 실패 세 경우가 정말 같은 에러를 내는지, 로그인하면 출입증 두 개가 나오는지, 가입하면 저장이 한 번 일어나는지, 마케팅 동의 시각, 아이디·이메일 중복, 중복 확인 결과, 만료된 갱신용 출입증 거절, 짧은 출입증을 갱신용 자리에 넣으면 거절하는지, 없는 회원·정지된 회원, 연장하면 새 출입증 한 쌍이 나오는지를 확인한다.

업무 규칙 테스트는 진짜 DB 대신 흉내만 내는 가짜 DB 담당을 끼워서 돌린다. 실제 DB 로 확인하는 통합 테스트는 나중에 따로 만들기로 했고 이때는 아직 없었다. 테스트 준비 파일에는 시작할 때 모든 DB 모델을 미리 불러오는 줄을 넣었다. 모델끼리 이름으로만 이어 두었기 때문에, 다 불러와 있지 않으면 연결을 못 찾아 에러가 난다.

{% hint style="success" %}
**전날 정한 규칙의 첫 실전**

테스트 이름을 "대상\_상황\_기대동작"으로 짓고, 실패 경우부터 쓰고, 준비·실행·확인을 나누고, 바깥 의존은 가짜로 바꾸는 5/5 규칙을 그대로 따랐다.
{% endhint %}

### 6. 화면 쪽 회원 정보 이름 맞추기 + 이름 입력란

서버에서 칸 이름을 바꾼 데 맞춰 화면 쪽도 바꿨다. 로그인 정보 보관함의 회원 정보에서 로그인용 아이디는 `loginId`, 화면에 보일 이름은 `username` 으로 불러 서버와 같아졌다. 브라우저 저장 이름도 v2 에서 v3 로 올려서, 옛 형식으로 저장된 로그인 정보는 자동으로 버려지게 했다(안내문의 "저장 형식이 바뀌면 버전을 올린다" 규칙).

회원가입 화면에는 "이름" 입력란을 새로 넣었다. 안내 글은 "화면에 표시될 이름"이고 한 글자 이상이면 통과하며, 가입 버튼이 켜지는 조건에 이름도 들어갔다. 로그인, 아이디 찾기, 비밀번호 찾기 화면은 안쪽 변수 이름만 바뀌었고 보이는 문구는 그대로다. 머리와 마이페이지의 "○○ 님"은 새 이름 칸을 쓰고, 내 정보 화면은 이름과 "@아이디"를 따로 보여 준다.
