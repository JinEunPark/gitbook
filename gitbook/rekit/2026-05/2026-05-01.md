# 05.01 · 프로젝트 시작 — 디자인 시안 14화면과 서버 뼈대

{% hint style="info" %}
📜 **소급 작성** (작성일 2026-11-16, 읽기 쉽게 다시 씀) — 근거: 이날 올린 코드와 문서(프론트 2번, 백엔드 1번 저장), DB 변경 스크립트에 찍힌 작성 시각. 대화 기록은 없어서 문서에 없는 "왜"는 "추정" 상자 으로 표시했다.

용어: [용어 풀이](../glossary.md) · 다음: [05.02 일지](2026-05-02.md)

### 이날을 한 문단으로

프로젝트 첫날이다. 디자인 도구(Claude Design)로 먼저 그려 둔 쇼핑몰 화면 14개를 웹 코드로 옮겨 참고용 디자인 페이지로 보관해 두고, 그걸 보면서 실제로 쓸 화면 4개(홈·로그인·회원가입·마이페이지)를 휴대폰과 PC 양쪽에 맞게 새로 만들었다. 서버 쪽은 상품·주문·결제 같은 데이터를 담을 DB 표 11개와 사진 올리기 기능만 먼저 만들어 두었다. 무엇을 만들지 정리한 요구사항 정의서와, 화면마다 서버에 어떤 기능이 필요한지 적은 설계 문서도 같이 썼다. 이때는 로그인이나 주문 기능이 아직 없어서 화면은 전부 가짜 데이터로 움직였다.

### 1. 화면 프로젝트 만들기

Vue(화면을 만드는 도구) 공식 시작 템플릿으로 빈 프로젝트를 만들었다. TypeScript(타입 검사), 페이지 이동(Vue Router), 공용 데이터 보관함(Pinia), 코드 검사기(ESLint·Prettier·oxlint)를 켠 상태로 시작했다.

_근거 커밋: `3a33aec`_

### 2. 디자인 시안 화면을 참고용 페이지로 보관

디자인은 Claude Design 이라는 도구에서 그림처럼 먼저 만들어 두었다. 시안은 휴대폰(390×844)과 PC(1440) 크기가 고정된 그림이라 서비스에 그대로 쓸 수가 없어서, 두 단계로 가기로 했다. 먼저 시안을 웹 코드로 똑같이 옮겨 `/_design` 주소 아래 모아 두고, 실제 화면은 그걸 옆에 띄워 놓고 보면서 새로 만드는 방식이다.

화면 쪽 계획서에는 색·아이콘·가짜 데이터·버튼 같은 부품은 가져다 쓰고, 휴대폰 테두리나 위쪽 "9:41" 시계줄 같은 그림용 장식은 버린다고 적어 두었다.

| 구분              | 옮긴 화면                                                |
| --------------- | ---------------------------------------------------- |
| 구매자 9개 (휴대폰 크기) | 로그인, 홈, 상품 목록, 상품 상세, 장바구니, 본인 확인, 주문서, 주문 완료, 마이페이지 |
| 관리자 5개 (PC 크기)  | 대시보드, 상품 관리, 주문 관리, 회원 관리, 매출                        |
| PC 참고 2개        | PC용 홈, PC용 상품 상세                                     |
| 목차 1개           | `/_design` — 위 화면들을 카드로 모아 둔 목록                      |

시안 화면은 검은 바탕의 캔버스 틀 안에 띄우고, 위쪽에 "← 모든 화면" 버튼과 현재 주소를 보여 준다. 주소에 따라 바깥 틀(레이아웃)을 다르게 고르는 장치도 이날 디자인 틀 / 디자인 목차 / 로그인 화면 / 일반 화면 4가지로 시작했는데, 지금은 체크아웃·관리자 등이 붙어서 7가지가 됐다. Spring 으로 치면 URL 별로 다른 레이아웃 템플릿을 고르는 것과 같다.

{% hint style="info" %}
**시안을 지우지 않고 남겨 둔 이유**

실제 화면을 만들 때마다 같은 화면의 시안 주소를 옆 탭에 띄워 비교할 수 있다. 지금도 "시안 페이지는 잠금, 실제 서비스 코드에서 가져다 쓰지 말 것"이라는 규칙으로 남아 있다.
{% endhint %}

_근거 커밋: `42bf8c4` · 개발자용: `src/_design/` 아래 17개 파일, 약 4,500줄_

### 3. 디자인 부품 — 색·글꼴·버튼·아이콘, 가짜 상품

모든 화면이 같은 색과 모양을 쓰도록 디자인 부품 상자를 만들었다. 상품 사진이 아직 없어서 사진 자리에는 가전 아이콘과 파스텔 배경을 넣어 화면이 완성돼 보이게 했고, 가짜 상품 8개로 화면을 채웠다.

#### 색과 글꼴

| 무엇      | 값                                                        |
| ------- | -------------------------------------------------------- |
| 바탕·글자   | 연회색 바탕, 흰 카드, 글자는 순검정 대신 따뜻한 먹색                          |
| 포인트 색   | 민트 초록 (진하기 4단계)                                          |
| 상품 등급 색 | A 민트 · B 머스터드 · C 주황갈색                                   |
| 경고·안내   | 빨강 · 파랑                                                  |
| 글꼴      | 본문 Pretendard, 제목용 명조(Noto Serif KR), 숫자는 JetBrains Mono |
| 가격 표시   | `180000` 을 "180,000원" 으로 바꿔 주는 함수                        |

같은 색 값을 코드용 상수 파일과 화면 스타일 변수 두 곳에 적어 두었다. 그래서 지금도 색을 바꾸면 두 곳을 같이 고쳐야 한다는 규칙이 있다.

#### 부품 6가지

| 부품      | 하는 일                                                                                                           |
| ------- | -------------------------------------------------------------------------------------------------------------- |
| 로고      | 나뭇잎 그림과 "rekit" 글자. 잎은 "다시 살린다"는 뜻                                                                             |
| 가전 아이콘  | 사진 대신 쓰는 냉장고·세탁기·TV·에어컨·전자레인지·청소기 그림                                                                           |
| 상품 썸네일  | 가전 아이콘, 파스텔 배경, 등급 배지. 나중에 실사진이 들어오면서 바뀌고, 11/13 사진 로딩 표시도 이 부품에 들어갔다 (→ [11.13 일지](../2026-11/2026-11-13.md)) |
| 배지 · 버튼 | 색·크기 변형                                                                                                        |
| 아이콘     | 선 아이콘 40종                                                                                                      |

#### 가짜 상품 8개 (예)

| 상품                      | 판매가 / 정가   | 등급 | 표시            |
| ----------------------- | ---------- | -- | ------------- |
| 삼성 양문형 냉장고 384L (2021)  | 18만 / 129만 | A  | 동작보증          |
| LG 트롬 드럼세탁기 21kg (2020) | 24만 / 169만 | B  | 인기            |

카드에 보이는 "86%" 같은 할인율은 `(1 − 판매가 ÷ 정가) × 100` 을 반올림한 값이다.

### 4. 실제 화면 4개와 휴대폰/PC 공용 레이아웃

시안과 달리 화면 크기에 맞춰 늘었다 줄었다 하는 진짜 화면을 처음 만들었다. 홈·로그인·회원가입·마이페이지 4개다. 서버와는 아직 연결하지 않아서 로그인하면 가짜 사용자 정보가 채워진다.

#### 머리·꼬리·하단 탭

| 부분     | 휴대폰 (폭 768px 미만)                    | PC (768px 이상)                  |
| ------ | ----------------------------------- | ------------------------------ |
| 머리(헤더) | 메뉴 버튼(옆에서 나오는 서랍), 로고, 검색 아이콘, 장바구니 | 로고, 카테고리 메뉴 7개, 검색창, 찜·장바구니·마이 |
| 하단 탭   | 화면 아래 고정                            | 숨김                             |
| 꼬리(푸터) | 공통                                  | 공통                             |

{% hint style="info" %}
**이후 바뀐 점**

이날은 PC 머리에 카테고리 메뉴를 넣었지만, 지금은 카테고리를 머리에 두지 않고 홈 화면 칸·상품 목록 버튼·하단 탭에만 둔다.
{% endhint %}

#### 홈

홈은 위에서부터 네 덩어리다. 맨 위 안내 띠를 누르면 이용 안내(`/guide`)로 가고, 그 아래 카테고리 8칸(냉장고·세탁기·TV·에어컨·주방가전·청소기·소형가전·전체)이 있다. 다음은 "오늘 들어온 매물"로, 가짜 상품 8개를 할인율·가격·정가·동작보증·찜 버튼이 있는 카드로 보여 준다. 찜 버튼을 눌러도 상세로 넘어가지 않게 막아 두었다. 마지막은 "rekit 만의 약속" 3가지로, 동작 보증(7일 안에 고장 나면 전액 환불), 직접 배송(서울·경기 당일, 운반·설치), 합리적 가격(새 제품의 70\~80%, 평균 73% 할인)이다.

{% hint style="warning" %}
**이때 문구는 "철거" 이야기였다**

안내 띠는 "철거 현장에서 바로 도착, 평균 73% 할인", 약속 제목은 "철거 가전이지만 새 가전처럼 만나보세요"였다. 소비자에게 거부감이 있다는 이유로 나중에 "폐업 매장" 이야기로 바꿨다(→ [05.05 일지](2026-05-05.md)). "평균 73% 할인"은 지금도 쓰는 숫자다.
{% endhint %}

#### 로그인 · 회원가입

로그인은 아이디와 비밀번호로 한다. 화면 문구는 "다시 살아나는 가전, 새로운 주인을 기다려요"이고, 아이디 4자·비밀번호 6자 이상이 되어야 로그인 버튼이 눌린다. "로그인 상태 유지"와 아이디/비밀번호 찾기 링크도 넣었는데, 찾기 화면은 아직 없다.

회원가입 규칙은 이렇게 잡았다.

| 항목      | 규칙                                                                    |
| ------- | --------------------------------------------------------------------- |
| 아이디     | 영문·숫자·밑줄 4\~20자, 중복 확인 필수 (가짜로 `admin`·`root`·`test` 를 넣으면 "이미 사용 중") |
| 비밀번호    | 8자 이상, 영문과 숫자 포함                                                      |
| 비밀번호 확인 | 같아야 함                                                                 |
| 이메일     | 형식 검사                                                                 |
| 약관      | 이용약관·개인정보 필수, 마케팅 선택, "전체 동의"                                         |

로그인 전에 보던 페이지가 있으면 로그인한 뒤 그 페이지로 돌려보낸다. 입력칸 모양을 화면마다 복사해서 쓰는 방식도 여기서 시작됐는데, 지금 "이런 폼이 하나 더 생기면 공용 입력칸 부품으로 뽑아낸다"는 규칙이 걸려 있는 게 바로 이 부분이다.

{% hint style="info" %}
**추정 — 회원가입에 휴대폰 인증이 없는 이유**

같은 날 쓴 요구사항 정의서에는 "가입 시 휴대폰 문자 인증 필수"라고 되어 있는데, 실제 가입 화면에는 휴대폰 입력이 없다. 화면 계획서도 로그인을 "이메일 + 인증번호"로 적어 놓고 실제로는 아이디와 비밀번호로 만들었다. 일단 단순하게 만든 건지 이때 이미 방향을 바꾼 건지는 기록이 없다. (11/5 에 문자 인증은 하지 않기로 최종 결정 → [11.05 일지](../2026-11/2026-11-05.md))
{% endhint %}

#### 마이페이지

로그인하지 않은 상태로 들어오면 다른 페이지로 튕겨내지 않고, 같은 화면에서 "로그인하고 마이페이지를 확인하세요"와 로그인/가입 버튼, 혜택 3줄을 보여 준다. 로그인한 상태에서는 프로필, "지금까지 약 86kg의 가전을 다시 살렸어요" 문구, 주문 단계별 개수(결제완료 1·준비중 2·배송중 1·배송완료 5, 숫자는 고정값), 그리고 관심상품·배송지·본인 확인·공지·문의 메뉴가 나온다.

#### 로그인 상태 저장 (가짜)

로그인하면 서버 없이 데모 사용자를 채워서 브라우저 저장소에 넣는다. 코드 주석에는 "나중에 진짜 서버가 이걸 대신할 것"이라고 적어 두었다. 브라우저 저장 이름을 `rekit.<기능>.v<버전>` 으로 짓고, 버전을 올리면 옛 데이터는 버리는 규칙도 여기서 시작됐다.

### 5. 화면 쪽 작업 계획서

### 6. 요구사항 정의서 v1.1

문서 제목은 "철거 가전 직거래 플랫폼 MVP 요구사항 정의서"이고 414줄이다. 처음 사업 그림이 가장 잘 남아 있는 문서라서 자세히 적어 둔다. 누가 팔고 누가 사는지, 첫 버전(MVP)에 무엇을 넣고 뺄지, 본인 확인을 언제 할지, 법적으로 필요한 게 뭔지를 정리했다.

#### 사업 그림

철거 현장에서 나오는 쓸 만한 가전을 버리지 않고 싸게 다시 파는 게 출발점이었다. 판매자는 철거업을 하는 친구 한 명이고, 첫 버전에는 판매자가 이 한 명뿐이다. 사는 사람으로는 자취생·신혼부부·고시원/원룸 운영자·소상공인·사무실을 생각했다. 직접 배송 지역도 "친구가 철거 차량으로 직접 배달할 수 있는 서울/경기"로 정했다.

#### 첫 버전 범위

여러 판매자 입점, 실시간 채팅, 후기, 쿠폰, 앱(반응형 웹으로 대신), 추천은 뺐다. 대신 믿음을 주는 장치로 상태 등급 A(거의 새 것)/B(사용감)/C(흠집 많음, 동작은 됨), 동작 보증 여부, A/S 불가 명시, 사진 필수(정면/측면/흠집)를 넣었다. 장바구니는 "가전은 보통 1개씩 사서 꼭 필요하진 않지만 나중을 위해 넣음"이라고 적었다.

#### 본인 확인 3단계

| 단계 | 언제      | 방법                   | 왜                  |
| -- | ------- | -------------------- | ------------------ |
| 1  | 회원가입    | 문자 인증                | 자동 가입·중복 가입 막기     |
| 2  | 첫 주문 직전 | 이름 + 생년월일 + 통신사 본인인증 | 신원 확인, 만 14세 미만 막기 |
| 3  | 결제      | 카드사 본인 확인            | 남의 카드 결제 막기        |

{% hint style="success" %}
**원칙 — 확인은 필요한 순간에**

정의서에는 "가입할 때 본인인증을 강제하면 가입하는 사람이 크게 줄어든다, 주문 직전 1번이면 충분"이라고 적었다. 지금도 주문 첫 단계가 본인 확인 화면인 이유가 이거다.
{% endhint %}

#### 이때 이미 정해 둔 것

보안은 비밀번호를 복원 불가능한 방식(bcrypt)으로 저장하고, 카드 정보는 결제대행사에 맡기고, 개인정보를 암호화하고, 로그인 출입증(JWT) 유효시간과 요청 횟수 제한, 관리자 접속 제한을 두는 것으로 정했다.

속도 목표는 느린 모바일(3G)에서도 3초 안에 뜨는 것이었고, 사진은 필요할 때 불러오고 WebP 형식으로 쓰기로 했다. 11/13 사진 최적화가 반년 뒤에 이 요구를 채운 셈이다.

검색 노출에 대해서는 "이런 방식의 화면(SPA)은 검색에 약하다"고 보고 Nuxt 전환을 권장, 미리 만든 HTML(프리렌더)을 대안, 최소한 제목·사이트맵이라도 두는 것으로 적었다. 결국 8/30 에 프리렌더로 갔다.

법적으로는 통신판매업 신고, 사업자 등록, 약관·개인정보·환불 정책, 고장 시 7일 안 환불, 단순 변심 반품 제한을 챙겼다. 위험 요소로는 큰 가전 반품비, 동작 불량 항의("동작 보증" 상품과 "외관/부품용" 상품을 나눠서 대응), 배송 중 파손(화물 보험·포장 사진)을 꼽았다.

### 7. 서버 뼈대

서버가 다룰 데이터를 담을 DB 표 11개를 설계하고, DB·캐시·사진 저장소·앱 4개를 한 번에 띄우는 실행 환경을 만들었다. 실제로 쓸 수 있는 기능은 사진 올리기 하나뿐이고, 로그인·상품·주문 기능은 아직 없다.

{% hint style="success" %}
**복사본을 두는 이유**

주문 상품에는 상품명·가격을, 주문에는 배송지를 복사해 둔다. 나중에 상품 가격이 바뀌어도 지난 주문 내역은 그때 가격 그대로 보여야 하기 때문이다. JPA 에서 연관관계로만 들고 있으면 바뀐 값이 보이는 함정과 같은 이야기다.
{% endhint %}

#### 디자인을 보고 DB 고치기 (같은 날 4번)

디자인 화면에는 있는데 DB 에 칸이 없던 것들을 채웠다.

| 화면에 보이는 것                             | 추가한 칸                   |
| ------------------------------------- | ----------------------- |
| 장바구니의 "직접 배송 할인 −20,000원"             | 주문 할인 금액, 배송 방식         |
| 결제 완료 화면의 "신한카드 1234 · 일시불"           | 카드사, 카드 끝 4자리, 할부, 승인번호 |
| 상세 화면 사진 6장의 이름표(정면/측면/내부/흠집/뒷면/제품번호) | 사진 종류                   |
| 주문 내역의 상품 사진                          | 주문할 때 사진 주소 복사본         |

{% hint style="danger" %}
**오늘 잡은 어긋남 — 번호 자동 증가 방식**

코드에는 번호를 DB 가 자동으로 매기는 최신 방식(IDENTITY)으로 적어 놓았는데, 실제 DB 는 옛 방식(SERIAL)으로 만들어져 있어서 둘이 달랐다. 그대로 두면 다음에 DB 변경 스크립트를 만들 때마다 이 차이가 계속 잡힌다. 표마다 지금 가장 큰 번호 다음부터 이어지게 해서 새 방식으로 바꿨고, 기존 데이터는 그대로 두었다. 되돌리는 스크립트도 같이 만들었다.
{% endhint %}

#### 사진 올리기 — 3단계

사진은 이런 순서로 올라간다. 화면이 서버에 사진 올릴 주소를 달라고 하면 서버가 10분만 쓸 수 있는 업로드 주소를 준다. 브라우저는 그 주소로 사진 저장소에 직접 올리고, 다 올린 뒤 서버에 알리면 서버가 확인해서 10MB 가 넘는 파일은 지우고 거절한다.

이렇게 하면 사진 파일이 서버를 거치지 않아서 서버의 통신량과 메모리를 아낄 수 있다. 받는 형식은 jpg/png/webp 뿐이고, 서버가 켜질 때 사진 보관함이 없으면 만든다. 운영 환경에서는 API 설명서 페이지(`/docs`)를 감춘다. 사진 저장소 권한은 서버 계정은 읽기·쓰기, 외부는 읽기만 주었다. 상품 사진은 어차피 공개니까.

{% hint style="warning" %}
**남겨 둔 구멍**

업로드 주소를 달라는 요청에 관리자 확인이 없다. 아직 로그인 기능이 없어서 아무나 업로드 주소를 받을 수 있는 상태이고, 문서에 할 일로 적어 두었다. (→ 10/2 에 직접 재현하고 막음, [10.02 일지](../2026-10/2026-10-02.md))
{% endhint %}

{% hint style="info" %}
**"일부러 지워 둔 상태"**

서버 기록 문서에는 로그인·상품·주문·결제 기능을 일부러 지워 둔 상태라고 적혀 있다. "DB 구조 + 실행 환경 + 업로드만 먼저 만들고 기능은 단계별로 추가"한다는 설명이다. 전에 한 번 다 만들었다가 걷어냈을 수도 있다.
{% endhint %}

### 8. 서버 설계 문서

디자인 화면을 하나씩 보면서 이 화면을 움직이려면 서버에 어떤 기능과 데이터가 필요한지 정리한 문서(548줄)와, 지금 서버가 어디까지 만들어졌는지 적은 기록 문서(189줄)를 썼다.

#### 설계 문서 (화면별 서버 기능)

구매자 9화면과 관리자 5화면마다 필요한 데이터와 사용자 행동을 표로 정리했다. 필요한 서버 기능은 15묶음(로그인·본인 확인·배송지·상품·찜·장바구니·주문/결제·배송·공지·관리자 5종·업로드)이고, 이 중 완성된 건 업로드뿐이다.

DB 를 바꿔야 할 부분은 시안 파일 위치까지 근거로 달아 두었다.

* 카테고리를 6개에서 8개로 늘린다(청소기·소형가전 추가). 홈 화면이 8칸이라서다. "'전체'는 카테고리가 아니라 필터를 안 건 상태"라고 메모했다.
* 마이페이지의 "약 86kg 살렸어요"는 따로 저장하지 않고 배송 완료된 상품 무게를 더해서 계산한다.
* 결제는 카드 번호 전체·CVC·유효기간을 절대 저장하지 않고, 카드사·끝 4자리·할부·승인번호만 남긴다. 결제대행사 거래 번호는 같은 요청이 두 번 와도 한 번만 처리하는 기준으로 쓴다.
* 찜 표는 필수, 기획전·알림·공지 표는 있으면 좋음, 상품 문의는 보류.

업무 규칙으로는 7일 환불(동작 불량만, 단순 변심은 거절), 직접 배송은 서울/경기 우편번호만, 본인 확인을 안 했으면 주문 거절, 재고는 주문할 때 붙잡고 결제되면 확정하는 것으로 정했다. 금액은 화물 6만, 직접 배송 4만, 직접 배송 할인 2만, 일반 택배 5천, 환불 기간 7일이다. 여기서 "직접 배송 4만 − 할인 2만"이 10/21 에 화면과 결제 금액이 어긋나는 문제로 이어진다(⑮).

#### 기록 문서 — 아직 못 정한 것

본인인증 정보 암호화 방식, 사진 크기를 어디서 줄일지, 캐시(Redis) 용도, 검색 노출(SPA 유지 vs Nuxt), 서버를 어디에 둘지(네이버 클라우드 / AWS Lightsail / EC2)가 남아 있었다.

### 이름 — 이날의 상태

이날은 이름이 섞여 있었다. 화면 쪽 로고·색 이름·저장 이름·계획서 제목은 rekit 인데, 디자인 원본 폴더는 rekle 이고, 서버 문서·DB·사진 보관함·프로그램 이름은 Rekle 이다. 사업 이야기는 양쪽 다 철거 가전 / 철거 현장 / 철거업자였다.

{% hint style="info" %}
**추정 — rekle 에서 rekit 으로는 언제?**

화면 쪽은 첫 저장부터 rekit 이다. 디자인 원본 폴더는 rekle 인데 그 안의 색 이름이 이미 REKIT 이라서, 디자인을 다듬던 중(저장 전)에 이름을 바꾼 것으로 보인다. 서버 쪽은 DB·폴더 이름이 rekle 로 남았다. 상표 문제를 언제 알았는지는 기록이 없다.
{% endhint %}
