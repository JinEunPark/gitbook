# 05.10 · 화면과 서버 첫 연결, 소셜 로그인 3사

### 이날을 한 문단으로

화면이 처음으로 진짜 서버에 붙은 날이다. 서버에는 카카오·네이버·구글 계정으로 로그인하는 기능을 만들었고, 화면은 가짜 로그인을 걷어내고 서버를 부르는 공통 통로(출입증이 만료되면 알아서 연장해 주는)와 소셜 로그인 화면 두 개를 붙였다. 붙이다 보니 브라우저에는 "CORS 에러"라고 나오는데 실제로는 서버 내부 오류였던 문제가 있어서 원인을 찾아 고쳤다. 같은 이메일로 이미 가입한 사람이 카카오로 들어오면 따로 가입시키지 않고 기존 계정에 자동으로 이어 주도록 정책도 바꿨다. 전에 미뤄 둔 "메일 보내기를 DB 작업 밖으로 빼기"도 이날 처리했고, 서버 테스트는 131개가 됐다.

### 1. 카카오·네이버·구글 소셜 로그인

아이디와 비밀번호 말고 카카오·네이버·구글 계정으로도 들어올 수 있게 했다. 이미 연결된 사람은 바로 로그인되고, 처음 온 사람은 아이디·이름·약관 동의만 받는 짧은 가입 화면을 거친다.

흐름은 이렇다. 화면에서 카카오 버튼을 누르면 위조 방지용 임의 문자열(state)을 만들어 브라우저에 잠깐 저장하고 카카오 동의 화면으로 보낸다. 동의가 끝나면 카카오가 rekit 화면의 콜백 주소로 일회용 코드와 아까 그 문자열을 붙여 돌려보내고, 화면은 문자열이 같은지 확인한 뒤 코드를 서버로 넘긴다. 서버는 그 코드로 카카오에서 출입증을 받아 회원 정보(고유 번호, 이메일, 이름)를 조회하고 rekit 회원과 맞춰 본다. 이미 연결된 회원이면 출입증을 주고 끝이다. 처음 보는 사람이면 "가입 필요"와 함께 15분짜리 임시 가입증, 이메일, 추천 이름을 돌려준다. 화면은 소셜 가입 화면으로 넘어가 아이디·이름·약관을 받고, 서버는 임시 가입증을 확인해 가입시키면서 바로 로그인까지 해 준다.

서버 쪽은 세 회사마다 연결 코드를 하나씩 두고, 회사마다 다른 응답을 "회사, 고유 번호, 이메일, 이름" 한 가지 모양으로 맞췄다. 설정 값이 비어 있는 회사를 누르면 "이 소셜 로그인은 아직 설정 안 됨(503)"으로 답한다. 설정을 채우면 바로 살아나는 일시적인 상태라서 503 으로 했다. 회원 한 명에게 소셜 계정 여러 개를 이어 둘 수 있도록 연결 정보 표를 새로 만들었고, 같은 회사의 같은 고유 번호는 한 번만 들어가게 막았다. 회원이 지워지면 연결 정보도 같이 지워지고, 연결할 때의 이메일을 기록용으로 따로 남긴다. 임시 가입증은 15분짜리이고 한 번 쓰면 사라지는 방식은 아니다. 짧은 기한과 서명이면 충분하다고 봤다.

|          | 카카오                       | 네이버                                         | 구글                           |
| -------- | ------------------------- | ------------------------------------------- | ---------------------------- |
| 회원 고유 번호 | 숫자 id (문자로 저장)            | `response.id`                               | `sub`                        |
| 이메일      | 개발자 콘솔에서 이메일 동의 항목을 켜야 온다 | `response.email`                            | 이메일 확인이 안 된 계정이면 이메일을 버린다    |
| 그 밖에     | 비밀 키는 선택(콘솔에서 끌 수 있음)     | 출입증 교환 때 state 가 꼭 필요, 결과 코드가 "00" 이 아니면 실패 | 요청 범위 `openid email profile` |

정책은 세 가지로 정했다. 이메일을 주지 않으면 가입할 수 없다("이메일 동의 후 다시 시도", 422). 이메일이 rekit 계정과 잇는 열쇠라서다. 소셜로 가입한 사람의 비밀번호 칸에는 아무도 모르는 임의 32자를 암호화해 넣는다. 나중에 아이디·비밀번호로도 들어오고 싶으면 비밀번호 찾기로 임시 비밀번호를 받으면 된다. 위조 방지 문자열 확인은 화면 몫이고, 서버는 네이버 출입증 교환에 필요해서 그대로 넘겨주기만 한다.

{% hint style="info" %}
**처음에는 이메일이 같아도 자동으로 잇지 않았다**

이 시점에는 같은 이메일로 일반 가입한 회원이 있으면 소셜 가입 단계에서 "이메일 중복(409)"으로 거절했다. 남의 계정을 가로채는 걸 막고 약관 동의도 다시 받으려는 이유였다. 이 정책은 두 시간 뒤 4번에서 뒤집힌다.
{% endhint %}

{% hint style="info" %}
**테스트 22개, 그리고 통합 테스트가 막힌 이유**

가짜 소셜 연결로 돌리는 업무 규칙 테스트 11개, 회사별 연결 고르기 7개, 주소·입력 검사 4개를 넣었다. 저장 기록에는 "DB 를 여러 번 부르는 통합 테스트는 비동기 DB 라이브러리와 테스트 도구가 서로 다른 이벤트 루프를 써서 충돌하기 때문에, 업무 규칙 단위로만 확인했다"고 적혀 있다. 5/6 부터 미뤄 온 통합 테스트가 여기서 기술적인 벽에 부딪혔다.
{% endhint %}

{% hint style="warning" %}
**DB 변경 스크립트와 모델의 회사 목록이 다르다**

스크립트에는 회사 목록이 카카오·네이버 둘뿐이고 모델에는 구글까지 셋이다. DB 에는 그냥 문자 칸(20자)으로 만들고 허용 값 제한을 걸지 않아서 동작에는 문제가 없지만, 칸 설명("kakao/naver")과 모델이 어긋나 있다.
{% endhint %}

### 2. 메일 보내기를 응답 뒤로 빼기

5/7 에 만든 아이디 찾기·비밀번호 찾기는 메일을 다 보낼 때까지 DB 연결을 쥐고 기다렸다. Gmail 이 몇백 ms 걸리면 그동안 연결 하나가 묶이니까, 요청이 몰리면 DB 연결이 바닥날 수 있었다. 5/7 에 다음 할 일로 남겨 두었고 코드 정리 도구 검토에서도 지적된 부분이다.

{% hint style="success" %}
**메일이 안 갔는데 계정이 잠기는 사고를 막았다**

예전 순서라면 메일은 실패했는데 비밀번호는 이미 바뀌어서, 사용자는 원래 비밀번호로도 임시 비밀번호로도 들어갈 수 없게 된다. 지금은 메일이 실패하면 DB 를 건드리지 않으니 원래 비밀번호가 그대로 살아 있고 다시 요청하면 된다. 반대로 메일은 갔는데 DB 반영이 실패하면 "메일은 발송됨"이라는 기록을 남긴다.
{% endhint %}

실제로 띄워 보니 비밀번호 찾기 응답이 13ms 로 나왔다. 테스트는 "응답 뒤 작업에 올바른 값으로 올라갔는지"와 "응답 뒤 작업을 직접 돌렸을 때 메일 발송, 실패 시 에러 대신 기록, 메일 실패 시 DB 그대로"를 따로 확인하게 다시 짰다(28개 그대로).

### 3. "CORS 에러"처럼 보이던 서버 내부 오류

{% hint style="danger" %}
**브라우저는 CORS 라고 했지만 실제로는 서버 500 이었다**

개발 중인 화면(localhost:5173)에서 소셜 로그인 콜백을 부르면 브라우저 콘솔에 CORS 에러가 떴다. 따라가 보니 카카오 쪽 호출이 실패하면서 서버에서 처리하지 못한 에러가 났고, 그러면 웹 프레임워크(Starlette)가 맨 바깥에서 날것의 500 응답을 만든다. 이 응답은 CORS 처리 장치 바깥에서 만들어지기 때문에 "이 화면 주소는 허락함" 헤더가 빠진다. 그래서 브라우저는 응답 내용을 보지도 못하고 "CORS 위반"이라고만 알려 줬다. 덤으로 서버 에러 추적 내용(traceback)이 그대로 바깥에 보였다. 두 가지로 고쳤다. 하나는 처리 못 한 에러를 모두 받아서 "서버 오류가 발생했습니다"(500)라는 정해진 모양으로 바꿔 주는 공통 처리기다. 우리 처리기가 응답을 만들면 CORS 장치를 지나가면서 헤더가 제대로 붙고, 에러 추적 내용은 서버 기록에만 남는다. 다른 하나는 소셜 회사 쪽 호출이 실패하면 "소셜 로그인 실패(502)"로 답하게 한 것이다. 502 는 우리 문제가 아니라 바깥 서버 응답이 이상하다는 뜻이다. 흔한 원인은 일회용 코드의 1분 기한이 지났거나, 콘솔에 등록한 돌아올 주소가 다르거나, 같은 코드를 두 번 쓴 경우다. 5173 에서 8000 서버의 콜백을 불렀을 때 502 응답에도 `access-control-allow-origin: http://localhost:5173` 헤더가 붙어 오는 걸 확인했다. 테스트는 3개 늘어 128개.
{% endhint %}

_근거 커밋: `0d47a5a` · 개발자용: `main.py` 의 `@app.exception_handler(Exception)`(`INTERNAL_ERROR`), 소셜 연결의 `httpx.HTTPStatusError`/`RequestError` → `SOCIAL_OAUTH_FAILED`_

### 4. 같은 이메일이면 같은 사람으로, 소셜 계정 자동 연결

1번의 정책대로라면 일반 가입한 사람이 같은 이메일의 카카오로 들어오면 소셜 가입 화면으로 갔다가 "이메일 중복"으로 막혔다. 이미 가입했는데 또 가입하라고 하고, 그마저 막히니 헷갈릴 수밖에 없다. 그래서 오후에 정책을 바꿨다. 서버는 이제 세 단계로 맞춰 본다. 먼저 이 소셜 계정이 이미 연결돼 있으면 바로 로그인시킨다. 아니면 같은 이메일의 기존 회원을 찾아서, 있으면 그 회원에게 소셜 계정을 자동으로 이어 붙이고 바로 로그인시킨다(정지된 계정이면 401). 둘 다 아니면 완전히 새 사람이니 소셜 가입으로 보낸다. 소셜 가입의 "이메일 중복" 검사는 이제 임시 가입증을 받은 뒤 그 15분 사이에 누가 같은 이메일로 먼저 가입한 경우만 막는 용도로 남았다.

{% hint style="warning" %}
**편의와 맞바꾼 보안 (저장 기록과 서버 명세서에 적어 둠)**

카카오와 네이버는 이메일이 정말 그 사람 것인지 확인했다고 분명히 보장하지 않는다(구글만 확인 여부를 알려 준다). 그래서 누군가 남의 이메일로 카카오 계정을 만들면, 그 이메일을 쓰는 rekit 일반 회원 계정에 자동으로 이어져 로그인될 수 있다. 줄이는 방법으로 "운영 때 각 회사 콘솔에서 '이메일 확인 후 동의' 옵션을 켠다"를 적었다. 같은 날 오후 1시 반에는 바로 이 이유로 자동 연결을 막았었다.
{% endhint %}

같이 넣은 것도 있다. 세 회사 연결 코드가 출입증 교환에서 4xx 를 받으면 회사가 준 에러 본문(에러 코드와 설명)을 서버 기록에 남기게 했다. 카카오의 `KOE006`, `KOE010`, `KOE320` 같은 코드를 보고 바로 원인을 짚을 수 있다. 사용자에게는 보여 주지 않는다. 테스트는 3개 늘어 131개.

### 5. "내 정보" 서버 기능

로그인한 사람의 회원 정보를 돌려주는 기능이다. 응답 모양은 로그인 쪽에서 쓰던 것을 그대로 쓰고, 임시 비밀번호 상태인 사람은 막는다(403). 화면을 서버에 붙이다가 빈 곳을 발견했다. 이게 없으니 화면이 로그인한 뒤 회원 정보를 받을 방법이 없어서, 이름 자리에 "카카오 사용자님" 같은 기본값을 띄울 수밖에 없었다.

### 6. 코드 정리 도구(`/simplify`) 검토 반영

코드 정리 도구 의 코드 정리 기능으로 이날 오후 바뀐 코드를 검토받아 세 가지를 고치고 두 가지는 일부러 미뤄다.

고친 것 중 첫째는 업무 규칙 코드가 바깥 통신 라이브러리(httpx)를 직접 불러오던 부분이다. 5/5 에 "업무 규칙은 연결 규격만 쓴다"고 정해 놓고 어긴 셈이라, 통신 에러를 "소셜 로그인 실패"로 바꾸는 일을 소셜 연결 코드 쪽으로 옮겼다. 덕분에 에러 문장에 회사 이름이 들어가게 됐다("kakao OAuth 응답 오류 (400)"). 둘째는 "값이 꼭 있어야 한다"를 파이썬 assert 로 확인하던 곳을 명시적인 에러 던지기로 바꾼 것이다. 최적화 옵션(`python -O`)으로 서버를 돌리면 assert 가 통째로 사라져 운영에서 검사가 없어지기 때문이다. 셋째로 설명문과 겹치는 "1) 2) 3)" 단계 주석을 지우고, 왜 그렇게 했는지(무엇을 맞바꿨는지)만 설명문에 남겼다.

미룬 것은 회원 응답 모양을 회원 폴더로 옮기는 일(로그인 쪽에서도 써서 영향이 커 따로 하기로)과, 통신 클라이언트를 하나 만들어 계속 재사용하는 일(지금 규모에는 과하다고 봄)이다.

실제로 띄워서 잘못된 카카오 코드를 넣어 보니 "kakao OAuth 응답 오류 (400)"와 함께 502 가 오고 CORS 헤더도 제대로 붙었다. 테스트 131개 통과.

{% hint style="info" %}
**`/simplify` 를 처음 쓴 날**

이후 여러 날의 작업에 "/simplify 로 정리"가 반복해서 나온다. 기능을 만들고, 검토받고, 정리해서 다시 저장하는 리듬이 여기서 시작됐다.
{% endhint %}

### 7. 화면을 실제 서버에 연결

화면이 처음으로 진짜 서버를 부르게 됐다. 가장 중요한 건 서버를 부르는 공통 통로다. 모든 요청이 이 통로를 지나는데, 로그인이 필요한 요청에는 출입증을 붙이고, 갱신용 쿠키가 따라가도록 쿠키 포함 옵션을 켠다. 출입증이 만료돼서 401 이 오면 로그인 연장을 한 번 하고 원래 요청을 다시 보낸다. 여러 요청이 동시에 401 을 받아도 연장 요청은 하나만 보내고 다들 그 결과를 같이 기다리며, 다시 보낸 요청이 또 401 이면 더 반복하지 않는다. 연장까지 실패하면 "로그인 만료" 신호를 앱 전체에 보내서 로그인 정보를 정리한다. 서버의 에러 응답은 상태 코드와 에러 코드를 꺼내 화면이 다루기 쉬운 에러 객체로 바꿔 준다.

그 위에 로그인 관련 서버 기능 9개(로그인, 가입, 아이디 중복 확인, 아이디 찾기, 비밀번호 찾기, 연장, 로그아웃, 소셜 콜백, 소셜 가입)와 "내 정보" 부르는 코드를 만들었다. 소셜 로그인 설정에는 세 회사의 앱 번호와 돌아올 주소를 두고, 위조 방지 문자열은 브라우저 탭 저장소(sessionStorage)에 넣었다가 꺼낼 때 지워서 한 번만 쓰게 했다.

새 화면은 두 개다. 소셜 콜백 화면은 회사가 에러를 돌려준 경우를 처리하고, 위조 방지 문자열이 다르면 "보안 검증(state)에 실패"라고 띄운다. 새 사람이면 소셜 가입 화면으로 보내고, 기존 회원이면 로그인 상태를 저장한 뒤 "○○ 로그인 완료"를 보여 주고 0.8초 뒤에 이동한다. 소셜 가입 화면은 아이디, 이름(회사에서 받은 이름으로 미리 채움), 약관 3개(전체 동의 포함)를 받는다.

기존 화면도 바뀌었다. 로그인 정보 보관함은 서버에서 "내 정보"를 받아 덮어쓰는 기능이 생겼고, 로그아웃할 때 서버에도 알리며, "로그인 만료" 신호를 받으면 정리한다. 앱이 켜질 때마다 "내 정보"를 불러서 새로고침해도 회원 정보가 최신으로 맞춰진다. 로그인 화면은 실제로 서버를 부르고, 아이디·비밀번호가 틀리면 "아이디 또는 비밀번호가 올바르지 않아요."라고 띄우며, 소셜 버튼 세 개가 동작한다. 회원가입 화면은 실제 중복 확인과 가입을 하고, 서버가 가입 때 출입증을 주지 않으니 가입에 성공하면 같은 아이디·비밀번호로 곧바로 로그인(로그인 유지 켬)을 해 준다. 아이디 찾기는 화면에 가린 아이디를 보여 주던 가짜에서 "아이디 메일 받기"를 누르면 "메일로 보냈어요"가 뜨는 방식으로, 비밀번호 찾기는 "재설정 링크 받기"에서 "임시 비밀번호 받기"로 바뀌었고 완료 문구는 "로그인 후 비밀번호를 꼭 변경해 주세요"다. 5/2 에 GitHub Pages 용으로 넣었던 화면 경로 앞의 `/rekit_client/` 설정은 지웠다.

{% hint style="warning" %}
**당시 남은 구멍**

* 로그인 응답에 "비밀번호 바꿔야 함"이 켜져 와도 개발자 콘솔에 경고만 찍고 홈으로 보낸다(TODO 주석). 임시 비밀번호로 들어온 사람은 이후 로그인 필요 기능에서 403 을 받게 되는데, 비밀번호 변경 화면도 아직 없다.
* 짧은 출입증을 브라우저 localStorage 에 저장한다. 화면에 악성 코드가 끼어들면 훔쳐 갈 수 있다. 갱신용은 자바스크립트가 못 읽는 쿠키라 안전하다.
* 소셜 신규 가입 때 임시 가입증을 주소 뒤에 붙여 다음 화면으로 넘긴다. 브라우저 방문 기록에 남는데, 15분이면 만료되는 걸로 위험을 줄였다.
* 소셜 로그인 직후에는 이름을 "카카오 사용자"로 임시로 넣어 두었다가 "내 정보"로 덮어쓴다.
{% endhint %}
