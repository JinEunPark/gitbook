### 1. GitHub Pages 자동 게시

아직 서버 없이 가짜 데이터로만 움직이는 화면이라, 파일만 올려 두면 되는 무료 호스팅(GitHub Pages)에 올려서 링크로 화면을 보여 줄 수 있게 했다. 본 줄기에 저장할 때마다 자동으로 빌드해서 올라간다.

주소가 `사용자.github.io/rekit_client/` 처럼 저장소 이름 아래로 잡히기 때문에, 화면 파일 경로 앞에 `/rekit_client/` 가 붙도록 설정했다. 여기서 화면 저장소의 원격 이름이 처음부터 rekit\_client 였다는 걸 알 수 있다(내 컴퓨터 폴더 이름만 `rekle`). 게시가 겹치면 앞의 것을 끊지 않고 차례로 처리한다.

{% hint style="warning" %}
**이런 화면(SPA)과 GitHub Pages 를 같이 쓸 때의 함정**

`/products/p1` 같은 주소에서 새로고침하면 GitHub Pages 는 그 이름의 파일을 찾다가 404 를 낸다. 이날 코드에는 이걸 피하는 장치가 없고, 실제로 겪었는지도 기록이 없다. 나중에 실제 운영은 `rekit.co.kr` 도메인과 자체 서버(nginx), Jenkins 로 옮겨 간다(→ [08.23 일지](../2026-08/2026-08-23.md)).
{% endhint %}

제목·소개글·본문으로 된 공용 틀을 하나 만들고, 그 위에 이용 안내·회사 소개·자주 묻는 질문·공지·문의·이용약관·개인정보처리방침을 얹었다. 없는 주소로 들어오면 "페이지 없음" 화면이 나온다.

#### 당시 문구 — 사업 이야기가 가장 구체적으로 남은 곳

이용 안내의 흐름은 4단계였다. 첫 단계가 "철거 현장 입고"로, "협력 철거 업체에서 가전을 회수해 물류센터로" 가져온다고 썼다. 그다음 전부 검사(전원·기능·외관, 등급 A/B/C), 상품 등록(실측 크기·흠집 사진 공개), 직접 배송(서울·경기) 또는 화물 택배 순이다.

설명 문구는 "신축·리모델링 철거 현장에서는 멀쩡한 가전이 단지 '이사 시점이 다르다'는 이유로 함께 버려져요. rekit 은 그 가전을 직접 회수해서 유통 단계가 없고, 평균 새 제품의 30% 가격으로…"였다. 회사 소개 제목은 "버려질 가전이 다시 누군가의 집으로"이고, 숫자로 `2,400+ 다시 거래된 가전`, `월 2.4t 폐기 줄임`, `평균 73% 절약` 을 넣었다.

{% hint style="warning" %}
**지금 기준으로 바뀐 것들**

* "협력 철거 업체", "철거 현장"은 지금 규칙으로는 "협력 정리 업체", "폐업 매장"이다(→ [05.05 일지](2026-05-05.md)).
* "새 제품의 30% 가격"과 홈의 "평균 73% 할인"은 같은 뜻(73% 할인이면 대략 27% 가격)을 다르게 쓴 것이다.
* `2,400+`, `월 2.4t` 은 출시 전이라 실제 실적이 아니라 자리를 채운 숫자로 보인다.
{% endhint %}

### 3. 상품 목록과 필터

상품 목록 화면에서 카테고리(전체·냉장고·세탁기·TV·에어컨·주방가전·청소기), 상품 등급, "동작 보증만", 검색어로 거를 수 있고 최신순·가격 낮은순/높은순·할인율순으로 정렬할 수 있게 했다. 홈에 있던 상품 카드는 부품으로 떼어내서 홈·목록·상세(관련 상품)에서 같이 쓴다. 다만 "최신순"은 가짜 데이터에 날짜가 없어서 실제로는 정렬이 안 된다.

{% hint style="success" %}
**걸러내는 계산을 따로 떼어 둔 이유**

어떤 상품을 보여 줄지 계산하는 부분을 데이터 보관함과 분리해 두면, 나중에 서버가 걸러서 주도록 바꿀 때 화면은 그대로 두고 데이터 출처만 바꾸면 된다. 실제로 검색은 6/27 에 서버로 옮겼다(→ [06.27 일지](../2026-06/2026-06-27.md)). Spring 으로 치면 검색 조건 조합 로직을 서비스 밖 유틸로 둔 것과 비슷하다.
{% endhint %}

### 4\~8. 구매자 화면 전부 (새 화면 15개)

전날 계획서에 적은 구매자 화면을 한 번에 거의 다 채웠다. 이제 서버 없이 화면만으로 상품을 보고, 장바구니에 담고, 본인 확인을 하고, 주문한 뒤 주문 내역을 확인하는 데까지 끝까지 해 볼 수 있다.

| 묶음   | 화면                              |
| ---- | ------------------------------- |
| 상품   | 상품 상세                           |
| 검색   | 휴대폰 전체 화면 검색, PC 검색창 펼침         |
| 장바구니 | 장바구니                            |
| 주문   | 본인 확인, 주문서, 주문 완료 (진행 단계 표시 포함) |
| 마이   | 주문 목록·상세, 찜 목록, 배송지 관리, 내 정보    |
| 계정   | 아이디 찾기, 비밀번호 찾기                 |

#### 상품 상세

사진 6장 자리에 정면/측면/내부/흠집/뒷면/제품번호 이름표를 달았다. 사진이 아직 없어서 색만 다른 칸이고, 전날 서버 DB 에 넣은 "사진 종류" 6가지와 같다. 등급 설명은 A "거의 새 것", B "눈에 띄는 사용감, 동작은 정상", C "흠집 많음, 부품용 추천"으로 적었다. 그 밖에 사양 표, "홈 › 카테고리 › 상품" 위치 표시, 같은 종류 관련 상품 4개를 넣었고 수량은 재고까지만 고를 수 있다.

#### 검색 — 휴대폰과 PC 를 다르게

휴대폰에서는 돋보기를 누르면 머리·꼬리 없는 검색 전용 전체 화면으로 넘어간다. PC 에서는 머리의 검색창 아래로 최근 검색어, 인기 검색어, 입력 중 미리보기가 펼쳐지고, 엔터를 치면 상품 목록에서 검색 결과를 보여 준다. 최근 검색어는 10개까지 브라우저에 저장하고, 검색 화면과 PC 검색창이 같은 목록을 같이 쓴다. 인기 검색어 8개는 가짜로 넣어 두었고 나중에 서버에서 받을 예정이다.

#### 머리(헤더) 정리

전날 PC 머리에 넣었던 카테고리 메뉴 7개를 뺐다. 그때 남긴 규칙은 "카테고리는 홈 화면 칸, 상품 목록 버튼, 하단 탭에만 두고 머리에는 두지 않는다. 옆 서랍 메뉴는 계정·고객센터 링크만"이다. 장바구니 아이콘에는 담은 개수를 표시했다.

#### 장바구니에서 주문 완료까지

```
장바구니 ─(로그인 안 함)→ 로그인 화면 → 다시 주문으로
   ├─(본인 확인 안 함)→ 본인 확인 → 주문서 → 주문 완료
   └─(본인 확인 함)──────────────→ 주문서 → 주문 완료
```

| 화면    | 하는 일                                                                                                                                                                             |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 장바구니  | 하나씩 고르기(전체 선택·선택 삭제), 수량 조절(재고까지), 고른 것만 합계. 배송비는 일단 직접 배송 4만 원 고정                                                                                                               |
| 본인 확인 | "주문 전에 본인 확인을 해 주세요 — 첫 주문 때 한 번, 다음부터는 생략". 휴대폰 번호를 넣고 인증번호를 요청해 6자리를 입력한다 (가짜라서 누르면 확인된 것으로 저장)                                                                                |
| 주문서   | 들어오는 순간 고른 상품을 고정해 둔다. 주문하는 동안 장바구니를 고쳐도 주문이 바뀌지 않게 하려는 것. 배송지(기본 배송지, 없으면 회원 정보로 채움), 배송 방법(직접 배송 4만·서울/경기·1\~2일 / 화물 택배 6만·2\~4일), 결제 수단(카드·계좌이체·간편결제). 빈칸이 있으면 첫 빈칸으로 커서를 옮긴다 |
| 주문 완료 | 주문번호로 결과 표시                                                                                                                                                                      |

세 화면은 들어올 때 로그인, 장바구니 선택, 본인 확인 순으로 스스로 조건을 검사해서 안 맞으면 앞 단계로 돌려보낸다. 주문 화면은 머리만 있고 꼬리와 하단 탭이 없는 집중 화면으로 만들었다.

{% hint style="info" %}
**전날 요구사항이 화면이 됐다**

"본인 확인은 첫 주문 직전 한 번"이 본인 확인 화면이 됐고, 서버 설계 문서의 "화물 6만 / 직접 배송 4만"이 주문서 선택지로 그대로 들어갔다. 다만 "직접 배송 할인 −2만 원"은 화면에서 빼고 직접 배송비를 4만 원으로 바로 적었다. 서버는 나중에 할인 2만 원을 빼서 계산하게 되는 바람에 10/21 에 화면은 4만, 실제 결제는 2만으로 어긋난다(⑮).
{% endhint %}

#### 마이페이지 하위와 계정 찾기

주문 목록·상세에는 주문번호, 상품, 배송지, 결제, 도착 예정일이 나온다. 배송지는 여러 개를 "집", "회사" 같은 별명과 함께 등록하고 기본 배송지를 고를 수 있다. 찜 목록과 내 정보(본인 확인 상태)도 만들었고, 전날 링크만 있던 아이디·비밀번호 찾기 화면도 채웠다.

#### 브라우저 저장 보관함 4개

| 보관함  | 하는 일                                                                                                                 |
| ---- | -------------------------------------------------------------------------------------------------------------------- |
| 장바구니 | 상품·수량·선택 여부. 같은 상품을 또 담으면 수량이 늘고 다시 선택됨                                                                              |
| 찜    | 상품 번호 목록, 누르면 넣고 빼기                                                                                                  |
| 배송지  | 추가·수정·삭제, 기본 배송지는 항상 1개(첫 주소가 자동으로 기본, 기본을 지우면 첫 번째가 이어받음). 하루 전 "기본 주소 1개"로 저장했던 옛 데이터가 있으면 새 주소록 형식으로 옮기고 옛 것은 지운다 |
| 주문   | 주문번호는 `RK-년월일` 에 임의 4자리. 상태(결제완료/준비중/배송중/배송완료/취소), 도착 예정일 "5월 3일(토) \~ 5월 4일(일)" 형식, 주문할 때 가격·상품명 복사본                |

{% hint style="info" %}
**배운 점 — 브라우저 저장소도 옛 데이터를 옮겨야 한다**

하루 사이에 "기본 주소 1개"에서 "주소록"으로 설계가 바뀌면서, 이미 사용자 브라우저에 남아 있는 옛 형식을 새 형식으로 옮기는 코드가 필요해졌다. 서버 DB 구조를 바꿀 때 변경 스크립트를 쓰는 것과 같은 일이고, "저장 형식을 바꾸면 저장 이름의 버전을 올린다"는 규칙과 짝을 이룬다.
{% endhint %}

{% hint style="warning" %}
**가짜라서 통하는 부분**

본인 확인 화면이 보관함을 거치지 않고 브라우저 저장소에 직접 써 넣는다. 주문번호도 임의 4자리라 겹칠 수 있다. 둘 다 서버와 연결할 때 바꿔야 한다.
{% endhint %}

### 9. 서버 기능 명세서 v1 (50개)

지금 화면은 가짜 데이터로 움직이는데, 서버가 이 주소로 이런 모양의 데이터를 주면 가짜를 전부 걷어낼 수 있다는 걸 정리한 1,314줄짜리 문서다. 이날까지 만든 화면을 기준으로 썼고, 화면·서버 두 저장소에 똑같은 파일을 넣었다. 이후 서버를 만들 때 이 문서가 기준이 됐다.

#### 공통 약속

| 항목    | 정한 것                                                    |
| ----- | ------------------------------------------------------- |
| 서버 주소 | `api.rekit.kr` (가정값 — 실제 도메인은 나중에 산 `rekit.co.kr`)      |
| 시간    | 모두 세계 표준시(UTC)                                          |
| 로그인   | 짧은 출입증 30분(요청마다 헤더로) + 갱신용 출입증 14일(브라우저가 자동 보관하는 쿠키)    |
| 응답 모양 | 성공 `{ data, meta }` / 실패 `{ error: { code, message } }` |
| 목록    | 한 페이지 20개(최대 100)                                       |
| 보안    | https 강제, 요청 횟수 제한(로그인류 1분 10번 / 일반 60번)                |

에러 이름도 11개 미리 정했다. 아이디·비밀번호 틀림, 출입증 만료, 아이디·이메일 중복, 본인 확인 필요, 재고 없음, 가격 바뀜(장바구니에 담은 뒤 주문하기 전에 가격이 바뀐 경우), 결제 실패, 인증번호 틀림, 요청 너무 많음 같은 것들이다.

#### 기능 50개

| 묶음     | 수  | 예                                                                                 |
| ------ | -- | --------------------------------------------------------------------------------- |
| 로그인·가입 | 11 | 아이디 중복 확인, 가입, 로그인·로그아웃, 출입증 갱신, 소셜 로그인(자리만), 아이디 찾기, 비밀번호 재설정, 본인 확인 인증번호 보내기/확인 |
| 내 정보   | 4  | 보기, 고치기, 비밀번호 바꾸기, 탈퇴                                                             |
| 상품     | 5  | 목록, 상세, 관련 상품, 카테고리, 인기 검색어                                                       |
| 찜      | 3  | 목록, 넣기, 빼기                                                                        |
| 장바구니   | 6  | 보기, 담기, 수량, 지우기, 비우기                                                              |
| 배송지    | 5  | 추가·수정·삭제, 기본 설정                                                                   |

| 기타     | 1  | 우편번호 (외부 도구 권장)                                                                   |

결제 쪽은 "카드번호·CVC·인증번호 같은 결제 비밀 정보는 절대 rekit 서버를 거치지 않는다. 결제사 화면이 브라우저와 결제사 사이에서 직접 주고받는다"를 원칙으로 적었다.

**나중에 틀린 걸로 밝혀진 가정 — 결제사 알림의 서명**

{% endhint %}

{% hint style="info" %}
**전날 서버 설계와 다르게 정한 것**

* 찜 주소: 전날은 `favorites` 였는데 화면 쪽 말을 따라 `wishlist` 로 했다.
* 결제 확정: 전날 `confirm` 에서 `verify` 로.
* 본인 확인: 전날은 결제사 본인인증 화면으로 넘어갔다 오는 방식이었는데, 화면에 맞춰 휴대폰 인증번호 2단계로 단순화했다.
* 로그인할 때 쓰는 것: 전날 요구사항은 이메일이었고, 이날은 아이디로 정했다(이메일은 중복만 따로 검사).
{% endhint %}

### 10. 첫 CLAUDE.md

AI 도구(Claude Code)가 이 저장소를 열 때 자동으로 읽는 프로젝트 안내문을 처음 만들었다. 지금 쓰는 안내문의 뼈대가 이날 거의 다 나왔다. 기술 구성, 폴더 구조, 색 값 두 곳 동기화, 주소별 바깥 틀 규칙, 머리·검색 규칙, 브라우저 저장 이름 규칙, 입력칸 중복 규칙, 카드 안 버튼 규칙, 만든 것/안 만든 것 목록, 시안 페이지 사용 금지, 결제·개인정보 저장 금지 원칙까지 들어갔다.

바깥 틀은 이날 디자인 틀, 디자인 목차, 로그인 집중, 검색 집중, 주문 집중(머리만), 일반 이렇게 6가지가 됐다. 상태는 "구매자 화면은 기능상 완성"으로 적었고, 안 만든 것으로는 서버(전부 가짜), 관리자 화면, 판매자 가입·진짜 소셜 로그인·진짜 결제·진짜 인증번호를 꼽았다.

#### 이름 변경이 처음 문서에 나온다

> "rekle 에서 rekit 으로 바꿨다(상표 충돌). rekle 을 다시 쓰지 말 것 — 내 컴퓨터 폴더 이름 `/rekle/` 만 남겨 둠(바꾸면 편집기 상태가 깨져서)."

전날 노트에 남긴 "언제 이름을 바꿨나?"라는 질문의 단서가 여기 있다. 늦어도 5/2 에는 상표 문제로 이름을 바꾼 상태였다. 반면 같은 안내문 첫 줄은 아직 "철거 가전 직거래 플랫폼"이라서, "폐업" 이야기로 바꾸는 건 이보다 뒤인 5/5 다.

### 11. 서버 — DB 칸마다 설명 달기

서버 DB 의 표 9개, 모든 칸에 이 칸이 무엇인지 설명을 달았다. 설명이 DB 자체에 저장되기 때문에 DataGrip 같은 DB 도구에서 바로 보인다. Hibernate 의 `@Comment` 와 같은 역할이다.

주문 표를 예로 들면, 상태는 결제대기 → 결제완료 → 준비중 → 배송중 → 배송완료로 흐르고 중간에 취소/환불로 빠질 수 있으며 "송장을 넣으면 자동으로 배송중"이 된다고 적었다. 주문 금액은 상품 금액 합에 배송비를 더하고 할인을 뺀 값이다. 회원이 탈퇴해도 주문은 지우지 못하게 막았는데, 거래 기록은 5년 보관해야 하는 법적 의무가 있어서다. 직접 배송은 우편번호가 서울/경기일 때만 되고, 배송지 칸에는 "(주문할 때 복사본)"이라고 표시했다.

{% hint style="info" %}
**추정 — 실제 DB 에 반영됐나**

코드에 설명은 달았지만 실제 DB 에 반영하는 변경 스크립트는 이날 없다. 이후 날짜에서 확인할 것.
{% endhint %}
