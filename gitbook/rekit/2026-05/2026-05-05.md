# 05.05 · '철거'에서 '폐업'으로, 무통장입금, 첫 테스트

### 이날을 한 문단으로

방향이 크게 두 번 꺾인 날이다. 먼저 서비스 소개를 "철거 현장에서 나온 가전"에서 "폐업 매장에서 나온 가전(영업용이 많음)"으로 바꿨다. 철거 현장이라는 말이 소비자에게 거부감을 준다는 판단이었고, 화면 곳곳의 문구 13군데를 고친 뒤 다시는 예전 표현을 쓰지 않도록 안내문에 규칙을 박아 두었다. 결제도 카드·간편결제를 빼고 무통장입금 하나로 줄여서, 구매자가 주문번호를 입금자명으로 넣어 돈을 보내면 운영자가 관리자 화면에서 확인해 주는 흐름을 만들었다. 서버 쪽은 아직 기능은 없었지만, 코드를 기능별 폴더로 다시 나누고 외부 서비스(결제사·문자 등)를 갈아 끼울 수 있게 틀을 잡았으며, 테스트를 먼저 쓰는 규칙과 첫 테스트 30개, 7주짜리 서버 개발 계획을 만들었다.

### 1\~3. 서버 코드 다시 나누기

5/1 에 만든 서버 코드는 "DB 모델 폴더, 요청/응답 모양 폴더, 업무 규칙 폴더, 주소 폴더"처럼 역할별로 나뉘어 있었다. 기능이 늘어나면 주문 하나 고치려고 네 폴더를 오가야 해서, 이날 `order/`, `payment/`, `catalog/` 처럼 기능별 폴더로 바꿨다. 배포는 여전히 한 덩어리로 하고, 각 기능 폴더 안에서 "요청 받는 곳 → 업무 규칙 → DB 읽고 쓰기" 순서를 지키게 했다. 결제사·문자·사진 저장소처럼 바깥 회사에 붙는 부분만 인터페이스로 한 겹 감싸서, 테스트 때는 가짜로 바꾸고 회사를 바꿀 때는 구현만 갈아 끼울 수 있게 했다.

{% hint style="info" %}
`controller/ service/ repository/` 로 나누던 패키지를 기능별 패키지로 바꾼 것이다. 외부 연동만 `PaymentGateway` 인터페이스, `TosspaymentsAdapter` 구현체, 설정 클래스로 분리했다. 연결 규격 파일 설명에 실제로 이 비유가 적혀 있다. 안내문에는 이 구조를 "모듈러 모놀리스 + 계층 구조 + 외부 연동만 포트/어댑터"라고 적었다.
{% endhint %}

새 폴더는 이렇게 나뉜다. 공통 설정·로그인 검사·에러·목록 나눠 보기는 `core/`, DB 바탕과 "모든 DB 모델을 한곳에서 불러오는 목록"은 `db/`, 그 밖에 회원가입·로그인(`auth/`), 회원(`user/`), 상품(`catalog/`), 장바구니(`cart/`), 배송지(`address/`), 주문(`order/`), 결제(`payment/`), 사진 저장·업로드(`common/`)가 각자 폴더를 가졌다. 주문 폴더에는 배송 정보도 같이 넣었는데, 안내문에는 "주문과 배송은 한 덩어리로 다룬다"고 적었다. 예전 역할별 폴더 여섯 개는 지웠다.

안내문에 적은 폴더 사이 규칙은 네 가지다. 요청 받는 곳이 DB 를 직접 만지지 않고 반드시 업무 규칙을 거칠 것, 업무 규칙은 바깥 회사의 라이브러리를 직접 부르지 말고 연결 규격으로만 부를 것, 다른 기능의 DB 모델은 직접 불러오지 말고 이름으로만 이어 둘 것, 새 기능 폴더를 만들면 DB 모델 목록에 한 줄 추가할 것.

#### 바깥 서비스 연결 규격

| 규격      | 하는 일                                                                        |
| ------- | --------------------------------------------------------------------------- |
| 결제사     | 결제 시작, 결제 확인(금액이 다르면 에러, 같은 거래번호로 두 번 와도 한 번만 처리), 취소(전액/부분), 결제사 알림의 서명 확인 |
| 문자 인증번호 | 휴대폰으로 번호 보내기, 받은 번호 확인                                                      |
| 본인인증    | 통신사 인증 결과(CI/DI·이름·생년월일·성별) 받기                                              |
| 소셜 로그인  | 카카오·네이버에서 받은 코드를 회원 정보로 바꾸기                                                 |
| 파일 저장소  | 5/1 에 만든 사진 저장 기능을 이 규격 아래로 옮김                                              |

결제 결과(카드사·카드 끝 4자리·할부·승인번호)는 한번 만들면 바꿀 수 없는 객체로 돌려주게 했다.

{% hint style="warning" %}
**결제사 알림 서명은 나중에 틀린 가정으로 밝혀졌다**

결제 규격에 "결제사 알림의 서명 확인"을 넣었는데, 8/30 에 토스페이먼츠 결제 알림에는 서명이 없다는 걸 알게 됐다. 그 뒤로는 알림을 받으면 토스에 다시 조회해서 확인하는 방식으로 바꿨다([08.30 일지](../2026-08/2026-08-30.md)).
{% endhint %}

#### 공통 바탕

로그인 쪽은 비밀번호를 bcrypt 로 암호화해 저장·비교하고, 로그인 출입증(JWT)을 만들고 읽는 부분을 만들었다. 출입증에는 누구인지, 언제 만들었는지, 언제 끝나는지, 짧은 출입증인지 갱신용인지가 들어간다. 기한이 지나면 "만료"로, 위조됐으면 "유효하지 않음"으로 거절하고, 갱신용 출입증을 짧은 출입증 자리에 넣어도 거절한다. 기한은 짧은 출입증 30분, 갱신용 14일, "로그인 유지"를 고르면 30일로 정했다. 출입증 서명 키 설정 이름도 `SECRET_KEY` 에서 `JWT_SECRET` 으로 바꿨다.

목록 나눠 보기는 쪽 번호 방식(1쪽부터, 한 쪽 1\~100개, 기본 10개)과 "여기부터 더 보기" 방식(한 번에 1\~100개, 기본 20개) 두 가지를 준비했다. DB 연결은 요청 하나마다 하나씩 열고 에러가 나면 되돌리게 했다(JPA 의 EntityManager 주입과 비슷하다).

### 4. 테스트 먼저 쓰기 규칙과 첫 테스트 30개

서버용 안내문(CLAUDE.md, 136줄)을 새로 쓰고 "테스트를 먼저 쓰고 구현은 그다음"(TDD)을 모든 새 기능과 버그 수정의 규칙으로 정했다. 정상 상황보다 경계값과 실패 상황을 먼저 테스트하고, 테스트 하나는 동작 하나만 확인한다. 바깥 서비스는 연결 규격이 있으니 테스트 때 가짜 결제사로 바꿔 끼운다. 바뀐 파일의 테스트 범위는 80% 이상을 권장했다. 코드 검사 도구(ruff, mypy)를 쓰고, 주석에는 "왜"만 적기로 했다.

시간은 서버에서 전부 세계 표준시(UTC)로 다루고, 한국 시간으로 보여 주는 건 화면 몫으로 정했다. 환경 설정 값을 하나 추가할 때는 설정 코드, 예시 파일, 실제 설정 파일 세 곳을 같이 고치고, 비밀 값에는 기본값을 두지 않게 했다. 운영 서버에서 설정이 빠졌을 때 조용히 기본값으로 돌지 않고 바로 실패하게 하려는 것이다.

{% hint style="info" %}
**이 규칙들이 이후 몇 달을 버텼다**

"설정 세 곳 같이 고치기"는 8/30 에 토스 결제 키가 서로 안 맞는 사고로 다시 등장한다. 테스트 수는 이후 592개, 11/13 에는 765개까지 늘었다.
{% endhint %}

첫 테스트는 목록 나눠 보기 15개, 로그인 보안 15개다. 목록 쪽은 기본값, 0이나 음수 쪽 번호 거절, 한 쪽 0개나 100개 초과 거절, 숫자가 아닌 값 거절, 전체 쪽 수 계산(나누어떨어질 때, 올림할 때, 0건일 때)을 확인한다. 보안 쪽은 암호화한 값이 원래 비밀번호와 다른지, 같은 비밀번호도 매번 다른 값이 나오는지, 맞는/틀린 비밀번호 판정, 출입증을 만들고 다시 읽으면 같은지, 만든 시각이 UTC 로 들어가는지, 기본 기한이 30분인지, 만료·위조·엉터리 출입증을 거절하는지, 종류가 다른 출입증을 거절하는지를 본다.

{% hint style="success" %}
**출입증 내용을 바깥에서 덮어쓰지 못하게**

출입증을 만들 때 호출하는 쪽이 추가 정보를 넘길 수 있는데, 그 정보를 먼저 넣고 "누구인지·언제 만들었는지·만료 시각·종류"를 나중에 써서 바깥에서 만료 시각이나 종류를 바꿔치기할 수 없게 했다. 테스트 3개가 이 동작을 지킨다.
{% endhint %}

### 6. 서비스 소개 바꾸기: 철거에서 폐업·영업용으로

그동안 rekit 은 "철거 현장에서 나온 멀쩡한 가전"을 판다고 소개해 왔다. 그런데 "철거 현장"이라는 말이 소비자에게 꺼림칙하게 들린다는 판단이 들어서, 사용자에게 보이는 문구를 모두 "폐업 매장(카페·식당·매장)에서 나온 가전"으로 바꿨다. 프론트 안내문에도 이유와 함께 "철거 현장 / 철거 가전 / 협력 철거 업체를 다시 쓰지 말고 폐업 매장 / 폐업 가전 / 협력 정리 업체로 쓸 것, 영업용 가전이 많다는 점은 자연스러운 곳에서 살릴 것"이라는 규칙을 적었다. 사업 설명도 "물건이 주로 폐업 정리 업체를 통해 들어오기 때문에 영업용 제품 비중이 높다"로 다시 썼다.

### 7\~8. 결제를 무통장입금 하나로

주문서에는 카드·계좌이체·간편결제 중에 고르는 칸이 있었지만 실제로 결제가 되는 건 하나도 없었다. 이날 이걸 "계좌이체(무통장입금)" 하나로 줄이고, 구매자가 정해진 회사 계좌로 돈을 보낼 때 입금자명을 주문번호로 쓰게 했다. 운영자는 관리자 주문 화면에서 들어온 돈을 확인하고 "입금 승인"을 누른다. 구매자 입장에서는 주문 직후 입금할 계좌와 금액이 바로 보이고, 보낸 뒤 "입금 완료했어요"를 누르면 운영자 화면 맨 위에 그 주문이 올라간다.

주문 흐름은 이렇게 바뀌었다. 주문서에서 결제 수단 고르는 칸을 지우고 "계좌이체(무통장입금)" 안내 상자 하나만 두었으며, 버튼 글자도 "○○원 결제하기"에서 "○○원 주문하기"로 바꿨다. 주문이 만들어지면 상태가 예전처럼 바로 "결제완료"가 되지 않고 "입금대기"로 시작한다. 완료 화면에는 입금 안내 카드가 나오는데, 은행·계좌번호·예금주·입금 금액과 함께 입금자명으로 쓸 주문번호가 있고 계좌번호와 주문번호는 눌러서 복사할 수 있다(1.6초 동안 "복사됨" 표시). 카드에는 "입금자명이 다르면 자동 매칭이 안 돼요, 꼭 RK-… 그대로 입력해 주세요", "영업일 9\~18시 기준 평균 2시간 안에 확인, 야간·주말은 다음 영업일에 한꺼번에 확인"이라는 안내도 넣었다.

구매자가 완료 화면이나 주문 상세에서 "입금 완료했어요"를 누르면 주문이 "입금대기"에서 "결제확인요청"으로 바뀌고, 운영자가 승인하면 "결제완료"가 된다. 완료 화면 제목도 상태에 따라 "입금 확인 요청 접수됨", "결제가 확인됐어요"로 바뀐다. 주문 상태는 이 두 개가 늘어서 모두 일곱 가지가 됐고, 마이페이지 주문 목록과 상세에도 입금 대기 표시와 입금 안내가 붙었다.

{% hint style="info" %}
**입금자명을 주문번호로 정한 이유**

무통장입금에서 가장 흔한 사고는 누가 보낸 돈인지 모르는 것이다. 입금자명을 주문번호로 정해 두면 통장 내역 한 줄과 주문 하나가 그대로 맞아떨어진다.
{% endhint %}

관리자 주문 화면은 지난번에 화면 안에 적어 둔 가짜 주문 6건을 버리고, 구매자 화면에서 실제로 만든 주문(브라우저에 저장된 것)을 읽게 바꿨다. 상태 탭에 "입금 안내"를 추가하고 탭별 개수도 실제 주문으로 세게 했다. 구매자가 입금했다고 알린 주문은 맨 위로 올리고, 위쪽에 오늘 주문 수와 입금 대기 수, "입금 확인이 필요한 주문이 N건 있어요" 배너를 띄웠다. 주문 줄마다 입금 승인 버튼이 있다. 이제 화면 안에서 구매자 주문부터 운영자 입금 확인까지 한 바퀴를 돌려 볼 수 있다.

{% hint style="info" %}
**계좌 정보는 자리 채움 값**

카드에 적힌 은행·계좌번호·예금주("(주)rekit")는 형식만 맞춘 값으로 보인다. 실제 사업자는 개인사업자 "리키트(REKIT)"다(8/30 꼬리 정보 교체 참고).
{% endhint %}

{% hint style="warning" %}
**서버 명세서와 어긋난다**

서버 명세서의 결제 부분은 여전히 결제사 화면 기준(결제 시작, 확인, 결제사 알림)이다. 입금 확인 요청과 관리자 승인 흐름은 명세서에 들어가지 않았다.
{% endhint %}
