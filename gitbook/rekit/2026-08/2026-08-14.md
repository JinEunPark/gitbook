### 1. 나이스페이 계획을 접고 토스페이먼츠 유지

7/10 에 가입비와 연회비 조건을 비교하다가 결제대행사를 나이스페이로 바꾸기로 하고, 테스트부터 짜는 방식(TDD)으로 단계를 0\~12 까지 나눈 계획서를 860줄 써 뒀었다([07.10 일지](../2026-07/2026-07-10.md)). 두 회사의 큰 차이는 결제 인증이 끝난 뒤의 흐름이다. 나이스페이는 결제창이 우리 서버 주소로 결과를 바로 보내 주고, 토스는 화면이 결과 페이지로 돌아온 뒤 서버가 토스에 승인을 요청한다. 이날 그 계획서를 지우면서 토스페이먼츠를 그대로 쓰기로 했다. 나이스페이 쪽은 계획서만 있었고 실제 코드는 들어간 적이 없다.

결제 방식은 몇 달 동안 계속 바뀌어 왔고, 여기서 정리됐다. 5/1 에는 토스를 추천했고, 5/5 에 무통장입금만 받기로 했다가, 6/20 서버에 토스 카드 결제 흐름을 만들었다. 7/2 에 PortOne v2 로 "결정 완료"라고 적었는데 7/4 에 다시 무통장으로 갔고, 7/10 나이스페이 계획을 거쳐 8/14 에 토스로 돌아왔다. 화면에 토스 결제위젯을 붙인 건 9/3 이다([09.03 일지](../2026-09/2026-09-03.md)).

{% hint style="info" %}
**추정 — 토스로 돌아온 이유**

남은 기록에는 결정만 있고 이유는 없다. 다만 7/6 과 7/10 에 두 번 한 동시 결제 점검이 전부 토스 코드를 기준으로 끝나 있었고, 나이스페이로 가면 그 점검에서 고친 부분을 다시 써야 한다고 계획서 스스로 적어 두었다. 이미 다져 둔 토스 코드를 버리는 비용이 가입비·연회비 차이보다 크다고 본 것 같다.
{% endhint %}

{% hint style="warning" %}
**실은 계획서만 있던 게 아니었다**

같은 날 할 일 목록에 이런 기록이 있다. 작업 도중 다른 Claude Code 세션이 같은 파일(결제대행사 연결 틀 `app/payment/adapters/ports.py`)을 동시에 건드려, 나이스페이 전환 준비로 클래스 이름만 바꾸고 나머지 파일은 그대로 둔 채 남겨 둔 적이 있었다. 그 상태로는 서버가 아예 안 떠서(불러오기 오류) 원래대로 되돌렸다고 한다. 저장 기록에는 안 남았지만 작업 중인 파일에서는 나이스페이 전환이 실제로 시작됐었다는 뜻이다. 이 일이 철회를 결정한 계기였을 수도 있다(추정).
{% endhint %}

**8/13 저장 전에 실제 키로 붙여 봤다는 근거**

5번에 나오는 "실제 키로 붙여 봐야 드러나는" 버그 두 개는 8/13 에 저장된 코드에 이미 고쳐져 있고 테스트도 있다(201 도 성공으로 받기, 성공하면 코드 지우기). 그러니 8/13 저장 전에 실제 Octomo API 를 적어도 QR 발급과 수신 확인까지는 불러 봤다고 볼 수 있다. 다만 휴대폰으로 QR 을 찍고 문자를 보내 인증까지 가는 전체 확인은 여전히 체크되지 않아서, 거기까지 했는지는 기록이 없다. [08.13 일지](2026-08-13.md) 에 "실기기 검증 기록 없음"이라고 쓴 부분을 이걸로 조금 보완한다.
