### 1. 웹훅 검증 재작성 — Task 1·2 (백엔드, 미커밋)

#### 배경 — 어제 드러난 사실

{% hint style="warning" %}
**토스 결제 웹훅에는 HMAC 서명이 없다**

`tosspayments-webhook-signature` 헤더는 **지급대행(`payout.changed`/`seller.changed`) 이벤트 전용**. `PAYMENT_STATUS_CHANGED` 등 결제 웹훅엔 서명 없음. 기존 코드의 `verify_webhook_signature`(HMAC-SHA256) + 라우터의 `TossPayments-Signature` 헤더 읽기 = **존재하지 않는 스펙**.
{% endhint %}

토스 공식 권장 위변조 방지 = **웹훅 body 를 믿지 말고, `paymentKey` 로 결제 조회 API 를 호출해 실제 상태를 재확인**한 뒤 그 결과로만 전이.

#### 웹훅 status 처리 (조회 결과 8종)

| `remote.status`                             | 처리                                                                        |
| ------------------------------------------- | ------------------------------------------------------------------------- |
| `DONE`                                      | Payment→PAID (+ 웹훅이 confirm 보다 먼저면 카드 메타도 채움), Order PENDING→PAID         |
| `CANCELED`                                  | Payment→CANCELLED + 재고 복구 + 주문 취소                                         |
| `PARTIAL_CANCELED`                          | Payment→`PARTIAL_CANCELLED` (재고 정책 미정, 스킵) — 기존엔 `CANCELLED` 로 잘못 넣던 것 정정 |
| `ABORTED` / **`EXPIRED`(신규)**               | Payment→FAILED, `fail_reason="토스 결제 상태: {status}"` + 재고 복구 + 주문 취소        |
| `READY`/`IN_PROGRESS`/`WAITING_FOR_DEPOSIT` | 무시 (확정 전, 로그만)                                                            |

> 어제 노트에 "`ABORTED` 는 없는 값"이라 적었는데 **정정**: 결제 조회(`GET /v1/payments`) 응답의 `Payment.status` 는 8종 전부 존재(`ABORTED` 포함). `PAYMENT_STATUS_CHANGED` 웹훅 body 의 status 목록이 좁게 문서화돼 있던 것. 어차피 body 안 믿고 조회하므로 8종 다 처리.

토스 웹훅 발신 IP 화이트리스트 미들웨어는 아직 없음. 현재는 "조회 재확인"만으로 방어 — 위조 body 로는 상태 변경 불가하나, 유효 `paymentKey` 를 아는 공격자가 우리→토스 조회 호출을 유발할 수는 있음(토스 재시도 정책상 rate 제한적).

#### B. 화면 첫 파일은 저장해 두지 않게 (21:27)

8/23 에 화면 컨테이너의 nginx 는 빌드된 파일(`/assets/`)만 1년 저장하라고 알려 주고, 화면의 첫 파일(`index.html`)에는 아무 지시도 없었다. 그러자 브라우저가 "마지막으로 바뀐 시각"을 보고 알아서 짐작해 첫 파일을 한동안 재사용했고, 배포 직후에도 옛 첫 파일이 옛 빌드 파일들을 불러왔다. 그래서 첫 파일(그리고 favicon·robots·sitemap 같은 파일)에는 "쓸 때마다 서버에 바뀌었는지 물어볼 것(no-cache)"을 붙였다. 안 바뀌었으면 서버가 짧게 "그대로"라고만 답하니 부담은 작다. Spring Boot 로 치면 정적 파일 캐시 설정을 HTML 은 no-cache, 이름에 해시가 붙은 파일은 오래 저장으로 나눈 것이다.

_근거 커밋: `e52f221` · 개발자용: 프론트 `nginx.conf` 의 `location /`_

#### C·D. 프리렌더가 화면 잠금까지 찍어 버린 버그 (21:38, 21:50)

홈에 처음 들어오면 뜨는 안내 창(`HomePromiseModal`)은 열려 있는 동안 뒤 페이지가 스크롤되지 않게 페이지 전체에 잠금 스타일을 건다. 8/30 에 넣은 프리렌더는 빌드 때 보이지 않는 브라우저로 홈을 열어 그 순간의 HTML 을 저장하는데, 하필 안내 창이 페이지를 잠근 순간이 그대로 저장됐다. 문제는 이 홈 HTML 이 다른 모든 주소의 시작 파일로도 쓰인다는 점이다. 상품 상세, 장바구니, 마이페이지, 관리자처럼 따로 프리렌더하지 않는 주소는 전부 이 파일로 시작하는데, 화면 코드(Vue)는 이 잠금 스타일을 관리하지 않으니 그대로 남았다. 그래서 운영의 그 페이지들은 스크롤이 완전히 막혔다. 내 컴퓨터의 개발 서버는 프리렌더를 거치지 않아서 정상이었다.

먼저 21:38 에 프리렌더가 HTML 을 저장하기 직전에 열려 있는 창을 지우고 페이지 잠금 스타일을 풀게 했다. 검색엔진용 HTML 에 안내 창이 박히지 않는다는 덤도 생겼다. 12분 뒤에는 원인부터 막았다. 프리렌더할 때만 브라우저에 "지금은 프리렌더 중"이라는 표시를 남기고, 안내 창은 그 표시가 있으면 아예 열리지 않게 했다. 실제 사용자 브라우저에는 그 표시가 없으니 안내 창은 평소대로 뜬다. 그리고 저장한 HTML 마다 페이지 맨 바깥에 스크롤 잠금 스타일이 남아 있는지 검사해서, 남아 있으면 오류를 내고 빌드를 실패시키게 했다. 앞으로 어떤 이유로든 잠금이 찍히면 배포 전에 걸린다. 처음 넣은 정리도 그대로 남겨서 세 겹으로 막은 셈이다.

{% hint style="info" %}
**프리렌더는 그 순간의 화면을 통째로 찍는다**

프리렌더가 저장하는 건 화면이 뜬 직후의 상태 전부다. 열린 창, 페이지에 걸린 스타일, 시간이 지나면 뜨는 배너까지 같이 찍힌다. 게다가 홈 HTML 은 모든 주소의 시작점이라 거기 찍힌 상태는 사이트 전체로 번진다. 잠깐 뜨는 화면 요소는 프리렌더 중에는 띄우지 않고, 저장한 HTML 을 검사해 이상하면 빌드를 막는 것까지 두 겹이 필요했다. 11/15 에 고친 "프리렌더 중 서버 요청이 실패해 그 오류 화면이 저장되던 문제"도 같은 종류다.
{% endhint %}

#### E. Octomo 인증과 프록시 문제 (22:50, 서버)

8/13 에 만든 Octomo 휴대폰 인증([08.13 일지](2026-08-13.md))에서 운영 중 드러난 문제 두 개와, 8/23 배포 구조에서 생긴 주소 문제 하나를 같이 고쳤다.

첫째, QR 발급이 한 번 실패하면(Octomo 쪽 서버 오류 등) 그 뒤 1분 동안 다시 시도해도 계속 "너무 자주 요청함"으로 거절됐다. 서버가 "60초에 한 번" 잠금을 먼저 걸고 QR 을 발급하는데, 발급이 실패해도 잠금은 그대로 남았기 때문이다. 발급이 실패하면 잠금을 풀고 오류를 돌려주게 바꿨다. 코드 설명에 "잠금은 QR 을 제대로 발급했다는 뜻이어야 한다"고 적었다.

둘째, QR 을 받고 5분이 거의 다 됐을 때(4분 59초쯤) 문자를 보내고 확인을 누르면 실패했다. 우리 서버가 코드를 5분 동안 보관하고, Octomo 도 "최근 5분 안에 온 문자"를 보는데, 두 5분의 기준 시각이 다르다. 우리 쪽은 QR 을 발급한 때부터, Octomo 쪽은 확인을 요청한 때부터 거꾸로 센다. 그래서 경계에서는 우리 코드가 먼저 사라져 Octomo 에 물어보지도 못했다. 8/13 에는 두 값을 일부러 같게 맞췄던 것인데("5분, Octomo 와 일치시킴") 그게 오히려 문제였다. 보관 시간을 10분으로 늘리고 "시간이 지났는지는 Octomo 가 판단하고, 우리 쪽 보관은 재사용을 막는 용도일 뿐"이라고 적었다. 화면의 5분 카운트다운은 그대로라 사용자가 느끼는 건 같다.

셋째, https 로 접속했는데 서버가 다른 주소로 넘겨 보낼 때(주소 끝 `/` 맞추기 등) 넘겨 주는 주소가 `http://` 로 내려갔다. 바깥 nginx 는 Docker 네트워크 안의 주소로 서버에 요청을 넘기는데, 서버 프로그램(gunicorn)은 기본적으로 서버 안 주소(`127.0.0.1`)에서 온 "원래는 https 였음" 표시만 믿는다. 그래서 그 표시를 무시하고 http 로 판단했다. 운영 설정에서 이 표시를 어느 주소에서 오든 믿게(`FORWARDED_ALLOW_IPS="*"`) 했다. 설정 설명은 "서버 포트는 서버 안에서만 열려 있고 nginx 만 닿으니 열어도 안전"이다. Spring Boot 로 치면 프록시 헤더 처리를 켜고 믿을 프록시 범위를 열어 준 것이다.

테스트는 두 개 늘었다. 코드 보관 시간이 Octomo 확인 범위보다 긴지, QR 발급이 실패하면 잠금이 풀리는지를 본다.

{% hint style="warning" %}
**"nginx 만 닿는다"는 전제**

안전하다는 근거는 nginx 만 서버에 닿는다는 것인데, 서버 컨테이너는 nginx 와 같은 공유 네트워크에도 붙어 있어서 같은 네트워크의 다른 컨테이너(예: 화면 컨테이너)도 서버 포트에 바로 닿을 수 있다. 지금 구성에서는 실제 위험이 없지만, 그 네트워크에 다른 서비스를 붙일 때는 누군가 "원래는 https 였음" 같은 표시를 꾸며 보낼 수 있다는 점을 생각해야 한다.
{% endhint %}
