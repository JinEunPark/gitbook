### 1. 소셜 로그인 앱 번호를 화면 빌드 때 넣기

화면 도구(Vite)는 `VITE_` 로 시작하는 설정 값을 빌드할 때 화면 파일 안에 박아 넣는다. 8/23 의 Docker 빌드는 서버 주소 하나만 넣었기 때문에, 운영 화면에는 카카오·네이버·구글 앱 번호(client id)가 비어 있었고 소셜 로그인 버튼이 운영에서 동작하지 않았다. 8/26 할 일로 적은 "네이버 개발자센터에 운영 주소 등록"과 짝이 되는 작업이다. 콘솔 등록과 화면에 값 넣기가 둘 다 있어야 소셜 로그인이 된다.

빌드 설정에 세 회사의 앱 번호와 돌아올 주소, 모두 6개 값을 받을 자리를 만들었다. Jenkins 빌드 작업은 서버의 정해진 폴더에 있는 화면용 설정 파일을 읽어 그 값을 빌드에 넘긴다. 파일이 없으면 경고만 남기고 빈 값으로 빌드해서, 소셜 로그인만 꺼진 채로 나머지는 정상으로 뜬다. 코드 주석에도 적었듯 앱 번호와 돌아올 주소는 브라우저에 그대로 보이는 공개 값이라 비밀은 아니지만, 저장소에 넣지 않고 서버와 같은 방식으로 설정 파일에 두기로 통일했다. 주석을 보면 Jenkins 도 컨테이너로 돌고, 그 컨테이너에 설정 폴더를 읽기 전용으로 붙여 두었다. 빌드가 끝나고 띄우는 안내 문구의 배포 작업 이름이 실제 이름과 달라서 그것도 고쳤다.

Spring 으로 치면 빌드할 때 운영 프로퍼티를 구워 넣는 것과 비슷한데, 화면은 브라우저에서 도는 앱이라 실행 중에 값을 바꿀 수 없고 값을 바꾸려면 다시 빌드해야 한다.

{% hint style="info" %}
**Jenkins 명령의 따옴표를 바꾼 이유**

Jenkins 설정 언어(Groovy)에서 큰따옴표 세 개로 감싼 명령은 `${값}` 을 Jenkins 가 먼저 바꿔 넣는다. 그러면 명령 안에서 설정 파일을 읽어 만든 값이 보이지 않는다. 그래서 작은따옴표 세 개로 바꿔 명령이 직접 값을 해석하게 했고, 기존에 쓰던 이미지 보관소 주소 같은 값도 같은 방식으로 함께 바꿨다.
{% endhint %}

### 2. 소셜 가입 간소화

5/10 에 만든 소셜 가입은 카카오 등으로 로그인한 뒤 15분짜리 임시 통행증을 들고 가입 화면으로 가서 아이디·이름·약관을 입력하는 방식이었다([05.10 일지](../2026-05/2026-05-10.md)). 저장 기록에 남은 이유는, 소셜 로그인 직후 아이디와 이름을 또 입력받는 게 흔한 소셜 간편가입과 맞지 않고, 카카오 "이름" 동의항목 심사가 반려된 원인이기도 했다는 것이다. 그래서 가입 화면에서 아이디와 이름 칸을 없애고 약관 동의만 받게 했다. 이제 구매자는 소셜 로그인 후 약관에 동의하면 바로 가입이 끝난다.

{% hint style="info" %}
**추정 — 카카오가 반려한 이유**

기록에는 "이름 동의항목 심사 반려"만 있다. 가입 화면에서 이름을 따로 다시 입력받으니 동의항목으로 이름을 받을 필요가 없다는 취지였을 수도 있고, 그 반대였을 수도 있다. 어느 쪽이든 결과는 소셜 회사가 준 닉네임만 쓰는 쪽으로 정리됐다.
{% endhint %}

서버는 가입 요청에서 아이디와 이름 항목을 빼고 임시 통행증과 약관 동의만 받는다. 이름은 임시 통행증에 원래 들어 있던 소셜 닉네임을 쓰고, 없으면 "새싹회원"으로 넣는다. 아이디는 `social_` 뒤에 무작위 12자를 붙여 자동으로 만들고, 이미 있는 아이디와 겹치면 최대 5번까지 다시 만든다(5번 연속 겹치는 건 확률상 일어날 수 없다고 봤다). 모두 19자라 기존 아이디 규칙(4\~20자)에도 맞는다. 코드 설명에 "소셜 전용 계정은 늘 소셜 버튼으로만 들어와서 이 값을 사람이 칠 일이 없다"고 적었다. 이 아이디는 화면에 보이지 않고, DB 의 "아이디 중복 금지" 제약을 채우는 용도로만 있다. 이름 중복으로 가입을 거절하던 오류도 없어졌고, 남은 중복 오류는 이메일뿐이다.

화면에서는 소셜 가입 화면의 아이디·이름 입력칸과 그 검사를 지웠다(약 110줄 감소). 가입 버튼은 임시 통행증이 있고 필수 약관에 동의하면 눌린다. 안내 문구도 "사용할 아이디만 정해주시면 됩니다"에서 "약관에 동의하면 바로 가입이 완료돼요"로 바꿨다. 가입 직후에는 화면 쪽 로그인 정보에 임시 값을 넣어 두고, 곧바로 내 정보를 다시 불러와 정확한 값으로 채운다.

서버는 11:20 에, 화면은 14:49 에 저장됐다. 그 사이 옛 화면이 아이디와 이름을 더 보내도 서버가 모르는 항목은 무시하게 돼 있어서 가입 자체는 됐다. 다만 사용자가 정한 아이디는 버려지고 자동 아이디가 들어갔다.

{% hint style="info" %}
**8/27 과 이어 보면**

이제 소셜 가입자는 아이디가 자동으로 만들어지고, 비밀번호 없음으로 기록되고, 이름은 소셜 닉네임이다. 소셜 계정은 소셜 버튼으로만 들어오는 계정으로 완전히 나뉘 셈이다. 비밀번호 찾기로 임시 비밀번호를 받으면 비밀번호 있음이 되지만, 아이디로 로그인할 때 쓸 자동 아이디(`social_…`)는 아이디 찾기 메일로만 알 수 있다.
{% endhint %}

### 3. 예전 전화번호 형식 고치기

8/13 에 전화번호 저장 형식을 `010-0000-0000` 으로 바꾸면서 이미 저장된 값은 그대로 뒀었다([08.13 일지](2026-08-13.md)). 8/14 할 일 목록에도 우선순위 낮음으로 적어 두었다. 이날 그걸 고치는 DB 변경 스크립트를 저장했다. 스크립트 작성 시각은 8/18 이라, 만들어 두고 열흘 뒤에 올린 것이다.

DB 구조는 그대로 두고 값만 고친다. 대상은 회원 전화번호, 배송지 전화번호, 주문의 받는 사람 전화번호 세 곳이다. 8/13 에 만든 전화번호 규칙을 그대로 DB 명령으로 옮겨서, 하이픈 없이 숫자만 있는 휴대폰 번호만 골라 11자리는 3-4-4, 10자리는 3-3-4 로 끊는다. 이미 하이픈이 있는 값이나 비어 있는 값은 애초에 고르지 않으니 몇 번을 돌려도 결과가 같다(멱등). 되돌리면 하이픈을 다시 지운다. 할 일 목록에는 "개발용 DB 에 적용해 회원 3건, 배송지 7건, 주문 12건이 바뀐 것 확인, 되돌리기 왕복 확인"이라고 적었고, 운영에는 8/23 구조대로 다음 배포 때 서버가 켜지면서 자동으로 적용된다. Flyway 로 치면 엔티티는 안 건드리고 기존 행만 고치는 데이터 전용 스크립트다.

{% hint style="danger" %}
**전날 끊겼던 DB 변경 순서가 다시 이어짐**

### 4. Claude Code 권한 허용 목록 저장

8/14 할 일 1번의 후속이다. 예전 세션에서 Octomo 를 시험하려고 실행한 명령이 Claude Code 권한 허용 목록에 그대로 기록되면서 실제로 쓰던 Octomo API 키가 그대로 노출됐었는데, 그 항목을 지우고 허용 목록을 저장소에 올렸다. 실제로 바뀐 내용을 보면 지워진 건 마지막 항목의 쉼표 하나뿐이다. 키가 들어 있던 줄은 내 컴퓨터에만 있었고 저장하기 전에 지운 것이다. 저장소 기록에서 키 값을 찾아봐도 전체 키가 올라간 적은 없다(8/14 할 일 목록에 적힌 앞 8자리는 빼고).

새로 들어간 허용 항목들에는 7\~8월 작업 흔적이 남아 있다. Octomo 웹사이트 조회와 Octomo 예제 저장소 조회, 화면 쪽 타입 검사와 코드 검사(8/13 계획서의 "정적 검증"), DB 변경 순서 확인, 최신 코드 받아 오기와 재정렬(8/14 "세션끼리 부딪치지 않게" 이후)이 있다. 그리고 추가 작업 폴더로 화면 저장소의 부품 폴더와 서버 호출 폴더가 등록돼 있는데, 이건 서버 쪽 세션에서 화면 파일을 직접 고쳤다는 뜻이다. 7/12 의 Octomo 화면이 서버 세션에서 만들어졌다는 근거가 된다.
