### 0. 배포 구조

설정 파일들을 모아 보면 구조는 이렇다. 인터넷에서 `rekit.co.kr` 로 들어오면 서버에 따로 떠 있는 nginx 가 받아서 주소에 따라 나눠 보낸다. 그냥 페이지 요청은 화면 컨테이너로, `/api/` 로 시작하는 요청은 서버 컨테이너로, `/s3/` 로 시작하는 요청은 사진 저장소(SeaweedFS)로 넘긴다. nginx 와 SeaweedFS 는 이 두 저장소 밖에서 따로 세팅돼 있던 것을 그대로 썼다.

```
인터넷 ─ rekit.co.kr ─ nginx (서버에 원래 있던 것)
                         ├─ 일반 페이지  → 화면 컨테이너 (rekle-web)
                         ├─ /api/…      → 서버 컨테이너 (rekle-app, 프로세스 4개)
                         └─ /s3/…       → 사진 저장소 (원래 있던 SeaweedFS)
서버 컨테이너 옆에 DB(PostgreSQL)와 Redis 를 같이 띄움

Jenkins (같은 서버) → 이미지 빌드 → 같은 서버 안의 이미지 보관소 → 내려받아 실행
```

### 1. 서버 첫 자동 배포 설정

Jenkins 작업은 "빌드하고 보관소에 올리기"와 "배포" 두 단계로 시작했다. 배포 단계는 비밀 설정을 복사하고, 새 이미지를 내려받고, DB·Redis·서버를 띄운 뒤 안 쓰는 옛 이미지를 지운다. 운영용 실행 설정에서는 PostgreSQL 15 와 Redis 7 을 띄우고 둘 다 준비가 끝난 걸 확인한 뒤에 서버를 켜게 했다. 운영 모드로 켜고 디버그는 껐다. 서버 포트는 같은 서버 안에서만 열어 두고(`127.0.0.1:8000`) 바깥에는 nginx 를 거쳐서만 닿게 했다. 개발용 설정(5/1)은 SeaweedFS 까지 직접 띄웠지만 운영에서는 이미 떠 있는 SeaweedFS 의 네트워크에 붙기만 한다.

### 2. 빈 DB 에서 DB 변경 스크립트가 실패

운영 DB 를 처음 만들려고 DB 변경 스크립트를 처음부터 차례로 적용했더니, 중간의 "번호 자동 증가 방식 바꾸기" 스크립트에서 "이 칸은 이미 새 방식이다"라는 오류로 멈췄다. 첫 배포 설정을 올리고 36분 뒤에 고쳤다.

원인은 5/1 에 있었다. 그날 개발용 DB 는 옛 방식(SERIAL)으로 만들어졌는데 코드는 새 방식(IDENTITY)으로 적혀 있어서, 옛 방식을 새 방식으로 바꾸는 스크립트를 따로 만들었다([05.01 일지](../2026-05/2026-05-01.md)). 그런데 그보다 앞에 있는 "처음 표 만들기" 스크립트는 코드를 기준으로 만들어져서 처음부터 새 방식으로 표를 만든다. 그러니 빈 DB 에 처음부터 쭉 적용하면 이미 새 방식인 칸을 또 바꾸려다 실패한다. 개발용 DB 는 5/1 이후 늘 이미 적용된 상태였기 때문에 석 달 넘게 안 드러났고, 운영 DB 를 처음 만들 때 터진 것이다.

고친 방법은 칸마다 지금 방식을 먼저 확인하고 옛 방식일 때만 바꾸는 것이다. 되돌리는 스크립트도 마찬가지로 새 방식일 때만 되돌린다. Flyway 로 치면 "이미 IDENTITY 면 건너뛰기"를 넣어 몇 번을 돌려도 결과가 같게(멱등하게) 만든 것이다.

{% hint style="success" %}
**DB 변경 스크립트는 빈 DB 에서 끝까지 한 번은 돌려 본다**

기존 개발용 DB 에 새 스크립트만 덧붙여 적용하면 앞쪽 스크립트는 다시 실행되지 않아서 이런 오류가 숨는다. 7/6 부터 있는 실제 DB 테스트도 DB 를 새로 만들지 않고 이미 적용된 내 컴퓨터 DB 에 그대로 붙어서 돌기 때문에 이걸 못 잡았다. 자동 검사에서 빈 PostgreSQL 에 처음부터 끝까지 적용해 보면 잡힌다.
{% endhint %}

{% hint style="warning" %}
**8/13 가짜 데이터 버그와 같은 조건**

[08.13 일지](2026-08-13.md) 에 적은 가짜 데이터 스크립트 버그(지운 칸에 값을 넣으려는 것)도 빈 DB 에서만 터지는 종류다. 운영 DB 에 가짜 데이터를 넣었다면 이날 같이 만났을 텐데 관련 수정이 없다. 운영에는 가짜 데이터를 안 넣은 것 같다(추정).
{% endhint %}

### 3. 빌드와 배포를 나눔

3분 뒤 Jenkins 작업을 둘로 쪼갰다. 빌드 작업은 이미지를 만들어 보관소에 올리기만 하고, 끝나면 배포는 배포 작업에서 버전 번호를 넣어 직접 실행하라고 안내한다. 배포 작업은 어떤 버전을 띄울지 입력받는데, 비워 두면 최신(`latest`)이고 문제가 생기면 이전 버전 번호를 넣어 되돌릴 수 있다. 빌드는 됐어도 배포는 내가 누를 때만 되고, 특정 버전으로 되돌리기도 쉬워졌다. 두 작업 모두 손으로 실행하는 방식이고, 코드를 올리면 자동으로 배포되는 단계는 아직 없다.

### 5. 화면도 Docker 로

화면도 서버와 같은 방식으로 이미지로 묶어 Jenkins 로 빌드·배포하게 했다. Node 로 화면을 빌드한 뒤 결과물만 작은 nginx 이미지에 담는 2단계 구성이다. 빌드할 때 서버 주소를 `/api/v1` 이라는 상대 주소로 넣어서, 어느 도메인이나 IP 로 접속하든 같은 주소 아래의 서버를 부르게 된다. 코드 주석에도 "CORS 회피"라고 적었다. 그래서 화면 쪽은 배포할 때 비밀 설정을 복사하는 단계가 없다.

화면 컨테이너 안의 nginx 에는 두 가지를 넣었다. 하나는 `/my/orders` 같은 주소에서 새로고침해도 404 가 나지 않게 모든 주소를 화면 첫 파일로 돌려보내는 설정이고, 다른 하나는 빌드된 파일(`/assets/`)을 브라우저가 1년 동안 저장해 두게 하는 설정이다. 빌드할 때마다 파일 이름이 바뀌니 오래 저장해도 옛 파일이 남을 걱정은 없다. 화면 컨테이너는 바깥에 포트를 열지 않고 nginx 네트워크로만 닿는다. 5/2 에 만든 GitHub Pages 자동 배포는 아직 남아 있었고 9/4 에 지웠다.

### 6. 사진 업로드가 늘 실패

화면 배포 두 시간 뒤에, 관리자가 상품 사진을 올리면 항상 실패하는 문제를 고쳤다. 7/3 에 만든 업로드는 서버가 "10분짜리 업로드 주소(presigned URL)"를 만들어 주면 브라우저가 그 주소로 사진 저장소에 직접 올리는 방식이다([07.03 일지](../2026-07/2026-07-03.md)). 그런데 운영 설정에 사진 저장소 주소를 Docker 내부에서만 통하는 이름(`seaweedfs:8333`)으로 박아 두는 바람에, 업로드 주소도 그 이름으로 만들어졌다. 브라우저는 그 이름을 모르니 매번 실패했다. 주소의 앞부분만 바꿔 끼울 수도 없는 게, 업로드 주소에 붙는 서명에 주소의 호스트 이름까지 들어가 있어서 바꾸면 서명이 깨진다.

게다가 운영 설정 파일에 직접 적은 값이 비밀 설정(.env)보다 우선이라, .env 에 공개 주소를 넣어 둬도 무시됐다. 그래서 운영 설정에서 그 줄을 지웠다. 이제 .env 의 공개 주소(nginx 가 `/s3/` 로 사진 저장소에 넘겨 주는 `rekit.co.kr`)로 업로드 주소가 만들어진다. nginx 의 `/s3/` 설정은 이 저장소 밖에서 따로 했다.

{% hint style="info" %}
**업로드 주소는 그 주소를 여는 쪽 기준으로 만든다**

서버가 사진 저장소와 이야기할 때 쓰는 주소와 브라우저가 쓸 주소가 다르면, 업로드 주소는 브라우저 쪽 주소로 만들어야 한다. 대신 이렇게 고친 뒤로는 서버가 사진 저장소를 부르는 다른 경우(업로드가 끝났는지 확인하기 등)도 공개 주소로 nginx 를 거쳐 나간다. 동작은 하지만 내부 통신이 바깥을 한 바퀴 돌아오는 셈이다. 11/13 의 사진 저장소 관련 작업도 이 구조 위에서 했다.
{% endhint %}
