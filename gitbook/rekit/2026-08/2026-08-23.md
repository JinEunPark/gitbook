## 배포 구성

`rekit.co.kr`의 nginx가 일반 요청은 프론트엔드 컨테이너로, `/api/` 요청은 백엔드 컨테이너로, `/s3/` 요청은 SeaweedFS로 전달하도록 구성했다. 백엔드 옆에는 PostgreSQL 15와 Redis 7을 함께 실행했다.

```
인터넷 → rekit.co.kr → nginx
                       ├─ 일반 페이지 → rekle-web
                       ├─ /api/       → rekle-app
                       └─ /s3/        → SeaweedFS
Jenkins → 이미지 빌드 → 로컬 레지스트리 → 버전 지정 배포
```

이미지는 로컬 레지스트리(`127.0.0.1:5000`)에 저장하고, 커밋의 짧은 SHA와 `latest` 태그를 함께 사용했다. 운영 비밀 설정은 저장소에 포함하지 않고 배포 시에만 주입했다. 컨테이너 시작 시 마이그레이션을 적용해 애플리케이션 배포와 DB 변경을 함께 반영하도록 했다.

백엔드는 외부 포트를 열지 않고 nginx를 통해서만 접근하게 했고, 프로세스 4개로 요청을 처리했다. 프론트엔드는 API 주소를 상대 경로 `/api/v1`로 설정해 같은 도메인에서 제공했다. 이 구성으로 브라우저 CORS 문제가 발생하지 않도록 했다.

## 빈 DB 마이그레이션 오류

운영 DB를 새로 만들고 마이그레이션을 처음부터 적용했을 때, 자동 증가 컬럼을 변경하는 스크립트가 이미 IDENTITY인 컬럼을 다시 변경하려 하면서 실패했다.

초기 테이블 생성 스크립트는 IDENTITY 컬럼을 만들지만, 이후 마이그레이션은 기존 개발 DB의 SERIAL 컬럼 전환을 전제로 작성되어 있었다. 개발 DB에서는 앞선 마이그레이션을 다시 실행하지 않아 오류가 드러나지 않았다.

컬럼의 현재 상태를 확인한 뒤 SERIAL인 경우에만 IDENTITY로 바꾸도록 수정했고, 다운그레이드도 반대 조건에서만 동작하도록 만들었다. 빈 PostgreSQL에서 전체 마이그레이션을 실행하는 검증은 후속 작업으로 남겼다.

_근거 커밋: `13fe44a` · `alembic/versions/3509e1f6a778_…py`_

## 빌드와 배포 분리

빌드 작업은 이미지를 만들어 레지스트리에 올리는 역할만 하도록 분리했다. 배포 작업은 배포할 이미지 태그를 입력받고, 값이 없으면 `latest`를 사용한다. 문제가 생기면 이전 태그를 지정해 되돌릴 수 있다.

자동 배포는 아직 사용하지 않고, 빌드와 배포 모두 Jenkins에서 수동으로 실행했다.

_근거 커밋: `397f85a` · `Jenkinsfile.build`, `Jenkinsfile.deploy`_

## 프론트엔드 배포

프론트엔드는 Node 빌드 결과물만 nginx 이미지에 담는 다단계 Docker 빌드로 구성했다. SPA 경로를 새로고침해도 404가 나지 않도록 모든 화면 경로를 첫 HTML로 연결했고, 해시가 포함된 `/assets/` 파일은 1년간 캐시하게 설정했다.

_근거 커밋: `e9215d5`_

## 이미지 업로드 오류

운영에서 상품 이미지를 업로드할 때 presigned URL이 Docker 내부 주소 `seaweedfs:8333`를 가리켜 브라우저가 업로드할 수 없었다. presigned URL은 호스트 이름까지 서명에 포함하므로 브라우저에서 주소만 바꿔 사용할 수 없다.

운영 설정의 내부 endpoint 값을 제거하고, nginx의 `/s3/` 경로를 통과하는 공개 주소 `rekit.co.kr`를 환경 변수에서 사용하도록 수정했다. 브라우저가 접근 가능한 URL로 서명된 업로드 주소를 만들 수 있게 됐다.

**확인된 제약:** 이 설정에서는 백엔드가 SeaweedFS를 호출할 때도 공개 nginx 경로를 통과한다. 내부용 주소와 공개용 주소를 분리할지 후속으로 검토한다.

_근거 커밋: `af76abb` · `docker-compose.prod.yml`_
