# 08.26 · 상품 등록 폼 정리, 네이버 검수 준비

### 이날을 한 문단으로

8/23 첫 배포 뒤 운영에서 실제로 상품을 올려 보다가, 관리자 상품 등록 화면에 모양만 있고 저장은 안 되는 칸들이 있다는 걸 알았다. 특히 브랜드와 제조연도는 입력할 방법 자체가 없어서 등록한 상품에 늘 빈 값으로 들어가고 있었다. 이걸 실제 입력칸으로 바꾸고, 저장되지 않는 배송·A/S 카드는 지우고, 사진 최소 장수를 4장에서 2장으로 낮췄다. 석 달 동안 실제 서버와 어긋나 있던 API 설명 문서도 실제 서버 기준으로 고치기 시작했다. 저녁에는 네이버 로그인 검수를 준비하면서 개인정보처리방침에 소셜 로그인으로 받는 정보를 적고, 검수에 걸릴 만한 서버 문제(비밀번호 없는 소셜 가입자는 탈퇴를 못 함)를 찾아 할 일로 넘겼다.

### 1. 관리자 상품 등록 화면 정리

5/3 에 만든 관리자 화면은 디자인 시안을 보이는 그대로 옮긴 것이었다([05.03 일지](../2026-05/2026-05-03.md)). 7/3 서버와 연결할 때 상품명·가격·카테고리 같은 칸은 실제 값으로 묶었지만, 시안에서 선택 상자처럼 보이게 만든 버튼들은 그대로 남았다. 8/23 배포 후 실제로 등록해 보니 저장이 안 되는 칸들이 눈에 띈 것이다.

| 문제                  | 전                                                                         | 후                                                                                    |
| ------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 브랜드·제조연도가 저장 안 됨    | 화면에는 선택 상자처럼 생긴 버튼만 있고 글자를 넣을 방법이 없었다. 그래서 등록할 때 보내는 브랜드와 제조연도가 늘 빈 값이었다  | 일반 입력칸으로 바꿈. 제조연도에는 "예: 2022" 안내                                                     |
| 카테고리 선택 상자 화살표가 어긋남 | 브라우저 기본 화살표                                                               | 기본 화살표를 끄고 다른 칸과 같은 아이콘을 겹쳐 표시                                                       |
| 저장 안 되는 카드          | "배송 / A/S 정보" 카드에 배송 방식("전문 설치 배송"), 배송비, 설치 가능 지역(가짜 버튼), A/S 불가 안내가 있었다 | 카드를 지웠다. 서버의 상품 등록·수정 항목에 없는 값이라 입력해도 저장되지 않는 칸이었기 때문이다. 실제로 쓰는 재고 수량만 가격 정보 카드로 옮겼다 |
| 사진 최소 장수            | 최소 4장                                                                     | 최소 2장. 등록·수정 화면이 서로 다른 기준을 보여 주지 않게 둘 다 같은 값과 안내 문구로 맞춤                              |
| 미리보기 썸네일            | 올린 사진과 상관없이 항상 상자 아이콘                                                     | 첫 번째 사진이 있으면 그 사진, 없으면 아이콘                                                           |

7/3 에 만든 수정 화면은 처음부터 브랜드와 제조연도가 입력칸이었다. 등록 화면에만 시안의 가짜 버튼이 남아 있었던 것이라, 7/3 부터 이날까지는 일단 등록한 뒤 수정 화면에서만 브랜드를 넣을 수 있었다. 서버의 상품 등록 항목 이름과 화면이 보내는 이름은 맞았다. 이름이 틀린 게 아니라 입력할 칸이 없었던 것이다.

{% hint style="danger" %}
**오른쪽 체크리스트의 "기본 정보 입력"이 끝까지 완료되지 않았음 (7/3 \~ 8/26)**

등록 화면 오른쪽 체크리스트의 첫 항목은 상품명과 브랜드가 둘 다 있어야 완료로 바뀐다. 브랜드를 넣을 방법이 없었으니 7/3 서버 연결 이후 이 항목은 무엇을 해도 미완료로 보였다. 입력칸을 바꾸면서 같이 해결됐다.
{% endhint %}

{% hint style="info" %}
**A/S 불가 안내는 구매자 화면에도 나오나?**

지운 안내는 "폐업 매장에서 입고된 가전 특성상 제조사 A/S 는 적용되지 않습니다. 단, 배송 후 7일 내 동작 불량 발견 시 무상 교환·환불"이라는 문구로, 관리자에게 이게 자동으로 표시된다고 알려 주는 용도였다. 구매자 화면에 실제로 자동 표시되는지는 이날 작업 범위 밖이라 확인하지 않았다.
{% endhint %}

### 2. API 설명 문서를 실제 서버에 맞추기 시작

5/2 에 쓴 API 설명 문서(`docs/api.md`)는 "서버가 이렇게 만들어지면 좋겠다"는 목표 문서였다. 6월에 서버가 다른 모양으로 만들어지면서 어긋남이 쌓였고, 6/26 장바구니 불일치가 대표적이다([06.26 일지](../2026-06/2026-06-26.md)). 7/3 에 관리자 부분 두 장만 서버 설명서(Swagger) 기준으로 맞춰 둔 상태였는데, 이날 앞부분 공통 규칙과 전체 요약표를 실제 서버 기준으로 고쳤다.

* 응답 모양: 문서에는 모든 응답을 `{ data: … }` 로 한 번 감싼다고 돼 있었지만 실제 서버는 감싸지 않고 결과를 그대로 준다. 페이지가 있는 목록은 `{items, meta}` 이고 전체 페이지 수 이름은 `total_pages`(밑줄 표기)다. 페이지 없는 목록은 배열 그대로다.
* 이름 표기가 기능마다 다르다. 로그인·회원 쪽은 `accessToken` 처럼 낙타 표기, 상품·장바구니·배송지·주문·결제·관리자 쪽은 밑줄 표기다. 문서에 "한꺼번에 바꾸지 말 것"이라고 적었다.
* 실패 응답 모양도 제각각이다. 우리가 만든 오류는 `{code, message, fields}` 인데 일부는 한 번 더 감싸져 있고, 입력값 자동 검사에서 걸린 오류는 FastAPI 기본 모양으로 온다. 화면의 서버 호출 통로는 감싼 게 있으면 안쪽을, 없으면 그대로를 오류로 읽게 방어해 두었다. 오류 코드 표에는 주문 없음, 문의 없음, 권한 없음 세 개를 추가했다.
* 전체 요약표: 서버 기능 수를 59개에서 실제 서버 설명서에 나오는 79개로 고쳤다. 로그인 11→9, 회원 4→6(휴대폰 인증 포함), 찜은 이름이 Favorites 로, 주문 7개(견적, 배송 조회 포함), 결제 5→3, 관리자는 주문·회원·대시보드·매출·카테고리 20개와 상품 7개, 고객센터 4개.
* 기능별 상세 설명(3장\~10장)을 다시 쓰는 건 다음으로 미뤘다.

{% hint style="info" %}
**이제는 서버가 기준이고 문서가 따라간다**

5월에는 문서가 약속이고 서버가 그걸 따라 만드는 구조였는데, 7/3 부터는 반대로 실제 서버가 사실이고 문서가 따라간다. 문서 안에는 "2026-07 실측"이라고 적혀 있지만 실제로 고친 건 8/26 이다. 정정이 끝나지 않은 동안에도 6/26 장바구니와 7/3 매출·대시보드에서 화면과 서버가 주고받는 값이 어긋난 문제는 남아 있다(11/16 현재도).
{% endhint %}

### 3. 네이버 로그인 검수 준비

네이버 로그인을 일반 사용자에게 열려면 네이버의 검수를 받아야 한다. 저녁에 검수에서 자주 지적된다는 항목을 점검했다. 개인정보처리방침 1장에 "소셜 로그인(카카오·네이버·구글): 이메일, 이름/닉네임 등 프로필 식별정보. 각 제공자가 이용자 동의를 받은 항목에 한해 전달받음"이라는 줄을 넣었다. 로그인 버튼 디자인(초록 바탕에 흰 N)과, 로그인하고 돌아올 때 남이 끼어든 요청이 아닌지 확인하는 장치(state 값 검사)는 이미 기준을 채우고 있었다.

검수 전에 남은 일은 할 일 목록에 새로 적었다.

* 서버의 회원 탈퇴가 비밀번호를 꼭 받게 돼 있다. 소셜 로그인으로만 가입해 비밀번호를 정한 적 없는 사람은 탈퇴(연동 해제)를 할 수 없다는 뜻이다. 6/28 탈퇴를 다시 설계할 때 생긴 구멍이다([06.28 일지](../2026-06/2026-06-28.md)). 다음 날 고쳤다([08.27 일지](2026-08-27.md)).
* 네이버 개발자센터에 서비스 주소와 로그인 후 돌아올 주소를 실제 운영 주소(https)로 등록하고 검수를 신청하기. 5/10 부터 "소셜 로그인 돌아올 주소를 운영 도메인으로"가 미해결이었는데, 8/23 배포로 비로소 할 수 있게 됐다.
* API 설명 문서 3장\~10장 다시 쓰기.

할 일 목록의 현황표도 바꿨다. 서버 연결 진행률은 98%("본인인증만 남음")에서 99%("본인인증 포함 핵심 흐름 완료, 배송 조회·마이페이지 최근 주문 등 남음")로, 본인인증은 "미연결(가짜 화면)"에서 "Octomo QR 실제 연결 완료"로 바꿨다.

{% hint style="warning" %}
**"99% 연결"이라는 숫자와 실제**

표에는 99% 라고 적었지만 결제는 여전히 화면과 연결되지 않았고(9/3 토스 결제위젯 연결 전이고, 서버는 가짜 결제대행사로 돎), 6/26 장바구니 불일치도 그대로다. 본인인증 줄에는 예전 설명("PortOne v2 패스 인증 예정이나 아직 미구현, 가짜 화면 유지 중")을 지우지 않고 "단, Octomo QR 방식으로 실제 연결됨"을 덧붙여서, 한 줄 안에 서로 반대되는 두 문장이 같이 남았다.
{% endhint %}
