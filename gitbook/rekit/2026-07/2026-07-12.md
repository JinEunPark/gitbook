### 1. 품절 표시

상품 카드와 상세 화면은 재고 수를 들고 있으면서도 어디서도 품절인지 따져 보지 않았다. 그래서 재고가 0 인 상품도 정상 판매 중인 것처럼 보이고 장바구니에 담을 수 있었다. 재고가 0 이하면 품절로 보도록 판정 함수를 하나 만들고, 카드에는 사진 위에 어두운 "품절" 배지를 얹었다. 상세에서는 제목 옆에 품절 배지가 붙고 수량이 0 으로 보이며, 장바구니·바로 구매 버튼이 눌리지 않는다. 버튼을 막는 것과 별도로 버튼이 눌렸을 때 처리하는 곳에서도 품절이면 그냥 멈추게 해서 이중으로 막았다.

{% hint style="info" %}
**7/6 재고 되돌리기와 이어진다**

7/6 에 취소·결제 실패·만료 때 재고를 되돌리는 길을 만들었으니, 화면도 "재고 0 이면 품절, 돌아오면 다시 판매"를 보여 줘야 했다. 판매 상태가 아니라 재고 수로 판정한 건, 당시 서버가 재고가 0 이 돼도 판매 상태를 "판매 중"으로 그대로 두었기 때문으로 보인다. 서버는 8/13 에 "재고가 0 이 되면 품절로 자동 전환, 재고가 돌아오면 판매 중으로 자동 복원"으로 따라온다([08.13 일지](../2026-08/2026-08-13.md)).
{% endhint %}

### 2. QR 로 하는 휴대폰 인증 (Octomo)

7/1 에 만든 휴대폰 인증은 화면에서만 도는 가짜라서 아무 숫자 6자리면 통과했고, 주문 전 본인확인도 브라우저 안의 "인증됨" 표시만 바꿨다. 이걸 Octomo 방식으로 바꿨다. 서버가 문자를 보내는 대신 QR 을 만들어 주고, 사용자가 그 QR 을 휴대폰 카메라로 찍으면 문자 앱이 열려서 정해진 문자를 자기 번호로 보낸다. 서버는 그 문자가 실제로 도착했는지 확인한다. 사용자가 직접 보낸 문자로 "이 번호의 주인"임을 증명하는 방식이라, 일반 문자 인증처럼 발신번호를 등록하거나 건당 발송비를 낼 필요가 없다(7/1 에 "로그로만 찍는" 문자 발송 부품을 둔 자리를 대신한다).

화면이 서버에 기대하는 모양은 두 가지다. 인증 시작 요청에 휴대폰 번호를 보내면 서버가 QR 이미지를 돌려주고, 화면은 그 이미지를 그대로 띄운다. 인증 확인 요청에는 번호만 보내고 인증번호는 보내지 않는다. 서버가 발급해 둔 값을 스스로 다시 조회해서 확인하기 때문이다.

#### 인증 부품이 하는 일

QR 은 5분 동안 유효하고(Octomo 쪽 유효시간 5분과 같게), 화면에 남은 시간을 보여 준다. 다시 받기는 60초에 한 번만 된다(7/1 서버 재요청 제한과 같은 값). 5분이 지나고 60초 제한도 풀리면 자동으로 새 QR 을 받아 온다. 안내 문구는 "카메라로 QR을 스캔하면 문자 앱이 열려요. 그대로 전송만 눌러주세요."이고, 문자를 보낸 뒤 "인증 확인"을 누르면 서버에 확인을 요청한다.

QR 을 받는 중이거나 QR 이 유효한 동안에는 번호 입력칸을 잠근다. 주문 전 본인확인에서는 계정에 이미 번호가 있으면 입력칸 자체를 잠가서, 다른 번호로 바꿔치기해 인증하는 걸 막았다.

#### 바뀐 화면

| 화면          | 전                                              | 후                                                                                                                         |
| ----------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 주문 전 본인확인   | 인증번호 입력 흉내를 낸 뒤 브라우저의 "인증됨" 표시만 바꿈 (7/1 노트 경고) | "주문 전에 휴대폰 인증을 진행해 주세요 · 첫 주문 시 1회 · 다음 주문부터는 자동으로 생략돼요" 안내와 인증 부품. 성공하면 서버에서 내 정보를 다시 받아 온 뒤 다음 단계로. 아래에 "인증 제공: Octomo" |
| 내 정보 휴대폰 변경 | 아무 6자리 숫자면 번호가 바로 저장됨 (7/1)                    | 같은 인증 부품, 성공하면 서버가 번호를 저장                                                                                                 |
| 배송지 휴대폰 입력  | 아무렇게나 입력                                       | 하이픈 자동                                                                                                                    |

주문 단계 표시의 첫 단계 이름도 한 줄 고쳤다.

본인인증 방향도 여기서 바뀌었다. 5/1 요구사항은 결제대행사를 통한 본인인증(CI/DI), 7/2 문서는 "PortOne v2 패스 인증"이었는데, 휴대폰 번호 주인 확인으로 대신하게 됐다. 이 흐름은 11/5 노트의 "문자 인증은 하지 않기로 최종 결정"으로 이어진다.

{% hint style="warning" %}
**화면이 서버보다 한 달 먼저 저장됐다**

저장소에 있던 서버 기능(7/1)은 인증 확인 때 6자리 인증번호를 꼭 받아야 하고, 인증 시작 요청에는 아무 내용 없이 "성공"만 돌려준다. 이 화면은 인증번호 없이 보내고 QR 이미지를 기다리니, 저장소에 있던 서버와는 함께 동작하지 않는다. 서버 쪽 Octomo 기능과 "전화번호를 010-0000-0000 형태로 맞춰 저장"은 8/13 에 저장된다. 화면 쪽 설명에 적힌 "백엔드가 이 형식(하이픈)을 기대한다"도 그 8/13 내용과 맞는다.
{% endhint %}

{% hint style="info" %}
**추정 — 서버 코드는 이미 작업 중이었다**

화면 쪽 설명이 Octomo 유효시간 5분, "서버가 발급해 둔 값을 스스로 재조회" 같은 서버 구현 세부를 알고 있다. 그래서 7/12 에 서버 Octomo 코드가 개발자 컴퓨터에는 이미 있었고 저장만 8/13 에 한 것으로 본다. 7/12 부터 8/13 사이 서버 저장은 하나도 없다. 8/13 에 확인한 근거로 보강하면, 8/13 에 저장된 서버 DB 변경 스크립트의 작성 시각이 7/12 08:24 다. 이 화면 저장(14:52)보다 6시간 앞서 서버 쪽 DB 변경이 이미 만들어져 있었고, Octomo 작업 계획서는 7/10 에 썼다([08.13 일지](../2026-08/2026-08-13.md) §0).
{% endhint %}

{% hint style="danger" %}
**"전화번호는 암호화 저장" — 사실과 다른 안내 (당시 \~ 11/16 현재도)**

주문 전 본인확인 화면 아래에 "· 전화번호는 암호화 저장되며 분쟁 대응 외 사용되지 않습니다."라고 적혀 있다. 그런데 회원 표의 휴대폰 번호는 그냥 글자 그대로 저장되고, 서버 어디에도 암호화하는 코드가 없다. 11/16 에 서버 코드를 암호화 관련 단어로 찾아봐도 0건이었고, 7/4 서버 작업 기록에도 "CI/DI 평문 저장"이라고 적혀 있다. 11/16 지금도 화면 문구가 그대로다. 개인정보에 관한 안내라서 문구를 고치든 실제로 암호화하든 해야 한다. 5/1 디자인 시안의 "인증 정보는 암호화 저장" 문구를 옮겨 온 것으로 보인다.
{% endhint %}
