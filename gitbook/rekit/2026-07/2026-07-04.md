### 1. 문의는 로그인한 회원만

7/3 버전은 로그인 없이 이름·이메일·연락처를 직접 적어 문의할 수 있었고, 적힌 주소로 접수 확인 메일을 보냈다. 남의 주소를 적으면 그 사람에게 메일이 가는 구조라 스팸 발송에 쓰일 수 있었고, 로그인한 회원이 문의해도 회원 번호가 저장되지 않았다. 이날 문의 남기기를 로그인 필수로 바꾸고, 요청에는 제목과 내용만 받도록 했다. 이름과 이메일은 로그인한 회원 정보에서 가져오니 메일은 이제 본인 계정 주소로만 간다.

|        | 7/3              | 7/4                    |
| ------ | ---------------- | ---------------------- |
| 누가     | 누구나              | 로그인한(정지되지 않은) 회원       |
| 받는 것   | 이름·이메일·연락처·제목·내용 | 제목·내용만                 |
| 이름·이메일 | 적은 그대로           | 회원 정보에서                |
| 회원 번호  | 항상 비어 있음         | 저장됨 (탈퇴하면 비워지고 문의는 남음) |
| 연락처 칸  | 있음               | DB 에서 삭제               |

주소도 `/help/contact` 에서 `/help/contacts` 로 바뀌어서, 예전 방식으로 부르던 쪽은 깨진다.

화면의 문의 페이지는 로그인하지 않았으면 입력 폼 대신 "로그인 후 문의하실 수 있어요 · 문의 내역과 답변은 로그인된 계정 기준으로 관리돼요"와 로그인 버튼을 보여 주고, 로그인하면 다시 문의 페이지로 돌아온다. 이메일 입력칸 자리는 제목 입력칸이 됐다. 서버에 "주제" 칸이 없어서 고른 주제를 제목 앞에 `[주문/배송] 제목` 처럼 붙여 저장하고, 그만큼 제목 최대 길이를 줄였다. 내용 아래에는 "n / 최소 10자" 글자 수를 보여 준다.

### 2. 답변 등록과 답변 메일

운영자가 문의에 답변을 적으면 답변 내용이 저장되고, 상태가 "답변 완료"로 바뀌며, 문의한 사람에게 "\[rekit] 문의하신 내용에 답변이 등록되었습니다" 메일이 간다. DB 문의 표에 답변 내용 칸을 추가했고 답변은 최대 3,000자다.

상태와 "답한 시각"은 항상 같이 바뀌어야 해서, 그 규칙을 한 곳에만 두고 답변 등록과 상태 바꾸기가 같이 쓰게 했다. 상태 바꾸기는 사실상 "답변 대기로 되돌리기" 용도로 남겼다. 되돌려도 답변 내용은 지우지 않고 답한 시각만 비운다. 같이 한 정리로는 목록·상세 조회에서 겹치던 페이지 나누기 코드를 합치고, 메일 틀의 머리·꼬리 같은 공통 부분을 하나로 뽑아 메일 종류마다 가져다 쓰게 했다.

{% hint style="warning" %}
**메일 보내기가 실패하면 답변도 저장되지 않을 수 있다**

답변 메일을 뒤로 미루지 않고 요청 안에서 보낸다. 서버의 DB 저장은 요청이 정상으로 끝날 때만 확정되므로(5/7 에 만든 방식), 메일 서버가 오류를 내면 답변 저장까지 같이 취소될 수 있다. 실제로 그런 일이 있었다는 기록은 없다. 7/3 접수 메일과 같은 구조다.
{% endhint %}

### 3. 내 문의내역

회원이 자기가 남긴 문의와 답변을 다시 볼 곳이 없었다. 서버에 내 문의 목록과 상세를 만들고, 마이페이지에 "내 문의내역" 화면 두 개를 붙였다.

상세를 가져올 때는 "이 번호의 문의이면서 주인이 나인 것"을 DB 조회 조건에 같이 넣는다. 남의 문의 번호를 넣으면 있는지 없는지도 알려 주지 않고 "없음"으로 답한다. 7/3 사진 한 장 고치기와 같은 선택이고, Spring Data 로 치면 `findByIdAndUserId` 와 같은 생각이다.

목록 화면(299줄)은 전체/답변 대기/답변 완료로 거를 수 있고 상태마다 색이 다른 배지를 단다. 상세 화면(213줄)은 질문 아래에 답변을 보여 준다. 마이페이지 메인 메뉴 한 줄도 이 화면으로 바꿨다.

### 5. 관리자 고객센터 화면

운영자가 공지·FAQ 를 쓰고 문의에 답할 화면이 없었다. 관리자 왼쪽 메뉴에 "고객센터"를 추가하고, 한 화면(698줄)에 탭 세 개를 넣었다.

공지 탭에서는 목록을 보고 제목·내용·상단 고정·게시 여부를 정해 새로 쓰거나 고치고, 확인 창을 거쳐 지운다. FAQ 탭은 분류·질문·답변·순서·게시 여부를 같은 식으로 다룬다. 1:1 문의 탭은 상태로 거르고, 줄을 펼치면 상세를 불러와 답변을 쓰거나 고칠 수 있다. 버튼 문구는 이미 답한 문의인지에 따라 바뀌고, "답변 대기로 되돌리기"도 있다.

### 6. 입력 오류를 자세히, 날짜 표시는 한 곳에서

전에는 입력이 잘못되면 "입력값이 올바르지 않습니다." 한 줄만 보였다. 서버는 5/7 부터 칸별로 이유를 한국어 문장으로 같이 보내 주고 있었으니, 화면이 그 이유를 뒤에 붙여서 "입력값이 올바르지 않습니다. (제목은 2자 이상…)"처럼 보여 주게 했다.

날짜를 `2026.07.04` 형태로 바꾸는 함수가 7/3 관리자 화면마다 따로 있었는데, 공용 함수 두 개(날짜 / 날짜+시각)로 모았다. 날짜가 이상하면 받은 글자를 그대로 보여 준다.

{% hint style="danger" %}
**FAQ 내용이 실제 서비스와 다르다 (당시 \~ 11/16 현재도 기본 데이터 그대로)**

문구가 일반 중고 오픈마켓을 기준으로 쓰여 rekit 과 맞지 않는다.

* "서울/경기 지역은 철거 차량을 이용한 직접 배송도 가능합니다" — 쓰지 않기로 한 "철거"라는 말이 구매자에게 보이는 문구로 다시 들어왔다. (다른 날에도 있는지는 다 찾아보지 않았다)
* "여러 판매자… 배송비도 판매자 단위", "판매자와 협의 후 반품" — rekit 은 직접 사서 직접 판다. 판매자는 rekit 하나다.
* "비밀번호 찾기에서 재설정 링크" — 5/7 부터 임시 비밀번호를 메일로 보내는 방식이다.
* "진행 중인 주문이 있으면 탈퇴가 제한" — 6/28 에 만든 탈퇴에는 그런 검사가 없다.
* "신용카드·간편결제 지원" — 같은 날 화면 쪽 계획서는 "무통장입금 전용"이다.

운영 DB 에 이 데이터를 넣었다면 FAQ 화면에 그대로 보인다. 관리자 화면에서 고칠 수는 있다.

### 8. 두 작업 문서가 말하는 이날의 상태

화면 쪽 계획서는 서버 연결을 98%("본인인증만 남음"), 관리자 확인은 완료로 적었다. 결제는 7/3 의 PortOne v2 결정을 지우고 "계좌이체(무통장입금) 전용으로 실제 구현 변경됨 (고정 회사 계좌 + 주문번호로 입금자명 매칭)"이라고 고쳤다. API 문서의 결제 부분은 아직 결제대행사 기준이라 맞지 않는다는 메모와 함께, "입금 확인 관리 기능 필요"를 우선순위 1 로 올렸다. 본인인증 화면은 여전히 화면 안에서만 도는 가짜라고 적었다.

{% hint style="info" %}
**7/1 부터 이어 보면**

7/1 에 주문 상태를 서버에 맞추면서 "입금 완료했어요" 흐름이 사라졌고, 7/3 문서에서는 PortOne 이 "결정 완료"였다. 7/4 문서는 다시 무통장입금 전용으로 돌아가면서 "입금 확인 관리 기능 필요"라고 적는다. 서버의 결제대기 상태 위에 무통장입금을 다시 얹어야 한다는 걸 이때 알아챜 것으로 보인다. 실제 카드 결제는 9/3 토스 위젯으로 들어갔다([09.03 일지](../2026-09/2026-09-03.md)).
{% endhint %}

서버 쪽 작업 기록 문서에는 아직 안 만든 것으로 가입 때 문자 인증, 실제 문자 발송, 결제대행사 본인인증, 배송 추적, 앱 안 알림, 결제대행사 환불 실제 호출, 서비스 전체 요청 횟수 제한(관련 라이브러리만 설치돼 있음), 보안 헤더, 본인인증 고유번호(CI/DI) 암호화(지금은 그대로 저장)가 적혀 있다.

같은 문서에 "본인인증 … DB 직접 설정으로 우회 중"이라는 줄이 있다. 7/1 노트의 "서버에 본인인증 기록이 없으면 주문이 항상 실패"를 그때 어떻게 넘겼는지가 여기서 확인된다. 테스트 계정의 본인인증 시각을 DB 에 직접 넣어 두었던 것이다.

{% hint style="danger" %}
**알려진 버그로 기록 — 대시보드 매출 그래프가 서버 오류(500)**

대시보드 매출 그래프를 부르면 서버가 500 오류를 낸다. 날짜를 "일 단위로 자르는" 식을 조회·묶기·정렬 세 곳에 각각 쓰는데, 그 안의 단위 글자('day')가 세 곳에서 따로따로 값으로 넘어가서 DB(PostgreSQL)가 세 식을 같은 식으로 보지 못하고 "묶지 않은 값을 골랐다"는 오류를 낸다. 7/3 에 대시보드를 연결하고 실제로 화면을 열어 보다 찾은 것으로 보인다. 화면은 오류를 조용히 넘겨서 빈 그래프만 보였다. → [07.06 일지](2026-07-06.md) 에 고쳤다.

JPA 로 치면 JPQL 에서 `FUNCTION('date_trunc', :unit, o.createdAt)` 를 SELECT 와 GROUP BY 에 따로 쓰면 파라미터가 따로 바인딩돼 같은 식이 아니게 되는 것과 같다. 상수는 쿼리에 직접 박거나 식을 한 번 만들어 재사용해야 한다.
{% endhint %}
