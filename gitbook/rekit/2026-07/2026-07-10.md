### 1. 두 번째 점검에서 찾은 것과 고친 것

7/6 에 결제 흐름의 동시성 문제를 막았지만, 잠금을 건 곳과 안 건 곳이 섞여 있었다. 다시 훑어서 7가지를 찾았다.

| 번호  | 문제                                  | 심각도 | 어떻게 고쳤나                                                                                                |
| --- | ----------------------------------- | --- | ------------------------------------------------------------------------------------------------------ |
| F-1 | 회원 주문 취소가 주문을 잠그지 않고 읽음 (7/6 작업 1)  | 높음  | 잠그고 읽게 바꿨다. 두 번 누르기나 자동 재시도로 취소가 동시에 와도 재고가 두 번 돌아오지 않는다. 본인 주문인지 확인은 잠근 뒤에 직접 한다                      |
| F-2 | 30분 만료 처리에 잠금이 없음 (7/6 작업 2)        | 중간  | 먼저 잠그지 않고 "결제대기이고 30분 지났나"로 후보만 고르고, 후보면 잠근 뒤 다시 읽어서 여전히 결제대기일 때만 재고를 되돌린다. 주문 상세를 볼 때마다 잠그지 않으려는 절충이다 |
| F-3 | 토스 알림 처리 전체에 잠금이 없음                 | 높음  | 결제 번호로 찾을 때, 주문번호로 대신 찾을 때, 주문을 읽을 때 모두 잠근다. 토스가 같은 알림을 동시에 다시 보내도 재고가 두 번 돌아오지 않는다                    |
| F-4 | 결제완료 뒤에 오는 정상 환불 알림까지 막힘            | 높음  | 아래 버그 설명 참고                                                                                            |

| F-6 | 결제 시작 잠금이 정말 대기 기록을 하나만 만드는지 확인 안 됨 | 낮음  | 실제 DB 테스트로 작성                                                                                          |

{% hint style="danger" %}
**결제완료 뒤 환불 알림이 무시되던 문제 (F-4)**

토스 알림이 두 번 와도 한 번만 처리하려고 "결제가 이미 완료면 알림을 무시한다"는 장치를 7/6 에 넣었다. 그런데 이 장치가 결제완료 뒤에 정당하게 오는 "결제 취소(환불)" 알림까지 막았다. 예를 들어 토스 관리 화면에서 환불하면 토스가 취소 알림을 보내는데, 서버는 이미 결제완료라는 이유로 무시해서 rekit 에서는 주문이 계속 결제완료로 남는다. 고친 뒤에는 결제완료 상태에서 "결제 완료" 알림이 다시 오면 무시하고, "취소"·"부분 취소" 알림은 통과시켜 환불로 처리한다. "결제 거절" 알림은 결제완료 뒤에 올 수 없는 조합이라 경고 기록만 남기고 무시한다. 이 결제 처리 코드에 처음으로 서버 기록(logging)이 들어갔다.
{% endhint %}

{% hint style="info" %}
**잠근 뒤에도 옛날 값을 보는 함정 — JPA 1차 캐시와 같다**

서버의 DB 도구(SQLAlchemy)는 같은 작업 안에서 이미 읽은 주문이 있으면, 잠그면서 새로 읽어도 기억해 둔 옛날 객체를 돌려준다. 잠금은 걸었는데 상태는 옛날 값인 셈이다. JPA 에서 영속성 컨텍스트에 엔티티가 있으면 `find()` 가 DB 를 다시 보지 않는 것과 같고, 거기서 `em.refresh()` 를 쓰듯 여기서는 "DB 에서 읽은 값으로 덮어쓰라"는 옵션(`populate_existing`)을 켰다. F-2 의 "먼저 읽고 잠근 뒤 다시 읽기"가 정확히 이 함정에 걸리는 구조라 꼭 필요했다. 이날은 주문 쪽에만 넣었고, 결제 기록 쪽에는 10/16 에 같은 옵션이 들어간다.
{% endhint %}

{% hint style="info" %}
**7/6 노트의 지적과 일치**

7/6 노트에 적은 "회원 취소엔 잠금이 없었다", "만료 처리에 잠금이 없다" 두 구멍(F-1, F-2)을 4일 뒤 스스로 찾아 막았다. 다만 결제 승인이 주문을 잠그지 않아서, 승인을 기다리는 사이 만료가 끼어드는 근본 문제는 남았고 10/16 에 풀린다.
{% endhint %}

### 2. AI 도구를 사람 없이 반복 실행하는 스크립트

점검 문서에 체크 안 된 항목이 남아 있는 동안 Claude Code 를 대화창 없이 한 번씩 실행해서, 한 번에 작업 하나씩 처리하게 하는 셸 스크립트를 만들었다. 7/7 에 대화 안에서 쓰는 반복 실행 기능을 허용한 데 이어, 이번엔 아예 사람 없이 도는 방식으로 간 것이다.

스크립트가 AI 에게 주는 지시는 이렇다. 남은 작업 중 하나만 고른다. 테스트를 먼저 쓰고(실패 확인 → 통과 → 정리) 끝나면 테스트·스타일 검사·타입 검사(7/3 에 정한 완료 조건)를 통과하는지 확인한다. 문서에 완료 체크와 고친 위치를 적는다. 그리고 저장(commit)이나 올리기(push)는 절대 하지 않는다. 사용자가 확인한 뒤 직접 저장한다.

문서에 체크 안 된 항목이 없거나 AI 가 "ALL\_DONE"이라고 출력하면 멈춘다. 실행마다 기록 파일을 남기고, 사용량 한도에 걸렸다는 말이 기록에 보이면 20분 기다렸다가 같은 작업을 다시 하고, 이상하게 끝나면 1분 뒤, 정상이면 10초 뒤 다음으로 넘어간다.

7/6 에는 작업마다 따로 저장했는데 이날은 7개 항목이 저장 하나에 다 들어 있다. 스크립트가 여러 번 돌아 고친 결과를 사람이 한 번에 확인하고 저장한 것으로 보인다.

{% hint style="warning" %}
**권한 확인을 전부 띈 채로 돌렸다**

사람이 없으니 AI 가 명령을 실행할 때마다 묻는 권한 확인을 모두 껏다(`--dangerously-skip-permissions`). "저장 금지"는 지시일 뿐 강제가 아니다. 이 저장소에는 DB·메일·토스 비밀값이 든 설정 파일이 있으니, 별도 작업 공간이나 컨테이너로 떼어 놓지 않고 돌리면 AI 가 무엇이든 실행할 수 있는 상태였다. 결과를 사람이 바뀐 내용으로 확인하는 단계가 유일한 안전장치였다.
{% endhint %}

{% hint style="info" %}
**추정 — 왜 반복 실행으로 돌렸나**

점검 문서 첫머리에 "자동 루프가 다른 세션에서 아직 돌고 있다면 반드시 먼저 중지"라고 적혀 있다. 반복 실행을 뒤에서 돌려 두고, 그동안 다른 대화에서 나이스페이를 조사한 것으로 보인다. 사용량 한도 대기가 20분인 것도 자리를 비운 동안 돌려 두는 쓰임에 맞춘 설계로 보인다.
{% endhint %}

### 3. 결제대행사를 나이스페이로 바꾸는 계획서

문서 첫머리에는 "대행사를 하나만 쓰기로 하고 토스페이먼츠로 코드를 짰었는데, 가입비/연회비 조건 비교 끝에 나이스페이로 PG 를 교체하기로 했다"고 적었다. 그래서 토스에 묶인 코드를 전부 찾고 나이스페이 방식으로 옮기는 순서를 860줄로 정리했다. 실제 교체는 하지 않았다.

먼저 토스에 묶인 코드를 13곳 찾았다. 토스 연결 부품, 결제사 공통 약속(이름부터 "토스 승인 결과"로 돼 있음), 토스 알림 형식, 토스 전용 상수, 서버 주소, 결제사 목록, 설정, 테스트, 문서 등이다. 덤으로, 예시 설정 파일에 있는 토스 화면용 키는 서버 설정에 받는 자리가 없어서 실제로는 읽히지 않는 값이라는 것도 찾았다.

나이스페이 조사에서 가장 큰 차이로 꼽은 건 결제 흐름이다. 토스는 결제 뒤 화면이 성공 페이지로 이동하고 거기서 서버에 승인을 요청하는데, 나이스페이는 결제 인증이 끝나면 나이스페이가 정해 둔 서버 주소로 직접 결과를 보내온다. 작업은 0\~12단계로 나눴다. 결정 사항 정리, 설정, 공통 약속을 결제사 이름 없는 것으로 다시 짜기, 연결 부품, 알림 형식·서명, 서버 주소, 서비스 분기, 결제사 목록, 가짜 결제 모듈, 취소, 화면 쪽 결과 수신 구조, 테스트 옮기기, 점검 문서와의 관계 순이다.

순서는 (A) 두 번째 점검을 먼저 하고 교체하기(동시성 로직은 결제사와 상관없으니까), (B) 교체를 먼저 하고 점검을 다시 적용하기 두 가지를 적어 두었는데, 이날 점검이 끝나 있으니 (A) 로 간 셈이다.
