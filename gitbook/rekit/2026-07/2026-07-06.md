### A-1. 대시보드 매출 그래프 서버 오류 고치기

7/4 에 기록한 대로 대시보드 매출 그래프를 부르면 서버가 500 오류를 냈다. 날짜를 하루 단위로 자르는 식을 조회·묶기·정렬 세 곳에 따로 쓰다 보니 그 안의 'day' 라는 글자가 세 번 따로 넘어갔고, DB(PostgreSQL)가 세 식을 같은 식으로 인정하지 않았다. 세 곳이 식 하나를 같이 쓰도록 하고, 'day' 를 쿼리 안에 직접 박아 넣는 방식으로 고쳤다. 이제 대시보드에 매출 그래프가 그려진다.

매출 화면의 날짜별·주별 그래프에도 같은 문제가 있어서 바로 이어서 공용 함수 하나로 묶었다. 쿼리에 직접 박는 글자는 아무 글자나 들어오면 위험하니, 함수가 'day' 와 'week' 두 가지만 받도록 타입으로 막았다.

{% hint style="warning" %}
**5/10 에 막았던 "CORS 오류처럼 보이는 500" 이 다시 나왔다**

처리되지 않은 서버 오류가 나면, 다른 주소에서 부를 때 필요한 허락 헤더(CORS)가 빠진 채로 응답이 나가서 화면에는 서버 오류가 아니라 CORS 오류로 보였다고 적혀 있다. 5/10 에 모든 오류를 받아 주는 처리기를 달아 막았던 증상과 같다. 이 경로로는 여전히 새고 있었다는 뜻이다. 11/5 에 같은 문제가 다시 나와 또 고친다([11.05 일지](../2026-11/2026-11-05.md)).
{% endhint %}

#### 처음 도입한 실제 DB 테스트

가짜 DB 로 돌리는 테스트에서는 이 오류가 재현되지 않았다. PostgreSQL 은 "같은 식인지"를 쿼리를 읽는 단계에서 검사하기 때문에, 데이터가 하나도 없어도 실제 DB 에 보내 보면 바로 재현된다. 그래서 실제 DB 에 붙는 테스트 묶음을 처음 만들었다.

걸림돌은 5/10 부터 미뤄 둔 문제였다. 비동기 DB 연결은 만들어진 실행 흐름(이벤트 루프)에 묶이는데, 테스트 도구는 테스트마다 새 실행 흐름을 만들어서 "Event loop is closed" 오류가 났다. 테스트가 끝날 때마다 연결을 모두 버리도록 해서 풀었다. 이 준비는 DB 가 필요한 테스트만 요청해서 쓰게 해서, DB 를 안 쓰는 테스트에는 비용이 들지 않는다.

{% hint style="info" %}
**5/10 에 미뤄 둔 일의 결말**

5/10 에는 "통합 테스트는 실행 흐름 충돌로 보류"라고 적었다. 두 달 만에 풀렸고, 아래 작업 1·3 의 잠금 확인 테스트가 이 준비 위에서 돈다.

### A-2. 관리자 주문 상세·회원 상세

관리자 화면에는 주문·회원 목록만 있어서 한 건을 자세히 볼 곳이 없었다. 주문 상세 화면(428줄)에서는 주문자, 배송지, 상품(사진·브랜드·모델명·수량·금액), 결제, 배송 정보를 한눈에 보고, 목록에서 하던 준비 시작·송장 입력·취소도 상세에서 바로 할 수 있다. 회원 상세 화면(199줄)은 기본 정보, 구매 활동, 인증 상태(휴대폰 확인·본인인증·마케팅 동의 시각)를 보여 주고 정지/활성 전환을 할 수 있다.

상품 사진 편집 부품에는 마우스로 끌어다 놓아 순서를 바꾸는 기능을 넣었다. 끄는 동안 사진이 반투명해지고 놓을 자리가 표시된다. 화살표 버튼도 그대로 남겼다. 주문 상품 금액은 1개면 "수량 1개", 2개 이상이면 "₩100,000 × 2개"처럼 보여 준다.

서버에서는 주문 상품에 "주문 당시 모델명" 복사본 칸을 추가했다. 이미 있던 주문은 상품 표의 모델명으로 채워 넣었다. 관리자용과 구매자용 주문 상품 정보의 이름을 같게 맞추고 상품 번호를 넣어서, 관리자 화면에서 상품을 누르면 상품 수정 화면으로 갈 수 있다. 7/1 브랜드에 이은 두 번째 복사본 칸이다. 화면 쪽 계획서의 "주문 상세·회원 상세·사진 순서 바꾸기" 항목도 체크했다.

### C. 작업 1 — 취소하면 재고 되돌리기

재고가 1개뿐인 상품이 대부분인데, 주문을 취소해도 재고가 0 으로 남아서 그 상품은 다시 팔 수 없었다. 재고를 늘리는 기능을 만들고, 회원이 취소할 때, 관리자가 취소할 때, 토스에서 결제 거절·결제 취소 알림이 올 때 모두 주문 상품 수만큼 재고를 되돌리게 했다. 이제 취소된 상품은 바로 다시 판매 목록에 뜬다.

재고 늘리기는 "지금 재고 + n" 을 DB 가 한 번에 계산하게 해서, 재고 빼기와 짝이 맞는다. 실제 DB 테스트로 5+2=7, 3 을 뺐다가 3 을 더하면 원래대로 돌아오는 것을 확인했다.

회원 취소는 이미 취소된 주문을 다시 취소하면 오류를 내니 두 번 복구되지는 않는다. 관리자 취소는 주문을 읽을 때 잠그도록 했는데, 원래 "잠그고 읽기"라는 이름의 함수가 실제로는 잠그지 않고 있었다. 잠금이 진짜 동작하는지는 실제 DB 연결 두 개로 확인했다. 한쪽이 주문을 잠근 동안 다른 쪽이 같은 주문을 읽으려 하면 1초 안에 끝나지 못하는 걸 봤다.

토스 알림이 "결제 거절" 또는 "결제 취소"면 결제 기록을 실패/취소로 바꾸고 재고를 되돌리며 주문을 취소한다. 이미 취소된 주문이면 건너뛴다. "부분 취소" 알림은 재고를 되돌리지 않는다.

{% hint style="danger" %}
**회원 취소에는 잠금이 없었다 (7/6 \~ 7/10)**

관리자 취소는 잠갔지만 회원 취소는 그냥 읽는다. "취소"를 빠르게 두 번 누르면 두 요청이 둘 다 "결제대기"를 보고 재고를 두 번 되돌릴 수 있다. 재고 1개 상품이 2개가 되는 식이다. 7/10 에 회원 취소도 잠그고 읽게 고쳤다([07.10 일지](2026-07-10.md)). 또 결제완료 주문을 회원이 취소하면 "결제 취소는 결제 쪽 책임"이라며 주문 상태만 바꾸고 돈은 돌려주지 않는다. 결제사 환불 실제 호출은 9/4 에 들어갔다.
{% endhint %}

### D. 결제 작업 4·5·3 (새벽 4분 동안 세 개)

결제는 "결제 시작(대기 기록 만들기) → 사용자가 결제창에서 결제 → 서버가 토스에 승인 요청" 순서로 흐르고, 토스는 따로 결제 상태 알림(웹훅)을 보낸다. 이 흐름에서 같은 요청이 두 번 오거나 알림이 승인보다 먼저 오는 경우를 막았다.

작업 4는 결제창을 두 번 여는 경우다. 결제 시작 때 주문을 잠그고, 이미 결제 대기 기록이 있으면 새로 만들지 않고 그걸 다시 쓴다. 결제창을 몇 번 열어도 대기 기록은 하나다.

작업 5는 승인 요청이 두 번 오는 경우다. 승인 전에 주문이 결제대기인지 확인해서 시간이 지나 취소된 주문의 승인을 막고, 결제 기록들을 잠근다. 그리고 대기 기록이 없고 이미 결제완료 기록이 있으면 토스를 다시 부르지 않고 이전 결과를 돌려주게 했다(같은 요청이 두 번 와도 한 번 온 것과 같게, 멱등).

작업 3은 토스 알림이다. "결제 완료" 알림이 오면 주문도 결제완료로 바꾼다(결제대기일 때만). 알림이 승인보다 먼저 오면 토스 결제 번호로는 기록을 못 찾기 때문에, 주문번호로 대기 기록을 찾아 결제 번호를 채워 넣는다.

{% hint style="danger" %}
**"이미 결제됐으면 이전 결과 돌려주기"가 실제로는 실행되지 않는다 (7/6 \~ 11/16 현재도)**

승인 처리는 "주문이 결제대기인가" 확인을 먼저 하고, "이미 결제완료면 이전 결과 돌려주기"를 그다음에 한다. 그런데 첫 승인이 성공하면 같은 처리 안에서 주문이 결제완료가 된다. 그래서 결제 성공 화면을 새로고침하거나 재시도해서 승인이 한 번 더 오면, 앞의 확인에서 "주문 상태가 결제대기가 아닙니다"로 실패한다. 테스트는 "결제는 완료인데 주문은 결제대기"라는, 실제로는 생기지 않는 상태를 만들어서 통과한다. 11/16 지금 코드도 순서가 그대로다. 돈이 두 번 빠지지는 않지만, 결제가 된 사람이 실패 화면을 볼 수 있다.
{% endhint %}

### E. 작업 2·7·8 (오후)

오후 3분 동안 남은 작은 작업 세 개를 했다.

작업 2는 결제를 안 하고 떠난 주문이다. 결제 기한을 30분으로 정했다. 문서에 "임의로 숫자를 정해 넣지 말 것"이라고 적어 뒀다가 사용자 확인을 받고 30분으로 결정했다고 기록했다. 따로 주기적으로 도는 작업을 두지 않고, 누군가 주문 상세를 조회할 때 30분이 지났으면 그때 재고를 되돌리고 취소하는 방식이다. 주기적으로 도는 방식은 다음 단계로 미뤘다.

작업 7은 관리자가 상품 재고를 고칠 때다. 요청에 재고가 들어 있을 때만 상품 줄을 잠그고 고친다.

작업 8은 결제사에 보내는 금액이다. 토스 승인 요청에 화면이 보낸 금액 대신 서버가 가진 주문 총액을 보낸다. 화면이 보낸 금액은 맞는지 비교하는 데만 쓴다.

{% hint style="warning" %}
**당시 남은 한계 (10/16 에 정면으로 다룸)**

* 조회할 때 만료시키는 방식이라 누군가 주문 상세를 열어야만 취소된다. 결제창을 닫고 떠난 주문은 재고를 계속 잡고 있다.
* 만료 처리에 잠금이 없다. 결제 승인을 기다리는 사이 상세 조회가 끼어들면 "재고를 되돌린 뒤 결제완료로 덮어쓰는" 이중 판매가 생길 수 있다.
* 10/16 에 "30분 만료는 주문 상세 조회 때만 돌았다"고 짚고, 승인 때 주문을 잠가 이중 판매를 막고(실제 DB 테스트로 재현), 방치 주문을 주기적으로 치우는 작업(스위퍼)을 넣고, "결제됐는지 불확실하면 취소하지 않는다"는 원칙을 세운다([10.16 일지](../2026-10/2026-10-16.md)).
* 작업 7은 재고 수정 요청끼리 줄을 세울 뿐이다. 관리자 폼은 "5개" 같은 최종 값을 보내므로, 폼을 열어 둔 사이 주문이 들어와 4개가 됐어도 저장하면 다시 5개가 된다. 잠금으로는 못 막는 종류라서 버전 칸(JPA `@Version` 같은 낙관적 잠금)이나 "몇 개 늘리기/줄이기" 방식이 필요하다.
{% endhint %}

{% hint style="success" %}
**이날의 작업 방식**

실제 버그(그래프 500)를 고치다가 가짜 DB 테스트로는 쿼리 구조 버그를 못 잡는다는 걸 알았고, 그 김에 결제 흐름 전체를 동시성 관점에서 점검해 문서로 남겼다. 그리고 작업마다 "실패하는 테스트 → 구현 → 문서 체크"를 저장 기록으로 남겼다. 문서를 "다음에 이어서 할 수 있게" 쓴 건 AI 도구와의 대화가 끊겨도 이어 가려는 장치로 보인다. 이 방식은 7/10 의 두 번째 점검 문서로 이어진다.
{% endhint %}
