### 이날을 한 문단으로

8/31 에 만들어 놓고 저장만 안 해 둔 토스 결제 작업을 한꺼번에 올린 날이다. 그때까지 rekit 은 무통장입금만 받았는데, 관리자가 입금을 확인하고 "결제완료"로 바꿔 줄 방법이 없어서 주문이 계속 결제대기로 쌓이기만 했다. 그래서 주문서에 토스 결제창을 붙이고, 결제를 마치거나 실패했을 때 돌아오는 화면 두 개를 새로 만들었다. 서버 쪽은 8/31 에 바꿔 둔 웹훅 처리(토스가 보내는 결제 알림을 그대로 믿지 않고 토스에 다시 물어보는 방식)와 결제 안내 문서 두 개가 같이 올라갔다. 밤에는 내 PC 에서 토스 테스트 결제를 끝까지 눌러 볼 수 있게 개발 서버에 작은 중계 장치를 달았다. 결제를 취소하고 다시 시도하면 재고 1개짜리 상품을 못 사는 문제, 완료 화면에 카드사 이름 대신 숫자 코드가 찍히는 문제는 이날 그대로 남았다.

8/31 노트는 저장 전 상태에서 쓴 것이라, 이 노트에는 그 작업이 실제로 어떤 모양으로 저장됐는지와 8/31 에 없던 화면 완성본·중계 장치만 적는다. 웹훅 방식을 바꾼 이유와 토스 키 정리는 [08.31 일지](../2026-08/2026-08-31.md) 에 있다.

### 1. 주문서에 토스 결제창 붙이기

지금까지는 주문을 넣으면 입금 계좌 안내만 나왔고, 관리자 주문 화면에는 결제대기 탭도, 입금 확인 버튼도 없었다. 5/5 에 결제를 무통장입금 전용으로 바꾼 뒤([05.05 일지](../2026-05/2026-05-05.md)) 7/1 에 주문을 서버와 연결하면서 생긴 빈틈이다. 8/14 에 결제대행사를 토스로 정했고([08.14 일지](../2026-08/2026-08-14.md)), 서버의 결제 준비·승인 기능은 6/20 부터 있었으니 화면만 붙이면 되는 상태였다. 이날 주문서에 토스 결제창을 넣어서, 구매자는 입금을 기다리지 않고 그 자리에서 카드나 간편결제로 결제를 끝낼 수 있게 됐다. 화면은 공개 키로 결제창만 열고, 실제 승인은 비밀 키를 가진 서버가 대신 한다는 8/31 원칙을 그대로 따랐다.

결제는 이런 순서로 돈다. 주문서는 장바구니 내용을 다 불러온 다음 토스 결제수단·약관 칸을 그린다. \[결제하기]를 누르면 서버에 결제대기 주문이 만들어지고 이때 재고가 1 줄어든다. 이어서 서버에 결제 준비를 요청해 서버가 계산한 최종 금액을 받아 결제창 금액을 다시 맞추고, 토스 결제창으로 넘어간다. 결제가 성공하면 "결제 확인 중" 화면으로 돌아와 서버가 토스에 승인을 요청하고, 성공하면 완료 화면에 "신한카드 1234 · 일시불" 같은 줄이 나온다. 결제창에서 취소하거나 실패하면 실패 안내 화면으로 오는데, 승인 전이라 돈은 빠지지 않는다.

화면마다 바뀐 점은 다음과 같다.

* 주문서: "계좌이체(무통장입금) — 영업일 9\~18시 평균 2시간 내 입금 확인" 안내 상자를 지우고 결제창 자리 두 칸을 넣었다. 버튼 이름은 "주문하기"에서 "결제하기"로 바꿨고, 결제창이 준비되기 전엔 누를 수 없으며 누르면 "결제창을 여는 중…"이 뜬다. 결제창을 못 불러오면 "결제 수단을 불러오지 못했어요. 새로고침 후 다시 시도해 주세요."
* 결제 후 돌아오는 화면(새로 만듦): 토스가 넘겨준 결제 번호·주문번호·금액 중 하나라도 없으면 홈으로 보낸다. 승인에 성공하면 그때 장바구니에서 산 상품을 빼고 완료 화면으로 간다. 서버가 토스 응답을 못 받아 결과가 애매하면 "결제 확인 중이에요"와 주문내역 링크를, 주문이 없으면 "주문 정보를 찾을 수 없어요"를, 그 밖의 실패는 서버 메시지와 "다시 결제하기"를 보여 준다.
* 결제 실패 화면(새로 만듦): 사용자가 취소했으면 "결제를 취소하셨어요", 중간에 끊겼으면 "결제가 중단됐어요"를 띄우고 토스 오류 코드는 작게 표시한다. "아직 결제 승인 전이라 금액이 청구되지 않았어요." 아래에 장바구니로 / 다시 결제하기 버튼이 있다.
* 주문 완료: 입금 계좌 안내 카드를 뺐다. 아직 결제대기면 "결제를 확인하고 있어요 / 잠시 후 배송이 시작됩니다", 결제가 끝났으면 "결제가 완료됐어요". 배송 방식 줄 자리에 "카드사 끝4자리 · N개월/일시불"을 먼저 보여 준다.

장바구니를 비우는 시점도 바꿨다. 전에는 주문을 만들자마자 비웠는데 이제는 승인에 성공한 뒤에 비우기 때문에, 결제를 취소해도 장바구니가 그대로 남는다. 완료 화면에 카드 정보를 넘길 때는 승인 결과를 브라우저 탭 저장소에 잠깐 넣어 두고 꺼내 쓰는데, 주문번호가 같고 10분이 안 지났을 때만 쓰고 브라우저가 저장을 막으면 그냥 건너뛴다.

그 밖의 세부도 적어 둔다. 토스에 넘기는 고객 구분값은 로그인했으면 `rekit-아이디`(50자까지), 아니면 익명이다. 결제창에서 고른 수단은 서버가 아는 다섯 가지(카드·계좌·토스페이·네이버페이·카카오페이)로 바꿔 보내고, 계좌이체와 가상계좌는 계좌로, 모르는 값은 카드로 처리한다. 주문번호는 RK-YYMMDDNNNN 형식이 토스 규칙(6\~64자)에 맞아서 그대로 쓰고, 주문 이름은 첫 상품명 40자에 " 외 N건"을 붙인다. 고객 이메일·이름과 휴대폰(숫자만, 8\~15자리일 때만)도 보낸다. 화면 코드에는 공개 키만 두고 설정이 없으면 토스 문서용 공개 테스트 키를 쓴다. 코드 주석에도 "비밀 키는 빌드 결과물에 그대로 박히니 화면에 절대 두지 않는다"고 적었다. 결제 관련 서버 호출 코드는 구매자 화면이 쓰니까 관리자 폴더 밖으로 옮겼고, 서버가 "결과 확인 중"으로 답하면 다시 시도하지 않고 안내만 한다. 최종 상태는 웹훅으로 반영되기 때문이다. 결제 후 돌아오는 두 화면은 결제 단계 화면이라 머리만 있고 꼬리·하단 탭은 없는 틀로 뜬다. 화면 쪽 할 일 문서에서는 결제 상태를 🟡에서 🟢로 올리고, "결제대행사 다시 쓸지"(D8)를 결정 완료로 바꾸고, "관리자 입금 확인 처리" 항목을 지운 자리에 "토스 연동 후 남은 것" 네 가지를 적었다.

{% hint style="success" %}
**금액은 세 번 맞춘다**

처음엔 화면에서 계산한 합계로 결제창을 띄우고, 결제 직전에 서버가 계산한 금액으로 덮어쓰고, 승인할 때 서버가 DB 의 주문 금액과 토스가 돌려준 금액을 한 번 더 대조한다(7/6 에 정한 "결제대행사에는 서버 금액을 보낸다"). 누가 주소창의 금액을 고쳐도 마지막 대조에서 막힌다. Spring 으로 치면 컨트롤러가 받은 금액을 믿지 않고 서비스가 DB 값으로 다시 검사하는 것과 같다.
{% endhint %}

{% hint style="info" %}
**화면과 서버의 약속 대조 (원본 확인)**

결제 준비(주문번호·결제수단), 승인 요청(결제 번호·주문번호·금액), 승인 응답(주문번호·상태·결제 시각·카드사·끝 4자리·할부)의 필드 이름이 양쪽에서 전부 같다. 6/26 장바구니나 7/3 관리자 검색 때처럼 이름이 어긋난 곳은 없었다.
{% endhint %}

{% hint style="danger" %}
**결제를 취소하고 다시 결제하면 재고 1개짜리 상품을 못 산다 (9/3 시점)**

주문은 결제창을 열기 전에 만들어지고 그때 재고를 줄인다. 결제창에서 취소하면 그 결제대기 주문이 남아서 재고를 계속 붙잡는다. 30분 뒤 만료시키는 장치는 있지만 누가 그 주문을 조회할 때만 돈다. "다시 결제하기"는 장바구니로 새 주문을 만들기 때문에 재고가 1개인 상품(폐업 가전은 대부분 한 점뿐)은 재고 없음 오류가 난다. 8/13 이후로는 재고가 0 이 되면 자동으로 품절 처리되니 목록에서도 사라진다. 예를 들어 냉장고 한 대를 결제하다 창을 닫고 다시 결제하기를 누르면 "재고가 없습니다"가 뜨고 목록에서도 그 냉장고가 안 보인다. 화면 할 일 문서에 "결제 취소·중단 때 남은 결제대기 주문 정리, 서버에서 만료시킬지 화면에서 취소할지 정해야 함"이라고 적어 두기만 했다. 10/16 에 서버(방치 주문 자동 정리)와 화면(결제창 이탈 시 바로 취소) 양쪽에서 고쳤다. [10.16 일지](../2026-10/2026-10-16.md)
{% endhint %}

{% hint style="danger" %}
**완료 화면에 카드사 이름 대신 숫자 코드가 보인다 (지금도)**

서버는 토스가 준 카드사 코드(신한이면 "41" 같은 두 자리 숫자)를 6/20 부터 그대로 저장하고 있고, 11/16 현재도 마찬가지다. 화면은 이 값을 그대로 붙이니 "신한카드 1234"가 아니라 "41 1234 · 일시불"로 보인다. 코드를 이름으로 바꾸는 곳이 화면에도 서버에도 없고, 결제 완료 메일의 결제수단 줄도 같은 값을 쓴다. 같은 날 밤 만든 중계 장치(3번)만 코드를 이름으로 바꾸는 표를 갖고 있어서, 그걸로 시험하면 "신한카드"로 멀쩡하게 보인다는 게 함정이다.
{% endhint %}

{% hint style="warning" %}
**끝 4자리에 `*` 가 섞일 수 있음 (추정)**

서버는 토스가 준 카드번호 문자열의 마지막 네 글자를 그대로 쓴다. 토스는 카드번호 일부를 가려서 주기 때문에 형식에 따라 끝자리에 `*`가 들어갈 수 있다. 실제 응답을 남긴 자료가 없어서 확인하지 못했다.
{% endhint %}

이날 저장한 테스트는 없다. 클릭으로 시험하는 순서는 같은 날 밤 결제 시험 안내 문서(3번)에 정리했다. 실제 서비스 반영 기록도 없다.

### 2. 서버 쪽 웹훅 처리와 결제 안내 문서

토스는 결제 상태가 바뀌면 rekit 서버로 웹훅을 보낸다. 이 알림은 남이 흉내 낼 수 있어서, 8/31 에 알림 내용은 믿지 않고 토스에 직접 다시 조회한 결과로 처리하도록 바꿔 뒀다(8/31 노트 1번). 이날 그 코드가 그대로 저장됐다. 저장본을 8/31 노트와 대조해서 같다는 걸 확인했고, 여기엔 8/31 에 안 적힌 것만 남긴다.

토스 연결부의 코드 설명이 "토스 임시 대역, 나중에 실제 호출로 교체 예정"에서 "토스 API 를 직접 호출"로 바뀌었다. 6/20 이후 처음으로 임시 꼬리표가 떨어진 셈이다. 토스 응답은 10초까지 기다리고, 승인 응답에 승인 시각이 빠져 있으면 서버 오류(500)를 내던 것을 결제 실패로 처리하게 했다. 가짜 결제 모듈은 조회하면 늘 완료, 카드사 "개발카드", 끝 4자리 "0000"을 돌려준다.

상태 처리도 조금 늘었다. 토스 쪽이 준비·진행 중·입금 대기 상태면 기록만 남기고 기다리고, 이미 결제완료인 건에 취소 아닌 다른 상태가 오면 경고만 남기고 무시한다. 웹훅이 승인보다 먼저 도착하는 경우에는 조회 결과로 카드 정보 다섯 가지를 채워 넣는다. 토스에 다시 물어보다 실패하면 서버가 502 로 답하고, 그러면 토스가 알림을 다시 보낸다.

API 문서에서는 웹훅 받는 주소를 실제 경로(`/payments/webhooks/toss`)로 고쳤다. 5/2 에 쓴 문서와 실제 주소가 원래부터 달랐던 것도 이때 같이 바로잡혔다. "서명 검사 필수"라고 돼 있던 설명은 "인증 없음(대신 토스에 다시 조회)"으로 바꾸고 상태별 처리를 다섯 줄로 적었다. 테스트는 웹훅 4건, 토스 연결부 3건(응답 읽기, 200 이 아닌 응답, 네트워크 오류)이 새로 들어갔고 통합 테스트도 손봤다.

문서는 두 개, 합쳐서 850줄쯤 새로 썼다. 하나는 "결제 개발 현황 — 코드 익히기 안내"(496줄)로, 30초 요약부터 흐름 세 가지(정상 결제, 승인이 실패했는데 웹훅이 대신 도착하는 경우, 아직 미완성인 취소·환불), 관련 파일 11개의 지도(아무도 안 쓰는 파일 하나 표시), 상태 변화표, 동시 요청·중복 요청 처리, DB 구조, 테스트 지도, 가짜·미완성 부분, 토스 문서 링크, 용어집까지 담았다. 다른 하나는 "토스 실연동 작업 안내"(353줄)다. "하루에 작업 하나씩"을 원칙으로 작업마다 왜 하는지, 무엇을 바꾸는지, 어떻게 확인하는지, 언제 끝난 걸로 보는지를 적고 테스트부터 쓰게 했다. "규격 조사 결과 (2026-08-31 — 다시 안 찾아도 됨)"라는 절이 따로 있고, 작업 1·2 는 끝, 3\~8 은 남았다. 시작 전에 정할 것으로 가상계좌와 부분취소를 들었는데, 권장안은 둘 다 미루고 카드·간편결제와 전액 취소만으로 먼저 열자는 것(대략 6일치)이었다.

### 3. 내 PC 에서 쓰는 결제 연습용 중계 장치 (23:44)

화면 개발 서버(Vite)에 작은 중계 기능을 붙였다. 결제 준비와 결제 승인 요청만 가로채서 개발 서버가 직접 토스 테스트 환경에 승인을 요청하고, 나머지 요청은 원래 서버로 그대로 넘긴다. 이걸로 내 PC 에서 토스 테스트 결제창부터 승인, 완료 화면까지 끝까지 눌러 볼 수 있게 됐다. 개발 서버를 띄울 때만 켜지고 실제 서비스 빌드에는 들어가지 않는다. 장치 설명에는 "서버에 결제 기능이 아직 없어도 화면 결제 흐름을 처음부터 끝까지 확인 가능", "비밀 키가 브라우저 쪽 코드에 안 들어감"이라고 적었다.

{% hint style="info" %}
**추정 — 서버에 결제 기능이 있는데 왜 중계 장치를 만들었나**

서버의 결제 준비·승인 기능은 6/20 부터 있었고 8/31 인수인계 문서도 "없다"를 "있음"으로 고쳐 놨다. 그런데 장치 설명은 "서버에 결제 기능이 아직 없거나"를 전제로 한다. 화면 쪽 대화가 인수인계 이전의 가정을 들고 있었거나, PC 의 서버가 가짜 결제 모듈로 설정돼 있어서 진짜 토스 결제창과 승인을 끝까지 돌릴 수 없으니 화면 쪽에서 우회로를 만든 것으로 보인다.
{% endhint %}

결제 준비 요청이 오면 실제 서버에서 그 주문을 로그인 정보 그대로 조회해 총액을 읽어 돌려주고, 실패하면 기본 금액 1,000원을 쓴다. 승인 요청이 오면 개발 서버가 비밀 키로 토스 승인 API 를 직접 부른다. 토스가 서버 오류를 내면 "결과 확인 중"(502)으로, 거절하면 토스 오류 코드와 메시지(422)로 답하고, 성공하면 rekit 서버 응답과 같은 모양으로 바꿔 준다. 이때 카드사 코드를 이름으로 바꾸는 표(20개)를 쓰고, 간편결제면 결제사 이름을 넣는다. 이 장치는 개발 설정에 토스 테스트 비밀 키가 있을 때만 켜지고, 연결할 서버 주소(기본은 내 PC 8000번)와 기본 금액도 설정으로 바꿀 수 있다.

결제 시험 안내 문서(69줄)도 새로 썼다. 방법 A 는 서버를 진짜 토스 테스트 키로 설정하고 화면 설정에서는 테스트 비밀 키 줄을 지우는 것이다(그 줄이 있으면 중계 모드가 켜진다). 방법 B 는 중계 장치를 쓰는 것인데, 가짜 결제 번호로 승인을 보냈을 때 토스가 "결제 세션 없음"(422)으로 답하면 비밀 키 인증은 통과한 것이니 정상이라고 보는 확인법을 같이 적었다. 테스트 카드 번호로 결제하고, 결제창 취소 후 실패 화면을 확인하는 클릭 시험 5단계도 들어 있다.

{% hint style="info" %}
**설정 이름 앞에 `VITE_` 가 붙느냐가 경계선**

Vite 는 이름이 `VITE_` 로 시작하는 설정값만 브라우저용 코드에 박아 넣는다. 비밀 키를 `VITE_` 없는 이름으로 두고 개발 서버 설정 파일에서만 읽으면 개발 서버 프로그램 안에만 머물고 브라우저로는 나가지 않는다. Spring 으로 치면 `application.yml` 의 서버 전용 설정과 프론트로 내려보내는 공개 설정을 나누는 것과 비슷하다.
{% endhint %}

{% hint style="warning" %}
**중계 장치의 한계 (문서에 적어 둠)**

승인에 성공해도 rekit 서버의 주문은 결제대기 그대로다. 중계 장치는 토스 승인만 받고 rekit DB 의 결제·주문은 건드리지 않으니, 완료 화면엔 카드 정보가 보여도 주문내역에는 "결제 대기"로 나온다. 또 1번의 카드사 숫자 코드 문제가 이 장치로 시험하면 가려진다.
{% endhint %}
