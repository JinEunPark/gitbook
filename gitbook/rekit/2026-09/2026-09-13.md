### 이날을 한 문단으로

### 1. 첫 실제 매물 6개 (대화 11:05\~11:18)

팔려는 물건 사진을 주면서 👤 "우리 벡엔드 데이터 양식에 맞춰서 해당 물건들 데이터를 만들어줘"라고 했다. 관리자 상품 등록 화면이 받는 항목을 기준으로 정리했는데, 6개 모두 폐업 매장 주방에서 나온 업소용 설비였다. 프로젝트 소개에 적어 둔 "영업용 가전이 많다"는 이야기가 첫 실제 재고에서 그대로 나타난 셈이다.

### 2. 토스 실결제 계약 심사 메일 (대화 11:19\~11:21)

테스트 결제가 아닌 실제 결제를 받으려면 토스와 계약하고 카드사 심사를 통과해야 한다. 토스가 보낸 심사 메일을 붙여 넣고 회신 초안과 준비할 것을 정리했다. 심사가 보는 건 서버 코드가 아니라 사이트에 실제로 보이는 정보라서, 빠진 것을 찾아 저녁에 화면 문구를 고치는 것으로 이어졌다.

메일은 크게 두 부분이었다. 첫째는 회신해야 할 질문으로, 결제할 상품 주소, 환불정책 주소, 상품 설명, 한 번에 결제되는 최고 금액, 비회원 구매가 안 되면 심사용 테스트 계정("소셜 로그인 테스트 계정은 사용 불가"), 최대 배송 기간("6주를 넘으면 입점 불가, 상품 페이지에 명확히 적을 것"), 앱 링크, 직접 연동 여부였다. 둘째는 카드사 심사를 위한 홈페이지 준비사항으로, 결제 가능한 상품 1개 이상, 사이트 하단 사업자 정보 다섯 가지(상호·대표자·사업자번호·주소·유선 전화번호, "사업자등록증과 완전히 일치"), 결제창 연동, 예시와 같은 구성의 결제 경로 설명 자료(PPT)였다.

11:21 에 받은 초안과 점검 결과는 이렇다.

| 항목       | 초안 또는 상태                                                               |
| -------- | ---------------------------------------------------------------------- |
| 환불정책 주소  | 이용약관 제6조나 이용 안내 페이지. "도착 후 7일 이내 동작 불량 … 전액 환불"이 서버의 환불 기간 설정과 같다      |
| 상품 설명    | "폐업한 매장의 영업용 가전을 매입해 상태 점검 후 재판매 … 등급(A/B/C) … 토스페이먼츠 단건 결제"           |
| 최고 금액    | 직접 정해야 함. 대형 냉장고를 생각하면 300만 원 정도로 여유 있게 잡자는 권장(넘으면 재심사)                |
| 테스트 계정   | 개발용 시드 계정은 내 PC 에만 있으니 운영 DB 에 심사 전용 이메일 가입 계정을 만들 것                   |
| 배송 기간    | 정기결제는 없음. 상품 상세 화면에 배송 예정 기간 문구가 안 보여서 추가 권장                           |
| 앱, 직접 연동 | 앱 없음. 직접 연동은 "예, 자체 서버(FastAPI)에서 토스 API 를 직접 호출"                      |
| 사업자 정보   | 네 가지는 8/30 부터 하단에 있음. 유선 전화번호가 빠져 있음                                   |
| 결제 경로 자료 | 목록, 상세, 로그인, 장바구니·주문서, 토스 결제창, 완료까지 6단계 실제 화면 캡처가 필요. "내가 대신 캡처는 못 해줘" |

정리하면 당장 할 일은 세 가지였다. 운영 사이트에 테스트 구매자 계정과 상품 최소 1개, 상세 화면 배송 기간 문구, 최고 금액 결정.

{% hint style="warning" %}
**회신 초안의 도메인이 틀렸다**

초안의 주소가 전부 `https://rekit.kr/…`였고, 근거로 API 문서에 적힌 `rekit.kr`을 들었다. 실제 운영 도메인은 `rekit.co.kr`(가비아)이다. 5/2 API 문서에 가정으로 적은 주소가 남아 있다가 심사 회신 초안까지 흘러간 것이다([05.02 일지](../2026-05/2026-05-02.md)). 회신할 때 고쳐서 보냈는지는 기록이 없다.
{% endhint %}

저녁 20:25 에 👤 "지금 운영기 DB 에 테스트 계정 있나 확인되나"라고 물었다. Claude 가 운영 서버에 SSH 로 접속하려 했는데, 자동 모드에서는 운영 데이터 읽기로 분류돼 승인이 필요하다며 멈췄다. 대신 세 가지 방법을 제시했다. 직접 DB 에 들어가 보기, 읽기 전용 작업을 허용하기, 그리고 권장안으로 심사 전용 계정을 새로 만들기("기존 계정이 있어도 심사 중에 상태가 바뀌면 안 되니까")다. 이 대화는 여기서 끝나고, 6분 뒤부터 다른 대화에서 프론트 저장 세 개가 이어진다.

{% hint style="info" %}
**배운 점 — 심사는 코드가 아니라 화면에 보이는 것을 본다**

결제대행사 심사가 요구한 건 API 가 아니라 사이트에 표시된 정보(사업자 정보, 환불정책, 배송 기간, 실제 상품, 결제 경로 캡처)였다. 8/26\~28 소셜 로그인 검수, 8/30 구글 로그인 게시 조건에 이은 세 번째 심사 대응이었고, 이번에도 고친 건 대부분 정적 페이지와 하단 문구였다.
{% endhint %}

### 3. 통신판매업 신고번호와 환불 규정 (0.0.3)

카드사 결제 경로 심사에 대비해서 사이트 하단 사업자 정보에 통신판매업 신고번호를 한 줄 넣고, 이용약관 제6조(환불)를 기간과 비용 부담이 분명하게 보이도록 고쳤다. 그 전까지 약관은 "대형 가전의 특성상 단순 변심에 의한 반품은 제한될 수 있으며 … 회수 비용이 차감될 수 있습니다" 한 문단뿐이라, 구매자가 언제까지 무엇을 돌려받을 수 있는지 알 수 없었다.

하단 사업자 정보는 상호, 대표자, 사업자번호 다음에 통신판매업 신고번호가 들어가고 주소가 이어지는 다섯 줄이 됐다(번호 값은 노트에 적지 않는다). 8/28 에 임시 값으로 채울 때는 유선 전화번호 줄이 있었는데, 8/30 실제 정보로 바꾸면서 빠진 상태 그대로다. 대화에서 지적된 이 빈칸은 10/21 에 다시 채웠다.

약관 제6조는 네 개 항목으로 바뀌었다.

1. 단순 변심에 의한 환불·교환은 수령일을 포함해 7일 이내에 고객센터나 문의하기로 요청한 경우에만 된다.
2. 7일이 지났거나 사용 흔적·오염·구성품 누락이 있으면 제한될 수 있다.
3. 단순 변심이면 왕복 배송비는 이용자가 낸다.
4. 제5조(도착 후 7일 이내 동작 불량)에 따른 환불은 배송비까지 포함해 전액 돌려주고 이용자 부담은 없다.

{% hint style="info" %}
**왜 구체화했나**

"단순 변심 반품은 제한될 수 있으며"라는 옛 문구는 전자상거래법 제17조(받은 날부터 7일 안에는 청약 철회 가능)와 부딪칠 수 있는 애매한 표현이었다. 심사 메일이 환불정책을 확인할 주소를 요구하니, 기간과 비용을 누가 내는지를 분명히 적은 것으로 보인다. 저장할 때도 "심사 대비"라고 적었다.
{% endhint %}

{% hint style="warning" %}
**약관과 실제 환불 기능의 차이**

### 5. 마이페이지 첫 화면을 실제 데이터로 (0.2.0)

마이페이지 첫 화면은 5/1\~5/2 에 가짜 데이터로 만든 모습 그대로였다([05.02 일지](../2026-05/2026-05-02.md)). 6/27\~7/1 에 주문·찜·배송지 데이터는 서버와 연결됐지만 이 화면은 그 데이터를 가져다 쓰지 않아서, 넉 달 동안 누가 로그인하든 "결제완료 1 · 준비중 2 · 배송중 1 · 배송완료 5", "배송중 · RK-26050001 · 삼성 양문형 냉장고 384L 외 2건 · 5월 3일(토) 도착 예정", "관심상품 12", "배송지 2", "본인인증 인증완료"가 보였다. 이날 이 숫자들을 로그인한 사람의 실제 주문·찜·배송지·본인 확인 상태로 바꿨다.

{% hint style="info" %}
**추정 — 왜 이날 발견했나**

심사용 테스트 계정(2번)으로 로그인해 결제 경로 화면을 캡처하다가, 아무것도 안 한 계정인데 주문과 관심상품 숫자가 찍혀 있는 걸 본 것 같다. 20:25 에 테스트 계정 이야기를 하고 21:26 에 이 수정을 저장했다.
{% endhint %}

주문 상태 네 칸(결제완료·준비중·배송중·배송완료)은 내 주문을 상태별로 세서 보여 준다. 칸을 누르면 가는 주소도 고쳤다. 전에는 `/my/orders?status=결제완료`처럼 한글 이름을 붙였는데, 주문 목록 화면은 영문 상태 값(`PAID` 등)으로 거르기 때문에 이 링크를 누르면 언제나 빈 목록이 나왔다. 이제는 영문 값으로 넘긴다.

"진행 중인 주문" 카드는 결제대기·결제완료·준비중·배송중인 주문 가운데 첫 번째를 보여 주고, 그런 주문이 없으면 카드 자체를 숨긴다. 상태 배지, 주문할 때 저장한 첫 상품 사진, "외 N건"을 표시하고, 아무 동작도 없던 주문상세 버튼이 실제로 그 주문 상세로 가게 했다. 가짜 도착 예정일 줄은 지웠다. 메뉴 옆 배지도 찜 개수, 배송지 개수, 본인 확인 여부("인증완료" 또는 "미인증")를 실제 값으로 보여 준다. 세 데이터는 로그인 상태면 처음 쓰일 때 스스로 서버에서 불러오는 구조라 화면에서 따로 불러올 필요가 없었다.

{% hint style="warning" %}
**주문 개수는 최근 20건 기준**

주문 목록을 첫 페이지 20건만 받아 오기 때문에, 주문이 20건을 넘는 사람은 상태별 숫자가 실제보다 적게 나온다. 지금 규모에서는 문제가 안 된다.
{% endhint %}
