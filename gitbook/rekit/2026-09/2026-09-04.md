### 1. 토스 테스트 키를 rekit 전용 키로

화면 설정에 기본값으로 박혀 있던 토스 공개 키를, 토스 문서에 실린 모두의 공용 데모 키에서 rekit 테스트 계정 키로 바꿨다. 공개 키는 원래 공개해도 되는 값이라 코드에 두고, 운영 키는 서버 설정으로 넣게 주석을 달았다(8/31 노트 4번). 공용 데모 키는 호출 횟수 제한이 있고 데이터가 주기적으로 지워져서, 내 상점 장부에 결제가 찍혀야 제대로 확인했다고 할 수 있다. 다음 날 시험 목록에도 "개발자센터 결제내역에 승인 1건이 보이면 내 키가 정상"이라는 항목이 있다.

결제 시험 안내 문서에 그대로 적혀 있던 키 두 개(공개 키와 데모 비밀 키)는 지우고 "토스 개발자센터 → API 키에서 발급. 비밀 키 값은 이 문서·저장소에 적지 않는다"로 바꿨다. 키 짝이 안 맞으면 `INVALID_API_KEY` 오류가 난다는 설명도 붙였다. 서버 할 일 문서에는 "내 계정 테스트 키 설정 완료, 설정 파일은 저장소에서 제외"라고 적었는데 키 앞부분 몇 글자가 같이 적혔다. 8/14 Octomo 키 때와 같은 습관이고, 비밀인 부분은 아니다.

### 3. 주문 취소·환불 때 토스에 실제 취소 요청

이 전까지는 구매자나 관리자가 결제된 주문을 취소하거나 환불하면 DB 의 주문 상태만 바뀌고 토스에는 아무 요청도 가지 않았다. 화면에는 "취소됨"이 떠도 카드 결제는 그대로 살아 있어서 돈이 돌아가지 않는 상태였다. 6/24 환불 기능을 만들 때부터 그랬고, 7/10 테스트 계획에서도 풀리지 않은 채 8/31 작업 안내 문서에 작업 3·4 로 잡혀 있던 일이다([08.31 일지](../2026-08/2026-08-31.md)). 이날부터는 취소·환불 시 토스 결제 취소 API 를 먼저 부르고, 성공해야 재고 복구와 상태 변경이 일어난다.

토스 연결부에 취소 기능을 새로 넣었다. 금액을 안 주면 전액, 주면 그만큼 부분 취소를 요청하고, 같은 요청이 네트워크 재시도로 두 번 가도 한 번만 취소되도록 요청마다 고유한 표시를 붙인다(멱등 처리, "결제 번호 + 금액 또는 전액"으로 만든 값). 토스가 거절하면 토스의 오류 코드와 메시지를 담아 결제 실패로 올리고, 네트워크가 끊기면 "취소됐는지 알 수 없음"으로 구분한다. 이 오류 변환 함수는 승인에도 쓸 수 있게 만들어 뒀지만 승인 쪽 적용은 나중 작업(작업 5)으로 넘겼다. 토스 쪽 상태가 부분 취소이거나 남은 금액이 있으면 결제를 "부분 취소"로, 아니면 "취소"로 기록하고 취소 시각을 남긴다.

결제 취소 처리는 그 주문의 결제 기록을 행 잠금으로 읽어 결제완료인 건을 하나 찾는다. 없으면 아무 일도 하지 않고 끝나는데, 결제 전이거나 이미 취소된 경우라서다. 토스 결제 번호가 없으면 오류를 내고, 있으면 토스에 취소를 요청한 뒤 상태를 바꾼다. 이걸 세 군데에서 부른다.

* 구매자 주문 취소: 결제완료나 상품 준비 중인 주문이면 "구매자 주문 취소" 사유로 토스 취소를 먼저 하고, 그다음 재고를 돌려놓고 주문을 취소 상태로 만든다.
* 구매자 환불 요청(배송 완료 주문만): "구매자 환불 요청" 사유로 토스 취소 후 주문을 환불 상태로 바꾼다. 배송까지 끝난 실물이라 재고는 돌려놓지 않는다.
* 관리자 주문 취소: 취소 가능한 상태(결제대기·결제완료·준비 중) 중 결제된 두 상태면 관리자가 적은 사유(없으면 "관리자 주문 취소")로 토스 취소를 한다.

주문 처리와 결제 취소가 같은 DB 세션, 즉 한 트랜잭션 안에서 돌도록 묶었다. 주문 처리 쪽에서 결제 처리를 안 넘기면 토스 취소를 건너뛰게 해 두었는데, 토스 연동을 검사하지 않는 단위 테스트용이고 실제 서버에서는 늘 넘긴다. 테스트는 18개 늘었다. 토스 연결부 6개(전액 취소, 부분 취소 금액 전달, 중복 방지 표시, 거절 메시지 전달, 네트워크 오류, 승인 상태가 완료가 아니면 거절), 결제 취소 처리 5개(정상, 부분, 결제 없음, 토스 번호 없음, 거절 전달), 그리고 주문·관리자 연동과 되돌리기 시험이다.

가상계좌는 받지 않기로 했다. 가상계좌는 승인 때 상태가 "입금 대기"로 오는데, 이걸 결제완료로 처리하면 돈이 들어오기도 전에 주문이 확정된다. 그래서 승인 결과가 "완료"가 아니면 거절하게 했다.

{% hint style="success" %}
**토스 먼저, DB 나중**

취소 순서를 "토스 취소, 성공하면 재고 복구와 상태 변경"으로 잡고 한 트랜잭션 안에서 돌렸다. 토스가 거절하면 예외가 그대로 올라가서 주문 취소 자체가 되돌려진다. 순서가 반대였다면 주문은 취소됐는데 돈은 안 돌아간 상태가 남을 수 있다. Spring 의 `@Transactional` 서비스 안에서 외부 결제 API 를 먼저 부르고 실패하면 `RuntimeException` 으로 전부 롤백하는 것과 같다.
{% endhint %}

{% hint style="warning" %}
**반대 방향의 틈 — 토스 취소는 됐는데 DB 저장이 실패하면**

토스 취소가 성공한 뒤 DB 에 반영하기 직전에 오류가 나면, 돈은 돌려줬는데 주문은 결제완료로 남는다. 외부 호출은 되돌릴 수 없어서다. 나중에 토스가 보내는 취소 웹훅이 와서 맞춰 줄 수는 있는 구조지만(5번), 따로 보정하는 코드는 없다.
{% endhint %}

10초 뒤 저장한 문서 변경에서는 작업 안내 문서의 작업 1\~4 를 완료로 표시하고 가상계좌 작업(작업 7)은 "안 함 (2026-09-04 결정)"으로 접었다. 8/31 에 정할 거리로 남겨 둔 두 가지 중 가상계좌는 안 하기로, 부분취소는 "기능은 있지만 주문·관리자 화면은 전액 취소만 부르고, 상품별 재고를 어떻게 돌릴지는 미정"으로 정리됐다. API 문서에는 주문 취소(배송 시작 이후는 환불 절차로), 환불(부분 환불·사진 첨부·운영자 승인 단계는 2단계로 미룸), 결제 취소 절을 새로 썼다. 결제 준비·승인 절은 여전히 옛 설계 그대로라 작업 6 으로 남겼다. 결제 개발 현황 문서의 "주문 취소·환불 때 토스 취소를 안 부름" 항목에는 2026-09-04 해결 표시를 했다.

### 5. 웹훅 금액 대조와 토스 비밀 키 필수화 (00:44)

👤 "PAYMENT\_STATUS\_CHANGED 이거 배포하면 바로 연동될수 있게 만들어줘"라는 요청에 웹훅 코드를 훑어보니 기능은 다 있었는데 빈 곳이 하나 있었다. 승인 요청 쪽은 금액을 대조하는데, 웹훅으로 결제완료가 될 때는 금액을 보지 않았다. 화면에서 돌아오는 승인 요청이 유실되면 웹훅이 결제를 확정하는 유일한 길이 되니 같은 검사가 필요했다. 그래서 웹훅으로 결제완료 처리를 하기 직전에, 토스에서 다시 조회한 결제 금액이 rekit 의 결제 금액과 다르면 오류 기록만 남기고 상태를 바꾸지 않게 했다. 금액이 다르다는 건 다른 거래의 결제 번호라는 뜻이고 다시 보내 와도 결과가 같으니, 토스에는 200 으로 답해서 재전송을 멈추게 했다. 테스트를 먼저 써서 실패를 확인하고(00:35) 코드를 맞춘(00:36) 순서가 대화에 남아 있다.

웹훅을 받을 때마다 "토스 웹훅 수신 — 이벤트, 결제 번호, 토스 쪽 상태"를 기록하게 했다. 나중에 문제가 생겼을 때 웹훅이 아예 안 온 건지, 왔는데 처리가 안 된 건지 기록으로 가려내기 위해서다.

토스 비밀 키 설정도 비워 둘 수 있던 것을 필수로 바꿨다. 대화에서는 "비워 둘 수 있게 돼 있어서 '비밀 값에 기본값을 두지 말 것'이라는 프로젝트 규칙을 어기고 있었다. 이제 키가 없으면 서버가 아예 안 뜬다(조용히 502 만 내는 상황을 막는다)"고 설명했다. 설정 예시 파일에 필수 표시와 웹훅 등록 안내를 달았고, API 문서와 작업 안내 문서에 "웹훅 보강 (2026-09-04 완료)" 절과 "운영 서버 비밀 설정 파일에 토스 비밀 키 추가, 빠지면 서버가 안 뜸"이라는 운영 점검 항목을 넣었다. 테스트는 금액이 다를 때 결제완료로 안 바뀌는지, 같을 때 바뀌는지 두 개를 추가했고, 기존 동시 요청 테스트가 금액 0 으로 돌던 것도 바로잡았다.

{% hint style="success" %}
**승인 요청이 하는 검사는 웹훅도 해야 한다**

웹훅은 승인 요청이 유실됐을 때 결제를 확정하는 유일한 길이라 승인 쪽과 같은 검사가 필요하다. 9/3 의 "토스에 다시 조회"는 상태를 속이는 걸 막고, 이날의 금액 대조는 다른 거래의 결제 번호를 끼워 넣는 걸 막는다. 다시 보내도 결과가 같은 오류는 200 으로 끝내는 게 맞다. 5xx 로 답하면 토스가 7번 재전송을 헛되이 쓴다.
{% endhint %}

{% hint style="warning" %}
**배포 전에 꼭 할 것 (대화 00:39)**

"운영 서버 비밀 설정 파일에 토스 비밀 키가 없으면 앱이 안 뜬다." 안전장치이긴 하지만, 운영 설정에서 키가 빠지면 백엔드 전체가 멈추는 변경이기도 하다. 같은 날 새벽 배포 작업에 서버 상태 확인 단계가 생긴 것(9번)과 맞물린다.

00:39 에 배포 후 남은 일로 네 가지를 받았다. 토스에 웹훅 주소(`https://{도메인}/api/v1/payments/webhooks/toss`, 결제 상태 변경 알림만) 등록, 맨 앞 nginx 에서 웹훅 경로가 로그인 없이 통과하는지 확인, 운영 비밀 설정에 토스 비밀 키 추가, 결제창 허용 도메인 등록이다. 00:43 에 👤 "전부 등록했어"라고 답했고, 확인할 시나리오 네 가지를 받았다. 테스트 결제 한 건, 개발자센터의 웹훅 전송 기록이 200 인지, 결제창에서 인증까지 하고 돌아오기 직전에 브라우저를 닫아 승인 요청이 유실되는 경우, 그리고 취소 경로다. 00:44 👤 "일단 커밋 푸시해줘"로 저장해서 올렸고(파일 7개, +98/−12), "이 코드가 운영에 배포되면 웹훅 연동 끝"이라는 답으로 마무리됐다.

{% hint style="danger" %}
**환불 뒤 토스 취소 웹훅이 오면 배송 끝난 상품이 다시 판매중이 된다 (코드상, 지금도)**

구매자 환불은 토스 취소 후 주문을 환불 상태로 두고, 배송이 끝난 실물이라 재고는 건드리지 않는다. 그런데 토스 취소 때문에 결제 상태 변경 웹훅이 오면(다시 조회하면 "취소"), 웹훅 처리 쪽은 "재고 돌려놓고 주문 취소"를 실행한다. 이 처리의 중복 방지 검사는 주문이 이미 "취소" 상태인지만 본다(11/16 현재 코드도 같음). 환불 상태 주문은 이 검사를 그냥 통과해서 재고가 1 늘고(8/13 이후 품절이던 상품이 판매중으로 돌아옴) 주문 상태도 환불에서 취소로 덮어써진다. 예: 배송 완료된 냉장고를 환불하면, 잠시 뒤 그 냉장고가 목록에 다시 판매중으로 뜨고 주문내역의 "환불"이 "취소"로 바뀐다. 구매자 취소와 관리자 취소는 주문을 먼저 취소 상태로 만드니 이 검사에 걸려서 괜찮다. 이 문제는 토스가 API 로 건 취소에도 이 웹훅을 보낸다는 전제 위에 있다. 대화 00:31 설명("상태가 바뀔 때마다 보낸다")과 다음 날 시험 목록 D·E 가 그렇게 가정하는데, 실제로 받은 기록은 없다.

8/30 에 검색 노출 1·2단계(사이트 설명 정보, 사이트맵, 미리 그려 둔 페이지)를 마쳤고([08.30 SEO 정리](../2026-08/2026-08-30-seo.md)), 이날은 그다음 단계로 제목과 설명 문구를 바꿨다. 그때까지 사이트 제목은 "폐업 가전 직거래 플랫폼"이라는 브랜드 문구였는데, 사람들이 실제로 검색창에 치는 말인 "업소용 중고가전"이 제목과 설명 앞쪽에 오도록 했다. 카테고리를 고르면 탭 제목과 화면 제목도 "업소용 중고 냉장고"처럼 그 카테고리에 맞게 바뀐다.

{% hint style="info" %}
**추정 — 왜 "업소용"인가**

대화 기록이 없다. 사이트 안에서는 "영업용·폐업 가전"이라고 부르지만, 구매자가 검색할 땐 "업소용 중고 냉장고"처럼 친다고 본 것 같다(할 일 문서에 "'업소용 중고가전' 노출수 추적 시작"이 있다). 검색량을 조사한 근거는 남아 있지 않다.
{% endhint %}

사이트 전체 제목은 "rekit · 폐업 가전 직거래 플랫폼"에서 "업소용 중고가전 직거래 - 폐업 매장 영업용 가전 마켓 | rekit"으로 바꾸고, 설명과 링크 미리보기 문구도 "폐업 카페·식당·매장에서 나온 업소용 중고가전(냉장고·제빙기·에어컨·주방기기)을 전수 검수 후 …"로 맞췄다. 페이지마다 따로 제목을 안 주면 쓰는 기본 제목도 "rekit · 업소용 중고가전 직거래 플랫폼"이 됐다.

홈에는 원래 큰 제목(h1)이 없어서, 화면에는 안 보이고 화면 낭독기와 검색엔진만 읽는 제목 "업소용 중고가전 직거래 마켓 rekit — …"을 넣고 그런 숨김 제목용 스타일을 하나 만들었다. 상품 목록은 카테고리 7개(냉장고·세탁기·TV·에어컨·주방·청소기·기타)마다 화면 제목, 탭 제목, 설명을 따로 정했다. 냉장고라면 화면 제목은 "업소용 중고 냉장고", 탭 제목은 "업소용 중고 냉장고 - 영업용 냉장고·냉동고 직거래 | rekit"이다. 카테고리를 안 골랐으면 "업소용 중고가전 전체"가 나오고, 검색 중이면 화면 제목이 "'검색어' 검색 결과"가 된다. 상세 화면 탭 제목은 "브랜드 상품명 중고 — 가격 | rekit" 형식이다. 사이트맵의 마지막 수정일 9개도 8/30 에서 9/3 으로 바꿨다.

주소에 붙는 카테고리 값 이름(`cat`)이 같은 화면의 필터 코드와 맞는지, 설명 문구가 카테고리를 바꿀 때 따라 바뀌는지 원본에서 확인했고 문제없었다. 다만 검색엔진에 알려 주는 대표 주소는 카테고리와 상관없이 `/products` 하나로 그대로 뒀다. 그래서 할 일 문서에 "카테고리 페이지를 사이트맵에 넣을지 검토. 지금처럼 `/products?cat=…` 이면 대표 주소가 `/products` 라 색인 효과가 적고, `/c/:slug` 같은 별도 주소를 만드는 게 정석"이라고 적었다.

### 8. 배포를 버전 번호 기준으로 (01:41 \~ 02:02)

8/23 첫 배포([08.23 일지](../2026-08/2026-08-23.md)) 때는 배포할 프로그램 묶음(도커 이미지)에 코드 저장 번호 앞 몇 글자와 "latest"라는 이름을 붙였다. 배포 작업은 그 이름을 글자로 입력받았고(기본값 latest), 되돌리려면 이전 저장 번호를 손으로 찾아 넣어야 했다. 이날부터는 사람이 붙인 버전 번호(0.0.1 같은 것)가 배포 단위가 됐다. Jenkins 에서 버전을 목록에서 골라 빌드하고 배포하며, 되돌릴 때는 이전 버전을 고르면 된다. 이후 모든 배포가 0.0.x 번호로 남는다(맨 끝 숫자만 1씩 올린다는 규칙의 시작).

첫 번째 변경(01:41, 두 저장소에 0.0.1 표시)에서는 빌드 작업이 버전 번호를 입력받아 그 버전의 코드로 이동한 뒤, 그 코드에 X.Y.Z 형식 번호가 정확히 붙어 있지 않으면 실패하게 했다. latest 이름으로 올리던 것도 없앴다. 배포 작업에는 Jenkins 플러그인으로 버전 번호 드롭다운을 달아 최신 버전이 기본으로 선택되게 하고, 배포 전에 그 버전의 이미지가 저장소에 있는지 확인하는 단계를 넣었다. 백엔드 배포에는 서버 상태 확인 단계도 붙였다. 2초 간격으로 30번 서버 상태 주소를 불러 보고, 끝내 응답이 없으면 "배포 작업에서 이전 버전을 골라 되돌리라"는 안내를 띄운다. 화면 쪽은 5/2 부터 돌던 GitHub Pages 자동 배포 설정을 지웠다. 저장 설명에 "도커와 맨 앞 nginx 로 운영 배포를 하나로 모음(GitHub Pages 사이트도 API 로 닫음)"이라고 적혀 있다. 5/10 에 기본 경로 설정을 지운 뒤로 Pages 사이트는 경로가 어긋난 채 방치돼 있었다([05.10 일지](../2026-05/2026-05-10.md)).

01:52 에는 두 저장소 모두 내용 변경이 하나도 없는 빈 저장에 0.0.2 를 붙였다. 표시 설명은 "release 0.0.2 (롤백 테스트)"다. 0.0.2 를 배포해 본 다음 드롭다운에서 0.0.1 을 골라 되돌리는 시험을 한 것으로 보인다.

02:02 에 깨지는 단계를 고쳤다. 이미지가 있는지 확인하는 단계가 실패했는데, 저장 설명에 따르면 "명령이 Jenkins 컨테이너 안에서 돌아서 호스트의 127.0.0.1:5000(이미지 저장소)에 닿지 못했다". 그래서 이 단계는 빼고, 이미지가 없으면 이미지를 받아 오는 단계가 어차피 분명하게 실패한다고 정리했다. 백엔드 상태 확인도 같은 이유로 실패해서, 앱 컨테이너 안에서 상태 주소를 부르도록 바꿨다(백엔드 이미지에 curl 이 들어 있음). 실패하면 앱 기록 마지막 50줄을 보여 준다. 빌드 작업의 버전 번호도 손으로 입력하던 것을 드롭다운으로 바꾸고, 고른 값이 X.Y.Z 형식인지 확인한 뒤 그 버전 코드로 강제로 이동하게 했다. 주석에는 "Jenkins 는 기본으로 master 를 받아 오니 빌드할 버전의 코드로 직접 옮겨 가야 한다"고 적었다.

{% hint style="info" %}
**배운 점 — 호스트 Docker 를 빌려 쓰는 Jenkins 의 두 얼굴**

Jenkins 가 컨테이너로 돌면서 호스트의 Docker 를 빌려 쓰면, 이미지 빌드·올리기·띄우기는 호스트의 Docker 가 실행하니 127.0.0.1:5000 저장소가 잘 보인다. 반면 이미지 존재 확인 명령이나 curl 은 Jenkins 컨테이너 자기 네트워크에서 나가니 그 127.0.0.1 은 호스트가 아니다. 같은 스크립트 안에서도 명령마다 실제로 누가 실행하느냐가 다르다. Testcontainers 에서 `localhost` 대신 `getHost()` 와 매핑된 포트를 써야 하는 것과 비슷한 종류의 함정이다.
{% endhint %}

{% hint style="info" %}
**Jenkins 작업 이름**

대화와 백엔드 두 번째 변경에서는 백엔드 작업을 `build-was`·`deploy-was`, 화면은 `build-client`·`deploy-client`로 부른다. 백엔드 빌드 작업의 완료 문구는 여전히 옛 이름 "rekit-backend-deploy 잡에서…"를 출력한다.
{% endhint %}
