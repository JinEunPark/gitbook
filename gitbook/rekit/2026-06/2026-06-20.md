### 1. 상품 보기

화면의 상품 목록·상세·홈이 서버에서 데이터를 받을 수 있게 했다. 목록은 카테고리(냉장고·세탁기·TV·에어컨·주방가전·기타), 등급(A/B/C), 가격 범위, "동작 보증만", 검색어로 거를 수 있다. 검색어는 상품명·브랜드·모델명 중 어디에 들어 있어도 찾는다. 정렬은 최신순(기본), 가격 낮은순, 가격 높은순이고 값이 같으면 상품 번호로 한 번 더 정렬한다. 한 쪽에 기본 20개, 최대 100개다.

목록에는 판매 중인 상품만 나온다. 전체 개수는 거르기를 적용한 뒤 쪽을 나누기 전에 따로 세서 "전체 몇 쪽"을 알려 준다. 상품 사진은 상품마다 따로 DB 를 부르지 않고 한 번에 모아서 가져와, 상품이 20개면 DB 를 21번 부르는 문제(N+1)를 피했다. 관계 데이터를 함께 로딩해 N+1 조회를 피했다. 거르기 조건은 묶음 하나로 받아서 주입한다(필터 조건을 하나의 파라미터 객체로). DB 담당 코드에는 "거르기·정렬·쪽 나누기는 모두 DB 쿼리에서 하고 파이썬 반복문으로 하지 않는다"는 규칙을 적어 두었다.

상세는 설명, 연식, 크기, 무게, 재고, 사진 목록을 주고 없는 상품이면 "상품 없음(404)"이다. 홈 신착은 판매 중인 상품을 최신순으로 기본 4개 준다. 이 주소를 상세 주소보다 먼저 선언해야 "featured"를 상품 번호로 읽지 않는데, 그 이유를 주석으로 남겼다. 카테고리는 DB 없이 코드에 적어 둔 목록을 돌려주고, 아이콘 이름(fridge, washer 등)은 화면의 가전 그림 부품 이름과 같다. 할인율(정가 대비 몇 % 싼지, 정가가 없으면 비움)과 대표 사진(첫 번째 사진)은 서버가 계산해서 준다.

{% hint style="warning" %}
**상세는 상품 상태를 보지 않는다**

목록과 신착은 판매 중인 상품만 거르는데 상세는 그런 검사가 없다. 그래서 관리자가 지운(비공개로 돌린) 상품도 번호만 알면 상세가 보인다.
{% endhint %}

### 2. 관리자 상품 등록·수정·삭제 + 관리자 검사 장치

5/7 부터 미뤄 온 "관리자만 통과" 검사 장치를 만들었다. 출입증 확인, 임시 비밀번호 상태 차단 다음에 세 번째로 "역할이 관리자인지"를 보고, 아니면 "권한 없음(403)"으로 거절한다. 관리자 역할을 검사하도록 했다.

관리자 상품 목록은 판매 중이 아닌 것까지 모든 상태를 보여 주고 상태와 검색어로 거를 수 있다. 등록은 상품 정보 17칸과 사진 주소 최대 10개를 받고, 사진은 보낸 순서대로 순번을 매긴다. 수정은 보낸 칸만 바꾸고 나머지는 그대로 둔다. 다만 사진은 수정할 수 없어서 이틀 뒤 사진 교체 기능을 따로 만들었다. 삭제는 실제로 지우지 않고 상태만 "비공개"로 바꾼다.

### 3. 배송지

회원 한 명이 배송지를 최대 10개까지 둘 수 있고 넘으면 "배송지 개수 초과(422)"다. 기본 배송지로 지정해서 추가하거나 수정하면 그 회원의 다른 기본 배송지를 먼저 모두 해제해서 기본이 늘 하나가 되게 했다. 다만 기본 배송지를 지웠을 때 다른 배송지가 저절로 기본이 되지는 않는다(설명에 적어 둠). 목록은 기본 배송지가 먼저, 그다음 등록 순이다.

휴대폰 번호는 010·011·016·017·018·019 로 시작하는 형식만 받고, 하이픈과 공백을 빼고 숫자만 저장한다. 우편번호는 5자리다. 틀리면 "올바른 휴대폰 번호를 입력해주세요. (예: 010-1234-5678)" 같은 한국어 안내가 나간다. 수정할 때 상세 주소를 일부러 비워서(null) 보내면 지우고, 아예 안 보내면 그대로 둔다. 남의 배송지 번호를 넣으면 "없음(404)"으로 답해서 그 번호가 있는지조차 알려 주지 않는다. 응답 칸 이름을 화면식으로 바꿔 주는 건 이 기능뿐이고 다른 기능은 서버식(`is_default`) 그대로다.

_근거 커밋: `e9a3682` · 개발자용: `app/address/`, `MAX_ADDRESSES_PER_USER`, `ADDRESS_LIMIT_EXCEEDED`, 휴대폰 정규식 `^01[016789]\d{7,8}$`_

### 4. 장바구니

같은 상품을 또 담으면 줄이 하나 더 생기지 않고 수량이 더해진다. 상품이 없거나 판매 중이 아니면 "상품 없음", 더한 수량이 재고보다 많으면 "재고 없음(422)"이다. 수량은 1\~10 사이로만 바꿀 수 있고 재고를 넘으면 거절한다. 여러 개 지우기는 "이 회원의 장바구니 중 이 번호들"만 지워서, 남의 항목 번호가 섞여 있어도 조용히 무시된다. 담거나 수량을 바꾸면 장바구니 전체를 다시 돌려주는데, 상품 요약·대표 사진·줄별 합계와 함께 상품 합계, 예상 배송비, 총액이 들어 있다.

예상 배송비는 화물 택배 기준 60,000원으로 고정했고 "실제 주문 때 다시 계산한다"고 주석을 달았다. 장바구니 DB 담당은 상품 기능 코드를 가져다 쓰지 않고 상품 표를 직접 읽는다. 기능끼리 서로 얽히지 않게 하려는 것이라고 설명에 적었다.

_근거 커밋: `e9a3682` · 개발자용: `app/cart/`, `_SHIPPING_FEE_ESTIMATE`, `CartRepository.get_product()`, 여러 개 지우기 `POST /cart/items/bulk-delete`_

### 5. 찜(관심상품) — 새 표

화면에는 5/2 부터 찜 보관함이 있었지만 서버에는 받을 곳이 없었다. 5/1 에 만든 DB 표 목록에도 없던 표라 이날 새로 만들었다. 표는 "회원 번호 + 상품 번호" 둘을 합친 것을 기본 키로 써서 같은 상품을 두 번 찜할 수 없다(회원 ID와 상품 ID를 복합 기본 키로 사용한 구조). 회원이 탈퇴하거나 상품이 지워지면 찜도 같이 지워진다. 찜한 시각은 응답에서 `addedAt` 으로 내보낸다. 찜에서 상품 쪽으로만 연결을 두고 회원·상품 모델은 건드리지 않아 이 기능만 따로 떼어 둘 수 있게 했다.

찜 넣기는 이미 찜한 상품이어도 에러 없이 "찜됨"을 돌려준다. 몇 번을 눌러도 결과가 같다. 빼기는 찜하지 않은 상품이면 "찜 없음(404)"이다. 응답은 상품 번호와 찜 여부뿐이라 화면의 하트를 켜고 끄는 데 바로 쓸 수 있다.

_근거 커밋: `e9a3682` · 개발자용: `app/favorites/`, 모델 `Favorite`(복합 PK, `ON DELETE CASCADE`), `FAVORITE_NOT_FOUND`_

### 6. 주문

배송비 기준값을 한 파일에 모았다. 택배 5,000원, 화물 60,000원, 직접 배송 40,000원에 20,000원 할인(실제 부담 20,000원)이다. 직접 배송은 우편번호 앞 두 자리가 01\~08(서울)이나 10\~18(경기 일부)일 때만 된다. 환불 가능 기간 7일도 적어 두었지만 쓰는 곳은 아직 없다.

주문 만들기는 업무 규칙 코드에 번호를 매겨 11단계로 적었다. 먼저 본인 확인을 마친 회원인지 보고, 아니면 "본인 확인 필요"로 거절한다. 배송지가 그 회원 것인지, 직접 배송이면 가능한 지역인지 확인한다. 그다음 상품마다 행 잠금(`FOR UPDATE`, JPA 의 비관적 잠금)을 걸고 판매 중인지와 재고를 본다. 재고가 1개인 상품을 두 사람이 동시에 사는 일을 막으려는 것이다. 배송비를 계산해 총액(상품 합계 + 배송비 − 할인)을 내고, 주문을 만든다. 받는 사람·연락처·주소는 배송지에서 복사해 주문에 따로 저장하고, 주문 상품도 상품명·대표 사진·가격을 복사해 둔다. 나중에 배송지나 상품을 고쳐도 주문 내역은 그때 그대로 남게 하려는 것이다. 주문번호는 처음엔 임시값을 넣었다가, DB 에 한 번 써서 주문 번호(id)를 받은 뒤 "RK-년월일 + 번호 4자리"(예: RK-2606200001)로 바꾼다. 마지막으로 재고를 DB 에서 바로 빼는 방식으로 줄인다.

한 번에 살 수 있는 수량은 1\~10개다. 중고 가전이라 대량 구매가 필요 없다는 이유를 주석에 적었다. 주문 목록은 최신순이고, 남의 주문번호로 상세를 보면 "주문 없음"으로 답한다. 취소는 결제대기·결제완료·준비중 상태에서만 되고, 상태를 "취소"로 바꾸고 취소 시각을 남긴다. 결제사 쪽 결제 취소는 결제 기능이 맡고 여기서는 상태만 바꾼다고 적었다.

{% hint style="danger" %}
**확인된 제약 및 후속 작업**

### 7. 토스페이먼츠 카드 결제

카드로 결제하는 흐름을 세 단계로 만들었다. 결제 시작에서 서버는 주문이 그 회원 것이고 결제대기 상태인지 확인한 뒤 "결제 준비" 기록을 만들고 주문번호·금액·주문자 이름(받는 사람 이름)을 돌려준다. 화면은 그 값으로 토스 결제창을 띄우고, 결제가 끝나면 토스가 결제 번호(paymentKey)·주문번호·금액을 붙여 화면으로 돌려보낸다. 승인 단계에서 서버는 금액이 주문 총액과 같은지 확인하고(중간에 금액을 바꿔치기하는 걸 막으려고), 토스에 "이 결제 확정해 주세요"를 요청한다. 성공하면 결제 기록에 카드사·카드 끝 4자리·할부·승인번호를 저장하고 결제와 주문을 모두 "결제완료"로 바꾼다. 마지막으로 토스가 결제 상태가 바뀌었다고 알려 오면(웹훅), 서명 헤더를 확인한 뒤 완료면 결제완료, 취소면 취소, 중단이면 실패로 바꾼다. 이미 결제완료인 건은 건너뛰어서 같은 알림이 두 번 와도 한 번만 처리된다.

카드 번호는 토스가 가려서 주는 번호에서 끝 4자리만 저장한다(카드 정보를 최소화하기 위해). 결제사 연결 규격이 5/5 에 만든 넓은 규격과 이날 만든 "토스 승인 전용 간단 규격" 두 개가 같이 있게 됐는데, 새 파일 설명에 그렇게 적어 두었다.

{% hint style="warning" %}
**화면은 무통장입금인데 서버는 카드 결제**

5/5 에 화면은 결제를 무통장입금 하나로 바꿨다(입금대기, 결제확인요청, 관리자 승인). 이날 서버는 그 흐름 대신 토스 카드 결제를 만들었고, 무통장입금 확인 기능은 없다. 두 저장소의 결제 방식이 어긋난 채 출발했다.
{% endhint %}

{% hint style="danger" %}
**결제 연동의 확인된 제약**

* 토스 비밀 키를 설정에서 읽는데, 설정 목록에 그 칸이 아예 없다. 그래서 승인은 늘 "Toss secret key가 설정되지 않았습니다"로 실패하고, 알림 서명 확인도 늘 실패한다.
* 알림 서명 확인 자체가 틀린 가정이었다. 토스 결제 알림에는 이런 서명 헤더가 없다는 걸 8/30 에 알게 되고, 알림을 받으면 토스에 다시 조회해 확인하는 방식으로 바꿨다([08.30 일지](../2026-08/2026-08-30.md)). 5/2 서버 명세서의 "서명 헤더로 확인" 가정이 여기까지 이어진 것이다.
* 승인 단계는 로그인만 보고 그 주문의 주인인지는 확인하지 않는다. 금액 일치 확인이 있어서 피해는 제한적이다.
* 카드사 칸에 "신한카드" 같은 이름이 아니라 토스가 주는 카드사 코드(issuerCode)를 저장한다. 칸 설명과 코드 설명은 이름을 기대한다.
* 알림을 받는 곳이 업무 규칙 안쪽의 숨겨진 속성에 직접 손을 댄다. 6/22 에 따로 함수를 만들어 정리했다.
{% endhint %}

### 9. 기본 데이터 스크립트, 점검 스크립트, 문서

개발용 기본 데이터 스크립트(327줄)는 관리자 1명과 일반 회원 2명을 만든다. 일반 회원은 본인 확인을 마친 상태로 넣어서 바로 주문을 시험해 볼 수 있다. 상품은 6개로 LG 냉장고 462L, 삼성 드럼세탁기 12kg, LG 올레드 65인치, 캐리어 스탠드 에어컨 18평, 삼성 김치냉장고 234L, 다이슨 V11("부품 일부 분실")이고, 배송지·장바구니·찜도 조금씩 넣는다. 이메일로 이미 있는지 확인하기 때문에 여러 번 돌려도 안전하다. 기본 계정 이메일 주소는 옛 이름인 rekle 도메인으로 되어 있다.

점검 스크립트(287줄)는 서버를 띄운 뒤 일반 회원·관리자로 로그인하고, 내 정보, 상품, 장바구니, 찜, 배송지, 주문 순서로 실제로 불러 보면서 통과·실패를 색으로 찍는다(curl 과 jq 사용). 기본 데이터 스크립트로 만든 계정이 있어야 돈다.
