### 1. 카테고리를 DB 로 옮기기

5/1 부터 카테고리(냉장고·세탁기·TV·에어컨·주방가전·기타)는 서버 코드에 적힌 고정 목록이었고, 6/20 에 만든 카테고리 조회도 코드 안의 표를 그대로 돌려주는 식이었다. 그래서 "청소기" 하나를 더하려 해도 코드를 고치고, DB 변경 스크립트를 만들고, 다시 배포해야 했다. 이날 카테고리를 DB 표(번호·이름·아이콘·정렬 순서)로 옮기고, 처음 6개는 DB 변경 스크립트가 표를 만들면서 같이 넣게 했다. 6/20 고정 목록과 같은 값이다. 이제 화면은 DB 에 있는 카테고리를 정렬 순서대로 받고, 관리자는 서버 기능으로 카테고리를 조회·추가·수정·삭제할 수 있다. 새 카테고리 번호는 `REFRIGERATOR` 처럼 대문자로 시작하는 영문만 받고, 이미 있는 번호면 거절한다.

상품의 카테고리 칸은 이제 그냥 문자열이다. 상품을 등록할 때도 1\~30자인지만 본다. 시험용 데이터를 넣는 스크립트에도 카테고리를 먼저 넣는 단계가 생겼고, 여러 번 돌려도 중복으로 들어가지 않는다.

{% hint style="info" %}
**추정 — 왜 이날 했나**

같은 날 화면을 서버에 붙이다 보니, 시안의 홈 화면 8칸(청소기·소형가전 포함)과 서버의 6개가 안 맞는 게 드러났을 것이다. 운영 중에 관리자가 "청소기" 같은 카테고리를 직접 추가할 수 있게 하려던 것으로 보인다. 5/1 서버 코드에도 "나중에 청소기·소형가전 추가 예정"이라는 주석이 있었고, 화면 쪽 타입에는 이미 청소기가 들어가 있었다.
{% endhint %}

{% hint style="warning" %}
**상품과 카테고리를 DB 에서 일부러 묶지 않았다**

상품 표가 카테고리 표를 참조하도록 DB 차원의 연결(외래키)을 걸지 않았다. 그래서 없는 카테고리 번호로도 상품이 저장되고, 카테고리를 지울 때 그 카테고리에 상품이 남아 있는지 확인하지 않는다. 그렇게 되면 화면에서 카테고리 이름이 빈칸으로 보이는 상품이 생길 수 있다. JPA 로 치면 `@ManyToOne` 대신 `String categoryId` 를 들고 있는 설계다. 운영 중에 카테고리를 자유롭게 정리할 수 있는 대신, 데이터가 맞는지는 코드가 챙겨야 한다.
{% endhint %}

{% hint style="info" %}
**바꾸기가 쉬웠던 이유**

5/1 부터 정해진 값 목록(Enum)을 DB 에서는 전부 평범한 문자열 칸으로 저장하고 앱에서 검사하게 만들어 뒀다. 그래서 DB 칸 타입은 이미 문자열(30자)이었고, 이번 DB 변경 스크립트는 칸 타입을 건드릴 필요가 없었다.
{% endhint %}

### 2. 화면을 서버 상품에 연결

홈·상품 목록·상품 상세 세 화면이 가짜 상품 대신 서버에서 받은 상품을 보여 주게 됐다. 서버를 부르는 함수 4개(신상품, 목록, 상세, 카테고리)를 만들었는데, 서버 응답의 이름 규칙(`min_price` 같은 밑줄 방식)을 화면 쪽에서 바꾸지 않고 그대로 받았다.

카테고리는 화면 전체가 같이 쓰는 데이터 보관함(Pinia)에 한 번만 불러 둔다. 여러 화면이 동시에 달라고 해도 서버 호출은 한 번만 나가고 모두 그 결과를 나눠 받는다(5/10 로그인 토큰 갱신 때와 같은 방식). 주소에 쓰는 이름은 번호를 소문자로 바꿔서 만들고(`refrigerator`, `air_conditioner`), 목록 맨 끝에 "전체"를 붙인다.

화면마다 데이터를 불러오는 부분은 따로 떼어 ViewModel 이라는 함수로 만들었다. 화면 코드는 그 함수가 넘겨주는 상품 목록과 로딩 여부만 읽어서 그린다. Spring MVC 로 치면 컨트롤러가 서비스 결과를 `Model` 에 담아 뷰로 넘기는 일을 화면별 함수로 분리한 셈이다. 그 덕에 화면마다 로딩 중, 오류(다시 시도 버튼), 빈 목록, 정상의 네 가지 표시가 생겼다.

* 홈은 신상품 8개와 카테고리를 동시에 불러온다. 카테고리 칸은 시안의 8칸(청소기·소형가전 포함)에서 서버 카테고리 6개 + "전체"의 7칸으로 줄었다.
* 목록은 5/2 에 만든 화면 안 필터 대신 서버에 조건을 넘겨 거른다. 필터 칩을 빠르게 연타하거나 검색어를 치는 도중에 예전 요청의 응답이 늦게 도착하면, 그건 버리고 마지막 요청 결과만 보여 준다.
* 상세는 상품 정보와 같은 카테고리의 관련 상품 4개를 따로 부른다. 관련 상품은 실패해도 무시하고, 상품이 없으면 "찾을 수 없음" 화면으로 간다. 썸네일 줄도 실제 사진 목록으로 바뀌었고, 사진 종류가 없으면 "사진 1", "사진 2"처럼 붙인다.
* 상품 사진 칸은 사진 주소가 있으면 실제 사진을 필요할 때 불러와 꽉 채워 보여 주고, 사진을 못 불러오면 원래 쓰던 가전 아이콘으로 돌아간다. 상품 카드에서는 연식 정보가 없으면 " · " 구분점을 붙이지 않게 했다.
* 서버 상품을 화면용 상품 모양으로 바꾸는 변환기도 만들었다. 카테고리 아이콘이 화면에 있는 가전 아이콘이면 그대로 쓰고, 아니면 전자레인지 아이콘을 쓴다. 배경색은 상품 번호로 6가지 중 하나를 고른다.

{% hint style="warning" %}
**서버가 아직 못 하는 걸 화면이 임시로 메웠다**

서버에 할인율순 정렬이 없어서 최신순으로 받은 뒤 화면에서 다시 정렬한다. 등급도 서버는 하나만 받을 수 있어서, A·B 처럼 두 개 이상 고르면 서버 필터 없이 받아 화면에서 거른다. 이 두 가지 때문에 목록은 항상 1페이지 100개로 요청한다. 상품이 100개를 넘으면 목록이 잘리고, 페이지 넘기기 화면도 없다. 목록 응답에는 재고·모델명·연식이 없어서 재고는 1로 고정했고 모델명·연식은 빈값이다.
{% endhint %}

{% hint style="info" %}
**아직 가짜 데이터인 곳**

장바구니·관심상품·주문·배송지·관리자 화면은 여전히 브라우저 안 데이터로 움직인다. 서버 데이터를 쓰는 건 홈·목록·상세뿐이다. 장바구니에 담기는 상품 번호는 이제 서버 번호(`"1"` 같은 문자열)가 됐다.
{% endhint %}

### 3. 상품 사진을 사진 저장소에 올리는 스크립트

화면에 실제 사진이 나오려면 DB 에 사진 주소가 있어야 하는데, 시험용 상품에는 사진이 없거나 엉성했다. 그래서 상품 번호마다 인터넷 무료 사진(Unsplash) 주소를 정해 두고, 그 사진을 받아 사진 저장소(SeaweedFS)에 올린 다음 새 주소로 DB 를 채우는 스크립트(160줄)를 만들었다. 순서는 이렇다. 먼저 상품 사진 표를 통째로 비운다. 그다음 상품 번호별 사진(시험용 1\~6번과 테스트 상품 10\~20번)을 하나씩 받아 저장소의 `products/` 아래에 임의 이름으로 올리고, 올린 주소로 사진 행을 다시 만든다. 사진이 없던 테스트 전자레인지와 세탁기에도 이때 어울리는 사진을 넣었다.

5/1 에 만든 사진 올리기는 브라우저가 서버에게 받은 임시 업로드 주소([presigned URL](../glossary.md))로 저장소에 바로 올리는 방식이었다. 이번 스크립트는 그것과 별개로, 서버 쪽 스크립트가 저장소의 S3 방식 기능으로 직접 올리는 첫 경로다.

{% hint style="warning" %}
**개발 DB 에서만 돌릴 것**

첫 단계가 사진 표를 통째로 비우는 것이라 운영 DB 에서 돌리면 실제 상품 사진이 다 사라진다. 막아 주는 장치도 없다. 다음 날(6/24) 사진을 동시에 5장씩 처리하도록 빨라진다.
{% endhint %}
