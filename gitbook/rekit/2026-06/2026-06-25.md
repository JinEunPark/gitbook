### 1. 결제 완료 메일과 가짜 결제 모듈

토스 결제가 승인되면 서버가 주문자 이메일을 찾아서 "결제가 완료되었습니다" 메일을 보낸다. 메일은 응답을 먼저 돌려준 뒤 뒤에서 보내고, DB 작업과도 묶지 않는다. 5/10 비밀번호 찾기 메일 때 정한 원칙을 그대로 따랐다. 본문에는 주문번호, 결제금액(`300,000원` 형식), 결제수단(`신한카드 1234 · 일시불`, `3개월 할부` 같은 형식), "마이페이지에서 확인" 안내가 들어간다. 주문자 이메일이 없으면 보내지 않는다.

{% hint style="warning" %}
**결제 메일에 옛 이름 "Rekle"이 들어갔다**

제목이 `[Rekle] 주문 RK-... 결제가 완료되었습니다` 이고 본문도 "안녕하세요, Rekle입니다 … Rekle 팀"이다. 몇 시간 뒤 만든 인증 메일은 `[rekit]` 으로 나간다. 백엔드는 저장소와 DB 이름이 아직 `rekle` 이라 새로 만든 코드에 옛 이름이 섞여 들어간 것으로 보인다.
{% endhint %}

가짜 결제 모듈은 승인 요청을 받으면 무조건 성공으로 답한다. 카드사는 "개발카드", 카드 끝자리는 "0000", 승인번호는 "FAKE-APPROVAL"로 채우고, 결제 알림([웹훅](../glossary.md))의 서명 확인도 항상 통과시킨다. 설정 값 하나(`USE_FAKE_PG`)로 진짜와 가짜를 고르는데, 설정 예시 파일에는 기본값 false 와 함께 "운영에서는 반드시 false"라고 적어 두었다. Spring 으로 치면 `@Profile("dev")` 로 결제 빈을 바꿔 끼우는 것과 같다.

{% hint style="info" %}
**6/20 버그 하나가 풀렸다**

같은 작업에서 서버 설정에 토스 비밀키 칸이 생겼다. 6/20 의 토스 연결 코드는 있지도 않은 설정을 읽으려다 빈 값을 쓰고 있었는데, 이제 설정 파일에 키를 넣으면 실제 승인이 동작할 수 있다.
{% endhint %}

{% hint style="info" %}
**추정 — 가짜 결제를 만든 이유**

6/23 사진 스크립트에 "결제테스트 세탁기"라는 상품이 두 개 있었다. 로컬에서 주문부터 결제까지 끝까지 눌러 보고 싶은데, 토스 키와 결제창 없이는 승인이 항상 실패하니 결제를 통과시키는 스위치가 필요했을 것이다. 화면은 아직 무통장입금 가짜 흐름이라, 이 흐름은 서버 기능을 직접 불러서 시험했을 것으로 보인다.
{% endhint %}

### 2. 이메일 인증 회원가입

가입할 때 이메일이 진짜 본인 것인지 확인하는 단계를 넣었다. 흐름은 세 번의 요청으로 이어진다.

먼저 이메일을 보내 코드를 요청하면, 서버가 같은 이메일로 1분 안에 이미 요청한 적이 있는지 Redis 에서 확인하고 있으면 "1분에 한 번만" 오류로 돌려보낸다. 아니면 6자리 숫자 코드를 무작위로 만들어 Redis 에 10분간 보관하고, 인증 메일을 뒤에서 보낸다. 다음으로 이메일과 코드를 보내면 Redis 의 값과 비교한다. 다르거나 이미 만료됐으면 "인증 코드가 틀림"으로 답하고, 맞으면 코드를 바로 지워서(한 번만 쓰게) "이 이메일은 확인됨"이라는 15분짜리 증표([JWT](../glossary.md))를 준다. 마지막으로 가입할 때는 이메일 대신 이 증표를 보낸다. 서버는 증표에서 이메일을 꺼내 중복을 확인하고 가입시킨 다음, 로그인 토큰과 로그인 유지 쿠키까지 바로 내준다.

Redis 연결은 서버 프로세스마다 하나만 만들어 같이 쓴다. 주석에 앞으로 쓸 곳도 적어 두었다. 이메일 코드(10분), 나중에 만들 문자 인증 코드(5분), 요청 횟수 제한 표시(60초)다. "확인됨" 증표는 5/10 소셜 가입 때 쓴 임시 증표와 같은 방식으로, 용도를 증표 안에 적어 두고 15분만 유효하게 했다. 테스트에서는 진짜 Redis 없이 돌 수 있게 사전(dict)으로 흉내 낸 가짜 Redis 를 만들었다.

{% hint style="info" %}
**"가입해도 로그인되지 않는다"는 결정을 되돌렸다**

5/7 에 "가입은 토큰을 주지 않는다"고 정했고, 그래서 5/10 화면은 가입 직후 같은 아이디와 비밀번호로 로그인을 한 번 더 했다. 이번엔 이메일 소유가 확인된 가입이니 바로 로그인시켜도 된다고 보고 서버가 토큰을 직접 준다. 다만 이 시점의 가입 화면은 여전히 이메일을 그대로 보내는 예전 방식이라 가입이 실패하는 상태였다. 다음 날 화면 쪽에서 이메일 인증을 붙이면서 맞춰졌다([06.26 일지](2026-06-26.md)).
{% endhint %}

{% hint style="warning" %}
**인증 코드를 계속 찍어 보는 걸 막지 않는다**

코드 발송은 1분에 한 번으로 묶었지만, 코드 확인은 시도 횟수 제한이 없다. 6자리면 100만 가지라, 10분 동안 계속 찍어 보는 공격이 가능한 구조다. 예를 들어 5번 틀리면 코드를 폐기하는 식의 제한이 필요하다. 발송 제한도 이메일 단위라서, 한 곳(IP)에서 여러 이메일로 대량 발송하는 건 막지 못한다.
{% endhint %}

### 3. 인증 메일 HTML 양식

메일 보내는 기능에 HTML 본문을 같이 넣을 수 있게 했다. Gmail 로 보낼 때는 글자 본문과 HTML 본문을 함께 담아서, HTML 을 못 보는 메일 프로그램에서는 글자 본문이 보인다. 개발용 콘솔 출력에서는 "HTML 포함"이라고만 표시한다.

인증 메일 양식(110줄)은 Gmail, Apple Mail, Outlook 에서 모두 깨지지 않도록 표(table) 배치와 직접 붙인 스타일로 만들었다. 연회색 바탕에 위쪽 민트색 띠, 화면의 로고와 같은 잎 모양 그림과 "rekit" 글자, 모서리가 둥근 카드 모양이다. Claude Code 권한 설정에 디자인 미리보기 기능(artifact-design) 허용이 같이 들어간 걸 보면, 양식을 미리 띄워 보며 만든 것 같다(추정).

{% hint style="info" %}
**추정 — 왜 문자가 아니라 이메일 인증인가**

5/1 요구사항은 "가입 시 문자 인증"이었지만, 문자는 발신번호 등록과 건당 비용이 든다. 이미 Gmail 로 메일 보내는 기능(5/7)이 있으니 이메일 소유 확인으로 대신한 것으로 보인다. 비밀번호 찾기, 아이디 찾기, 결제 안내가 전부 이메일로 가니까 가입 이메일이 진짜인지부터 확인할 필요도 있었을 것이다. 문자 인증은 11/5 에 하지 않기로 최종 결정했다.
{% endhint %}
