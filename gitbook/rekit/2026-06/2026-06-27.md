### 이날을 한 문단으로

관심상품(찜)을 서버에 연결했다. 장바구니와 같은 방식으로 로그인 전에는 브라우저에 담고, 로그인하면 서버 목록과 합치는데, 찜은 실제 서버에 있는 기능만 써서 제대로 동작한다. 장바구니·찜·주문서가 상품 정보를 하나씩 따로 부르던 것도, 서버에 "이 번호들의 상품을 한꺼번에 달라"는 기능을 만들어 한 번에 받게 바꿨다. 검색도 화면 안 가짜 데이터를 거르던 데서 서버 검색으로 옮겼다. 이로써 화면 쪽 상품 데이터에서 가짜 상품 목록이 빠졌고, 그걸 아직 쓰는 건 관리자 화면뿐이다.

### 1. 여러 상품을 한 번에 받는 서버 기능

6/26 장바구니 화면은 담긴 상품 수만큼 상품 상세를 따로 불렀다. 찜 목록과 주문서에도 같은 일이 필요해지자, 상품 번호 목록을 보내면 상품 목록을 돌려주는 기능을 서버에 만들었다(`POST /products/bulk`). 한 번에 1\~100개까지 받고 로그인은 필요 없다. 조회인데 POST 로 만든 건 번호 100개를 주소 뒤에 줄줄이 붙이지 않으려고 그랬다. 없는 번호는 조용히 빼고 돌려주고, 돌려주는 순서는 보장하지 않는다.

같은 작업에서 상품 목록·신상품·이번 묶음 조회가 상품 사진을 다 읽지 않고 대표 사진 1장만 읽게 했다. 카드에는 첫 장만 쓰기 때문이다. 상품 20개에 사진이 10장씩이면 예전엔 사진 200행을 읽었는데 이제 20행만 읽는다. 상세 화면은 그대로 사진 전부를 읽는다.

{% hint style="info" %}
**관계를 불러올 때 조건 붙이기**

SQLAlchemy 의 관계 로딩에 "첫 번째 사진만"이라는 조건을 붙이는 기능(`relationship.and_()`)을 썼다. JPA 로 치면 Hibernate `@Filter` 나 fetch join 에 `ON` 조건을 거는 것과 비슷하다. 다만 이렇게 불러온 상품의 사진 목록은 1장짜리가 되기 때문에, 같은 처리 안에서 사진 전부가 필요한 코드와 섞이면 헷갈릴 수 있다.
{% endhint %}

{% hint style="warning" %}
**판매 상태를 따지지 않는다**

이 기능은 판매 중인지 확인하지 않는다. 장바구니나 찜에 담긴 상품이 판매 종료돼도 정보는 보여 주려는 의도로 보이지만, 그 바람에 관리자가 숨긴 상품도 번호만 알면 조회된다. 6/20 상세 조회와 같은 성격의 문제다.
{% endhint %}

### 2. 관심상품 서버 연결

찜 목록 보기, 찜하기, 찜 풀기 세 가지를 서버에 연결했다. 장바구니와 달리 이건 설계 문서가 아니라 6/20 서버가 실제로 돌려주는 모양 그대로 맞췄다.

로그인하지 않았을 땐 찜한 상품 번호를 브라우저에 담아 두고, 비면 지운다. 로그인하는 순간 서버 목록을 받아서, 브라우저에만 있고 서버엔 없는 것만 골라 하나씩 서버에 찜하기를 보낸 뒤 브라우저 저장은 지운다. 서버에 합치기 기능이 없으니 화면 쪽에서 합친 것이다. 로그인 상태에서 하트를 누르면 화면을 먼저 바꾸고 서버를 부르며, 실패해도 그냥 넘어간다. 로그아웃하면 비운다. 찜 목록 화면은 찜 목록이 바뀔 때마다 전체를 다시 받지 않고, 화면에 아직 없는 상품만 한 번에 받아 오고 빠진 상품은 지운다.

{% hint style="info" %}
**장바구니와 다른 점**

둘 다 "로그인 전에 담은 걸 로그인 후 합친다"는 구조인데, 찜은 서버에 있는 기능만으로 합치기 때문에(찜하기를 여러 번) 실제로 된다. 장바구니는 서버에 없는 합치기 기능을 불러서 조용히 실패한다([06.26 일지](2026-06-26.md) 참고).
{% endhint %}

### 3. 상품 조회를 한 번으로, 가짜 상품 목록 제거

화면 전체가 같이 쓰는 상품 데이터 보관함에서 가짜 상품 8개와, 그걸 번호로 찾는 기능을 지웠다. 대신 상품 하나를 서버에서 받는 기능과, 여러 개를 1절의 새 서버 기능으로 한 번에 받는 기능(카테고리도 같이 불러온다)을 넣었다. 장바구니는 담긴 상품마다 따로 부르던 걸 이걸로 한 번에 받고, 주문서는 결제 단계에 들어갈 때 고른 상품 정보를 한 번에 받으면서 "상품 정보를 불러오는 중…"을 보여 준다. 장바구니와 찜에서 똑같이 쓰던 번호 변환 함수는 공용 파일로 뺐다.

가짜 목록이 보관함에서 사라지자, 그걸 쓰던 관리자 상품·매출 화면은 가짜 데이터 파일을 직접 불러오게 고쳤다. 관리자 화면이 아직 가짜 데이터라는 게 코드에 그대로 드러난 셈이다. 목록 응답에는 재고가 없어서, 상태가 품절이면 재고 0, 아니면 1로 채운다. 서버의 품절 상태 이름이 `SOLD_OUT` 인데 화면 쪽은 `SOLD` 로 적고 있어서 서버에 맞췄다. 인기 검색어를 받는 함수도 타입만 미리 만들어 뒀는데, 부르는 곳도 없고 서버에도 그런 기능이 없다. 할 일 목록에 있는 미구현 항목을 먼저 적어 둔 정도다.

### 4. 검색을 서버로

모바일 검색 페이지와 PC 검색 드롭다운 둘 다 화면 안 가짜 상품을 거르던 방식이었다. 이제 입력이 멈추고 잠깐 기다렸다가(모바일 300ms, PC 200ms) 서버에 검색을 보낸다. 모바일은 20개까지 받아 "검색 중…"과 결과 개수를 보여 주고, PC 드롭다운은 미리보기로 5개만 받는다. 서버 검색은 6/20 에 만든 상품명·브랜드·모델명에 검색어가 들어 있는지 보는 방식이다. 최근 검색어와 인기 검색어는 지금처럼 브라우저 쪽에 둔다.

{% hint style="warning" %}
**늦게 온 응답이 화면을 덮을 수 있다**

상품 목록 화면(6/23)은 늦게 도착한 옛 응답을 버리는데, 검색 두 곳은 기다렸다 보내기만 있고 그 처리가 없다. "냉장고"를 쳤다가 빨리 "세탁기"로 고치면, "냉장고" 결과가 나중에 도착해서 "세탁기" 결과를 덮어쓸 수 있다.
{% endhint %}
