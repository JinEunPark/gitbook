### 1. 6/20 코드 다듬기

6/20 코드에는 "검토 필요"라는 꼬리표가 붙어 있었다. 이날 Claude Code 의 코드 다듬기 기능(`/simplify`)으로 한 번 훑었고, 나온 9건을 모두 고쳤다. 구매자 입장에서 달라지는 동작은 없고, 코드가 짧아지면서 DB 를 덜 부르게 됐다. 그중 의미가 큰 건 주문할 때 재고를 잠그는 방식이다. 상품 N개를 하나씩 잠그느라 DB 를 N번 부르던 것을, "이 id 들 전부"를 한 번에 잠그는 질의 하나로 바꿨다.

나머지는 이런 것들이다. 할인율 계산과 대표 사진 주소 만들기가 상품 목록·관리자 상품·찜 세 파일에 똑같이 복사돼 있어서 공용 파일로 뺐고, "전체 몇 개, 몇 페이지"를 계산하는 코드 4곳도 함수 하나로 합쳤다. 결제 알림([웹훅](../glossary.md))의 서명을 확인할 때 주소 담당 코드가 결제 모듈 내부 부품을 직접 꺼내 쓰고 있었는데, 결제 서비스에 확인을 맡기는 식으로 고쳤다. 토스 결제 상태 `"DONE"`, `"CANCELED"` 같은 문자열은 이름 붙은 상수 5개로 바꿨고, 처리 단계마다 달아 둔 `# 1.` \~ `# 11.` 번호 주석은 지우고 코드를 줄였다.

견적(주문 전 금액 미리보기)도 하나 걸렸다. 설명에는 "잠금 없이"라고 써 놓고 실제로는 상품 행을 잠그고 있었다(`FOR UPDATE`, 다른 요청이 그 행을 못 건드리게 붙잡아 두는 것). 미리보기일 뿐이라 잠그지 않는 조회로 바꿨다.

{% hint style="info" %}
**6/20 노트에 적은 "당시 코드 문제" 중 해결된 것**

견적의 잠금, 하나씩 잠그기, 복붙 중복, 결제 모듈 내부 접근은 해결됐다. 아직 남은 건 직배송이 안 되는 주소일 때 엉뚱한 "주문 취소 불가" 오류를 재활용하는 것, 취소해도 재고가 돌아오지 않는 것, 토스 비밀키 설정 칸이 없는 것, 판매 중지한 상품이 상세 조회에 보이는 것이다.
{% endhint %}

{% hint style="warning" %}
**한 번에 잠글 때 순서를 정하지 않았다**

두 주문이 같은 상품들을 서로 다른 순서로 잠그면, 이론상 서로 상대가 풀어 주기를 기다리며 멈추는 교착 상태(데드락)가 생길 수 있다. id 순으로 정렬해서 잠그면 막을 수 있다. 혼자 운영하고 중고 단품 위주라 실제로 일어날 가능성은 낮다.
{% endhint %}

### 2. 서버 할 일 목록 갱신

6/20 에 "모델(DB 표)만 있음"이라고 적어 둔 항목들이 실제로는 다 만들어져 있어서, 목록을 현재 상태에 맞게 고치고 테스트 273개 통과를 적어 두었다. 완료 쪽에는 로그인·회원·상품 목록·관리자 상품 관리·장바구니·찜·배송지·주문·결제·사진 올리기가 들어갔다. 아직 안 된 것으로는 문자 인증, 본인인증(결제대행사 연동), 배송 추적, 알림·공지, 관리자 대시보드·주문·회원·매출(한 시간 뒤 5번에서 만듦), 환불을 적었다.

본인인증 항목 옆에는 "DB 에 직접 값을 넣어 우회 중"이라고 붙였다. 주문은 본인인증을 마친 사람만 할 수 있는데 인증 기능이 아직 없으니, 시험용 데이터에 인증 완료 시각을 직접 채워 넣고 있었다는 얘기다. 서버를 한 바퀴 두드려 보는 점검 스크립트는 33가지 경우를 확인한다. 새 할 일로는 로그인 전에 담아 둔 장바구니를 로그인 후 서버 장바구니와 합치는 기능(`POST /cart/sync`), 같은 상품을 동시에 주문하면 1건만 성공하는지 보는 테스트, 상품별 직배송 가능 지역(나중 단계)을 올렸다.

### 3·4. 관리자용 상품 사진 전체 교체

6/20 에 만든 상품 수정 기능으로는 사진을 바꿀 수 없었다. 추가·삭제·순서 바꾸기를 따로 만드는 대신, "이 상품의 사진은 이제 이 목록이다"라고 통째로 보내면 그대로 바꿔 주는 기능 하나로 처리했다. 관리자 화면 쪽에서는 정렬해 둔 사진 목록만 보내면 된다.

사진은 최대 10장이고 각각 주소와 종류(정면·측면 등, 선택)를 담는다. 서버는 그 상품의 기존 사진을 모두 지운 뒤 새 목록을 넣는데, 한 [트랜잭션](../glossary.md) 안에서 하기 때문에 중간에 실패하면 아무것도 바뀌지 않는다. 빈 목록을 보내면 사진이 전부 지워진다. 처음엔 사진마다 몇 번째인지(0, 1, 2…) 번호를 같이 받게 해서 화면 쪽이 번호를 빠짐없이 매겨야 했는데, 12분 뒤에 번호 칸을 없애고 보낸 순서대로 자동으로 매기게 바꿨다. 그러면서 사진 객체를 만드는 건 서비스가, 저장은 저장소가 하도록 역할도 나눴다. 테스트는 추가, 교체, 순서 변경, 전부 삭제, 없는 상품 다섯 가지다.

{% hint style="info" %}
**수정(PATCH)이 아니라 교체(PUT)로 만든 이유**

목록 전체를 보낸 그대로 바꾸는 동작이라 PUT 이 맞다. JPA 로 치면 `product.getImages().clear(); addAll(...)` 에 `orphanRemoval` 을 건 것과 같은 효과를, 삭제와 삽입을 직접 써서 낸 것이다.
{% endhint %}

### 5. 관리자 서버 기능 20개

5/3 에 그림만 만들어 둔 관리자 화면 5개 가운데 상품은 6/20 에 서버를 붙였고, 남은 대시보드·주문·회원·매출 4개에 필요한 서버 기능을 이날 한 번에 만들었다. 전부 관리자만 부를 수 있다. 화면만 연결되면 관리자가 오늘 매출을 보고, 송장을 넣어 주문을 배송중으로 넘기고, 문제 있는 회원을 정지시키고, 매출을 파일로 내려받을 수 있게 된다.

대시보드는 상단 숫자 4개(오늘 주문 수, 취소를 뺀 오늘 매출, 결제완료·준비중을 합친 처리 대기, 판매 중이면서 재고가 3개 이하인 재고 부족)와 최근 7일/30일/90일 일별 매출 그래프, 오래된 순으로 처리 대기 주문 4건, 카테고리별 주문 건수·매출 상위 8개, 재고 3개 이하 상품 20개를 보여 준다.

주문 관리는 다음과 같다.

| 기능        | 내용                                                                             |
| --------- | ------------------------------------------------------------------------------ |
| 목록        | 상태 탭별 개수(전체·결제완료·준비중·배송중·배송완료·취소, 취소 탭은 환불 포함)를 질의 한 번으로 센다. 주문번호나 주문자 이름으로 검색 |
| 상세        | 주문자, 받는 사람, 주문 당시 상품 정보, 결제수단, 배송(택배사·송장·상태)                                   |
| 송장 입력     | 송장을 넣으면 주문이 배송중으로 바뀐다. 결제완료·준비중일 때만 가능하고, 배송 정보가 없으면 새로 만들고 있으면 고친다            |
| 상태 수동 변경  | 준비중·배송중·배송완료로만 바꿀 수 있다                                                         |
| 관리자 취소    | 입금대기·결제완료·준비중일 때만                                                              |
| 내려받기(CSV) | 주문번호·일시·주문자·연락처·상품·금액·상태·배송방식                                                  |

회원 관리는 요약(전체, 본인인증 완료, 이번 주 월요일 이후 신규, 구매 경험 있음)을 질의 한 번으로 내고, 목록에서는 이름·이메일·휴대폰·아이디로 검색하거나 상태로 거를 수 있다. 목록에 회원별 주문 수와 취소를 뺀 누적 구매액이 같이 나온다. 회원 한 명의 상세와 상태 변경(정상/정지/휴면)도 있다.

상태 변경을 위해 회원 표에 "회원 상태" 칸을 새로 만들었다(기본값 정상). 원래 있던 "활성 여부" 칸은 상태가 정상일 때만 켜지도록 같이 맞춘다. 5/7 에 만든 로그인 확인 장치가 활성이 아닌 회원의 요청을 모두 거부하기 때문에, 관리자가 정지나 휴면으로 바꾸는 순간 그 회원은 서비스를 못 쓰게 된다. 5/2 에 "회원 상태가 생기면 하나로 합칠 예정"이라고 주석으로 적어 둔 걸 이날 실제로 했다.

매출 쪽은 기간 매출·주문 수·객단가(주문 1건당 평균)·취소율 요약을 질의 1번으로 내고, 일 또는 주 단위 추이, 결제가 끝난 건만 모은 결제수단별 매출, 주문 당시 가격 × 수량으로 계산한 많이 팔린 상품, 주문번호·일시·금액·상태를 담은 CSV 를 제공한다. 기간은 시작일과 종료일(`YYYY-MM-DD`)로 받고 기본은 최근 30일이며, 종료일이 시작일보다 앞이면 입력 오류로 돌려보낸다.

같은 작업 안에서 다듬은 것도 8가지 있다. 결제 상태 비교를 문자열 대신 정해진 값으로 하게 했고, 송장 저장 뒤 다시 조회하던 걸 새로고침 한 번으로 줄였고, "배송중으로 바꿀지" 판단을 저장소에서 서비스로 옮겼다. 쓸데없는 방어 코드를 지우고, 주문 집계 부분을 함수로 떼고, 회원 목록 결과를 이름 붙은 묶음(`NamedTuple`)으로 바꿨다. 회원 요약은 질의 4번에서 2번으로, 매출 요약은 3번에서 1번으로 줄었다.

{% hint style="danger" %}
**코드만 봐도 보이는 문제 (테스트가 없어서 당시엔 드러나지 않았다)**

* 주문 내려받기가 서버 오류(500)를 낼 수 있다. 전체를 뽑으려고 "한 페이지 10,000개"로 요청을 만드는데, 같은 코드의 입력 규칙이 한 페이지 최대 100개라 요청을 만드는 순간 규칙 위반으로 터진다.
