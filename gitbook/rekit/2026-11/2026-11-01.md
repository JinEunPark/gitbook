### 이날을 한 문단으로

10/23 이후 9일 만에 rekit 을 다시 열었다. 코드는 건드리지 않고, Claude 에게 서버 전체를 분석해서 한 문서로 정리해 달라고 했다. 구조와 DB, 기능 수, 결제 처리 순서, 배포 방식에 더해 아직 위험한 부분 목록까지 나왔는데, 그중 "서버 안에서 무슨 일이 일어나는지 볼 수 있는 장치가 없다"는 항목을 나흘 뒤 [11.05 일지](2026-11-05.md) 에서 바로 손봤다. 그리고 개인 포트폴리오에 rekit 에서 실제로 해결한 문제 여섯 가지를 사례로 새로 정리했다. 이때 숫자로 보여 줄 성과가 부족하다는 지적을 받아서, 이후로는 해결 전후를 직접 재서 남기기로 했다.

### 1. 서버 전체 분석 문서 (`초안.md`)

반년 가까이 쌓인 서버 코드를 한눈에 볼 수 있는 문서가 없었다. 17:33 에 "아키텍처부터 배포 구조까지 모든 걸 분석해서 정리해 달라"고 맡겼고, 431줄짜리 문서가 나왔다. 서버가 어떻게 나뉘어 있는지, DB 표가 몇 개인지, 결제를 어떤 순서로 처리하는지, 실제 서버에 어떻게 올라가는지가 들어 있고, 마지막에 아직 손대지 않은 위험 목록이 붙어 있다. 다음에 무엇부터 고칠지 정할 근거가 처음으로 생겼다.

Claude 는 저장소의 코드·설정·문서·저장 이력만 보고 썼고, 운영 서버에는 접속하지 않았다. 테스트도 실제로 돌리지 않았기 때문에 문서에 나오는 "테스트 약 565개"는 실행 결과가 아니라 테스트 함수 개수를 센 값이다.

#### 문서 구성

| 절   | 내용                                                                                                                                                  |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1·2 | 요약과 서버 구조. 한 프로그램 안에서 주문·결제·상품 같은 기능 묶음별로 나눴고, 토스·Octomo 같은 외부 서비스와 닿는 부분만 갈아끼울 수 있게 분리해 둔 구조다. Spring/JPA 대응표, 폴더 구조, 어느 묶음이 어느 묶음을 불러도 되는지에 대한 규칙 |
| 3   | 데이터 — DB 표 15개, 배송비 계산 규칙                                                                                                                           |
| 4   | 서버 기능(API) 약 100개, 로그인 방식(출입증 토큰·소셜 로그인·휴대폰 확인)                                                                                                     |
| 5   | 주문 상태가 바뀌는 순서, 토스 결제 처리 순서(잠그는 순서, 같은 요청이 두 번 와도 안전하게 하는 방법, 결제사 알림을 받으면 토스에 다시 물어 확인하는 방식), 방치 주문 자동 정리, 사진·그림 파일 올리기, 메일                          |
| 6·7 | 테스트와 품질 검사, 내 컴퓨터 실행 환경, 실제 서버 배치(맨 앞 nginx 뒤에 컨테이너들), 배포 자동화(버전 이름표를 붙이면 빌드하고 배포한 뒤 살아 있는지 확인하고, 실패하면 이전 버전으로 되돌림)                                 |
| 8   | 개발 연대기 (저장 이력 80개 기준)                                                                                                                               |
| 9   | 남은 작업과 위험 목록                                                                                                                                        |

#### 위험 목록 (문서 9.3절 요지)

| 구분  | 무엇이 위험한가                                                                           | 이후                                   |
| --- | ---------------------------------------------------------------------------------- | ------------------------------------ |
| 보안  | 요청 횟수 제한 도구를 설치만 해 두고 실제로 걸지 않았다. 로그인이나 아이디 찾기에 비밀번호를 끝없이 대입해 볼 수 있는 상태            | 기록 없음                                |

| 보안  | 휴대폰 확인 서비스(Octomo) 키를 아직 재발급하지 않았다. 8/14 에 키가 설정 파일에 평문으로 남은 일이 있었다                | 11/5 재발급 확인                          |
| 운영  | 자동 배포 과정에 테스트·코드 검사 단계가 없어서 테스트가 깨진 채로도 배포된다                                       | 기록 없음                                |
| 운영  | 서버 안을 볼 장치가 거의 없다. 기록 정리 도구와 재시도 도구는 설치만 됐고, 에러 알림(Sentry) 주소는 설정에만 있을 뿐 연결 코드가 없다 | 11/5 기록 정리·수치 수집·에러 알림 작업            |
| 운영  | DB 백업·복구 절차 없음, 배포할 때 잠깐 서비스가 끊김, DB 구조 변경이 서버 시작과 묶여 있음                           | 기록 없음                                |
| 데이터 | 회원 전화번호·주소를 암호화하지 않고 그대로 저장                                                        | 7/12 화면의 "암호화 저장" 안내 문구 문제(⑥)와 같은 줄기 |
| 성능  | 토스에 요청할 때마다 연결 도구를 새로 만들고, 상품 검색이 "글자 포함" 방식이라 상품이 늘면 느려진다                         | 기록 없음                                |

Claude 가 끝에 하나 덧붙였다. 문서에 운영 서버 IP, 접속 호스트 이름, 비밀 파일 위치가 들어 있으니 볼트를 외부에 동기화하거나 공유할 거라면 그 부분은 빼는 게 좋다는 것.

{% hint style="info" %}
**문서 안의 옛 이름**

문서 제목이 "Rekle(Rekit) 백엔드 전체 분석"으로 옛 이름부터 시작한다. 서버 저장소·DB·사진 저장소·컨테이너 이름이 아직 `rekle` 이라서 그렇다. 사용자가 보는 화면 문구가 아니라서 브랜드 규칙과는 상관없다.
{% endhint %}

### 2. 포트폴리오에 rekit 문제 해결 사례 6개

볼트에 흩어져 있던 포트폴리오 문서를 "문제 해결 과정과 성과 중심으로, 최신순으로" 하나로 합쳐 달라고 했다(17:41). rekit 은 원래 그 문서들에 없던 프로젝트라 Claude 가 코드 분석 결과와 이 폴더의 작업 노트를 읽고 사례 여섯 개를 새로 썼다.

| 2 | 가짜 결제 완료 알림으로 주문이 완료 처리될 수 있던 문제              | [08.31 일지](../2026-08/2026-08-31.md) · [09.04 일지](../2026-09/2026-09-04.md) |
