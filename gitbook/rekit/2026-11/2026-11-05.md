### 2. 개념 정리 (오늘 배운 것)

#### 관측성 3요소

| 데이터      | 질문             | 비유       | 도구                           |
| -------- | -------------- | -------- | ---------------------------- |
| **메트릭**  | 지금 얼마나 심각한가?   | 자동차 계기판  | Prometheus, Grafana          |
| **로그**   | 정확히 무슨 일이 있었나? | 일기장      | structlog JSON, Loki, ELK    |
| **트레이스** | 어디서 막혔나?       | 택배 배송 조회 | OpenTelemetry, Jaeger, Tempo |

흐름: 메트릭 알림("결제 실패율 70%") → 트레이스("토스 API 구간 8초") → 로그(request\_id 로 검색 → 에러코드)

#### 용어

* **request\_id** — 요청별 번호표(택배 송장). 동시 요청 수백 개 속에서 한 요청의 로그만 골라냄. Spring 의 **MDC** 와 같은 역할 → Python 은 `contextvars`
* **OpenTelemetry** — 수집 표준. Java 의 **SLF4J** 같은 존재 (백엔드 교체해도 앱 코드 그대로)
* **카디널리티** — 메트릭 라벨 값의 경우의 수. `user_id` 를 라벨에 넣으면 시계열 폭발 → **ID 는 로그로, 라벨엔 종류 적은 값만**
* **SLO / 에러 예산** — "결제 99.9% 성공 / 30일" 같은 사용자 기준 목표. CPU 80% 같은 자원 알림 대신 이걸로 알림 (알림 피로 방지)
* **샘플링 / 핫·콜드 저장 / Kafka 파이프라인** — 대기업 규모 문제. 지금 Rekle 에는 불필요

#### Prometheus 메트릭 핵심

* **pull 방식** — 앱은 `/metrics` 로 현재 숫자만 보여주고, Prometheus 가 15초마다 가져감
* 종류: **Counter**(증가만, `rate()` 로 봄) / **Gauge**(오르내림) / **Histogram**(분포 → p95) / Summary(워커 합산 불가 → 안 씀)
* **p95** — 100명 중 95명이 이 시간 안에 응답받음. 평균은 느린 소수를 가림
* Histogram 구간(bucket)은 **SLO 근처를 촘촘하게** — 기본 `0.1, 0.5, 1` 은 부정확
* ⚠️ **gunicorn 워커 4개 함정** — 프로세스마다 메모리 분리 → `/metrics` 가 매번 다른 워커 값 → 그래프 톱니. `PROMETHEUS_MULTIPROC_DIR` + `child_exit` hook 필요 (Spring 은 1 JVM 이라 없는 문제)

#### gunicorn 은 미들웨어가 아니다

| 역할        | Spring Boot          | Rekle                      |
| --------- | -------------------- | -------------------------- |
| 리버스 프록시   | nginx                | nginx                      |
| 애플리케이션 서버 | 내장 Tomcat            | **uvicorn**                |
| 프로세스 관리자  | 없음 (JVM 1개 + 스레드)    | **gunicorn**               |
| 미들웨어      | Filter / Interceptor | CORS, (예정) request\_id·메트릭 |

* gunicorn 이 필요한 이유 = **GIL** (Python 프로세스 1개 ≈ CPU 코어 1개)
* 현업: VM/compose → gunicorn+uvicorn 워커 (지금 방식) / **쿠버네티스 → 컨테이너당 uvicorn 1개, 확장은 Pod 수로** (대기업 주류, multiprocess 메트릭 문제도 없음)

### 4. 구현 — O0 + O1-1 (커밋 `27ddb68`)

#### 변경 전 → 후

```
# 전: 운영 로그엔 uvicorn 액세스 로그만. 앱 INFO 는 0줄.

# 후 (APP_ENV=production, 로컬 gunicorn 으로 실측):
{"event": "Application startup complete.", "level": "info", "logger": "uvicorn.error", "timestamp": "2026-11-04T18:18:34.189041Z"}
```

#### 파일별 변경

| 파일                           | 변경                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------- |
| `app/core/logging.py` (신규)   | `configure_logging(level, json_logs)` — structlog `ProcessorFormatter` 를 표준 logging 핸들러에 연결 |
| `app/main.py`                | `create_app()` 첫 줄에서 `configure_logging()` 호출                                               |
| `app/core/config.py`         | `log_level: Literal[...] = "INFO"` (오타면 기동 실패) + `json_logs` property (development 외 JSON)  |
| `app/core/database.py`       | `echo=settings.debug` 제거 → DEBUG 시 `sqlalchemy.engine` 레벨만 INFO                             |
| `docker-compose.prod.yml`    | `x-logging` anchor (json-file 20m × 5) → postgres/redis/app 적용 · 워커 클래스 교체                  |
| `Dockerfile`                 | `-k uvicorn_worker.UvicornWorker`                                                           |
| `pyproject.toml`             | `uvicorn-worker>=0.4.0`                                                                     |
| `.env.example` / 로컬 `.env`   | `LOG_LEVEL=INFO`                                                                            |
| `docs/요구사항정의서.md`            | 권장 gunicorn 명령 갱신                                                                           |
| `tests/test_logging.py` (신규) | 12건                                                                                         |

#### `configure_logging` 이 하는 4가지

1. **root 로거에 핸들러 + 레벨** — 버그의 직접 해결 (Spring 은 logback 기본 설정이 자동, Python 은 수동)
2. **기존 코드 무수정** — `logging.getLogger(__name__).info("%d건", n)` 18곳이 그대로 JSON 출력 (= SLF4J 그대로 두고 logback encoder 만 JSON 으로 바꾼 것)
3. **공통 필드** — `merge_contextvars`(request\_id 준비, MDC 역할) · `add_log_level` · `add_logger_name` · `TimeStamper(utc=True)` · `format_exc_info`(JSON 만)
4. **uvicorn 로거 통합** — uvicorn 이 자기 로거에 핸들러 달고 `propagate=False` → 걷어내고 root 로 올려 한 포맷·한 번만 출력

> 💡 **`format_exc_info` 를 넣은 이유**
>
> structlog 25.5 소스 확인 결과 `ProcessorFormatter` 는 표준 logging 의 `exc_info` 를 event dict 에 **넘기기만** 하고 문자열화 안 함 → 없으면 JSON 에서 `logger.exception()` 스택트레이스 유실.

> 🐞 **작업 중 발견 — SQL 로그 이중 출력**
>
> 로깅 설정을 넣자 로컬에서 SQL 이 두 번(평문 + JSON). 원인: `echo=True` 면 SQLAlchemy 가 **자체 핸들러를 직접 붙임**. 이전엔 root 핸들러가 없어서 안 드러났던 것. 해결: `echo` 제거, 로거 레벨만 올림 (SQLAlchemy 문서 권장). 운영은 `DEBUG=false` 라 원래 무영향.

#### 테스트 (`tests/test_logging.py`, 12건)

* 잘못된 레벨 즉시 실패 / WARNING 이면 INFO 미출력 / **기존 INFO 가 JSON 으로 나옴(핵심)** / UTC `Z` / `%d` 포맷 합쳐짐 / 스택트레이스 보존 / contextvars 포함 / uvicorn 1회 출력 / 로컬은 콘솔 / 앱 기동 시 INFO 활성 / engine echo 꺼짐 / DEBUG 일 때만 SQL
* 전역 상태라 테스트마다 root 로거·structlog 원복 fixture
* SQL 테스트 2건은 **이전 코드로 되돌리면 실패하는지까지 확인** (테스트가 진짜 회귀를 잡는지)

> 💡 **배운 점 — SQLAlchemy `AsyncEngine`**
>
> `AsyncEngine.echo` 는 없음(`None`) → 실제 값은 `engine.sync_engine.echo`. 그리고 echo 미지정 시 값은 `False` 가 아니라 `None`.

#### 남은 한계

* gunicorn **master** 프로세스 로그(`Booting worker` 등)는 여전히 gunicorn 자체 포맷 + 로컬 TZ — 앱 import 전 단계라 영향 밖. O2-5 `gunicorn.conf.py` 에서 `logconfig_dict` 로 통일 예정

### 5. 구현 — O1-2 \~ O1-8 (커밋 `1abedcb`, 서브 에이전트)

#### 배경 — 왜 했나

O1-1 로 로그가 **나오게** 만 했다. 하지만 동시 요청 수백 개의 로그가 섞이면 "그 고객의 그 요청" 을 골라낼 수 없고, 비밀번호·토큰이 로그에 찍힐 위험도 있었다. 이번엔 **한 요청의 흐름을 찾고 검색할 수 있게** 만드는 단계. 메인 세션이 worklog hook 을 설정하는 동안 **포크 서브 에이전트**에 위임 (조건: TDD, 게이트 3종, 커밋·옵시디언 금지). 끝난 뒤 메인 세션에서 게이트를 재실행해 결과를 확인하고 커밋.

#### 변경 후 로그 (APP\_ENV=production gunicorn 실측)

#### 설계 판단 (왜 그렇게 했나)

> 💡 **BaseHTTPMiddleware 대신 순수 ASGI**
>
> `BaseHTTPMiddleware` 는 하위 앱을 **별도 task** 로 돌린다 → 인증 dependency 가 바인딩한 `user_id` 가 미들웨어(액세스 로그)로 돌아오지 않는다. contextvars 는 task 경계를 넘어 "위로" 전파되지 않기 때문. Spring 비유: Filter 에서 MDC 를 읽는데, 하위 처리가 다른 스레드에서 돌아 MDC 값이 안 보이는 상황과 같다.

> 💡 **contextvars 를 요청 "끝"이 아니라 "시작"에 초기화**
>
> Starlette 은 `Exception` 핸들러를 모든 사용자 미들웨어 **바깥**(`ServerErrorMiddleware`)에 둔다. 요청 끝에서 지우면 500 핸들러가 로그를 찍을 땐 이미 `request_id` 가 사라져 있다. 요청마다 task 가 분리돼 있어 다음 요청으로 새지 않는다는 것은 테스트로 확인. 500 응답의 `X-Request-ID` 헤더는 미들웨어를 안 거치므로 핸들러가 직접 붙인다.

> 💡 **미존재 아이디 로그인 실패는 입력 원문을 안 남김**
>
> 아이디 칸에 비밀번호를 치는 실수가 흔하다 → 원문을 남기면 비밀번호가 로그에 남을 수 있다.

> ✅ **마스킹은 "키 이름" 기준**
>
> 메시지 문자열 안에 섞인 값은 못 가린다 → **민감값은 반드시 키워드 인자로** 넘길 것 (`logger.info("...", phone=phone)` O / `f"... {phone}"` X).

### 9. deploy 잡 롤백 수정 — 백엔드 `ec02f66` · 프론트 `3f5aab0`

#### 배경

§7 ② 의 롤백 문제 해결. 프론트(`rekle`)도 같은 상황인지 확인해 달라는 요청.

#### 프론트도 같은 구조였나?

|               | 백엔드 `deploy-was`                | 프론트 `deploy-client`                |
| ------------- | ------------------------------- | ---------------------------------- |
| compose 출처    | 워크스페이스(master)                  | 워크스페이스(master) — **같은 구조**         |
| 이미지           | VERSION 태그                      | VERSION 태그                         |
| compose 변경 이력 | 오늘 실행 명령이 2번 바뀜 → **실제로 롤백 깨짐** | 0.0.1 이후 변경 없음 → **지금은 무사, 잠재 위험** |

→ 프론트는 당장 깨지진 않지만 compose 를 한 번만 바꿔도 같은 문제가 되므로 **둘 다 같은 방식으로** 수정.

#### 한 일 (두 레포 `Jenkinsfile.deploy` 동일 패턴)

```groovy
sh 'git fetch --tags --force --prune'
sh "git show tags/${env.DEPLOY_TAG}:docker-compose.prod.yml > ${DEPLOY_COMPOSE}"   // .deploy-compose.yml
// 이후 docker compose -f ${DEPLOY_COMPOSE} pull / up -d, post 에서 rm
```

* VERSION 형식 검증을 build 잡과 같은 `X.Y.Z` 로 통일 (기존엔 "비어있지 않음" 만 확인)

> 💡 **왜 `git checkout` 이 아니라 `git show ... > 파일` 인가**
>
> checkout 으로 `docker-compose.prod.yml` 을 덮어쓰면 워크스페이스의 추적 파일이 바뀐 채 남는다. 별도 파일로 꺼내 쓰고 지우면 다음 SCM checkout 과 충돌할 일이 없다.

> ✅ **Jenkinsfile 은 master 것이 실행된다**
>
> deploy 잡은 "Pipeline script from SCM"(master) 이라, 이번 수정은 **푸시 즉시** 모든 태그 배포에 적용된다 — 0.0.4 로 롤백해도 이제 0.0.4 의 compose 를 쓴다.

#### 검증

* 로컬에서 Jenkins 셸 동작 재현: 백엔드 0.0.1\~0.0.4 각 태그 compose 를 꺼내 `docker compose config` → 모두 해석 OK, 실행 명령(`uvicorn.workers.UvicornWorker`)이 그 태그 이미지와 일치, `rekit_edge` 네트워크 유지. master compose 는 `gunicorn -c gunicorn.conf.py` (0.0.5 이미지에 포함 예정)
* 프론트 0.0.1 / 0.3.5 / 0.3.6 태그 compose 해석·이미지 태그 주입 OK
* **실제 Jenkins 에서 돌려보진 못함** — 다음 배포 때 deploy 로그에 `compose 도 태그 X 기준` 이 찍히는지 확인
* 프론트 레포의 미커밋 `public/sitemap.xml` 변경은 이번 작업과 무관해 커밋에서 제외(그대로 남아 있음)

### 10. 메트릭 · 헬스체크 · Sentry · 로컬 모니터링 스택 (커밋 `dd0adea`)

#### 배경

O1(로깅) 이 끝나 "나머지 모니터링 작업" 진행. 외부 준비(스테이징 서버·알림 채널·Sentry 계정)가 필요한 O6·O7 은 빼고 **코드로 할 수 있는 O2·O3·O4·O5(로컬)** 까지.

#### 한 일

| 단계            | 내용                                                                                                                                        |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **O2 메트릭**    | `app/core/metrics.py` + `/metrics`. HTTP(요청 수·응답시간·처리 중 요청), DB 사용 중 커넥션, 비즈니스(결제 승인 결과·토스 API 시간·웹훅·주문·가입·방치 주문 정리)                      |
| **O4 헬스체크**   | `app/core/health.py` + `/health/ready` — DB `SELECT 1` + Redis `PING` 동시, 2초 타임아웃, 실패 시 503 + 어느 의존성인지. compose app healthcheck(liveness) |
| **O3 Sentry** | `app/core/sentry.py` — DSN 비면 비활성(현재). PII 스크럽, BusinessError 제외, request\_id·user\_id 태그, release=배포 태그                                  |
| **O5 로컬 스택**  | `infra/monitoring/` — Prometheus v3.5.0 + Grafana 12.1.0, "Rekle 서비스" 대시보드 10패널 자동 등록                                                     |

Spring 비유: Actuator(`/actuator/health`, `/actuator/prometheus`) + Micrometer 를 직접 만든 것. `/health` = liveness, `/health/ready` = readiness.

#### 계획과 달라진 판단 (왜)

> 💡 **instrumentator 를 안 쓰고 미들웨어에서 직접 기록**
>
> `prometheus-fastapi-instrumentator` 는 라우트 이름을 자체 방식으로 찾는다 → O1 에서 겪은 **FastAPI 0.162 중첩 라우터의 `/api/v1` 누락**이 메트릭 라벨에서 재발할 위험. 이미 두 버전에서 검증된 `RequestContextMiddleware` 가 **로그와 같은 path·status** 로 메트릭도 기록 → 로그·메트릭 값 일치 + 의존성 1개 감소.

> 💡 **워커 4개 대응을 `gunicorn.conf.py` hook 으로**
>
> compose 에 `rm -rf` 를 넣는 대신 `on_starting`(env 설정 + 이전 파일 삭제) · `child_exit`(죽은 워커 정리). env 를 파일 최상단이 아닌 hook 에서 설정해야 **conf 를 읽기만 하는 테스트까지 멀티프로세스 모드로 바뀌지 않는다**.

> 💡 **DB 풀은 "scrape 시점에 읽기" 가 아니라 이벤트로**
>
> scrape 를 받은 워커 하나의 pool 값만 보이므로 멀티 워커에서 틀린다 → checkout/checkin 이벤트로 Gauge(livesum) 증감.

* 결제 승인 메트릭은 **PG 호출 결과만** 센다 (금액 불일치 같은 사전 거절은 제외 — 테스트로 고정)
* Sentry traces 기본 **0.0**(에러만) — 무료 플랜 한도. 결제 이상 알림은 `capture_message` 를 곳곳에 넣지 않고, 이미 ERROR 로 남기는 로그를 Sentry LoggingIntegration 이 기본으로 잡는 것을 이용

#### 검증

> 💡 **핵심 실측 — 워커 4개 합산**
>
> `gunicorn -c gunicorn.conf.py`(워커 4) 에 요청 20건 → `/metrics` **6회 수집 모두 정확히 20**. 고치기 전이었다면 응답한 워커에 따라 5·4·6 처럼 톱니.

* `/health/ready` 200 `{"database":"ok","redis":"ok"}`, 처리 중 요청·DB 커넥션 요청 후 0 복귀
* 로컬 스택 E2E: Prometheus target `up` → 요청 60건이 경로·status 별 집계 → Grafana→Prometheus 쿼리 60. 대시보드 자동 등록 확인 (패널 화면은 직접 안 봄)
* 테스트 666 → **704 passed** / ruff 0 / mypy 0, **운영 이미지(FastAPI 0.162)에서도 704 passed**

> 🐞 **테스트 함정 — 이벤트 루프가 다른 커넥션**
>
> DB 풀 테스트가 단독으론 통과, 전체 실행에선 `attached to a different loop` 실패. 전역 engine 풀이 **앞선 테스트의 이벤트 루프에서 만든 커넥션**을 재사용했기 때문 → 테스트 전용 엔진 + dispose 후 실동작 검증으로 변경. (`event.contains` 는 dispose 가 풀 객체를 새로 만들면 False 라 부적합 — 리스너는 새 풀로 옮겨지지만 조회는 객체 단위)
