### 1. Kotlin + Spring 으로 옮긴다면

02:09 에 "현재 시스템을 kotlin spring 으로 전환하려해 그게 포트폴리오에 더 알맞는거 같아서 어떤 방식으로 진행하는게 좋을까"라고 물었다. Kotlin 이야기는 [11.05 일지](2026-11-05.md) 저녁에 처음 나왔다. 그때도 "대기업들이 자바를 많이 쓰잖아"라고 하면서 동시에 "근데 사실 현재 서비스에 굳이 전환이 필요한건 아니잖아"라고 했으니, 서비스 개선이 아니라 포트폴리오용이라는 건 그때부터 정해져 있었다. 11/5 의 결론이 "전부 다시 짜는 건 위험하니 모듈 하나씩"이었고, 이날은 그 순서와 학습 자료를 구체적으로 정리했다.

#### 지금 서버 규모 — 기술 검토 과정에서 말한 숫자와 실제

기술 검토 과정에서는 서버 기능(엔드포인트)이 97개, DB 구조 변경 스크립트가 24개, 로그인 출입증 서명 방식이 HS256 이라고 했다. 그날 시점 코드와 대조해 보니 기능 97개와 HS256 은 맞았고, 구조 변경 스크립트는 실제로 21개였다. 24 는 설정 파일이나 템플릿까지 같이 센 숫자로 보인다. 앱 코드 약 1만 3천 줄, 테스트 약 1만 4천 줄이라는 말은 따로 세어 보지 않았다.

#### 제안 — 바꾸지 않을 것부터 정한다

새 서버로 옮기는 동안 바깥에서 보기엔 아무것도 달라지지 않아야 한다. 그래서 네 가지를 고정하기로 했다.

* 화면과 서버 사이 약속(API 모양)은 지금 서버가 내놓는 명세를 그대로 따른다. 화면은 고칠 필요가 없다.
* DB 는 같은 Postgres 를 같이 쓴다. 옮기는 동안 DB 구조 변경은 지금 쓰는 도구(Alembic) 한 곳에서만 하고, Spring 쪽은 구조를 검사만 하게 둔다. 다 옮긴 뒤에 Flyway 로 넘긴다. 구조를 두 곳에서 관리하다 어긋나는 일을 막으려는 것.
* 로그인 출입증은 같은 비밀값으로 서명한다. 옮기는 중에도 로그인이 풀리지 않는다.
* 비밀번호 암호화 형식(bcrypt)은 Spring 의 비밀번호 검사기가 그대로 읽을 수 있다. 회원이 비밀번호를 다시 설정할 필요가 없다.

추천받은 기술은 Kotlin 2.x, Spring Boot 3.x, Spring MVC 에 Virtual Threads(WebFlux 나 코루틴보다 단순), JPA 와 QueryDSL 또는 Kotlin JDSL, Spring Security 로 출입증 검사, Redis, 요청 횟수 제한용 Bucket4j, 테스트는 JUnit5 나 Kotest 와 MockK, Testcontainers 였다. 수치 수집(Micrometer + Prometheus)은 수치 이름을 지금과 똑같이 맞춰 두면 11/10 에 만든 Grafana 대시보드와 알림 규칙을 그대로 쓸 수 있다고 했다.

#### 옮기는 순서

맨 앞 nginx 에서 주소별로 나눠 보내는 방식이다. 예를 들어 고객센터 주소(`/api/v1/help/*`)만 새 Spring 서버로 보내고 나머지는 기존 서버로 보낸다.

**11/5 와 달라진 첫 대상**

11/5 저녁에는 기술 검토 과정에서 결제 모듈부터 옮기라고 했다(면접에서 이야기할 거리가 많고 어렵다는 이유). 이날은 고객센터부터 시작하고 주문·결제는 다섯 번째에 묶어서 옮기는 걸로 바뀌었는데, 왜 바뀌었는지는 대화에 없다. 11/5 에 기술 검토 과정에서 짚은 "주문 취소와 결제 취소가 한 번의 DB 작업으로 묶여 있다"는 점을 생각하면, 결제만 먼저 떼어 내려면 두 서버에 걸친 작업을 맞추는 별도 장치(Saga·Outbox)가 필요해서 첫 단계로는 어렵다고 본 것 같다. 다른 선택지로 "기존 서버는 두고 새 기능(예: 판매자 가입 `/sell`)만 Kotlin 으로 만들기"도 나왔다. 다만 `/sell` 은 10/23 에 판매 구조를 정하면서 링크를 지운 상태다([10.23 일지](../2026-10/2026-10-23.md)).
{% endhint %}

다 옮긴 뒤에는 기존 부하테스트 대시보드로 두 서버의 응답 속도·처리량·메모리를 비교해 숫자로 남기고, "왜 바꿨나, 서비스를 멈추지 않고 어떻게 옮겼나, 무엇이 어려웠나, 결과는 어땠나" 순서로 회고를 쓰라는 제안이었다. 해결 전후를 실제로 재서 남긴다는 포트폴리오 규칙과 같은 방향이다.

### 3. "Implementing DDD with Spring" 강의를 rekit 에 넣는다면

02:40 에 Spring I/O 2024 강의 "Implementing Domain Driven Design with Spring" 링크(예제 저장소 `maciejwalkowiak/implementing-ddd-with-spring-talk`)를 주고, 되게 감명 깊었는데 지금 프로젝트에 도입하는 건 어떠냐고 물었다. 기술 검토 과정에서는 강의 예제(도서관 대출)와 rekit 의 주문·상품·결제 코드를 나란히 놓고 비교했다. 대부분은 가져올 만하지만, 재고 차감을 강의처럼 나중에 따로 처리하게 바꾸는 것만은 rekit 에서 위험하다는 결론이었다.

가져올 만하다고 본 것은 이렇다. 강의처럼 기능 묶음을 나누는 건 rekit 의 상품·주문·결제와 그대로 맞고, 패키지를 도메인·응용·인프라로 나누는 것도 옮기면서 바꿀 수 있다. 가장 효과가 큰 건 값 객체다. 강의의 `Isbn` 처럼 만들 때 형식을 검사하는 타입을 주문번호(RK-YYMMDDxxxx), 금액, 전화번호, 상품 번호에 쓰면 된다. 주문이 상품 객체 대신 상품 번호만 들고 있게 하는 것, Spring Modulith 의 검사 한 줄로 기능 묶음 사이 경계를 자동 검사에 넣는 것도 권했다.

지금 코드가 바로 강의가 풀려던 문제를 갖고 있다는 것도 확인했다. 주문과 결제 코드가 상품 쪽 내부 모델을 직접 가져다가 재고를 바꾼다. JPA 로 치면 `OrderService` 가 `ProductRepository` 를 직접 주입받아 상품 엔티티를 고치는 구조다.

{% hint style="warning" %}
**그대로 따라 하면 안 되는 부분 — 재고 차감을 이벤트로 빼기**

강의에서는 대출이 생기면 "대출됨" 이벤트를 내고, 그걸 듣는 쪽이 저장이 끝난 뒤 별도 작업으로 책을 "대출 불가"로 바꾼다. 잠깐 어긋나도 결국 맞춰지면 된다는 방식이고, 강의 코드에도 "이미 빌린 책이 또 빌려지지 않게 할 것"이라는 TODO 가 남아 있다고 한다. rekit 상품은 대부분 폐업 매장에서 나온 재고 1개짜리라서, 그 잠깐의 틈에 다른 사람이 같은 상품을 사면 그대로 이중 판매가 된다. 지금 서버는 상품을 잠근 채 주문과 같은 DB 작업 안에서 재고를 깎아서 이걸 막고 있다(10/16 이중 판매 문제 해결, 11/10 상품 잠그는 순서 고정).
{% endhint %}

그래서 경계를 이렇게 나누자고 했다. 재고 확인·차감과 결제 금액 검증은 지금처럼 주문과 같은 DB 작업 안에서 바로 처리한다(주문 쪽이 상품 쪽에 공개된 "재고 잡기" 기능을 부르고 잠금은 유지). 주문 완료 뒤 장바구니 비우기, 품절 표시, 관리자 알림, 메일은 이벤트로 빼도 된다. 주문 취소 때 재고를 되돌리는 것도 조금 늦어도 큰 문제가 없으니 이벤트로 처리할 수 있다고 봤다.

{% hint style="success" %}
**원칙 — DDD 는 핵심 기능에만**

고객센터·배송지·찜은 단순한 읽기·쓰기라서 애그리거트나 이벤트를 붙이면 과하다. 주문·결제·상품에만 제대로 적용하고 나머지는 패키지 구조만 맞춘다. 포트폴리오에 쓸 문장으로는 "강의 패턴을 그대로 쓰지 않고, 정합성이 꼭 필요한 곳(재고)과 조금 늦어도 되는 곳(부가 처리)을 나눴다"를 제안받았다.
{% endhint %}

{% hint style="info" %}
**확인 필요 — "취소 때 재고 복구는 늦어도 괜찮다"**

기술 검토 기준으로 분류인데, rekit 은 취소된 1개짜리 상품을 바로 다시 팔 수 있어야 한다. 복구가 늦어지면 그동안 품절로 보여서 팔 기회를 놓친다. 데이터가 틀리는 문제는 아니고 못 파는 시간이 생기는 문제라서, 이중 판매만큼 위험하진 않다는 뜻으로 읽힌다. 그리고 지금 코드에는 환불 뒤에 결제사 알림이 와서 재고가 한 번 더 늘어나는 버그(⑫, [09.04 일지](../2026-09/2026-09-04.md))가 있다. 재고 복구를 이벤트로 옮기려면 같은 취소가 두 번 와도 한 번만 되돌리게 하는 장치부터 갖춰야 한다.
{% endhint %}

Kotlin 쪽 메모도 있었다. 자바 `record CopyId` 는 Kotlin 에서 `data class CopyId(val id: UUID)` 에 `@Embeddable` 을 붙이면 되고, `@JvmInline value class` 는 JPA 와 잘 안 맞아서 ID 타입에는 쓰지 말라고 했다. JPA 기본 생성자 문제는 `kotlin("plugin.jpa")` 로 해결된다. 적용 순서는 고객센터로 뼈대만(DDD 없이), 상품으로 값 객체와 애그리거트 연습, 주문·결제에 이벤트와 Modulith 적용(재고만 바로 처리), 마지막으로 경계 검사 테스트와 모듈 문서 자동 생성.

대화는 기술 검토 과정에서 상품 모듈 Kotlin 예제를 만들어 주겠다고 제안한 데서 끝났다. Kotlin 프로젝트를 실제로 만든 기록은 없고, 11/16 지금도 `rekit_backend_kt` 같은 폴더는 없다.
