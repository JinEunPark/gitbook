# 08.13 · 본인 확인을 휴대폰 QR 로, 품절 자동 전환

### 이날을 한 문단으로

한 달 쉬고 처음 저장한 날이다. 7/12 에 화면만 먼저 만들어 둔 Octomo 휴대폰 인증(QR 을 찍어 문자 한 통 보내면 끝나는 방식)의 서버 쪽이 이날 들어왔다. 그러면서 처음부터 설계만 해 두고 한 번도 실제로 쓴 적 없던 실명 본인인증(CI/DI) 관련 DB 와 코드를 통째로 걷어냈고, 이제 주문할 수 있는 회원인지는 휴대폰 인증 하나로만 판단한다. 전화번호는 `010-1234-5678` 처럼 하이픈을 넣은 형식으로 통일했다. 그리고 재고가 0 이 되면 상품이 자동으로 품절 상태가 되고, 취소로 재고가 돌아오면 다시 판매 중이 되게 했다. 7/12 화면이 이날 처음으로 서버와 맞물려 돌 수 있게 됐지만, 실제 휴대폰으로 QR 을 찍어 본 기록은 없다.

### 1. 실명 본인인증을 없애고 Octomo 휴대폰 인증 하나로

처음 계획(5/1)은 가입 때 문자 인증, 첫 주문 전에 통신사 실명 본인인증(CI/DI), 결제 때 카드사 확인의 3단계였다. 그런데 실명 본인인증은 법적 의무가 아니었고, 코드도 설계만 있을 뿐 실제로 연결된 적이 한 번도 없었다. 그래서 가운데 단계를 없애고 첫 단계를 Octomo 방식 휴대폰 인증으로 바꿔, 휴대폰 인증을 한 회원을 곧 인증된 회원으로 보게 정리했다. 구매자는 주문 전에 QR 하나 찍고 문자 한 통 보내면 된다.

계획서에 적힌 이유는 두 가지다. 하나는 법 쪽인데, "개인 간 거래에는 사업자 규제가 직접 적용되지 않고 CI/DI 수집을 강제하는 조항도 없으며, 오히려 최근 규제 흐름은 신원정보 수집을 최소화하는 방향"이라는 판단이다. 다른 하나는 5/1 부터 있던 본인인증 기록 표와 연결 틀이 "아직 실제로 연동된 적 없는 뼈대"였다는 것. 7/4 서버 할 일 목록에 "본인인증은 DB 에 직접 값을 넣어 우회 중"이라고 적혀 있던 것도 그래서였다.

#### Octomo 인증이 돌아가는 순서

보통 문자 인증은 서버가 사용자에게 인증번호를 보낸다. Octomo 는 거꾸로 사용자가 Octomo 번호로 문자를 보내게 한다(역방향 인증, MO).

1. 구매자가 번호를 넣고 인증을 누르면, 서버가 16자리 코드를 만들어 Redis(잠깐 쓰는 메모리 저장소)에 5분 동안 보관하고 Octomo 에 이 코드로 QR 을 만들어 달라고 해서 그 QR 이미지를 화면에 돌려준다.
2. 구매자가 휴대폰으로 QR 을 찍으면 받는 번호(1666-3538)와 본문(코드)이 채워진 문자 앱이 열리고, 전송만 누르면 된다.
3. 화면이 확인을 요청하면 서버가 Octomo 에 "이 번호에서 최근 5분 안에 이 코드가 왔는지" 묻는다. 왔으면 보관한 코드를 지우고(재사용 방지) 회원의 전화번호와 인증 시각을 저장한다.

우리 서버는 문자를 한 통도 보내지 않으니 발신번호 등록이나 건당 발송비, 문자 업체 연동이 다 필요 없다. 계획서의 요금은 무료가 월 1만 건, 유료가 9,900원에 월 10만 건이고 "지금 트래픽이면 무료로 충분"이라고 적었다. 하나 걸린 게 있었는데, Octomo 는 성공하면 보통의 200 OK 대신 201 Created 를 돌려준다. 둘 다 성공으로 받게 하고 테스트도 2개 넣었다. Spring 으로 치면 "휴대폰 인증기" 인터페이스와 그 Octomo 구현체를 만들어 서비스에 주입한 구조다.

{% hint style="info" %}
**계획서와 실제 화면이 다른 곳 — QR 다시 받기**

계획서는 QR 이 만료되면 사용자가 직접 다시 받게 하겠다고 적고 "자동이 좋으면 알려 달라"고 했는데, 7/12 에 저장된 화면은 QR 만료와 60초 대기가 둘 다 끝나면 알아서 새 QR 을 받는다. 계획서(7/10)를 쓴 뒤 자동으로 바꾸고 문서는 안 고친 로 기록했다. 실제 코드를 기준으로 본다.
{% endhint %}

{% hint style="info" %}
**"전화번호는 암호화 저장" 안내는 일부러 남긴 문구**

7/12 노트에서 버그로 적은 "전화번호는 암호화해서 저장합니다" 안내는 실수로 남은 게 아니라 계획서에서 유지하기로 정한 문구다. 이날 고친 요구사항 정의서에도 전화번호는 암호화 저장한다고 그대로 적혀 있다. 그런데 이날도 암호화 코드는 없어서 전화번호는 `010-1234-5678` 그대로 저장된다. 11/16 현재도 같다.
{% endhint %}

### 2. 전화번호 저장 형식 통일

7/12 화면이 전화번호에 하이픈을 붙여 보내기 시작해서, 서버도 아예 하이픈을 넣은 `010-1234-5678` 형식으로 저장하게 바꿨다(전에는 숫자만 저장). 들어오는 값은 하이픈이 있든 없든, 공백이 섞여 있든 같은 형식으로 고쳐서 저장한다. 하이픈과 공백을 지운 뒤 휴대폰 번호 형식인지 보고, 11자리면 3-4-4, 011 같은 옛 10자리면 3-3-4 로 끊는다.

이 규칙은 "전화번호 타입" 하나로 만들어서 배송지 추가·수정, 내 정보 수정, 인증 요청·확인 다섯 곳이 같이 쓴다. 전에는 곳곳에 같은 검사가 복사돼 있었다. Spring 의 커스텀 검증 어노테이션 같은 것이다. 관리자 회원 검색은 저장 형식이 바뀌면 `01012345678` 로 찾을 때 안 걸리게 되니까, 저장된 값과 검색어 양쪽에서 하이픈을 지우고 비교하게 했다. 하이픈이 있을 때와 없을 때를 실제 DB 로 돌리는 테스트 2개를 넣었고, 개발용 가짜 회원 전화번호도 새 형식으로 바꿨다.

{% hint style="warning" %}
**이미 저장된 번호는 바꾸지 않음**

DB 변경 스크립트가 기존 전화번호 값은 건드리지 않아서, 예전 `01012345678` 과 새 `010-1234-5678` 이 DB 에 섞인다. 검색은 양쪽 하이픈을 지우고 비교하니 문제없지만 화면에 보이는 형식은 섞일 수 있다. 당시엔 개발용 DB 뿐이라 영향은 작았다.
{% endhint %}

### 3. 확인한 것과 이날 남은 문제

Octomo 부분은 실제 Octomo 를 부르지 않고 가짜 응답을 끼운 테스트로만 확인했다. 새로 넣은 테스트는 Octomo 부품 16개(코드가 16자리인지, 저장 이름이 숫자만인지, 201 응답 처리, 키가 없을 때 오류, 저장된 코드가 없으면 Octomo 를 아예 안 부르는지, 성공하면 코드가 지워지는지 등), 전화번호 형식 9개, 그리고 다시 쓴 휴대폰 인증 흐름 4개다. 계획서에는 DB 변경 뒤 회원 10명의 인증 상태를 "재확인 완료"했다고 적혀 있다. 실제 휴대폰으로 QR 흐름을 해 본 기록은 없다.

이날 생긴 문제 중 세 가지는 11/16 현재까지 남아 있다.

**내 정보 수정 API 로 인증 없이 번호를 바꿀 수 있음 (당시 \~ 11/16 현재도)**

6/24 에 만든 내 정보 수정은 전화번호가 들어오면 그대로 저장한다. 이날부터 휴대폰 인증이 주문 가능 여부의 유일한 기준이 되면서 이게 문제가 됐다. 예를 들어 번호 A 로 인증한 다음 수정 API 로 번호를 B 로 바꿔도 "인증됨"이 그대로 남는다. 화면의 프로필 수정은 이름만 보내고 번호는 인증 칸으로만 바꾸게 돼 있어서 화면으로는 안 되고 API 를 직접 부를 때만 된다. 수정 API 가 전화번호를 안 받게 하면 끝난다. 11/16 현재도 그대로다(`app/user/user_service.py` 53번째 줄).
{% endhint %}

{% hint style="info" %}
**인증 코드가 사람이 아니라 번호에 묶여 있음**

코드를 번호 기준으로 보관하기 때문에, 다른 계정이 같은 번호로 인증을 요청하면 먼저 띄운 QR 의 코드가 덮어써진다(60초 제한도 번호 단위다). 문자를 보낸 직후 다른 계정이 같은 번호로 확인을 먼저 누르면 그 계정이 인증되기도 한다. 둘 다 남의 번호를 알고 타이밍까지 맞춰야 해서 위험은 낮다. 그리고 전화번호에 중복 금지 제약이 없어서 한 번호로 여러 계정을 인증할 수 있다. 요구사항의 "중복 가입 방지"는 코드로는 지켜지지 않는 셈이다.
{% endhint %}

### 4. 재고 0 이면 자동 품절, 돌아오면 다시 판매 중

5/2 부터 DB 설명에는 "품절 — 재고 0 이면 자동 전환"이라고 적혀 있었지만 실제로 그렇게 하는 코드는 없었다. 그래서 재고가 0 인 상품도 판매 중으로 남아 있었고, 7/12 화면은 재고가 0 이하면 품절로 보여 주는 식으로 때우고 있었다. 이날 서버가 상태를 직접 바꾸게 했다. 주문으로 재고가 0 이 되면 품절, 취소로 재고가 돌아오면 다시 판매 중이다. 다만 운영자가 일부러 숨긴 상품은 재고가 늘어도 되살리지 않는다.

| 언제              | 재고   | 상태                   |
| --------------- | ---- | -------------------- |
| 주문 생성           | 줄어듦  | 0 이하가 되고 판매 중이었으면 품절 |
| 구매자 취소, 시간 초과   | 늘어남  | 0 보다 크고 품절이었으면 판매 중  |
| 관리자 취소          | 늘어남  | 위와 같음                |
| 결제 실패·취소 알림(웹훅) | 늘어남  | 위와 같음                |
| 운영자가 숨긴 상품      | 늘어나도 | 숨김 그대로               |

규칙은 한 곳에만 적어 두고 위 네 경로가 같이 쓴다. 그리고 재고를 바꾸는 DB 명령 한 번 안에서 상태도 같이 바꾸도록 했다. 7/6 에 만든 "재고를 한 번에 안전하게 줄이는 명령"에 상태 전환만 얹은 것이라, 두 사람이 동시에 사도 재고와 상태가 따로 놀지 않는다. JPA 로 치면 엔티티를 읽어서 `if` 로 바꾸는 대신 `@Modifying @Query("update … set status = case …")` 한 줄로 처리한 셈이다. 실제 DB 로 돌리는 테스트 8개로 확인했다(0 으로 줄면 품절, 남으면 판매 중 유지, 품절에서 늘면 판매 중, 숨김은 늘어도 숨김을 주문·관리자 주문·결제 세 곳에서 각각).

{% hint style="info" %}
**구매자 화면에서 달라지는 점**

상품 목록과 홈 추천은 판매 중인 상품만 보여 준다. 그래서 이날부터 품절 상품은 목록과 홈에서 사라지고, 7/12 에 만든 품절 배지는 상품 상세·장바구니·찜 목록에서만 보인다. 장바구니 담기와 주문은 이미 7/1 부터 판매 중이 아니면 거절하고 있었다.
{% endhint %}

{% hint style="warning" %}
**관리자가 재고를 고칠 때는 상태가 안 바뀜 (당시 \~ 11/16 현재도)**

자동 전환은 주문·취소·결제 알림 경로에만 붙었고, 관리자 상품 수정은 재고 숫자만 바꾼다. 그래서 품절 상품에 관리자가 재고 5 를 넣어도 계속 품절이라 목록에 안 나오고, 상태를 직접 판매 중으로 바꿔 줘야 한다. 반대로 재고를 0 으로 내려도 판매 중으로 남는다. 11/16 현재도 같다.
{% endhint %}
