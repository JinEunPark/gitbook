# 08.27 · 소셜 가입자 탈퇴 문제 해결

### 이날을 한 문단으로

전날 네이버 검수를 준비하다 찾은 문제, 소셜 로그인으로만 가입한 사람은 탈퇴를 할 수 없다는 문제(6/28 부터 있던 구멍)를 하루 만에 고쳤다. 회원마다 "직접 정한 비밀번호가 있는지"를 기록하는 칸을 새로 만들고, 비밀번호가 있으면 예전처럼 비밀번호로, 없으면 카카오·네이버·구글 로그인을 한 번 더 거쳐 본인임을 확인한 뒤 탈퇴하게 했다. 소셜 재확인이 끝나면 서버가 10분짜리 탈퇴 전용 통행증을 내주고, 화면은 그걸 내밀어 탈퇴를 마친다. 다만 이날 전에 소셜로 가입한 사람들은 기록 칸이 "비밀번호 있음"으로 채워져서 여전히 탈퇴를 못 하고, 이건 11/16 현재도 남아 있다.

### 1. 왜 했나

6/28 에 탈퇴를 다시 만들면서 "비밀번호를 한 번 더 입력해야 탈퇴"를 넣었다([06.28 일지](../2026-06/2026-06-28.md)). 그런데 5/10 에 만든 소셜 가입은 비밀번호 자리에 아무도 알 수 없는 임의의 값을 넣는다. 그러니 소셜로만 가입한 사람은 자기 비밀번호를 모르고, 결국 탈퇴 자체가 안 된다. 6/28 노트에 경고로 남겨 뒀던 부분이다. 8/26 네이버 검수를 준비하면서 "네이버 검수 때 회원 탈퇴가 실제로 동작해야 한다"는 조건 때문에 미룰 수 없는 문제가 됐다([08.26 일지](2026-08-26.md)).

***

### 2. 서버 쪽

비밀번호 없는 회원이 탈퇴하는 순서는 이렇다.

1. 탈퇴 창에서 카카오·네이버·구글 중 하나를 누르면 그 회사의 동의 화면으로 간다. 이때 "이번엔 탈퇴 목적"이라는 표시를 브라우저에 남겨 둔다. 돌아오는 주소는 평소 로그인과 같다.
2. 돌아오는 화면에서 평소처럼 위조 요청이 아닌지(state 값) 확인한 뒤, 서버에 "탈퇴용 재확인"을 요청한다. 이 요청은 로그인한 상태에서만 된다.
3. 서버는 그 소셜 회사에서 받은 계정 번호가 지금 로그인한 사람에게 연결된 소셜 계정인지 본다. 맞으면 10분짜리 탈퇴 통행증(JWT)을 준다.
4. 화면이 그 통행증을 담아 탈퇴를 요청하면, 서버는 통행증 종류와 주인이 맞는지 보고 6/28 에 만든 방식 그대로 개인정보를 지워 익명 처리한다.

회원 표에 "비밀번호 있음" 칸을 넣었고, 기본값은 있음이며 소셜로 새로 가입하면 없음으로 저장한다. 비밀번호 찾기로 임시 비밀번호를 받으면(5/7 기능) 그때부터는 실제 비밀번호를 아는 셈이라 있음으로 바꾼다. 탈퇴 API 는 비밀번호가 있는 회원에게는 비밀번호를, 없는 회원에게는 통행증을 요구한다. 내 정보 응답에도 이 값을 실어 화면이 어느 쪽 창을 보여 줄지 알 수 있게 했다. 통행증은 5/6 의 로그인 출입증, 6/25 의 본인 확인 통행증과 같은 방식으로 "종류" 표시를 넣어 만들었고, 탈퇴 확인 창에서 바로 이어 쓰는 용도라 10분이면 충분하다고 봤다.

Spring Security 로 치면 민감한 작업 전에 다시 로그인시키는 재인증인데, 비밀번호 대신 OAuth2 로그인을 한 번 더 태우고 그 결과를 수명이 짧은 토큰으로 받아 쓰는 구조다.

테스트로는 재확인 성공, 소셜 계정이 없을 때 거절, 다른 사람의 소셜 계정일 때 거절, 다른 종류의 통행증 거절, 비밀번호 회원인데 비밀번호가 없을 때, 소셜 회원인데 통행증이 없을 때, 정상 통행증, 남의 통행증일 때 거절을 확인했다. 실제 요청을 보내 보는 테스트 3개로 재확인부터 탈퇴까지의 전체 흐름, 다른 사람 소셜 계정 거절, 로그인 없이 부르면 거절도 확인했다.

{% hint style="warning" %}
**이날 전에 소셜로 가입한 사람은 여전히 탈퇴 못 함 (당시 \~ 11/16 현재도)**

DB 변경은 칸만 추가하면서 기존 회원을 모두 "비밀번호 있음"으로 채웠다. 소셜 계정만 있고 비밀번호를 정한 적 없는 기존 회원을 골라 "없음"으로 고치는 작업은 하지 않았다. 그래서 5/10\~8/27 사이 소셜로 가입한 사람은 탈퇴 창에 여전히 비밀번호 입력이 나오고 탈퇴를 할 수 없다. 피해 갈 방법은 비밀번호 찾기로 임시 비밀번호를 받는 것뿐이다. 이후 DB 변경에도 이걸 고친 것은 없다. 8/23 운영을 시작한 직후라 실제 회원은 거의 없었겠지만, 운영 DB 에 그 기간 소셜 가입 계정이 있으면 해당된다.
{% endhint %}

{% hint style="danger" %}
**이날 저장한 코드로는 서버가 뜨지 못했음 (8/27 15:07 \~ 다음 날 11:40)**

이날 만든 DB 변경 스크립트는 바로 앞 순서로 "예전 전화번호 형식 고치기" 스크립트(8/18 작성)를 가리키는데, 그 스크립트는 다음 날에야 저장소에 올라갔다. 내 컴퓨터에는 파일이 있어서 문제가 안 보였지만, 저장소 코드만으로 만든 이미지는 켜질 때 DB 변경을 적용하다 "앞 순서 스크립트를 찾을 수 없음"으로 멈춘다. 그 사이 운영 배포를 했는지는 기록이 없다. 다음 날 빠진 파일을 올리면서 해결됐다([08.28 일지](2026-08-28.md)).
{% endhint %}

{% hint style="info" %}
**탈퇴 통행증은 한 번 쓰고 버리는 방식이 아님**

통행증을 따로 저장하거나 폐기 목록에 올리지 않아서 10분 안에는 다시 쓸 수 있다. 다만 쓸 곳이 본인 계정 탈퇴 하나뿐이고, 로그인 상태와 통행증 주인 확인을 같이 요구하기 때문에 재사용해서 생길 위험은 없다.
{% endhint %}

### 3. 화면 쪽

마이페이지 프로필의 탈퇴 창은 비밀번호가 있는 회원에게는 예전처럼 비밀번호 칸을 보여 주고, 없는 회원에게는 "소셜 계정으로 가입해 별도 비밀번호가 없어요"라는 안내와 카카오(노랑)·네이버(초록)·Google 버튼 세 개를 보여 준다. 버튼을 누르면 탈퇴 목적 표시를 붙여 그 회사 로그인으로 넘어간다. 서버가 아직 비밀번호 여부를 알려 주기 전에는 일단 있다고 보고 비밀번호 칸을 보여 준다.

소셜 로그인에서 돌아오는 화면은 5/10 에 만든 위조 요청 확인을 먼저 통과시킨 뒤, 탈퇴 목적이면 서버에서 통행증을 받아 탈퇴하고 로그아웃한 다음 1.2초 뒤 홈으로 보낸다. 진행 중에는 "재인증 처리 중…", 끝나면 "회원 탈퇴가 완료됐어요", 실패하면 "탈퇴 처리에 실패했어요"와 "마이페이지로" 버튼을 보여 준다. 가입 때 쓰지 않은 소셜 계정으로 확인하면 "가입 시 사용한 소셜 계정이 아니에요. 다른 계정으로 다시 시도해 주세요."가 뜬다.

돌아오는 주소를 새로 만들지 않고 평소 로그인 주소에 목적 표시만 얹은 덕분에, 카카오·네이버·구글 개발자 콘솔에 주소를 따로 등록하지 않아도 됐다. 목적 표시는 탭을 닫으면 사라지는 브라우저 저장소(sessionStorage)에 두고, 돌아온 화면에서 한 번 읽으면 지운다.

화면이 부르는 주소, 보내는 값(인증 코드와 state), 받는 통행증 이름, 탈퇴 때 보내는 값(비밀번호 또는 통행증), 내 정보의 "비밀번호 있음" 이름까지 서버와 하나씩 맞춰 봤고 모두 일치했다.

{% hint style="info" %}
**버튼 세 개 중 아무거나 눌러도 되나**

안내는 "가입할 때 쓴 소셜 계정으로"라고 하고, 실제 판단은 서버가 소셜 회사와 그 회사의 계정 번호로 한다. 가입하지 않은 회사로 확인하면 거절되고 위 실패 문구가 나온다. 5/10 에 만든 "같은 이메일이면 같은 회원으로 연결" 덕분에 한 회원에 소셜 계정이 여러 개 붙어 있으면 그중 어느 것으로도 탈퇴할 수 있다.
{% endhint %}
