### 4. 토스페이먼츠 MCP 서버 + 결제연동 백엔드 조사 (구현 X)

#### 4-1. MCP 서버 연결 (완료)

```bash
claude mcp add tosspayments-integration-guide -- npx -y @tosspayments/integration-guide-mcp
```

* **문서 검색용**(stdio) 서버 — 결제 API를 직접 실행하는 게 아니라 토스 공식 연동 문서를 LLM이 검색/조회. nicepay-docs 와 같은 성격.

#### 4-2. 현재 백엔드 상태

토스 연동 **골격은 이미 대부분 구현돼 있음** — 모델·스키마·라우터·서비스·`TossPaymentGateway` 어댑터·deps 와이어링·Fake 어댑터·테스트. `PgProvider.TOSS` 단일 계약 전제.

| 영역                                                             | 파일                               |
| -------------------------------------------------------------- | -------------------------------- |
| 결제 모델 (PCI-DSS 안전 메타데이터만)                                      | `app/payment/models.py`          |
| `/payments/init` `/payments/confirm` `/payments/webhooks/toss` | `app/payment/payment_router.py`  |
| 결제 플로우 (멱등성, `FOR UPDATE` 락, 재고복구)                             | `app/payment/payment_service.py` |
| 토스 REST confirm + 웹훅 검증                                        | `app/payment/adapters/toss.py`   |

#### 4-3. ⚠️ 문서 확인으로 드러난 사실 (현재 코드가 틀림)

{% hint style="warning" %}
**결제 웹훅에는 HMAC 서명이 없다**

`tosspayments-webhook-signature` 헤더는 **`payout.changed`/`seller.changed`(지급대행) 이벤트에만** 존재. `PAYMENT_STATUS_CHANGED` / `DEPOSIT_CALLBACK` / `CANCEL_STATUS_CHANGED` 에는 서명 없음.

현재 `toss.py`의 `verify_webhook_signature` = `HMAC-SHA256(secret_key, body).hexdigest()` + 라우터의 `TossPayments-Signature` 헤더 읽기는 **존재하지 않는 스펙**. → 토스 공식 권장: 웹훅 body를 신뢰하지 말고 받은 즉시 **결제 조회 API로 재확인** (`GET /v1/payments/{paymentKey}`). `DEPOSIT_CALLBACK` 은 body `secret` 을 승인응답 `virtualAccount.secret` 과 대조.
{% endhint %}

* **취소 API**: `POST /v1/payments/{paymentKey}/cancel` · 헤더 `Authorization: Basic` + `Idempotency-Key` · body `cancelReason`(필수)/`cancelAmount`(생략=전액)/가상계좌는 `refundReceiveAccount` · 응답 `Payment.cancels[]`
* **confirm 응답**: `method` 는 한글("카드") · 실패 시 `{code, message}` (현재 `status_code` 만 봄)
* **웹훅 status 값**: `READY / IN_PROGRESS / WAITING_FOR_DEPOSIT / DONE / CANCELED / EXPIRED` — 현재 코드는 `ABORTED`(없음)/`PARTIAL_CANCELED` 가정, `EXPIRED` 미처리

### 5. 원격 DB 연결 오류 진단 (코드 변경 없음)

DataGrip/IntelliJ 에서 원격 Postgres 접속 시:

```
java.net.SocketException: Connection reset
    ... ConnectionFactoryImpl.enableSSL(...)
```

* **TCP 도달은 됨** (`Connection refused`/`timeout` 아님). Postgres 프로토콜 첫 단계(SSLRequest) 직후 상대가 소켓 RST.
* 진짜 원인: `DATABASE_URL=postgresql+asyncpg://rekle:***@postgres:5432/rekle` 의 host `postgres` 는 **Docker Compose 서비스명 — 컨테이너 네트워크 안에서만 유효**. 노트북에는 `postgres` 호스트가 없음.

{% hint style="success" %}
**호스트 머신에서 붙는 법**

* 로컬 docker compose → host `localhost`, port 는 compose `ports:` 매핑값
* 원격 서버 → 그 서버로 **SSH 터널** 뚫고 `localhost:5432` (DataGrip SSH 탭). 서버가 5432를 외부로 직접 안 여는 게 정상.
* user/password/dbname 은 URL 값 그대로
{% endhint %}

⚠️ 이 과정에서 운영 DB 비밀번호가 세션에 평문 노출됨 — 필요 시 로테이션 고려. (8/28 커밋 `dc3b373` 에서 permission 목록의 Octomo 키 평문 노출 정리한 것과 유사 이슈)

### 6. 구글 소셜 로그인 "state 검증 실패" — 원인 규명 + www DNS 제거

#### 증상

"내 구글 계정은 로그인되는데 다른 계정은 **'보안 검증(state)에 실패했습니다'**" (`CallbackView.vue:57-60`).

#### 구조

* state(CSRF 토큰)는 **전적으로 프론트 sessionStorage** 에만 저장/검증 (`src/config/oauth.ts` `buildAuthorizeUrl` 저장 → `CallbackView.vue` 가 `consumeStoredState` 로 **1회 읽고 삭제**)
* 백엔드(`rekle_backend`)의 `social_login` / OAuth 어댑터는 `state` 를 **받기만 하고 검증 안 함**

#### 원인

`rekit.co.kr` 과 `www.rekit.co.kr` **둘 다** 앱을 서빙(nginx `server_name _;`, 리다이렉트 없음)했는데 `VITE_GOOGLE_REDIRECT_URI` 는 **apex 하나로 고정**.

| 시작 호스트                           | state 저장 origin | Google 콜백 도착 | 결과                                |
| -------------------------------- | --------------- | ------------ | --------------------------------- |
| `rekit.co.kr` (본인 습관)            | apex            | apex         | 일치 ✅                              |
| `www.rekit.co.kr` (검색결과·공유링크 유입) | www             | apex         | sessionStorage 빔 → **state 실패** ❌ |

→ "계정 차이"가 아니라 **로그인을 시작한 호스트 차이**.

#### 조치

**가비아 DNS에서 `www` 레코드 제거** (사용자 결정). 코드 변경 없음. canonical·sitemap·robots·OG 전부 `https://rekit.co.kr` 단일 정본이라 www는 원래 불필요 + 중복콘텐츠 리스크였음. → [08.30 SEO 정리](2026-08-30-seo.md) 의 "www → 301" 남은작업은 이 방식으로 대체 해결.

#### 남은 잠재 버그 (미수정, 보류)

* **신규 미가입 계정**: `needsSignUp` → `/auth/social/sign-up` 이동. 그 사이 콜백 페이지 새로고침/뒤로가기 시 state 이미 삭제되어 재검증 실패. (`consumeStoredState` 가 read-and-delete)
* **http→https 진입**: http origin 에 state 저장 후 https 콜백이면 origin 달라 유실
* 제안했던 프론트 하드닝(콜백 진입 즉시 `history.replaceState` 로 쿼리 제거 + 재진입 가드 + 실패화면 버튼이 `buildAuthorizeUrl` 재시작)은 보류.

### 보강 (소급, 2026-11-16)

> 📜 이날 저장 기록 6개와 위 본문을 맞춰 보니 본문에 빠진 서버 쪽 저장이 하나 있어서 여기에만 덧붙인다(작성일 2026-11-16, 읽기 쉽게 다시 씀). 위 본문은 그대로 둔다. 용어: [용어 풀이](../glossary.md) · 이전 날: [08.28 일지](2026-08-28.md)

운영 DB 를 내 컴퓨터의 DB 도구(DataGrip)로 열어 보려 했는데 붙지 않았던 문제를 해결한 작업이다. 위 본문 5절의 결론은 "서버에 SSH 로 통로(터널)를 뚫고 그 안에서 DB 에 붙자"였는데, 8/23 운영 설정은 DB 컨테이너의 포트를 아예 열지 않아서 통로를 뚫어도 서버 쪽에 붙을 곳이 없었다. 이날 12:56 에 DB 포트를 서버 안에서만 통하는 주소(`127.0.0.1:5432`)로 열었다. 이제 SSH 로 서버에 들어온 사람만 DB 에 붙을 수 있고, 바깥이나 같은 공유기 안의 다른 기기에서 바로 붙는 길은 없다.

8/23 에 서버 앱 포트(`127.0.0.1:8000`)를 연 것과 같은 방식이다. 바깥에 열린 건 여전히 nginx(80/443)뿐이다. 운영 설정에 세 줄을 더했고, 주석에 "SSH 터널로만 접근, 서버 안에서만 열려 있어 외부·내부망 직접 노출 없음"이라고 적었다.

{% hint style="success" %}
**DB 포트는 모든 주소가 아니라 서버 안 주소에만 연다**

Docker 설정에 주소 없이 `"5432:5432"` 로만 쓰면 Docker 가 방화벽 규칙을 직접 고쳐 열기 때문에, 서버 방화벽(ufw)을 켜 둬도 그걸 건너뛰고 바깥에 노출된다. 앞에 `127.0.0.1:` 을 붙여 서버 안에서만 열고 SSH 터널로 들어가는 쪽이 안전하다.
{% endhint %}
