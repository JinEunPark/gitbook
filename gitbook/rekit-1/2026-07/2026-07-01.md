# 07.01 · 주문을 실제 서버에 연결

### 작업 요약

6/28 까지 구매자 화면 중 주문 만들기와 결제만 가짜 데이터로 남아 있었는데, 이날 오전 20분 사이에 주문을 실제 서버에 연결했다. 이제 주문은 브라우저가 아니라 서버에 저장되고 주문번호도 서버가 매긴다. 주문 상태 이름을 서버 쪽 7가지에 맞추다 보니 5/5 에 만든 무통장입금용 "입금 완료했어요" 버튼이 화면에서 사라졌다. 주문서의 배송지 입력은 세 번 바꾼 끝에 저장해 둔 배송지 중에서 고르기만 하는 방식으로 정리했다. 서버 쪽은 주문 오류를 상황별로 나누고, 휴대폰 번호 인증 기능을 만들었다(실제 문자는 아직 안 보내고 기록만 남긴다).

### 1. 주문을 서버에 연결

지금까지 주문은 버튼을 누르면 브라우저 안에만 저장되는 가짜였다. 다른 기기에서는 보이지 않았고 주문번호도 화면이 임의로 만들었다. 이날 주문 목록·상세·만들기·취소·환불을 모두 서버 API 로 바꿨다. 이제 주문은 서버 DB 에 남고, 주문 완료 화면이나 주문 상세를 새로고침해도 서버에서 다시 받아 그린다. 전에는 브라우저에 없으면 홈으로 튕겼다.

화면에서 쓰는 서버 기능은 내 주문 목록(20개씩), 주문 하나 보기, 주문 만들기(상품과 수량, 배송지 번호, 배송 방식, 메모), 주문 취소, 환불 신청이다. 금액 미리 계산(견적)과 배송 조회도 부르는 함수는 만들어 두었지만 화면에는 아직 안 붙였다. 주문 상태는 서버 기준으로 결제대기·결제완료·준비중·배송중·배송완료·취소·환불완료 7가지이고, 배송 방식은 택배·화물·직접 배송 세 가지다.

#### 주문 보관함이 바뀐 점

|                                 | 5/2 \~ 6/28 (가짜)         | 7/1                                        |
| ------------------------------- | ------------------------ | ------------------------------------------ |
| 저장 위치                           | 브라우저(localStorage)       | 서버 (브라우저엔 저장 안 함)                          |
| 주문번호                            | 화면이 `RK-날짜` + 랜덤 4자리로 만듦 | 서버가 매김                                     |
| 도착 예정일 ("7월 2일(목) \~ 7월 3일(금)") | 화면이 계산                   | 없앰 (서버에 그런 정보가 없다)                         |
| 결제수단 표시                         | 있음                       | 없앰                                         |
| 불러오는 때                          | -                        | 로그인하면 서버에서 받고 로그아웃하면 비움 (6/27 찜 목록과 같은 방식) |

#### 주문 버튼을 누르면 (첫 버전)

먼저 배송지를 저장해서 배송지 번호를 얻는다. 이때 기본 배송지가 있으면 이번에 입력한 값으로 덮어쓰고, 없으면 새로 추가했다. 그다음 서버에 주문을 만들고, 장바구니에서 주문한 상품을 빼고 주문 완료 화면으로 넘어간다. 처리 중에는 버튼이 "처리 중…"으로 잠기고, 실패하면 빨간 글씨로 알려 준다. 첫 단계의 덮어쓰기가 §3 에서 문제가 된다.

#### 상태 이름 통일과 사라진 "입금 완료했어요"

상태를 입금대기·결제확인요청 같은 한글 이름으로 저장하던 것을 서버의 영문 이름으로 바꾸고, 화면에는 한글로 바꿔 보여 준다. 그러면서 5/5 에 만든 무통장입금 장치 중 "입금 완료했어요" 버튼, "결제확인요청" 상태, "입금 확인 요청이 접수됐어요" 안내가 주문 완료 화면과 주문 상세에서 모두 빠졌다. 서버 상태에 "결제확인요청" 단계가 없어서다. 주문 완료 화면은 결제대기면 여전히 입금 계좌 안내 카드를 보여 준다. 계좌 안내는 남았고, 입금했다고 알리는 수단만 없어진 상태다.

#### 주문 상세와 목록

상세에는 결제대기부터 배송완료까지 5단계 진행 막대를 두고, 취소·환불된 주문은 막대를 숨긴다. 도착 예정 줄은 없앴다. 아래 버튼은 상태에 따라 달라서, 결제대기면 주문취소, 배송완료면 환불신청이 나온다(환불신청은 6/24 에 만든 서버 기능이라 누르면 바로 환불완료가 된다). 다른 상태에서는 버튼이 없다. 원래 있던 "배송조회" 버튼은 눌러도 아무 일이 없는 장식이어서 없앴다.

목록에서는 필터 이름 "입금 안내"를 "결제대기"로 바꾸고, 총 주문 수는 서버가 알려 준 값을 쓴다. 상품 합계는 서버가 따로 주지 않아 화면이 상품별 금액을 더해서 계산한다.

{% hint style="danger" %}
**관리자 주문 화면 — 버튼은 있는데 눌러도 아무 일도 안 한다 ()**

가짜 주문 보관함의 기능을 걷어내면서 관리자 주문 목록 화면의 "결제 승인"·"준비중으로" 버튼이 모양만 남고 동작이 지워졌다. 게다가 이 화면은 "로그인한 사람 본인의 주문 목록"을 보여 주고 있어서, 관리자로 들어가면 관리자 자기 주문만 보였다. 7/3 에 관리자 전용 서버 기능으로 화면 전체를 연결했다([07.03 일지](2026-07-03.md)).
{% endhint %}

### 2. 내 정보 — 이름 수정 저장, 휴대폰 변경 화면

내 정보 화면에서 이름을 고치면 이제 서버에 저장되고, 서버가 돌려준 정보로 로그인 사용자 정보를 바꿔 끼운다. "수정"을 누르면 화면 전체가 입력 폼으로 바뀌던 방식은 그 항목 바로 아래에 입력칸이 펼쳐지는 방식으로 바꿨다. 이메일 수정칸은 없앴다. 6/28 에 이메일 변경은 인증이 필요하다고 정해 두었기 때문이다. 휴대폰이 없으면 "미등록 (본인인증 시 자동 등록)" 대신 "미등록"과 등록/변경 버튼이 보인다.

{% hint style="danger" %}
**휴대폰 인증번호가 가짜였다 (7/1 \~ 7/12)**

"인증번호 보내기"를 누르면 번호 형식만 확인하고 실제로는 아무것도 보내지 않는다. 그다음 아무 숫자 6자리나 넣으면 통과되고, 그 번호가 곧바로 내 정보에 저장된다. 같은 날 서버에 진짜 인증 기능(§4)이 생겼지만 화면과 연결하지 않았다. 7/12 에 QR 방식 휴대폰 확인(Octomo)으로 바꿨다([07.12 일지](2026-07-12.md)).
{% endhint %}

### 3. 주문서 배송지 — 20분 동안 세 번 바꿈

처음엔 주문서에서 주소를 직접 입력했는데, 주문할 때마다 기본 배송지가 이번 입력값으로 덮어써졌다. 회사로 한 번 보내면 집 주소가 사라지는 식이다. 20분 동안 세 번 고친 끝에, 주소를 입력하고 고치는 건 배송지 관리 화면에서만 하고 주문서에서는 저장된 배송지 중에서 고르기만 하도록 나눴다. 구매자는 주문서에서 주소 카드 하나를 누르면 된다.

| 시각    | 주문서 배송지 영역                                                                                                                                              |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 09:35 | 입력 폼(받는 사람·휴대폰·우편번호와 카카오 주소 검색·주소·상세주소·메모). 주문할 때 기본 배송지를 입력값으로 덮어씀                                                                                     |
| 09:37 | 폼 위에 저장된 배송지를 옆으로 넘겨 보는 작은 카드(칩)와 "새 주소 입력" 칩을 추가. 칩을 고르면 폼이 채워지고, 주문할 때 고른 배송지면 그걸 수정, 아니면 새로 추가                                                       |
| 09:44 | 입력 폼을 통째로 없앰(약 330줄 삭제). 칩으로 고르면 아래에 읽기 전용 카드로 보여 주고, 저장된 배송지가 없으면 "저장된 배송지가 없어요 · 배송지 추가하기"로 배송지 관리 화면에 보낸다. 제목 옆에 "배송지 관리" 링크. 주문서는 더 이상 배송지를 고치지 않는다 |
| 09:56 | 칩 크기를 고정하고 고르면 검정 바탕으로 뒤집히게, 카드는 받는사람/전화번호/주소지/메모 2열 표 모양으로                                                                                             |

6/28 에 주문서에 넣은 카카오 우편번호 검색은 3일 만에 주문서에서 빠졌고, 배송지 관리 화면의 팝업에만 남았다. 주문 버튼이 켜지는 조건도 "배송지가 골라져 있는가" 하나로 줄었다.

{% hint style="info" %}
**왜 폼을 없앴나 (구현상 이유)**

첫 버전은 매번 기본 배송지를 덮어썼고, 칩 버전은 고른 배송지를 덮어썼다. 결국 편집과 선택을 다른 화면으로 나눠서 덮어쓰기 문제를 없앴다. 6/28 에 배송지 추가·수정·삭제가 서버에 붙어 있었기 때문에 할 수 있었던 단순화다.
{% endhint %}

### 4. 서버 — 주문 오류 정리, 브랜드 복사본, 휴대폰 인증

#### 주문 오류를 상황별로 나눔

전에는 "배송지가 없다"와 "남의 배송지다"가 같은 오류였고, 품절과 판매 중지도 "재고 부족" 하나로 나와서 화면에서 무슨 일인지 구분할 수 없었다. 상황마다 다른 오류와 문구를 주도록 나눴다.

| 상황            | 전             | 후                                        |
| ------------- | ------------- | ---------------------------------------- |
| 배송지가 없음       | "배송지 없음"      | "배송지 없음" (404)                           |
| 남의 배송지 번호로 주문 | "배송지 없음"      | "권한 없음" (403). 배송지를 먼저 찾고 주인이 본인인지 따로 비교 |
| 판매 중지·품절 상품   | "재고 부족"       | "현재 주문할 수 없는 상품입니다." (견적·주문 둘 다)         |
| 재고 부족         | "재고 부족" (422) | "재고 부족" (400)                            |

{% hint style="info" %}
**404 와 403 을 나눈 것의 득실**

남의 배송지를 "권한 없음"으로 알려 주면 그 번호의 배송지가 존재한다는 정보가 새어 나간다. 5/7 로그인·비밀번호 찾기에서 일부러 같은 응답을 줬던 것과는 반대 선택이다. 배송지 번호는 1, 2, 3… 순서라 실제 위험은 작고, 화면에서 어떤 오류인지 구분하기 쉽게 하는 쪽을 택한 로 정리했다.
{% endhint %}

#### 주문 브랜드명 복사해 두기

주문 상품에는 상품명과 가격을 주문할 때 값으로 복사해 두는데(5/1 원칙), 브랜드명은 없었다. DB 의 주문 상품 표에 "주문 브랜드" 칸을 추가하고(최대 100자, 브랜드를 안 적은 상품이 있어서 비어도 됨), 주문을 만들 때 상품 브랜드를 복사해서 응답에도 넣었다. 화면의 가짜 주문에는 카드 위에 작은 브랜드명이 이미 있었으니, 6/28 배송지 별칭 때처럼 서버가 화면을 따라온 경우다.

#### 휴대폰 인증 기능

"인증번호 보내기"와 "받은 번호 확인하기"를 서버에 만들었다. 다만 문자 회사와 계약하지 않아서 실제 문자는 보내지 않고 서버 로그에 번호를 찍기만 한다. 화면은 이 기능과 연결되지 않았다(§2).

인증번호 보내기는 6자리 번호를 만들어 Redis(빠른 임시 저장소)에 5분 동안 보관하고, 같은 번호로 60초 안에 다시 요청하면 거절한다. 확인하기는 번호가 맞으면 보관한 번호를 지우고 회원의 휴대폰 번호와 확인한 시각을 저장한다. 틀리거나 5분이 지나면 거절한다. 휴대폰 번호는 하이픈 없는 `010…` 형식만 받는다. 6/25 이메일 인증과 같은 구조다.

{% hint style="warning" %}
**확인된 제약**

* 인증번호 확인에 시도 횟수 제한이 없어서 5분 동안 6자리를 계속 넣어 볼 수 있다. 6/25 이메일 인증과 같은 구멍이다.
* 6/24 에 만든 "내 정보 고치기"가 여전히 휴대폰 번호를 인증 없이 바꿔 준다. 화면(§2)이 바로 그 길을 쓴다.
* 실제 문자 발송 부품이 없다. 8/13 에 QR 방식(Octomo)으로 대신하게 된다([08.13 일지](../2026-08/2026-08-13.md)).
{% endhint %}

#### 자동 테스트

주문 쪽은 남의 배송지면 권한 없음(견적·주문 둘 다), 판매 중지·품절이면 "주문할 수 없는 상품", 브랜드 복사(있을 때와 없을 때), 이미 취소·환불된 주문은 취소 불가를 확인한다. 주문이 하나도 없을 때 목록이 빈 배열과 전체 페이지 0 으로 제대로 나오는지도 넣었는데, 화면 목록을 붙이면서 빈 응답 모양을 확인한 로 정리했다. 휴대폰 인증은 진짜 DB·Redis 없이 가짜 저장소와 "보낸 문자를 기록만 하는" 가짜 발송기로 테스트한다.

{% hint style="warning" %}
**서버에 본인인증 기록이 없으면 주문이 늘 실패했다 ()**

서버는 6/20 부터 본인인증한 회원이 아니면 주문을 "본인인증 필요" 오류로 거절한다. 그런데 화면의 본인인증 단계는 아직 가짜라서 브라우저 안의 "인증됨" 표시만 바꾸고 서버에는 아무것도 저장하지 않는다. 그래서 DB 에 본인인증 시각을 직접 넣어 둔 계정이 아니면 주문을 만들 수 없었다. 서버 쪽 본인인증 저장은 8/13(Octomo)에 생긴다.
{% endhint %}
