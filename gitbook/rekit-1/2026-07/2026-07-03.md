### 1. 관리자 화면을 서버에 연결

지금까지 관리자 화면은 가짜 데이터로 그려진 그림에 가까웠고, 7/1 이후에는 주문 화면 버튼마저 동작하지 않았다. 이날 관리자 전용 서버 기능을 부르는 통로를 7개 묶음으로 만들고 화면 8개를 모두 연결했다. 이제 운영자가 관리자 화면에서 주문 상태를 바꾸고 송장을 넣고, 상품을 등록·수정하고, 회원을 정지시킬 수 있다.

#### 관리자만 들어가기

로그인 사용자 정보에 역할(일반 회원 / 관리자)을 추가하고, `/admin` 으로 시작하는 주소로 가려 하면 페이지 이동 직전에 검사하도록 했다. 로그인하지 않았으면 로그인 화면으로 보내고(로그인 후 원래 가려던 곳으로 돌아옴), 일반 회원이면 홈으로 보낸다. 예전에 브라우저에 저장된 로그인 정보에는 역할이 없어서, 없으면 일반 회원으로 본다. 5/1 에 미뤄 둔 결정(D6)이 이날 처음 실제로 켜졌다.

{% hint style="danger" %}
**확인된 제약 — CSV 내보내기를 누르면 파일 대신 인증 오류가 받아진다**

주문·매출 화면의 "CSV 내보내기"는 그냥 링크로 파일을 연다. 링크로 여는 요청에는 로그인 출입증(토큰) 헤더가 붙지 않는데, 서버의 관리자 기능은 그 헤더로만 관리자를 확인한다. 그래서 버튼을 누르면 주문 목록 대신 "인증 필요" 응답이 파일로 저장된다. 후속으로 확인 필요 관리자 주문 화면과 매출 화면이 같은 방식이다. 고치려면 화면이 헤더를 붙여 직접 받아 온 뒤 파일로 저장해야 한다.
{% endhint %}

{% hint style="danger" %}
**확인된 제약 — 매출·대시보드 기간을 바꿔도 결과가 그대로다**

매출 화면은 기간을 `start`/`end` 라는 이름으로 보내는데 서버는 `from_date`/`to_date` 만 읽는다. 서버(FastAPI)는 모르는 이름은 조용히 무시하기 때문에 7일·30일·이번 달 중 무엇을 골라도 서버 기본 범위로 계산된다. 주문 CSV 도 상태 조건을 붙여 보내지만 서버 쪽에 그걸 받는 자리가 없다. 대시보드도 마찬가지다. 매출 막대의 7/30/90일 버튼은 `days=7` 처럼 보내는데 서버는 `period=7d` 형태만 받아서 항상 7일 그래프가 나온다. 이 파일은 7/3 이후 고친 적이 없다.
{% endhint %}

{% hint style="warning" %}
**상품 폼의 카테고리가 고정 목록이다**

같은 날 카테고리 관리 화면을 만들었지만 상품 등록·수정의 카테고리 선택지는 코드에 적어 둔 7개(냉장고 … 청소기, 기타)다. 카테고리 화면에서 새로 만든 카테고리는 상품 폼에 뜨지 않는다. 게다가 6/23 에 넣은 기본 카테고리에는 청소기가 없어서(냉장고·세탁기·TV·에어컨·주방·기타 6개) 손으로 추가해야 맞물린다. 그리고 폼의 크기·무게 입력칸과 외관 손상 선택은 서버로 보내지 않는다. 입력해도 저장되지 않는다.
{% endhint %}

#### 화면 쪽 작업 계획서 새로 쓰기

제목을 "작업 현황 (2026-07-02 기준)"으로 바꾸고 전체를 다시 썼다(186줄 지우고 117줄). 요약표에는 구매자 화면 완료, 관리자 화면 "API 연동 완료", 서버 연결 95%("본인인증·결제·도움말만 남음"), 관리자 확인 "역할 응답 대기"로 적었다.

설계 결정으로 결제대행사는 PortOne v2(토스·카카오·네이버 등을 한 번에 붙이는 통합 서비스), 본인인증도 PortOne v2 의 인증을 쓰기로 했다고 기록했다. 결정 D3·D4·D6 는 "결정 완료"이고, 남은 건 D5 사진 저장 위치(S3/R2/CDN)와 D7 다크모드다. 주문서는 PortOne 결제창을 띄운 뒤 서버에서 확인받는 계획이었는데, 실제로는 9/3 에 토스페이먼츠 결제 위젯으로 갔다([09.03 일지](../2026-09/2026-09-03.md)).

계획서에는 장바구니 서버 연결이 완료로 적혀 있지만, 6/26 부터 있던 화면과 서버 사이 약속 불일치는 그대로 남아 있었다.

### 2. 공지사항·FAQ·1:1 문의 기능 (서버)

고객센터 화면에 넣을 공지사항, 자주 묻는 질문, 1:1 문의를 서버에 만들었다. DB 변경 스크립트에 찍힌 시각을 보면 전날(7/2) 저녁 6시쯤 쓰기 시작했다. 구매자는 공지와 FAQ 를 읽고 문의를 남길 수 있고, 운영자는 공지·FAQ 를 쓰고 고치고 문의에 답변 상태를 바꿀 수 있다. 다만 이날 버전은 비로그인 문의에 구멍이 있어서 다음 날 바로 손봤다.

DB 표는 세 개다. FAQ 는 분류(주문·배송·결제·회원·기타), 질문, 답, 순서, 공개 여부를 담는다. 공지는 제목, 내용, 상단 고정 여부, 공개 여부를 담는다. 문의는 회원 번호(비로그인은 비어 있음, 회원이 탈퇴해도 문의는 남음), 이름·이메일·연락처·제목·내용, 상태(답변 대기 / 답변 완료), 답한 시각을 담는다.

누구나 쓸 수 있는 기능은 공지 목록·공지 하나 보기·FAQ 목록(분류별)·문의 남기기 네 가지이고, 문의는 로그인하지 않아도 남길 수 있었다. 관리자 기능은 공지 4개, FAQ 4개(각각 목록·만들기·고치기·지우기), 문의 3개(목록·상세·상태 바꾸기)이고 묶음 전체에 관리자 확인을 걸었다.

문의가 들어오면 메일이 두 통 나간다. 고객에게는 "문의가 접수되었습니다"(민트색 띠), 관리자에게는 "\[관리자] 새 문의"(주황 띠, 이름·이메일·연락처·제목·내용 포함). 관리자 수신 주소가 따로 설정돼 있지 않으면 발신 주소로 보낸다. 메일 아래쪽 문구 "© 2025 rekit. 폐업 가전 직거래 플랫폼."은 6/25 인증 메일 틀을 그대로 가져다 썼다.

### 3. 사진 한 장 고치기 + 코드 검사 경고 정리 (서버)

#### 사진 한 장만 고치기

사진이 없거나 다른 상품의 사진이면 둘을 구분하지 않고 "사진 없음"으로 답한다. 장바구니에서 쓰던 방식과 맞춘 것이고, 7/1 배송지(없음과 권한 없음을 나눔)와는 반대로 골랐다. 테스트를 먼저 쓰는 방식(TDD)으로, 실패하는 경우(상품 없음, 사진 없음)를 성공하는 경우보다 먼저 작성했다고 적어 두었다.

#### 경고 114건 정리

서버 코드에 타입 검사기(mypy) 경고 19건과 스타일 검사기(ruff) 경고 95건이 아무도 모르게 쌓여 있었다. 자동 테스트는 통과하고 있어서 눈에 띄지 않았다. 이날 한꺼번에 정리했다.

| 무엇                           | 건수 | 어떻게                                                                                              |
| ---------------------------- | -- | ------------------------------------------------------------------------------------------------ |
| 오류 클래스 이름 규칙                 | 37 | 오류 종류 이름 끝을 전부 `~Error` 로 통일(`ProductNotFound` → `ProductNotFoundError`). 39개 파일을 스크립트로 한 번에 바꿨다 |
| 정해진 값 목록 쓰는 방식               | 16 | 파이썬 최신 문법(`StrEnum`)으로 교체                                                                        |
| 토스 웹훅(토스가 먼저 보내 주는 알림) 필드 이름 | 1  | 코드 안 이름만 파이썬식으로 바꾸고, 토스가 보내는 JSON 이름은 그대로 받게 했다                                                  |

| 타입 검사                        | 19 | 쓸모없어진 경고 무시 표시 제거, 막연한 타입을 구체적으로, 반환 타입 명시 등                                                     |

그리고 서버 쪽 안내 문서(`CLAUDE.md`, AI 코딩 도구가 작업할 때마다 읽는 파일)에 "작업 완료 전 필수 검사" 항목을 넣었다. 테스트·스타일 검사·타입 검사 세 가지가 서버 코드 전체 기준으로 0건이어야 끝난 것으로 친다. 이유로는 "테스트만 통과하고 검사 오류는 방치되는 게 가장 흔한 기술부채 경로다(실제 사례: mypy 19건 + ruff 95건이 쌓였다가 한 번에 터짐)"라고 적었다. 개발 도구가 묻지 않고 테스트·타입 검사를 돌릴 수 있도록 허용 목록에도 넣었다.

밤 11시 반에는 에디터(Pyright)에만 뜨던 잘못된 경고에 무시 표시를 달고, 테스트에서 역할을 글자 대신 정해진 값으로 쓰도록 맞췄다. 에디터와 타입 검사기의 경고를 일치시키는 마무리였다.

### 4. 관리자 사진 올리기를 실제로 연결

화면 쪽은 사진을 "관리자 업로드 주소에 파일을 직접 보낸다"고 가정하고 있었는데, 서버 API 설명서를 확인해 보니 그런 주소는 없었다. 실제 서버는 5/1 에 만든 3단계 방식(잠깐 쓰는 업로드 주소를 받아 저장소에 직접 올리고, 다 올렸다고 알림)이었다. 6/26 장바구니 때처럼 문서의 가정과 실제 서버가 달랐던 건데, 이번엔 서버 API 설명서(Swagger)를 기준으로 바로잡았다. 이제 관리자가 상품 등록·수정 화면에서 사진을 실제로 올리고 순서와 이름표를 정할 수 있다.

사진 편집 부품(363줄)은 등록·수정 화면이 같이 쓴다. 한 번에 여러 장, 최대 10장, 한 장에 5MB 까지 올릴 수 있고 좌우로 순서를 바꾸거나 지우거나 이름표를 고칠 수 있다. JPG/PNG/WEBP 만 받는다. 수정 화면에서는 바뀔 때마다 서버에 사진 목록 전체를 저장하고 서버 응답으로 맞추는데, 이름표만 바꿀 때는 §3 에서 만든 한 장 고치기 기능을 쓴다. 등록 화면에서는 아직 상품 번호가 없으니 들고만 있다가 상품이 만들어진 직후 사진을 저장한다. 등록 체크리스트에는 "사진 최소 4장"을 넣었다. 수정 화면에는 원래 사진 영역이 아예 없었는데 이번에 생겼다.

API 문서에는 관리자 상품(13장)과 사진 올리기(14장)를 새로 쓰고 관련 오류 코드를 넣었다. 뒤의 장 번호는 하나씩 밀렸다. API 문서를 실제 서버에 맞춰 고친 첫 번째 경우다.

{% hint style="info" %}
**업로드 크기 한도가 서로 다르다**

화면은 5MB, 서버는 5/1 부터 10MB 다. 화면이 더 엄격해서 오류는 안 난다. 사진을 올리기만 하고 상품을 저장하지 않으면 저장소에 주인 없는 파일이 남는데, 이걸 치우는 장치는 없다.
{% endhint %}

### 5. 상품 상세 사진 크게 보기

중고 가전은 A/B/C 등급만으로는 어디에 흠집이 있는지 알 수 없다. 그래서 구매자가 사진을 눌러 화면 가득 크게 볼 수 있는 창을 만들었다. 사진을 잘라 내지 않고 전부 보이게 해서 흠집이나 상태를 확인할 수 있다. 좌우 화살표, 아래쪽 작은 사진 목록, 키보드(좌우 방향키·Esc), 휴대폰에서 손가락으로 밀어 넘기기(40px 이상 밀면 넘어감)를 지원하고, 창이 열려 있는 동안은 뒤 페이지가 스크롤되지 않는다.

상품 상세 화면도 다듬었다. 큰 사진에 그림자와 확대 버튼을 달고, "1/2" 숫자 대신 점으로 몇 번째 사진인지 보여 준다. 작은 사진 아래 글자를 없애고 고른 사진에 민트색 테두리를 둘렀다. 사진이 적으면 6칸 격자가 비어 보이던 것은 있는 만큼만 나열하게 바꿨고, 이름표가 있는 사진은 큰 사진 위에 이름표를 띄운다.
