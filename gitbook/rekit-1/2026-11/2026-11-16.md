### 1. 작업 기록 정리 마무리

직접 그날그날 썼던 노트가 있는 날(11/5, 11/10, 11/11, 11/13, 11/15)은 노트에 적힌 저장 기록과 실제 저장 기록을 맞대 보고 빠진 게 있는지만 봤다. 11/5·11/10·11/13·11/15 는 빠진 게 없었다. 11/11 은 작업 계획서를 한 줄씩 고친 기록 세 개가 빠져 있어서, 원래 본문은 건드리지 않고 끝에 보강 섹션만 붙였다([11.11 일지](2026-11-11.md)).

11/12 는 코드 저장 없이 대화만 있던 날이라 새로 썼다. 서버를 Kotlin + Spring 으로 옮기는 방법 상담, DDD 강의 검토, 링크 미리보기 이미지 만들기가 그날 내용이다([11.12 일지](2026-11-12.md)). 그 대화에서 대화에서 정리한 수치도 실제 코드와 대조했는데, 서버 기능 97개와 출입증 서명 방식(HS256)은 맞았고 DB 구조 변경 스크립트 "24개"는 틀렸다(실제 21개).

### 2. 남은 문제 16개를 계획서에 모으기

일지에는 문제가 발견된 날짜마다 따로 적혀 있어서, 막상 고치려면 어느 날 노트였는지부터 찾아야 했다. 그래서 각 저장소 계획서 맨 위에 "작업 기록 점검에서 확인한 문제" 섹션을 만들고, 문제마다 어느 파일 몇 번째 줄인지와 언제부터 있던 문제인지를 같이 적었다. 적기 전에 16개 모두 오늘 기준 코드에서 해당 줄을 직접 열어 봤고, 고쳐진 건 하나도 없었다.

프론트와 서버 중 어느 쪽을 고쳐도 되는 문제(②③⑮)는 양쪽 계획서에 다 적고 어느 쪽을 고치는 게 나은지 달아 뒀다. ②③은 서버 쪽 이름이 이미 다른 곳에서도 쓰이고 있어서 화면 쪽을 서버에 맞추는 게 낫다. ⑮는 할인이 원래 의도한 정책인지부터 정해야 어느 쪽에 맞출지가 정해진다.

#### 결제·재고 (먼저 고칠 것)

* **⑫ 환불한 상품의 재고가 한 번 더 늘어난다** (9/4\~, 서버). 관리자가 주문을 환불하면 주문이 "환불됨"이 되고 재고가 1 돌아온다. 그 뒤 토스가 "결제 취소됨" 알림을 보내면, 서버는 이미 취소된 주문인지는 확인하지만 "환불됨"인지는 확인하지 않는다. 그래서 재고가 또 1 늘어나고 주문 상태도 "취소됨"으로 덮어써진다. 1개뿐인 상품이 재고 2개로 보이게 된다.
* **⑬ 결제 승인이 거절된 기록이 남지 않는다** (10/2\~, 서버). 토스가 승인을 거절하면 서버가 결제를 "실패"로 바꾸고 이유를 적은 다음 에러를 낸다. 그런데 에러가 나면 그 요청에서 한 DB 작업이 통째로 취소돼서 "실패"와 이유까지 같이 사라진다. 나중에 왜 실패했는지 찾아볼 수 없다. 테스트에서 쓰는 가짜 저장소는 이런 취소가 없어서 테스트는 통과했다.
* **④ 결제 승인을 다시 요청하면 에러가 난다** (7/6\~, 서버). 결제를 마치고 돌아오는 화면에서 새로고침하거나 재시도하면 같은 승인 요청이 한 번 더 간다. 원래는 "이미 결제된 주문이면 성공으로 돌려준다"는 처리가 있는데, 그보다 앞에 "결제 대기 중인 주문만 받는다"는 검사가 있어서 거기서 먼저 막히고 에러(422)가 난다. 화면 쪽은 10/16 부터 에러가 나면 주문 상태를 다시 물어보는 식으로 피해 가고 있을 뿐이다.
* **⑪ 카드사 이름 자리에 숫자 코드가 들어간다** (9/3\~, 서버). 토스가 주는 카드사 정보 중 이름 대신 "41" 같은 코드를 저장하고 있어서, 주문 상세에도 카드사가 숫자로 나온다. 코드를 카드사 이름으로 바꿔 주는 표가 필요하다.
* **⑮ 직접 배송비가 화면과 결제 금액에서 다르다** (10/21\~, 양쪽). 주문서 화면은 직접 배송비를 4만 원으로 보여 주고 합계에 더한다. 서버는 4만 원에서 직접 배송 할인 2만 원을 빼고 주문 금액을 계산한다. 결국 결제창에 뜨는 금액이 화면에서 본 합계보다 2만 원 적다.

#### 보안·데이터 정합성

* **⑧ 휴대폰 확인 없이 전화번호를 바꿀 수 있다** (8/13\~, 서버). 내 정보 수정에서 전화번호를 바꿔도 "휴대폰 확인 완료" 표시는 그대로 남는다. 확인받은 번호를 아무 번호로 바꿔도 주문 전 본인 확인을 통과한다.
* **⑭ 상태 칸에 아무 글자나 들어간다** (10/16\~, 서버). 주문 상태나 상품 상태처럼 정해진 값만 들어가야 하는 칸을 DB 가 검사하지 않는다. 10/16 에 DB 에 직접 잘못된 값을 한 줄 넣었다가 그 목록을 불러오는 기능 전체가 서버 에러(500)를 낸 적이 있다.
* **⑩ 예전 소셜 가입자가 탈퇴를 못 할 수 있다** (8/27\~, 서버). 8/27 에 "비밀번호가 있는 계정인지" 칸을 추가하면서 기존 회원은 모두 "있음"으로 채웠다. 그 전에 카카오·네이버 등으로만 가입해 비밀번호가 없는 회원도 "있음"이 돼서, 탈퇴할 때 있지도 않은 비밀번호를 요구받는다. 기존 소셜 회원 값을 바로잡아야 한다.
* **⑨ 관리자가 재고를 바꿔도 판매 상태가 따라오지 않는다** (8/13\~, 서버). 관리자 화면에서 재고를 0 으로 내려도 상품은 계속 "판매 중"이고, 0 에서 다시 올려도 "품절"로 남는다. 주문 쪽에는 재고에 따라 상태를 바꾸는 규칙이 이미 있는데 관리자 수정에는 적용되지 않는다.

#### 관리자 화면 (화면과 서버가 서로 다른 이름을 씀)

* **① 관리자 화면에서 CSV 내려받기가 안 된다** (7/3\~, 화면). 주문 목록과 매출 화면의 "CSV 내보내기"가 그냥 링크라서, 로그인 출입증이 요청에 붙지 않는다. 서버는 관리자인지 확인하지 못하니 거절(401)하고 파일이 내려오지 않는다. 화면이 출입증을 붙여 파일을 받아 온 뒤 저장하게 바꿔야 한다.
* **② 매출 화면에서 기간을 골라도 항상 최근 30일이 나온다** (7/3\~, 양쪽). 화면은 기간을 `start`/`end` 라는 이름으로 보내는데 서버는 `from_date`/`to_date` 를 기다린다. 서버는 모르는 이름을 무시하고 기본값인 최근 30일을 돌려준다. CSV 내보내기도 같은 이름을 쓴다.
* **③ 대시보드 그래프 기간을 바꿔도 항상 7일이다** (7/3\~, 양쪽). 화면은 `days=30` 처럼 보내고 서버는 `period=30d` 같은 값을 기다린다. ②와 같은 이유로 무시된다.

#### 문구·초기 데이터

* **⑥ 본인 확인 화면의 안내 문구가 사실과 다르다** (7/12\~, 화면). "전화번호는 암호화 저장되며…"라고 안내하지만 서버는 전화번호를 그대로 저장한다. 문구를 실제에 맞추든 서버에서 암호화하든 해야 한다.
* **⑯ "직거래" 표현이 26곳 남아 있다** (10/23\~, 화면). 10/23 에 rekit 이 주문이 확정되면 상품을 사들여 rekit 이름으로 판다고 정했다. 그런데 화면 곳곳의 "직거래"는 개인끼리 사고파는 곳으로 오해받을 수 있다. 검색 키워드로서 가치도 있어서 같이 따져 봐야 한다.
* **⑤ 고객센터 FAQ 초기 데이터에 "철거"가 남아 있다** (7/4\~, 서버). 빈 DB 에 넣는 기본 FAQ 중 "철거 차량을 이용한 직접 배송"이라는 답변이 있고, 서버 코드 설명문 두 곳에도 남아 있다. 확인하다 보니 같은 FAQ 에 "판매자"라는 표현(지금 직판 구조와 안 맞음)과 "재설정 링크"(실제 비밀번호 찾기 방식과 다른지 확인 필요)도 있었다. 운영 DB 에 이미 들어간 FAQ 도 같이 봐야 한다.
* **⑦ 빈 DB 에 초기 데이터를 넣는 스크립트가 실패한다** (8/13\~, 서버). 8/13 에 없앤 칸(옛 본인 확인 시각)에 값을 넣으려다 에러가 난다. 새 칸 이름으로 바꾸면 된다.
