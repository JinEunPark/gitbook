### 1. 시스템 재분석 → todo 추가

#### 배경 — 왜 했나

O2\~O5 로 메트릭·대시보드는 생겼지만, 부하테스트를 하면 **"느리다"는 건 보여도 "왜" 인지는 안 보이는** 상태였다. 타임아웃도 대부분 기본값이라 부하가 걸리면 요청이 무한정 기다리며 쌓일 구조였다.

#### 찾은 빈틈

* **원인 진단 지표 없음**: 이벤트 루프 막힘(bcrypt 가설 O8-1 검증 불가), DB 풀 _대기 시간_(in\_use 는 "꽉 찼다"만 보여줌)
* **멀티프로세스 모드 한계**: `prometheus_client` 는 워커 4개 모드에서 `process_*`(CPU·메모리) 를 안 냄 → 메모리 누수는 cAdvisor 로만 보임
* **타임아웃 공백**: `pool_timeout` 기본 30초, `statement_timeout` 없음, Redis 소켓 타임아웃 없음, gunicorn 튜닝값 기본
* **데드락 가능성**: `get_products_with_lock` 의 `IN (...) FOR UPDATE` 에 `ORDER BY` 없음
* **병목 후보**: httpx 클라이언트를 호출마다 생성(TLS 핸드셰이크 반복), 검색 3컬럼 `ILIKE '%x%'` + 매 페이지 `count(*)`

todo 에 추가한 것: O2-8·O2-9(메트릭), **O4b 신설**(타임아웃·보호 1\~5), O7 보강(remote write·정합성 시나리오·토큰 사전 발급·nginx 경유 측정·로컬≠운영 주의), O8-7\~9.

> `pool_timeout` = HikariCP `connectionTimeout`, `statement_timeout` = JPA `javax.persistence.query.timeout` 을 DB 서버 쪽에서 거는 것.

#### 진행 방식

사용자 요청으로 **개발은 작업 단위별 구현에게 위임**하고 내 작업 환경은 검토·게이트 재실행·커밋을 맡았다.

* 1차: 자동화 도구 1개 순차 (config·database 등 파일이 겹쳐서 병렬 X)
* 2차: 자동화 도구 2개 병렬 — **앱·배포 쪽** / **인프라 쪽**, 서로 건드릴 파일을 나눠 충돌 방지. 진행 중에 `/grafana` 서브경로·SeaweedFS 요구사항을 메시지로 추가 전달

### 2. 루프 지연·풀 대기 + 타임아웃 (`6081921`)

| 파일                                                 | 변경                                                                                                                                            |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `app/order/order_repository.py`                    | 상품 락 조회에 `.order_by(Product.id)` — 락 획득 순서 고정 (O8-7)                                                                                          |
| `app/core/database.py`·`config.py`·`exceptions.py` | `pool_timeout` 5초, 고갈 시 **503 `SERVICE_BUSY`** (O4b-1), asyncpg `server_settings` 로 `statement_timeout` 10s·`idle_in_transaction` 30s (O4b-2) |
| `app/core/metrics.py`                              | `rekle_db_pool_checkout_wait_seconds`·`rekle_db_pool_timeouts_total` (O2-9), `rekle_event_loop_lag_seconds` (O2-8)                            |
| `app/core/event_loop_lag.py` (신규)                  | lifespan 백그라운드 태스크 — `sleep(0.5)` 이 늦게 깬 만큼 = 루프가 막힌 시간                                                                                       |
| `app/core/redis.py`                                | `socket_timeout`·`connect_timeout` 2초, `max_connections` 50 (O4b-3)                                                                           |
| `gunicorn.conf.py`                                 | `timeout 30`·`graceful_timeout 8`·`keepalive 75`·`max_requests 10000±1000` (O4b-4)                                                            |

> 💡 **풀 대기 측정 방식**
>
> SQLAlchemy pool `checkout` 이벤트는 커넥션을 **얻은 뒤** 불려서 대기 시간을 못 잰다. 그래서 `AsyncAdaptedQueuePool` 을 상속해 공개 `connect()` 전체를 잰다. 내부 `_do_get` 은 경합 시 재귀 호출돼 이중 관측되므로 제외.

> 💡 **async 워커에서 gunicorn `timeout` 의 의미**
>
> 요청 타임아웃이 아니라 **하트비트**. 이벤트 루프가 30초 막히면 master 가 그 워커를 행 걸린 것으로 보고 재시작한다.

> ⚠️ **Redis 커넥션 상한**
>
> 기본 `ConnectionPool` 은 `max_connections` 초과 시 **기다리지 않고 즉시 ConnectionError**. 부하테스트에서 걸리면 상한 상향 또는 `BlockingConnectionPool`.

> 🐞 **graceful 종료가 실제로는 안 되던 문제**
>
> `sh -c "alembic ... && gunicorn ..."` 에선 sh 가 PID 1 이라 `docker stop` 의 SIGTERM 이 gunicorn 에 안 갈 수 있다 → 10초 뒤 SIGKILL 로 처리 중 요청이 끊김. `exec gunicorn` 으로 sh 를 gunicorn 으로 교체 (그래야 `graceful_timeout` 이 의미 있음).

> ⚠️ **배포 때 Postgres 재시작**
>
> postgres `command` 가 바뀌면 Jenkins `up -d postgres redis app` 이 컨테이너를 **재생성** (데이터는 볼륨이라 유지). `shared_preload_libraries` 는 서버 시작 시에만 읽혀서 재시작은 피할 수 없음 — `ALTER SYSTEM` 은 서버에만 남고 compose 는 git 에 남아서 compose 방식이 낫다.

> 💡 **compose 가 컨테이너를 "다시 만드는" 규칙**
>
> `docker compose up -d` 는 서비스 설정(command·env·포트·이미지)이 **바뀐 서비스만** 지우고 새로 만든다. 같으면 건드리지 않는다. 데이터는 컨테이너가 아니라 볼륨에 있어서 유지된다.

### 5. git — 리베이스·머지·태그

#### 한 일

1. 사용자가 VS Code 에서 feature 브랜치에 서서 `rebase master` → master 로 체크아웃 (머지 전 멈춤)
2. 내 작업 환경이 상태 확인 → `git merge --ff-only` → 게이트 재실행 → master 푸시
3. annotated 태그 **`0.0.6`** (기존 `0.0.5` 형식 — 변경 요약 + 배포 시 주의) 생성·푸시
4. 원격 feature 브랜치 삭제는 권한 시스템이 되돌리기 어려운 작업으로 막음 → **남겨 둠**

> 💡 **배운 것 — 머지 vs 리베이스**
>
> * **머지**: 갈라진 두 줄기를 그대로 두고 머지 커밋을 새로 만든다. 기존 커밋 안 건드림 → 공유 브랜치에 안전
> * **리베이스**: 내 커밋을 떼어 최신 기준 끝에 **다시 만들어** 붙인다 (해시 바뀜) → 히스토리 한 줄. 공유된 커밋엔 금지(강제 푸시 필요)
> * **fast-forward**: 기준 브랜치에 새 커밋이 없으면 포인터만 앞으로 → 머지 커밋도 충돌도 없음 (오늘 상황)
> * **방향**: 머지는 **받는 쪽(master)에 서서** `merge feature` / 리베이스는 **옮길 쪽(feature)에 서서** `rebase master`
> * master 에 서서 `rebase feature` 는 "master 의 커밋을 feature 위로 옮겨라" — 오늘은 master 고유 커밋이 없어 우연히 같은 결과지만, 있었다면 공유 브랜치를 다시 쓰게 된다

> ⚠️ **master 에 새 커밋이 없었는데도 리베이스가 해시를 바꿨다**
>

### 12. nginx ↔ 앱 request\_id 연결 (O1-2 남은 항목)

#### 배경

#### 한 일 (백업 `rekit-locations.inc.bak-20261110-134605`)

| 파일                                          | 변경                                                                                               |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `conf.d/00-log-format.conf` (신규, http 컨텍스트) | `log_format rekit` = 기본 main + `rid=$request_id rt=$request_time urt=$upstream_response_time`    |
| `conf.d/rekit-locations.inc`                | 서버 컨텍스트에 `access_log /var/log/nginx/access.log rekit;` (443·80 default 블록과 `rekit-ops.inc` 에 적용) |
|                                             | `/health`·`/api/` 에 `proxy_set_header X-Request-ID $request_id;`                                 |

#### 검증 — 실제 요청 하나를 양쪽 로그에서 추적

```
응답 헤더  X-Request-ID: 82d525e4ce2d216eb193e38d1c11beca
nginx     "GET /api/v1/products?size=1 HTTP/1.1" 200 ... rid=82d525e4ce2d216eb193e38d1c11beca rt=0.014 urt=0.013
app       {"event": "http_request", "path": "/api/v1/products", "status": 200, "duration_ms": 11.49,
           "request_id": "82d525e4ce2d216eb193e38d1c11beca", ...}
```

* 클라이언트가 `X-Request-ID: attacker-forged-id` 를 보내도 **무시**되고 nginx 가 새 ID 발급, 앱 로그에 위조값 0건 → 위조 방지 확인
* 쇼핑몰·Grafana·Jenkins·`/health` 200 유지

> ✅ **사용법 — 사용자가 문의한 요청 추적**
>
> 브라우저 개발자도구의 응답 헤더 `X-Request-ID` 값 하나로: `docker logs nginx 2>&1 | grep <id>` → 언제·어디서·얼마나 걸렸나 (`rt`=전체, `urt`=앱 응답시간) `docker logs rekle-app 2>&1 | grep <id>` → 그 요청의 앱 로그 전부 (SQL 로그·비즈니스 예외 포함) `rt` − `urt` 가 크면 nginx↔클라이언트 구간(네트워크·업로드)이 느린 것.

> 💡 **발견 — nginx → 앱 사이에 keepalive 가 아예 없다**
>
> `/api/` 에 `upstream { keepalive }` 블록도 `proxy_http_version 1.1` 도 없다 → nginx 는 **요청마다 앱에 새 TCP 연결**(HTTP/1.0)을 연다.
>
> * 그래서 todo 의 "nginx upstream `keepalive_timeout` ≤ 60초 확인" 항목은 **해당 없음** — 재사용할 커넥션이 없으니 gunicorn `keepalive 75` 와의 경합(간헐 502)도 없다
> * 대신 **부하테스트 최적화 후보**: upstream keepalive 풀 (같은 서버 내 docker 망이라 이득은 작을 수 있음 — 측정 후 판단)
> * `nginx.conf` 의 `keepalive_timeout 65` 는 **클라이언트↔nginx** 구간 설정이다

> 💡 **관찰 — 앱 로그의 `client_ip` 가 `<내부망 IP>`**
>
> 이번 검증 요청은 같은 LAN 의 Mac 에서 공인 IP 로 나갔다 들어온 것(공유기 헤어핀)이라 공유기 IP 로 찍혔다. 외부 사용자 요청에서 실제 IP 가 찍히는지는 별도 확인 필요.

### 15. 로그 흐름 진단 · 문제점 총정리 · SeaweedFS 차단 · Loki 계획

#### 로그가 지금 어디로 가나

앱(structlog) → root 로거 → `StreamHandler(sys.stdout)` 하나 → docker json-file → `/var/lib/docker/containers/<id>/<id>-json.log` → **끝** (`docker logs` 로만 조회). 수집기 없음, Sentry 는 DSN 없어 꺼짐.

> 🐞 **컨테이너 재생성 = 로그 삭제**
>
> 로그 파일이 컨테이너 디렉터리 안에 있어서 **배포(재생성) 때마다 앱 로그가 사라진다** — 0.0.6 배포 직후 rekle-app 로그 101줄뿐. 로테이션: rekle-app·postgres·redis·모니터링은 20MB×5, **nginx·jenkins·seaweedfs·registry·certbot·rekle-web 은 무제한** (`daemon.json` 없음).

#### 로그 도구 비교 (결론: Loki + Alloy)

|        | ELK / OpenSearch    | Loki                 |
| ------ | ------------------- | -------------------- |
| 색인     | 모든 단어 전문 색인 — 검색 강력 | 라벨만 색인, 본문은 grep     |
| 자원     | JVM, 최소 수 GB        | 수백 MB                |
| 우리와 궁합 | Kibana 추가           | 기존 Grafana 에서 메트릭↔로그 |

* **Kibana** = Elasticsearch 전용 화면(로그 탐색 Discover 강함) / **Grafana** = 여러 소스 범용(메트릭·대시보드 강함, Loki 붙이면 로그 검색)
* **Promtail** = Loki 용 수집 자동화 도구(파일 tail → 라벨 → push, positions 기록). **지원 종료** → 후속 **Grafana Alloy**
* **OpenSearch 를 넣을 이유?** 로그용은 없음. **상품 검색**(nori 형태소·오타·관련도·자동완성)용으로는 가치 있지만 운영 상품 **7개**(104kB) → 지금은 불필요. 상품 수만+ 이고 `pg_trgm`(O8-9)으로도 SLO 못 맞출 때 검토
* 커리어용으로는 로컬에서 ELK/OpenSearch 실습 권장 (shipper → store → UI 구조는 같다)

#### SeaweedFS 포트 차단 (2026-11-10 23:17 KST)

* 사용자 걱정 ① "관리 화면을 못 쓰지 않나" → **SSH 터널로 같은 화면** (`ssh -L 8888:localhost:8888 -L 9333:localhost:9333 externalhost` → `http://localhost:8888`). `~/.ssh/config` 의 `LocalForward` 로 한 번에 여는 법 안내
* 걱정 ② "관리 화면에 비밀번호가 없나" → **없다** (filer·master UI 로그인 기능 없음, `security.toml` 없음, `-s3.config` 없음). 별도 `weed admin` 은 `-adminPassword` 지원
* 걱정 ③ "클라이언트가 `/s3/` 로 이미지 요청" → nginx 가 docker 망에서 `seaweedfs:8333` 컨테이너명으로 접근하므로 **호스트 포트 바인딩과 무관**. 앱도 `S3_ENDPOINT_URL=https://rekit.co.kr/s3`
* 걱정 ④ "재시작해도 데이터 유지?" → 볼륨 본문(`*.dat`)과 filer 메타데이터(leveldb2 `/data/filerldb2`) 모두 bind mount `~/rekit/seaweedfs/data`(38MB) 에 있음 → 유지. 오늘 앞선 재생성 후에도 이미지 200 이었던 것이 증거
* 적용: `data` tar 백업(37MB) + compose 백업 → 4포트 `127.0.0.1:` → 재생성
* 검증: 외부 `IP:9333/8080/8888/8333` **전부 응답 없음**, 상품 이미지 200(2.5MB), 쇼핑몰·API 200, Prometheus seaweedfs up, 서버 안 filer `localhost:8888` 200 (재시작 후 filer 는 10초보다 늦게 뜸 — 정상)

> ⚠️ **S3 인증은 아직 — 서버 안 `localhost:8333/` 익명 GET 이 200**
>
> 익명 버킷 목록이 허용되는 정황. `/s3/` 는 nginx 공개 경로라 **키 없이 쓰기·삭제 가능성** → `-s3.config` 로 `anonymous: Read:rekle-images` 만, 앱 키에 Read·Write·List. 관리자 업로드를 사용자가 직접 확인할 수 있을 때 적용.
