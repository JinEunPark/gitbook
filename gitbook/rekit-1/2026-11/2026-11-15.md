# 11.15 · 프리렌더에 굳은 API 에러 고치기

> 네이버 검색 노출을 점검하면서, 검색봇이 받는 정적 HTML에 상품 대신 API 오류 문구가 들어가고 있다는 것을 확인했다. 프리렌더 서버의 API 중계와 빌드 가드를 추가한 뒤 운영 HTML을 다시 측정했다.

## 작업 배경

네이버 서치어드바이저에 사이트와 사이트맵을 등록한 뒤에도 검색 노출이 보이지 않았다. 처음에는 robots.txt 설정을 의심했지만, 검색봇과 같은 조건으로 공개 페이지를 직접 확인해 원인을 좁혔다.

## 먼저 확인한 사실

| 확인 항목        | 결과               |
| ------------ | ---------------- |
| 공개 페이지 응답    | 5개 페이지 모두 200    |
| robots 메타 태그 | `index, follow`  |
| 사이트맵         | 정상 응답            |
| HTTP → HTTPS | 308 리다이렉트 1회     |
| 프리렌더 HTML    | 상품 대신 오류 문구가 포함됨 |

홈과 상품 목록의 정적 HTML에는 `(intermediate value).slice is not a function` 오류가 들어 있었고, 상품 상세 링크도 생성되지 않았다. 브라우저에서는 앱이 다시 API를 호출하므로 정상처럼 보였지만, 자바스크립트를 실행하기 전 HTML을 읽는 검색봇에는 오류 상태가 그대로 전달되고 있었다.

## 원인

프리렌더는 빌드 과정에서 임시 정적 서버와 헤드리스 브라우저를 사용한다. 운영 환경에서는 nginx가 `/api/v1` 요청을 백엔드로 전달하지만, 프리렌더 임시 서버에는 이 중계가 없었다.

그 결과 API 요청이 JSON 대신 SPA의 `index.html`을 받았다. 상품 배열을 기대하던 화면 코드가 HTML 문자열에 `.slice()`를 호출하면서 오류가 났고, 프리렌더는 이 오류 상태를 정적 HTML로 저장했다.

## 수정한 내용

1. 프리렌더 임시 서버에서 `/api/*` 요청을 실제 백엔드로 중계하도록 수정했다.
2. 스냅샷을 만드는 동안 API 응답을 검사하도록 빌드 가드를 추가했다.
3. API 응답이 2xx가 아니거나 JSON이 아니면 해당 페이지를 저장하지 않고 빌드를 실패하게 했다.

이번 오류 문구만 찾는 방식 대신, API 응답 자체를 검사하도록 만들었다. 같은 형태의 실패가 다시 발생해도 정적 HTML에 오류 상태가 조용히 저장되지 않게 하기 위해서다.

## 검증

운영 사이트에서 검색봇 User-Agent로 받은 HTML을 수정 전과 같은 방식으로 다시 측정했다.

| 페이지   | 항목       |     수정 전 |     수정 후 |
| ----- | -------- | -------: | -------: |
| 홈     | HTML 크기  | 14,662 B | 33,721 B |
| 홈     | 상품 상세 링크 |        0 |        6 |
| 홈     | 카테고리 링크  |        1 |        7 |
| 홈     | 오류 문구    |        1 |        0 |
| 상품 목록 | HTML 크기  | 14,804 B | 30,081 B |
| 상품 목록 | 상품 상세 링크 |        0 |        6 |
| 상품 목록 | 오류 문구    |        1 |        0 |

공개 페이지 9개는 모두 프리렌더에 성공했다. 백엔드 주소를 의도적으로 닿지 않는 곳으로 바꿔 빌드했을 때는 API 오류를 기록하고 종료 코드 1로 빌드를 중단하는 것도 확인했다.

## 확인된 범위와 다음 작업

이번 수정은 검색봇이 받는 HTML 품질을 고친 작업이다. 검색 노출과 순위는 수집·색인 일정 등 다른 요인의 영향도 받기 때문에, 이 수정만으로 노출을 보장하지는 않는다.

다음으로 상품 상세 페이지도 프리렌더 대상과 사이트맵에 추가하고, 재수집 이후 검색 반영 상태를 다시 확인할 예정이다.

자세한 진단과 측정값은 [문제 해결 사례](../../cases/case-02-prerender.md)에 정리했다.
