# 11.19 · WSL 개발환경 이전과 빌드 검증

{% hint style="info" %}
게이밍과 개발을 같은 PC에서 병행할 수 있도록 Ubuntu WSL 2 환경을 D 드라이브에 구성했다. 백엔드와 프론트엔드 소스를 Linux 파일시스템으로 옮기고, 백엔드 빌드 게이트를 수정해 테스트했다.

| ------ | -------------------------------------------------------- |
| WSL 2  | Ubuntu 24.04를 D 드라이브에 설치하고 두 프로젝트를 Linux 홈으로 이전          |

| Git    | 백엔드 커밋 `a6b0cb7`과 태그 `0.0.8`을 원격에 푸시                     |

### 1. WSL 2 개발환경

기존 Windows 작업 폴더를 확인한 뒤 Linux 파일 접근 성능을 위해 소스는 Ubuntu의 ext4 파일시스템에 두었다. WSL 가상 디스크 자체는 D 드라이브에 있다.

| 항목          | 현재 설정                                      |
| ----------- | ------------------------------------------ |
| 배포판         | Ubuntu 24.04 LTS, WSL 2                    |
| 가상 디스크      | Windows `D:\\WSL\\Ubuntu-24.04\\ext4.vhdx` |
| Linux 기본 계정 | `wlsdm`                                    |
| 백엔드         | `/home/wlsdm/projects/rekit_backend`       |
| 프론트엔드       | `/home/wlsdm/projects/rekit_client`        |
| 백엔드 Python  | 3.11.18, 프로젝트의 `.venv`                     |
| 프론트 Node.js | 24.22.3, `~/.local/opt/node24`             |

두 작업본은 Windows 원본과 별도다. 백엔드는 원본의 미추적 이미지 2개와 `package-lock.json`도 보존했고, 프론트는 Git 저장소로 독립 복제한 뒤 GitHub `origin`과 `master` 추적 관계를 확인했다. Windows 원본 폴더는 이날 삭제하지 않았다.

**자원 할당:** Windows PC 메모리는 약 32GB다. WSL 안에서 확인한 메모리는 약 15.2GiB이고, `nproc`은 논리 CPU 12개를 표시했다. `C:\\Users\\wlsdm\\.wslconfig`는 없으며 별도의 메모리·CPU 제한값을 직접 지정하지 않았다. 이 수치는 WSL에서 확인한 사용 가능 자원이며, 고정으로 예약해 둔 사용량이 아니다. 게임 중에는 개발 작업을 저장하고 PowerShell에서 `wsl --shutdown`으로 WSL을 종료할 수 있다.

### 2. Docker 설정

Ubuntu 패키지로 Docker Engine 29.1.3, Docker Compose 2.40.3과 Buildx를 설치했다. Docker Desktop은 설치하지 않았다.

* Docker 데이터 경로는 Ubuntu 내부 `/var/lib/docker`이며, D 드라이브의 WSL 가상 디스크에 저장된다.
* Docker 서비스는 systemd에서 활성화했다. 기본 사용자 `wlsdm`을 `docker` 그룹에 추가해 해당 계정에서 Docker 명령을 실행할 수 있다. 이 그룹은 관리자에 준하는 권한을 제공한다.
* 테스트용 PostgreSQL과 Redis는 별도 Docker 네트워크에서 임시로 띄우고 테스트 후 정리했다. 확인 당시 상시 실행 중인 컨테이너는 없었다.
* `wsl --shutdown`은 WSL과 그 안의 Docker 서비스 및 컨테이너를 함께 종료한다. 개발할 때 WSL을 다시 열어 사용할 수 있다.

### 3. 백엔드 빌드 게이트 수정

서브에이전트 코드 리뷰 후 실제 빌드로 문제를 확인하고 수정했다.

* 테스트 파일의 긴 두 줄이 Ruff의 100열 제한을 넘던 문제를 고쳤다.
* Docker 테스트 단계에 `scripts` 의존성을 추가해 Pillow가 필요한 썸네일 테스트 8개가 실행되도록 했다.
* 기존 태그 `0.0.1`\~`0.0.7`의 Dockerfile에는 새 테스트 단계가 없으므로, 이전 릴리스용 호환 Dockerfile을 생성해 테스트와 운영 이미지를 빌드하도록 했다. `0.0.7`을 실제로 검증했다.
* 최신 Redis 타입 선언에서 불필요해진 `type: ignore`를 제거했다. 라우터 테스트의 S3 초기화 의존성을 분리하고, 비인증 요청이 OAuth 설정보다 인증 검사를 먼저 받도록 순서를 조정했다.
* 빈 DB용 시드 스크립트가 삭제된 `identity_verified_at` 필드를 참조하던 문제를 제거했다. 11.16에 기록한 시드 실패 항목의 원인과 같은 부분이다.
* `.dockerignore`를 추가해 Git 저장소, 가상환경과 로컬 환경 파일 등이 Docker 빌드 컨텍스트에 들어가지 않도록 했다.

현재 브랜치 테스트 이미지에서 Ruff와 mypy를 통과했고, **721개 통과·8개 제외**를 확인했다. 임시 PostgreSQL·Redis에 마이그레이션과 시드를 적용한 전체 테스트는 **770개 통과**했다. 이전 태그 `0.0.7`의 호환 빌드는 **710개 통과·8개 제외**였다. 운영 이미지에서도 앱 모듈을 가져오고 테스트 도구가 포함되지 않은 것을 확인했다.

백엔드 `feature/build-test-gate`에 커밋 [`a6b0cb7`](https://github.com/JinEunPark/rekit_backend/commit/a6b0cb7722e09a577b0587a8f4d4db050f088bf4)을 만들고 [태그 `0.0.8`](https://github.com/JinEunPark/rekit_backend/tree/0.0.8)을 함께 푸시했다. Jenkins에서의 실제 배포는 수행하지 않았다.

### 4. 프론트엔드 환경과 확인 사항

Windows의 `D:\\projects\\rekit_client`를 WSL 홈에 독립 Git 저장소로 복제했다. 복제 시 `master`는 `be3c61f`였고 GitHub 원격 추적 상태와 깨끗한 작업 트리를 확인했다.

`npm ci` 후 빌드와 타입 검사를 실행했다. 처음에는 Puppeteer Chrome이 없어 프리렌더가 건너뛰어져 Chrome과 필요한 Linux 라이브러리를 설치했다. 재실행 결과 **9개 경로 모두 프리렌더 완료**했다. 빌드가 생성한 사이트맵 변경은 원래 파일로 되돌려 작업 트리를 깨끗하게 유지했다.

설치 과정에서 npm이 **취약점 25건**(낮음 1, 보통 11, 높음 12, 심각 1)과 일부 Vite 플러그인의 피어 의존성 경고를 보고했다. 개별 영향도와 수정은 아직 확인하지 않았다.

### 다시 사용할 때

PowerShell에서 `wsl`을 실행해 접속한 다음 `cd ~/projects/rekit_backend` 또는 `cd ~/projects/rekit_client`로 이동한다. VS Code에서는 WSL 원격 연결로 해당 Linux 경로를 열어 작업한다. 현재 GitHub 푸시는 Windows Git Credential Manager를 사용한 이력이 있으므로, Windows Git을 삭제하기 전 WSL에서 인증 수단을 다시 확인해야 한다.
