# 검색봇에 에러 문구만 보여주던 프리렌더 HTML

{% hint style="success" %}
**"robots.txt가 다 막고 있는 것 같다"는 의심을 실측으로 기각하고, 진짜 문제를 찾아냈다.** 빌드 때 만드는 SEO용 정적 HTML에 상품 대신 `(intermediate value).slice is not a function` 에러 문구가 저장돼 배포되고 있었다. 고친 뒤 검색봇이 보는 홈 HTML의 **상품 링크 0개 → 6개, 카테고리 링크 1개 → 7개, 에러 문구 1건 → 0건** (운영 실측). 같은 문제가 다시 생기면 **빌드가 실패**하도록 막았다.
{% endhint %}

## 1. 문제

네이버 서치어드바이저에 사이트를 등록하고 사이트맵까지 제출했는데, 며칠째 검색 결과에 나오지 않았다. robots.txt를 열어 보니 `Disallow`만 있었다.

```
User-agent: *
Disallow: /admin
Disallow: /my
Disallow: /cart
Disallow: /checkout
Disallow: /auth
Disallow: /search
Disallow: /_design
```

"`Allow`가 하나도 없으니 전부 막힌 것 아닐까?"라는 의심이 출발점이었다.

## 2. 가설 검증 — robots.txt는 범인이 아니다

robots.txt는 **기본이 전부 허용**이고, `Disallow`에 적은 경로만 막는다. 이 파일은 관리자·마이페이지·장바구니처럼 색인되면 안 되는 비공개 경로만 막고 있어 의도대로였다. (이후 의도를 분명히 하려고 `Allow: /`를 명시했다. 네이버·구글은 더 구체적인 경로 규칙을 우선하므로 `Disallow`는 그대로 유지된다.)

추측에서 멈추지 않고, 네이버 검색봇(Yeti)과 같은 User-Agent로 운영 사이트를 직접 받아 색인에 영향을 주는 항목을 하나씩 확인했다.

| 항목                     | 결과                                    |
| ---------------------- | ------------------------------------- |
| 공개 페이지 5개 응답           | 모두 200, 페이지마다 고유한 `<title>`·canonical |
| `<meta name="robots">` | `index, follow` (noindex 없음)          |
| 사이트 소유 확인 메타 태그        | 있음                                    |
| `sitemap.xml`          | 200, 정상 XML                           |
| http → https           | 308 리다이렉트 1회 (정상)                     |
| 프리렌더 HTML              | 본문(h1·링크·푸터)이 HTML 안에 있음              |

색인을 **막는** 설정은 없었다. 새 도메인은 네이버 색인에 보통 몇 주가 걸리므로 미노출 자체는 대기 단계일 가능성이 높았다. 그런데 받아 온 HTML을 읽다가 이상한 줄을 발견했다.

```html
<h2 class="feat__title">오늘 들어온 매물</h2>
<div class="feat__state feat__state--error">
  (intermediate value).slice is not a function
  <button class="feat__retry">다시 시도</button>
</div>
```

브라우저로 들어가면 상품이 잘 보이는데, **검색봇이 받는 HTML에는 상품 대신 자바스크립트 에러 문구가 들어 있었다.**

## 3. 기준선 — 고치기 전 운영 실측

검색봇 User-Agent로 운영 사이트에서 받은 HTML을 그대로 쟀다.

| 페이지               |  HTML 크기 | 상품 상세 링크 |    카테고리 링크 | 에러 문구 |
| ----------------- | -------: | -------: | ---------: | ----: |
| 홈 `/`             | 14,662 B |    **0** | **1** (전체) | **1** |
| 상품 목록 `/products` | 14,804 B |    **0** |          0 | **1** |

홈의 카테고리 그리드에도 실제 카테고리 대신 "전체" 하나만 있었다. 검색봇 입장에서 이 사이트는 **상품이 하나도 없는 쇼핑몰**이었다.

## 4. 원인

이 사이트는 Vue SPA라서, 검색봇을 위해 **빌드 단계에서 헤드리스 브라우저로 공개 페이지를 미리 렌더링(프리렌더)** 해 정적 HTML로 저장한다.

```
[운영]  브라우저 ─ /api/v1/products ─▶ nginx ─ 프록시 ─▶ 백엔드        ✅ JSON

[빌드]  헤드리스 브라우저 ─ /api/v1/products ─▶ 프리렌더 임시 서버
                                               └─ "확장자 없는 경로 = SPA 라우트"
                                                  → index.html 반환            ❌ HTML
        → 앱이 HTML 문자열에 .slice() 호출 → 에러 → 에러 화면이 스냅샷으로 저장
```

1. 앱은 API를 **상대 경로**(`/api/v1`)로 부른다. 운영에서는 nginx가 이 경로를 백엔드로 넘겨 준다.
2. 빌드 때 쓰는 임시 정적 서버에는 nginx가 없다. 이 서버는 "확장자가 없는 경로는 SPA 라우트"로 보고 `index.html`을 돌려줬다. `/api/v1/products`도 확장자가 없으니 같은 취급을 받았다.
3. 앱은 JSON 배열을 기대하고 `.slice()`를 호출했지만, 받은 건 HTML 문자열이었다. 화면은 에러 상태가 됐고, 프리렌더는 그 순간을 그대로 저장했다.

{% hint style="warning" %}
**빌드는 성공했고, 브라우저로 보면 정상이었다.** 사용자의 브라우저에서는 앱이 다시 실행되면서 API를 정상적으로 불러오기 때문이다. 문제는 자바스크립트를 실행하기 전의 HTML을 읽는 **검색봇에게만** 보였다.
{% endhint %}

## 5. 해결

<table><thead><tr><th width="55.20001220703125">#</th><th>무엇을</th><th>방법</th></tr></thead><tbody><tr><td>①</td><td>API 중계</td><td>프리렌더 임시 서버에서 <code>/api/*</code> 요청만 실제 백엔드 origin으로 전달. 주소는 환경변수로 바꿀 수 있고 Docker 빌드 인자로 노출</td></tr><tr><td>②</td><td>재발 방지 가드</td><td>스냅샷을 찍는 동안 <code>/api/*</code> 응답을 감시. 2xx가 아니거나 JSON이 아니면 그 페이지는 저장하지 않고 <strong>빌드를 실패</strong>시킴. 백엔드 장애 중 긴급 배포가 필요할 때만 환경변수로 우회</td></tr></tbody></table>

```js
// 스냅샷 중 /api 응답이 실패하거나 JSON이 아니면(= fallback HTML) 기록
page.on('response', (r) => {
  const u = new URL(r.url())
  if (!u.pathname.startsWith('/api/')) return
  const ct = r.headers()['content-type'] || ''
  if (!r.ok() || !ct.includes('json')) apiProblems.push(`${r.status()} ${u.pathname}`)
})
```

**왜 이 방법을 골랐나**

* **API 주소를 절대 경로로 바꾸지 않은 이유**: 상대 경로는 "어느 도메인으로 접속해도 같은 출처의 API를 부른다"는 운영상 이유(CORS 회피)로 의도한 설정이다. 빌드 환경 때문에 운영 설정을 바꾸는 대신, 빌드 환경이 운영과 같이 동작하도록 맞췄다.
* **가드가 경고가 아니라 빌드 실패인 이유**: 이 버그는 빌드도 성공하고 브라우저로 봐도 정상이라 **아무도 모른 채 배포됐다.** 경고 로그는 또 묻힌다. 같은 프리렌더 스크립트에는 이전에 "모달이 스크롤 잠금 상태로 찍히면 빌드 실패" 가드를 넣은 적이 있어, 같은 원칙(스냅샷이 깨지면 배포하지 않는다)을 API 응답으로 넓혔다.
* **가드를 특정 문구 검사가 아니라 응답 감시로 만든 이유**: `slice is not a function` 같은 에러 문구를 찾으면 이번 증상만 잡힌다. **API 응답 자체를 보면** 어느 페이지의 어떤 API가 깨져도 잡힌다.

## 6. 결과 — 운영 실측

배포 후 개선 전과 **같은 방법**(검색봇 User-Agent로 운영 사이트 HTML 수신)으로 다시 쟀다. 배포 전 로컬 빌드로 잰 예측값과 운영 실측값이 **바이트 단위까지 같았다**.

| 페이지               | 지표       | 개선 전 (운영) |    개선 후 (운영) |
| ----------------- | -------- | --------: | -----------: |
| 홈 `/`             | HTML 크기  |  14,662 B | **33,721 B** |
|                   | 상품 상세 링크 |         0 |        **6** |
|                   | 카테고리 링크  |         1 |        **7** |
|                   | 에러 문구    |         1 |        **0** |
| 상품 목록 `/products` | HTML 크기  |  14,804 B | **30,081 B** |
|                   | 상품 상세 링크 |         0 |        **6** |
|                   | 에러 문구    |         1 |        **0** |

* 상품 링크 6개는 현재 판매 중인 상품 수(API 기준 6개)와 일치한다. 검색봇이 첫 HTML에서 모든 상품 상세 페이지로 가는 길을 얻게 됐다.
* 9개 공개 페이지 모두 프리렌더 성공(9/9).

**가드 동작 검증**: 백엔드 주소를 일부러 닿지 않는 곳으로 지정해 빌드했다. 홈·상품 목록·FAQ 등 API를 쓰는 페이지가 실패 목록에 찍히고 빌드가 **종료 코드 1**로 멈추는 것을 확인했다.

```
  ✗ / — API 응답 이상 2건:
      502 application/json /api/v1/products/featured?limit=8
      502 application/json /api/v1/categories
  ✗ /products — API 응답 이상 1건:
      502 application/json /api/v1/categories
  ✓ /guide           → 이용 가이드 · 리키트 rekit
```

## 8. 배운 점

1. **추측은 실측으로 기각한다.** "Disallow만 있어서 막혔다"는 그럴듯한 가설이었지만, 봇과 같은 조건으로 받아 보니 틀렸고, 그 과정에서 진짜 문제가 나왔다.
2. **SEO는 봇이 받는 HTML로 확인한다.** 브라우저에서 정상인 페이지도, 자바스크립트 실행 전 HTML에서는 깨져 있을 수 있다.
3. **빌드 환경은 운영의 숨은 의존성을 드러낸다.** 운영에선 nginx가 조용히 해 주던 일(API 프록시)이, 빌드 환경에선 아무도 하지 않고 있었다.
4. **"조용히 성공하는 실패"는 빌드를 멈춰서 막는다.** 경고는 묻히고, 실패한 빌드는 묻히지 않는다.
5. **네이버 리포트는 단계별로 읽는다.** "노출/클릭 정보 없음"은 오류가 아니라 아직 검색 결과에 나간 적이 없다는 뜻이다. 수집 → 색인 → 노출 → 집계 중 어디서 멈췄는지는 수집 현황부터 봐야 알 수 있다.

### 이 리포트에서 읽을 수 있는 것

* **수집 제한 0** → robots.txt나 서버 오류로 막힌 페이지가 없다. 2장에서 "robots.txt는 범인이 아니다"라고 결론 낸 것을 네이버 쪽 데이터로도 확인한 셈이다.
* **첫 수집은 수정 전에 일어났다** → 네이버가 11-13 전후에 가져간 홈·상품 목록 HTML에는 상품 링크 대신 **에러 문구**가 들어 있었다. 그래서 수정 배포 뒤 **수집을 다시 요청**했다.
* **노출/클릭이 0인 이유** → 수집은 됐지만 아직 검색 결과에 나간 기록이 없다. 수집 → 색인 → 노출 → 리포트 집계 순서에서 아직 노출 전 단계다.
* **약 12페이지 / 약 1,600KB** → 공개 라우트(9개)보다 많고, 페이지당 평균(약 130KB)도 HTML 크기(약 15KB)보다 크다. JS·CSS 등 리소스나 사이트맵·robots.txt 요청이 함께 집계된 것으로 **추정**한다. 어떤 URL이 포함됐는지는 이 리포트로 알 수 없다.

### 함께 발견한 것 — 상품 상세 페이지

상품 상세 URL(`/products/<id>`)을 검색봇 User-Agent로 받아 보니 **홈 HTML이 그대로** 나왔다. title도 홈의 것이고 canonical도 `https://rekit.co.kr/`였다. 상세 페이지는 아직 프리렌더 대상이 아니어서, 서버가 SPA fallback으로 홈 스냅샷을 돌려주기 때문이다.

이 상태로 상세 URL을 수집 요청하면 네이버는 6개 모두를 "홈과 같은 페이지"로 보고 색인하지 않을 가능성이 높다. 그래서 상세 URL은 수집 요청에서 뺐고, 상세 프리렌더를 다음 과제로 남겼다.
